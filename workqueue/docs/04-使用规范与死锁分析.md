## 一、WQ_* 标志全表（6.6 真实值与效果）

```c
WQ_UNBOUND         = 1 << 1   WQ_FREEZABLE      = 1 << 2
WQ_MEM_RECLAIM     = 1 << 3   WQ_HIGHPRI        = 1 << 4
WQ_CPU_INTENSIVE   = 1 << 5   WQ_SYSFS          = 1 << 6
WQ_POWER_EFFICIENT = 1 << 7
__WQ_DESTROYING=1<<15  __WQ_DRAINING=1<<16  __WQ_ORDERED=1<<17
__WQ_LEGACY=1<<18  __WQ_ORDERED_EXPLICIT=1<<19     /* 内部位 */
```

| 标志 | 改变的执行特性 | 使用要点 |
| :--- | :--- | :--- |
| `WQ_UNBOUND` | worker 绑 attrs 允许集而非单 CPU；池按 pod 划分；**不参与并发管理**（`WORKER_UNBOUND`，有活即拉人） | 长跑/可迁移 work 必选；配 affinity_scope 微调（第 3 章） |
| `WQ_FREEZABLE` | suspend 冻结期 `max_active` 清 0：新 work 全进 inactive_works，在跑的跑完即止 | wq 参与 freeze 协议（`freeze_workqueues_busy` 检查归零）；缺它可能导致"冻结时还有异步活动"的 suspend 失败/竞态 |
| `WQ_MEM_RECLAIM` | 建专属 **rescuer**（`kworker/R-<name>`，nice -20，绑全 CPU）：池建线程受阻时 mayday 求救，rescuer 无视池资源直接执行该 wq 的 work | **内存回收路径可能用到的 wq 必须加**（否则回收等 work、work 等回收的死亡螺旋）；代价 = 每 wq 一个常驻线程 |
| `WQ_HIGHPRI` | per-cpu：用每 CPU 的**第二个标准池**（nice=**-20**）；unbound：attrs->nice=-20 匹配/新建池 | 只是 CFS nice，不是 RT；别指望它抢占实时任务 |
| `WQ_CPU_INTENSIVE` | worker 执行该 wq 的 work 时置 `WORKER_CPU_INTENSIVE`：脱离并发管理，调度器自由抢占/迁移/并行 | for CPU 长跑且**不需要与其他 per-CPU work 排队公平**的场合；执行被 6.6 的自动检测兜底（阈值 10ms） |
| `WQ_SYSFS` | 在 `/sys/bus/workqueue/devices/<name>` 暴露调优属性 | 需要运行时调 max_active/nice/cpumask/scope 的 wq；ordered wq 拒绝 |
| `WQ_POWER_EFFICIENT` | per-cpu 起步；**`workqueue.power_efficient=1`（或 CONFIG_WQ_POWER_EFFICIENT_DEFAULT）时自动转 UNBOUND** | 为省功耗牺牲少量延迟——电池设备默认开启的发行版不少 |

组合禁忌（源码/文档明示）：`__WQ_ORDERED_EXPLICIT`（alloc_ordered_workqueue 产生）不允许 apply attrs/多 pwq/set_max_active/sysfs——一切会造出第二个 pwq 的操作都破坏串行保证。

常用组合速查：

| 组合 | 场景 |
| :--- | :--- |
| `WQ_UNBOUND \| WQ_MEM_RECLAIM` | 回写/压缩等回收路径长任务（如 fs 的 bdi_flush） |
| `WQ_UNBOUND \| WQ_HIGHPRI` | attrs->nice=-20 的 unbound 池（受限于池复用，全系统共享） |
| `WQ_UNBOUND \| WQ_CPU_INTENSIVE` | 冗余标志（unbound 本就不参与 CM），无副作用但无意义 |
| `alloc_ordered_workqueue` + `WQ_MEM_RECLAIM` | "必须串行且在回收时也要能推进"（很多文件系统后台任务） |
| `WQ_FREEZABLE \| WQ_UNBOUND` | suspend 期间停摆、平时可迁移的杂活 |

> 💡 关于 `WQ_CPU_INTENSIVE` 与 6.6 自动检测的关系再补一句：显式标志是**从执行开始就豁免**（process_one_work 第 ② 步置位）；自动检测是**跑超 10ms 后没收 CM 身份**（wq_worker_tick）。前者语义清晰后者兜底——源码注释建议：反复触发自动检测的函数就该"consider switching to WQ_UNBOUND"，而不是等 tick 来救。

## 二、max_active 语义与默认值

```
WQ_MAX_ACTIVE = 512        /* 上限，源码注释原话 "I like 512, better ideas?" */
WQ_UNBOUND_MAX_ACTIVE = 512
WQ_DFL_ACTIVE = 256        /* alloc_workqueue 传 0 时生效 */
```

**精确语义**：每个 pwq（不是每个 wq！）允许**同时在执行**（active：在 worklist 上或正在跑）的 work 数上限。超限进 inactive_works FIFO 等补位（第 2 章）。per-cpu wq 每 CPU 一个 pwq → 每 CPU 各 256；unbound wq 每 pod 一个 pwq → 每 pod 各自的 max_active。

- `alloc_workqueue(..., max_active)`：0 → 256；<1 或 >512 → clamp 并 warn。
- **`WQ_UNBOUND && max_active==1` 会隐式获得 `__WQ_ORDERED`**（6.6 兼容行为，源码注释：per-pod 池让"unbound+1"不再天然全局串行，但保留旧行为防 subtle breakage）。**要真正的全局串行必须用 `alloc_ordered_workqueue`**——它是 WQ_UNBOUND + `__WQ_ORDERED|__WQ_ORDERED_EXPLICIT` + 单 pwq 的组合拳。
- 运行时可调：`workqueue_set_max_active()`（≤512，ordered-explcit 拒绝）或写 sysfs `max_active`；调整会立即激活/抑制 inactive_works。

**怎么选**：默认 256 绰绰有余（瓶颈在池的 worker 数，不在名额）；**调小**是为了（a）限制并发内存/IO 足迹（如每 work 拿大 buffer），（b）per-pod 内近似保序。1 = 该 pwq 内严格串行 FIFO。

## 三、system_* 家族（6.6 实际 7 个）

| wq | 创建参数 | 用途 | 选用 |
| :--- | :--- | :--- | :--- |
| `system_wq`（events） | flags=0, max_active=0(→256) | 短小、常规 | `schedule_work()` 的默认去向；**别投长活/会睡眠久的活**——flush 警告与阻塞他人的重灾区 |
| `system_highpri_wq` | WQ_HIGHPRI | 需要抢先的短活 | 稀缺资源，谨慎 |
| `system_long_wq`（events_long） | flags=0 | 预期长跑（文档：flush 可能很慢） | 比 system_wq 宽容，仍建议自建 |
| `system_unbound_wq` | WQ_UNBOUND, **512** | 长跑/可迁移 | 首选公共 unbound；idle_cull 等 wq 自身也在用它 |
| `system_freezable_wq` | WQ_FREEZABLE | 冻结安全的常规活 | suspend 期间不需要跑的 |
| `system_power_efficient_wq` | WQ_POWER_EFFICIENT | 功耗敏感的常规活 | 桌面/移动优先 |
| `system_freezable_power_efficient_wq` | FREEZABLE\|POWER_EFFICIENT | 两者兼顾 | 同上 |

> ⚠️ 6.6 的头文件对 `flush_scheduled_work()`/flush system wq 明确拉响警报：`__warn_flushing_systemwide_wq()` 运行时 dump_stack，编译期 `__compiletime_warning`。**flush 公共 wq = 等全世界**，请自建 wq。何时**必须**自建 wq（官方清单归纳）：需要 flush/cancel 该 wq 的 work；需要限制并发（max_active）或顺序（ordered）；需要专属 flags 组合（MEM_RECLAIM/HIGHPRI/UNBOUND 细调）；需要 sysfs 调优。只是"排个活"永远优先 system_wq/system_unbound_wq。

按"活"的特征选 wq 的决策树：

```
这个 work 会睡眠吗（等 IO/锁/内存）？
├─ 不会，纯 CPU 数毫秒以内 → system_wq（schedule_work）
│    └─ 数十毫秒以上/不可预测 → system_unbound_wq 或自建 unbound
├─ 会睡眠，且睡眠时长有界、与提交 CPU 有 cache 亲缘 → system_wq（CM 正常接力）
├─ 会睡眠，可能睡很久（等外部事件） → unbound（别占 per-CPU 并发名额）
└─ 特殊约束：
     suspend 期间必须停 → +WQ_FREEZABLE
     回收路径会用到    → +WQ_MEM_RECLAIM
     全局串行          → alloc_ordered_workqueue
     需要区分设备/模块独立 flush → 自建（命名带实例号，配 set_worker_desc）
```

## 四、经典死锁逐例分析

### 例 1：work 内等另一个 work（max_active 耗尽 / 执行上下文枯竭）

```
wq = alloc_workqueue("X", 0, 4);          /* max_active=4，per-cpu → 每 CPU 4 名额 */
work_A() { ...; flush_work(&work_B); ... }   /* A 等 B */
```

**场景 a（同名额耗尽）**：4 个 CPU 上的 A 各占一个名额且都睡在 flush_work——B 要执行也得占名额（同一 pwq）→ 池里 4 个 worker 全睡死，B 永远拿不到名额。**CMWQ 让这个更隐蔽**：池 worker 数会因"全睡"而继续膨胀，但**名额**（nr_active）不膨胀——worker 再多也过不了 max_active 闸门。

```
时间线（per-cpu pwq，max_active=4，假设全落 CPU0）：
t0  A1..A4 入队 → nr_active=4，4 个 worker 各领一个，全部跑到
    flush_work(&B) 睡下（nr_running 归 0）
t1  B 入队：pwq->nr_active(4) == max_active(4)
    → B 进 inactive_works，带 WORK_STRUCT_INACTIVE
t2  池的反应：need_more_worker=1（worklist 有 B？否——B 在 inactive_works！）
    仔细想：inactive 的 B 不在 pool->worklist 上 → need_more_worker=0
    → 池连"建新 worker"的冲动都没有
t3  死锁成型：唯一能让 nr_active-- 的是 A 们完成，而 A 等 B，B 等名额
    watchdog 视角：pool->worklist 空 → 不报 lockup；
    A 们的 flush 睡在 wait_for_completion → 120s 后 hung task 报告
```

**场景 b（循环依赖）**：A 等 B，B 反过来（直接或间接）等 A——任何并发度都救不了：

```
wq1 的 A: flush_work(&B)      wq2 的 B: flush_work(&A)
两个 wq、两个 pwq、名额互不侵犯——照样死：A 等 B 完成，B 等 A 完成。
lockdep 的 wq_completion/work_completion 双层伪锁正是为画出这种环而生。
```

**解药**：链式依赖改成**函数尾部接续投递**（A 的最后一步 `queue_work(wq, &B)`）而不是**等待**；确需等待则把 A、B 放**不同 wq**（不同 pwq/名额池），并用 lockdep 全开跑一遍压测确认无环。

### 例 2：flush_workqueue 自等

work 函数里 `flush_workqueue(本 wq)`：flush 要等"当前所有 in-flight 归零"，而自己就是 in-flight——`wq->mutex` 与颜色机制都拦不住这种逻辑自噬（flusher 不占 in-flight 计数，但它等的集合包含自己正在执行的 work）。lockdep 有**部分**防护：`check_flush_dependency` 会 WARN "PF_MEMALLOC task is flushing !WQ_MEM_RECLAIM" / "WQ_MEM_RECLAIM work is flushing ..."——它盯的是**内存回收方向**的自噬，纯自等要靠 review。6.6 的 `start_flush_work` 对 ordered/rescuer wq 用 `lock_map_acquire` **强制** lockdep 报递归死锁（`lockdep_invariant_state` 注释里说明为何普通 wq 不强制——假阳性太多）。**军规：work 里永远不 flush 自己所在的 wq。**

```
自等的两种变体都要警惕：
(a) 直接型：work_fn() { flush_workqueue(my_wq); }          ← 显然
(b) 传递型：work_fn() { 拿锁 L; 调用 foo(); }
            foo()      { flush_workqueue(my_wq); }          ← 隐藏得深
变体 (b) 是文档"guidelines"反复点名的模式：一旦有其他 work 也要拿 L，
等价于"我占着 L 等 flush 完成，而完成需要那个 work 拿到 L"——flush 死锁
与锁死锁的复合体。反推军规 6 的另一半：不 flush 本 wq，也尽量不在 work
里拿"别人 flush 本 wq 时可能持有的锁"。
```

### 例 3：work 持锁 × cancel_work_sync 互锁

```
work_C() { mutex_lock(&m); ...; mutex_unlock(&m); }
线程 T:  mutex_lock(&m); cancel_work_sync(&C); mutex_unlock(&m);
```

T 拿着 m 等 C 跑完；C 跑到 `mutex_lock(&m)` 等 T → 死锁。**cancel_work_sync 的"等"与任何它执行路径上会拿的锁互斥**：

```
CPU0（work_C，kworker）             CPU1（线程 T）
─────────────────────────           ─────────────────────
mutex_lock(&m)  ← 拿到              mutex_lock(&m)  ← 自旋等待
执行 C 的正活……                      （还在等 m）
跑到 flush/cancel 等待点？不——       mutex_lock 拿不到？T 用的是
C 是被 cancel 的对象：C 正常跑完      mutex_lock→可睡眠→T 睡在 m 的
释放 m 即可解锁。真正死锁序：         waitqueue 上
  T 先拿 m → cancel_work_sync(C)
  → __flush_work 插 barrier 等 C 结束
  → C 醒来要 m → 等 T
  → T 等 C → 环闭合
```

正确姿势二选一：cancel 侧不持锁（先把状态位关掉、放锁、再 cancel_sync，用状态位防 work 重入临界区）；或 work 侧临界区极小且不含会等 canceler 的路径。**同族**：`destroy_workqueue`（内含 drain）、`flush_work` 同样不能在持有"work 可能要的锁"时调用。一个易漏的变体：**中断上下文里拿 spinlock + 别处 cancel_work_sync**——canceler 等的 work 若在等那把 spinlock 持有者唤醒的事件，同样成环（spinlock 侧看似无睡眠，但持锁路径若包含 queue_work 的关中断区，会拉长 cancel 的等待窗口）。

### 例 4：内存回收死亡螺旋（WQ_MEM_RECLAIM 的由来）

```
kswapd/直接回收 → 需要执行 wq X 的 work W（如回写元数据）才能释放内存
wq X 的池 → 创建 worker 失败（GFP_KERNEL 分配本身缺内存）→ 干等
```

第 1 章 §4.2 的 mayday 机制在此闭环：池建线程受阻超 10ms → `pool_mayday_timeout` 对 worklist 每个 work `send_mayday` → X 的 rescuer 醒来、attach 到池、**无视名额与 worker 创建**直接把本 wq 的 work 搬去执行。rescuer 常驻且绑全 CPU、nice -20，保证"救火通道"不缺资源。**lockdep 侧防线**：`check_flush_dependency` 的两条 WARN（回收上下文 flush 非 MEM_RECLAIM wq；MEM_RECLAIM work flush 非 MEM_RECLAIM wq）就是防你把依赖环织出来。驱动军规：**回收路径（writeback、shrink 回调、__GFP_RECLAIM 深处）可能触达的 wq 全部标 WQ_MEM_RECLAIM**。

### 例 5：PREEMPT_RT 下的注意点

6.6 主线 workqueue.c **没有** RT 专用分支（pool->lock 本就是 `raw_spinlock_t`，RT 补丁集无需转换它）。RT 环境的真实差异点：

- **kworker 是普通 SCHED_OTHER 线程**：WQ_HIGHPRI 只是 nice -20。RT 任务永不因等 kworker 而被 kworker 阻塞，反之 kworker 可被 RT 无限推迟——RT 系统上"低延迟 work"应考虑 RT 专用机制（rt workqueue/线程化），而非 HIGHPRI。
- **work 里的锁必须可 pi 传播**：work 在进程上下文，持 `spinlock_t`（RT 下可睡眠的 rtlock）睡眠时优先级继承照常生效——比 softirq/tasklet 上下文安全得多（这正是 RT 把任务往 wq 迁的动力）。
- **BH workqueue 是 6.10+ 的新特性，6.6 没有**：6.6 上 RT 的 softirq 线程化由 IRQ threading 承担；tasklet 在 RT 下仍原子上下文。别把"RT 下有 BH wq"写进认知——那是后来的 `irq_work`/`BH wq` 系列（6.10 起 `queue_work_bh` 等）。
- CMWQ 的 `local_irq_save` 在 RT 下依旧关硬中断但区间极短（无锁操作 + 链表插入），不构成延迟问题。

### 五类死锁速查表

| 死锁 | 根因 | 系统表现 | 检测手段 | 解药 |
| :--- | :--- | :--- | :--- | :--- |
| 名额耗尽 | 等"同 pwq 的后续 work" | inactive_works 有货、worklist 空、worker 全睡 | hung task（120s） | 尾部接续 / 分 wq |
| 循环依赖 | A⇄B 互等 | 同上，跨 wq 也成立 | lockdep 双层伪锁 | 重构依赖图 |
| flush 自等 | 等的集合含自己 | flusher 睡在 completion | lockdep（部分）；review | 军规 6 |
| cancel×锁互锁 | 持 work 要的锁去 cancel | canceler 与 kworker 互睡 | lockdep / hung task 双份回栈 | 先放锁 |
| 回收螺旋 | 建线程缺内存等回收 | mayday 风暴、RESCUED 上涨 | wq_monitor mayday 列 | WQ_MEM_RECLAIM |

## 五、检测工具箱

### 5.1 lockdep 对 workqueue 的双层理解

- **wq 级**：每个 wq 注册 `"(wq_completion)<name>"` 伪锁；`flush_workqueue`/`__queue_work` acquire 它。锁序：flush（W 锁）→ work 执行（W 递归读）→ work 里拿真锁。由此 lockdep 能推出"work A 里 flush wq B，而 B 的 work 又等 A 的 wq"这类**跨 wq 环**。
- **work 级**：每个 work_struct 有 `"(work_completion)<name>"` 伪锁；执行时 acquire。`flush_work` 的 barrier 等待构成依赖边。`start_flush_work` 对 ordered/rescuer wq 额外强制 acquire（真死锁而非假阳性）。
- `lockdep_invariant_state(true)`（6.6 源码）：执行 work 时把上述伪锁标记为"不变态"，屏蔽 flush/complete 之间的假依赖环——源码注释给出完整的反例推演，值得一读。

典型报告长相（示例为常见格式，重点看依赖链的起点/终点是否落在本 wq）：

```
======================================================
WARNING: possible circular locking dependency detected
------------------------------------------------------
kworker/0:1/217 is trying to acquire lock:
 (wq_completion)my_wq+.../...  at: flush_workqueue+...
but task is already holding lock:
 (work_completion)my_wq#.../...  at: process_one_work+...  ← work 里 flush 本 wq
which depends on lock: ... → 环成立
```

解读技巧：依赖链里出现 `(wq_completion)` 说明有 flush 参与环；`(work_completion)` 说明环穿过某个 work 的执行体——顺着链找第一个**非伪锁**的真锁，那就是要重构的依赖。

### 5.2 CONFIG_DEBUG_OBJECTS_WORK

跟踪 work_struct 生命周期：重复 INIT 活跃对象、free 活跃对象、激活未初始化对象——fixup 回调自动 `cancel_work_sync` 抢救并报告。`INIT_WORK_ONSTACK`/`destroy_work_on_stack` 让**栈上 work** 也可跟踪（wq_barrier/work_on_cpu 等内核自身用法即此）。抓"work 已释放却又被 queue"类 UAF 的第一道网。

### 5.3 watchdog × hung task 联动

- **wq watchdog**（CONFIG_WQ_WATCHDOG，`workqueue.watchdog_thresh` 默认 30s）：池头 work 换代停滞超阈值 → `BUG: workqueue lockup` + `show_all_workqueues()`（全部 wq 的 in-flight/pending/inactive + 函数指针）+ `show_cpu_pools_hogs()`（卡死 CPU 池中 running worker 的回栈）。`wq_watchdog_touch()` 被 printk 等热路径调用防误报；VM 被宿主暂停另有 `kvm_check_and_clear_guest_paused` 防误报。
- **hung task**（默认 120s）：D 状态 kworker 超时 → backtrace 里自动带 `Workqueue: <wq> <fn> (<desc>)` 行（`print_worker_info`）。
- 分工：watchdog 抓**池停摆**（有活没人干/干的人焊死），hung task 抓**单 work 睡死**。两者皆空时怀疑 cancel/flush 逻辑本身（-ENOENT 等待链挂死）。

### 5.4 destroy_workqueue 的排空语义（6.6 真实行为）

```
destroy_workqueue(wq):                     /* 返回 void！*/
  ① sysfs 注销
  ② 置 __WQ_DESTROYING（之后 __queue_work 对外来提交 WARN+丢弃）
  ③ drain_workqueue：反复 __flush_workqueue 直至全部 pwq
     nr_active==0 && inactive_works 空（10 次起 warn）
  ④ 杀 rescuer（kthread_stop；rescuer 清空 maydays 链后才退出）
  ⑤ 终极体检（持 wq_pool_mutex+wq->mutex+全部 pool->lock）：
     对每个 pwq 调 pwq_busy():
        任一色 nr_in_flight 非零 / refcnt>1 / nr_active / inactive_works 非空
     → WARN_ON + show_pwq() + return（★ 放弃销毁，wq 泄漏但系统存活）
  ⑥ 全净：摘出 workqueues 链，put 各 pwq 基础引用
     → 最后一个 pwq 的释放（bounce 到 pool_workqueue_release 线程）
     → RCU 后 kfree(wq)
```

> ⚠️ **与常见认知的偏差**：destroy_workqueue **没有 -EBUSY 返回**（void 函数）。"销毁失败"表现为 WARN + `has the following busy pwq` 转储 + wq 永不释放。典型残留原因：有人还在 queue（chained 检查漏网的跨 wq 依赖）、cancel 没等完就 free、或 flush/cancel 者自己卡死。第 ⑥ 步的异步释放意味着 `destroy_workqueue` 返回后 wq 内存还要过 RCU 宽限期才消失——**返回 ≠ 可以立刻 free 依赖它的东西**（如 attrs、name 所在的模块数据）。

排空完整时间轴（对照源码逐步核对用）：

```
T0  workqueue_sysfs_unregister(wq)
T1  wq->mutex: flags |= __WQ_DESTROYING        ← 之后外来 queue_work 被
                                                    WARN_ON_ONCE+丢弃
T2  drain_workqueue:
      nr_drainers++（首个 → __WQ_DRAINING）
      loop: __flush_workqueue(wq)
            检查每个 pwq: nr_active==0 && inactive_works 空?
            否 → reflush（10 次起 pr_warn，flush_cnt%100 继续）
      nr_drainers-- → 归零清 __WQ_DRAINING
T3  rescuer: wq_mayday_lock 下 wq->rescuer=NULL（先断新求救）
      kthread_stop(rescuer->task)   ← rescuer 清空 maydays 后退出（6.6 语义）
T4  体检: pwq_busy 全绿？
      否 → WARN_ON + show_pwq + show_one_workqueue + return（半死状态：
            DESTROYING 置位但 wq 还挂在全局链上，还能收 chained work）
T5  list_del_rcu(&wq->list)                      ← 冻结路径再也看不见它
T6  for_each_possible_cpu: put_pwq_unlocked(cpu_pwq[cpu])
    put_pwq_unlocked(wq->dfl_pwq)
    → refcnt 归零的 pwq 排队进 pool_workqueue_release 线程
    → pwq_release_workfn: 从 wq->pwqs 摘除（RCU）→ put_unbound_pool
    → 最后一个 pwq → wq_unregister_lockdep + call_rcu(rcu_free_wq)
T7  RCU 宽限期后: kfree(wq)                       ← 真正消失
```

排查 T4 失败的套路：`show_pwq` 的输出已带 `pending:`/`inactive:`/`in-flight:` 三段函数指针清单——哪类残留直接指认：pending/inactive 是"还在被 queue"（查 queue 侧引用），in-flight 是"执行中卡死"（回到 §5.3 的工具）。

## 六、驱动接入十条军规

1. **短活进 system_wq，长活进 system_unbound_wq 或自建 unbound**；"长"的分界参考 6.6 自动检测阈值 10ms——Hogging 警告就是判决书。
2. **需要 flush/cancel 本 wq 的 work → 必须自建 wq**；公共 wq 的 flush 已被编译期+运行时双重警告。
3. **回收路径可能触达的 wq → WQ_MEM_RECLAIM**；不确定就加上（代价一个 rescuer 线程）。
4. **全局严格串行只用 `alloc_ordered_workqueue`**；`UNBOUND+max_active=1` 的隐式 ordered 是兼容包袱不是承诺。
5. **work 函数退出时的状态必须与进入时一致**：不持锁、不在原子——process_one_work 的泄漏体检与 lockdep 都在盯。
6. **work 里绝不 flush 自己的 wq、不 cancel_sync 可能等自己的链**；需要顺序用尾部接续投递。
7. **cancel_work_sync 前先放掉 work 会拿的锁**；自续 work 必须配"运行条件开关"防复活。
8. **栈上 work 必配 `INIT_WORK_ONSTACK` + 用后 `destroy_work_on_stack`**（开 DEBUG_OBJECTS 时是硬要求）；work 结构的生存期必须覆盖到执行结束（free-on-run 除外，见第 2 章 busy_hash 注释）。
9. **延迟 work 的 timer 是 IRQSAFE 的**：dwork 所在内存同样要活过整个周期；`mod_delayed_work` 是"改期或提交"的原子组合，优于先 cancel 再 queue。
10. **给 work 标身份**：`set_worker_desc("dev%d", id)` 让 sysrq/hung task 报告直接指认到设备——排障时间从小时级降到分钟级。

对照范例（节选自良好实践的骨架）：

```c
struct my_dev {
	struct work_struct      reset_work;     /* 自建 wq 上跑 */
	struct delayed_work     poll_dwork;
	struct workqueue_struct *wq;            /* 专属 wq：要 flush/cancel 它 */
	bool                    resetting;      /* 军规 7 的状态开关 */
};

/* probe：
 * mydev->wq = alloc_workqueue("mydev%d", WQ_UNBOUND | WQ_MEM_RECLAIM, 0);
 * —— 设备级隔离（可 flush）、长活可迁移、回收安全 */
/* reset_work 里重启自身前查开关：
 * if (!READ_ONCE(dev->resetting)) queue_work(dev->wq, &dev->reset_work); */
/* remove 的顺序（军规 3/7/8 的合奏）：
 * dev_set_resetting(dev);                       关状态位
 * cancel_delayed_work_sync(&dev->poll_dwork);   等 dwork
 * if (dev->wq) { cancel_work_sync(&dev->reset_work);
 *                destroy_workqueue(dev->wq); }  等 reset + 排空销毁
 * —— 注意全程不持有 reset_work 会拿的锁 */
```

## 七、观测实战：谁占了 worker 最久

一次真实排障的完整流程（假想：机器周期性卡顿，怀疑 workqueue）：

```
# ① 先看有没有池停摆 / 霸核（30 秒就出结果）
cat /proc/sys/kernel/sysrq_w 等价：echo w > /proc/sysrq-trigger | grep -A3 workqueue
#   → 见 "hogged CPU for >10000us" 直接锁定函数，跳到 ④

# ② wq 级吞吐画像（6.6 官方工具，2 秒采样 × 5）
drgn tools/workqueue/wq_monitor.py -i 2 -n 5 | tee wqmon.log
#   看 CPUitsv（自动 CPU-intensive 次数）与 mayday 列：前者=霸核嫌疑，
#   后者=建线程受阻（内存压力/池过载）

# ③ tracepoint 配对，拿每个函数的执行驻留时间分布
perf record -e workqueue:workqueue_execute_start \
            -e workqueue:workqueue_execute_end -a -- sleep 30
perf script | 配对脚本（work 指针为键，start/end 差值）
#   bpftrace 等价一行流见第 2 章 §5.2 —— @dur_us 按函数 max/直方图

# ④ 区分"驻留久"是霸核还是睡眠：
#    霸核 → 该函数所在 wq 若是 per-cpu，迁 WQ_UNBOUND/自建 unbound
#    睡眠久 → 看它在等什么（hung task 回栈/lockdep），修依赖而非 wq

# ⑤ 修复后回归：同 tracepoint 对比 P99；wq_monitor 对比 CPUtime 归一化
```

补一个真实感的判读样例（字段为 6.6 wq_monitor.py 实际输出列）：

```
$ drgn tools/workqueue/wq_monitor.py -i 2 -n 3
    total     infl  CPUtime  CPUitsv  CMW/RPR  mayday  rescued  workqueue
   423.0K      213     1.4m     2.1K        0       0        0  events
      ...       ...     ...      ...      ...     ...      ...  ...
     18.0K       84   310.0s     1.8K        0     213      210  mydrv-flush
```

判读：`mydrv-flush` 的 CPUtime/total 比值远超 events（单 work 平均 CPU 驻留高）、CPUitsv 与 mayday 同时高——**霸核 + 建线程受阻**的组合画像：per-cpu wq 上有 work 长时间不睡眠（触发自动 CPU-intensive），且池创建 worker 时内存吃紧到触发 rescuer。处置方向：该 wq 迁 `WQ_UNBOUND`（离开 per-CPU 池，天然不受 CM 约束）+ 核查 213 次 mayday 是否指向真实的内存压力场景（若是，确认 WQ_MEM_RECLAIM 已加——示例里它显然加了，rescued=210 说明 rescuer 在有效兜底，但**频繁触发本身就是设计坏味道**：work 里可能持有了拖慢进度的锁）。

最后一个易被忽略的观测点：**kworker 线程的 `+/-` 后缀**。`ps -e -o comm | grep kworker` 里 `kworker/0:1+events` 表示该 worker 正在执行 events 的 work——生产机上一批 `+` 同一 wq 名而该 wq 的 infl 却接近 0，多半是观测瞬间的正常执行；若 sysrq-w 显示 in-flight 大量集中在同一函数，配合 ③ 的驻留分布即可定位"哪个 work 占了 worker 最久"的最终答案。
