# IO 调度器（elevator）

> 阅读目标：blk-mq 时代"电梯"的职责从"全局排序"收缩为"每个硬件队列的准入与派发策略"。本章过一遍 elevator 框架的完整回调表与切换协议，然后进入三套在树调度器的决策内核——mq-deadline 的读写期限与批次、kyber 的域令牌与 p99 自适应、bfq 的权重与预算——最后给出选型表与 ioprio/cgroup 的传导链。核对自 6.6 的 `block/elevator.c`、`block/elevator.h`、`block/mq-deadline.c`、`block/kyber-iosched.c`、`block/bfq-iosched.h`、`block/blk-ioprio.c`。

## 一、elevator 框架

### 1.1 回调表：elevator_mq_ops（6.6 全量）

```c
struct elevator_mq_ops {
    /* 生命周期 */
    int  (*init_sched)(struct request_queue *, struct elevator_type *);
    void (*exit_sched)(struct elevator_queue *);
    int  (*init_hctx)(struct blk_mq_hw_ctx *, unsigned int);
    void (*exit_hctx)(struct blk_mq_hw_ctx *, unsigned int);
    void (*depth_updated)(struct blk_mq_hw_ctx *);      /* nr_requests 变更回调 */
    /* 合并参与 */
    bool (*allow_merge)(struct request_queue *, struct request *, struct bio *);
    bool (*bio_merge)(struct request_queue *, struct bio *, unsigned int);
    int  (*request_merge)(struct request_queue *, struct request **, struct bio *);
    void (*request_merged)(struct request_queue *, struct request *, enum elv_merge);
    void (*requests_merged)(struct request_queue *, struct request *, struct request *);
    /* 准入 */
    void (*limit_depth)(blk_opf_t, struct blk_mq_alloc_data *);  /* 调 shallow_depth */
    void (*prepare_request)(struct request *);    /* RQF_USE_SCHED 的 rq 初始化 */
    void (*finish_request)(struct request *);     /* rq 终结(释放调度器侧状态) */
    /* 派发核心(必须实现) */
    void (*insert_requests)(struct blk_mq_hw_ctx *, struct list_head *, blk_insert_t);
    struct request *(*dispatch_request)(struct blk_mq_hw_ctx *);
    bool (*has_work)(struct blk_mq_hw_ctx *);
    /* 辅助 */
    void (*completed_request)(struct request *, u64);
    void (*requeue_request)(struct request *);
    struct request *(*former_request)(struct request_queue *, struct request *);
    struct request *(*next_request)(struct request_queue *, struct request *);
    /* io_cq 接口(bfq 用) */
    void (*init_icq)(struct io_cq *); void (*exit_icq)(struct io_cq *);
};
```

核心契约只有四条：`insert_requests`（请求怎么进）、`dispatch_request`（出队一个）、`has_work`（还有货吗）、`depth_updated`。blk-mq 派发链（第 3 章 §4.2）通过这四个回调把策略外包给调度器；其余全是合并与记账的参与点。

挂载点：`elevator_queue { type, elevator_data(调度器私有), kobj, hash(合并哈希, ELV_HASH_BITS=6) }`，队列级一个（`q->elevator`）；每 hctx 再有 `hctx->sched_data`（init_hctx 分配）与 `hctx->sched_tags`。

### 1.2 注册与默认选择

```c
struct elevator_type {
    struct elevator_mq_ops ops;
    size_t icq_size, icq_align;         /* bfq 的 icq 尺寸 */
    struct elv_fs_entry *elevator_attrs;/* /sys/.../queue/iosched/ 下的参数 */
    const char *elevator_name;
    const unsigned int elevator_features;
    struct module *elevator_owner;
    ...
};
elv_register(e) / elv_unregister(e)     /* 挂/摘 elv_list 全局链 */
```

**默认调度器的规则**（elevator.c `elevator_get_default`，6.6 实测）：

```c
if (q->tag_set->flags & BLK_MQ_F_NO_SCHED_BY_DEFAULT)
    return NULL;                              /* → none */
if (q->nr_hw_queues != 1 &&
    !blk_mq_is_shared_tags(q->tag_set->flags))
    return NULL;                              /* 多硬件队列 → none */
return elevator_find_get(q, "mq-deadline");   /* 单队列/共享 tag → mq-deadline */
```

即：**NVMe（多 hctx）默认 none；SATA/SCSI 单队列与共享 tagset 默认 mq-deadline**。`BLK_MQ_F_NO_SCHED_BY_DEFAULT` 供驱动（如 nvme 对共享 tagset）显式豁免。`device_add_disk()` 里 `elevator_init_mq()` 冻结队列后初始化。

### 1.3 sysfs 切换协议

```bash
cat /sys/block/sda/queue/scheduler     # [mq-deadline] kyber bfq none
echo kyber > /sys/block/sda/queue/scheduler
```

`elv_iosched_store` → `elevator_change` → `elevator_switch(q, new_e)`，6.6 的精确步骤：

```text
elevator_switch (elevator.c):
  ① blk_mq_freeze_queue(q)      # 拒绝新提交, 等在途 request 清零
  ② blk_mq_quiesce_queue(q)     # 停派发, 等 queue_rq 调用全部返回
  ③ elv_unregister_queue + elevator_exit(q)   # 拆旧调度器与 sched_tags
  ④ blk_mq_init_sched(q, new_e) # 重建 sched_tags(nr_requests =
                                #   2*min(queue_depth,128)), init_sched/init_hctx
  ⑤ elv_register_queue(q, true) # 重建 /sys/.../queue/iosched/ 参数树
  ⑥ unquiesce + unfreeze        # 恢复通行
  失败 → 回退 "none" (pr_warn)
切到 "none" 走 elevator_disable: 额外清 QUEUE_FLAG_SQ_SCHED,
  q->nr_requests = tag_set->queue_depth (深度语义切换!)
另: elevator_change 先 request_module("<name>-iosched") —— 调度器可编译为模块
```

运行时切换代价可观（freeze+quiesce 毫秒级停顿），适合整批设备一次性 udev 规则固化。

## 二、none：直通

无调度器即"none"：请求只经过 per-CPU 软队列（`ctx->rq_lists[hctx->type]`）短暂停留，派发时 `blk_mq_flush_busy_ctxs` 一把全倒给驱动。合并只剩第 4 章的 plug 免锁合并与 ctx 链的 8 次尝试（`blk_mq_sched_bio_merge` 的默认分支）。

适用：设备自排队能力强的多队列 SSD（NVMe），或上层已有完备调度（数据库/io_uring + 应用层批处理）。观测：`/sys/block/nvme0n1/queue/scheduler` 显示 `none`。

## 三、mq-deadline：期限 + 批次

### 3.1 数据结构（mq-deadline.c，6.6 全量）

```c
struct dd_per_prio {                     /* 按 ioprio class 三份 */
    struct list_head dispatch;           /* 已选定的派发暂存 */
    struct rb_root sort_list[2];         /* 扇区序红黑树(读/写) */
    struct list_head fifo_list[2];       /* 到期序 FIFO(读/写) */
    sector_t latest_pos[2];              /* 各方向最近派发位置 */
    struct io_stats_per_prio stats;      /* inserted/merged/dispatched/completed */
};
struct deadline_data {
    struct dd_per_prio per_prio[3];      /* DD_RT_PRIO/DD_BE_PRIO/DD_IDLE_PRIO,
                                            由 ioprio_class_to_prio[] 映射 */
    enum dd_data_dir last_dir;           /* 当前批次方向 */
    unsigned int batching, starved;      /* 批内计数 / 读饿写计数 */
    int fifo_expire[2];                  /* 期限: 读 HZ/2, 写 5*HZ (软!) */
    int fifo_batch;                      /* 批次上限 16 */
    int writes_starved;                  /* 读最多压制写 2 轮 */
    int front_merges;                    /* 允许前向合并(默认 1) */
    u32 async_depth;                     /* 异步/写 的 tag 浅水位 */
    int prio_aging_expire;               /* 低优先级老化 10*HZ */
    spinlock_t lock, zone_lock;
};
```

同一请求**同时**在 sort_list（供扇区局部性）与 fifo_list（供到期保护）上——deadline 的名字来自后者。

### 3.2 派发决策树（dd_dispatch_request → __dd_dispatch_request）

```text
dd_dispatch_request(hctx)                 [共享状态: 全队列一个 dd, 跨 hctx!]
 ├─ ① 老化保护: ≥2 个优先级有货时, 若 BE/IDLE 中有请求
 │     已等 > prio_aging_expire(10s) → 先发它 (防 RT 独占)
 ├─ ② 按 RT → BE → IDLE 顺序找第一个有货的 per_prio
 └─ ③ __dd_dispatch_request(per_prio, now):
      dispatch 链有货 → 直接取 (上轮选好未发的)
      同方向续批: last_dir 的 fifo_list 有货 且 batching < fifo_batch(16)
        → 从 sort_list 里取"最近派发位置之后"的下一个扇区 (latest_pos
           续航, ZNS 时回退到区起点)
      换方向: 读 FIFO 非空 且 写未被饿 starved >= writes_starved(2) 次
        → 继续读; 否则若有写 → 转发写 (starved 清零)
      选起点: 该方向 FIFO 队头已到期(deadline_check_fifo) 或无续航候选
        → 取 FIFO 头(最老请求); 否则取扇区序的下一个
      batching++; 记 latest_pos; stats.dispatched++
```

### 3.3 与 blk-mq 的两个接口

* **`dd_limit_depth`**：同步读免限；**写与异步请求**把 `data->shallow_depth = dd->async_depth`（`dd_depth_updated` 计算：`max(1, 3 * (1<<shift) / 4)`，即 sched_tags 深度的 3/4）——sbitmap 的"浅分配"确保读请求始终有 tag 可拿，不被写洪峰挤死。
* **`QUEUE_FLAG_SQ_SCHED`**：dd 在 `dd_init_sched` 里置位——它是"队列级共享状态"的调度器，派发不必尊重 hctx（`blk_mq_get_sq_hctx` 只从本 CPU 对应 hctx 派发，避免多 hctx 锁竞争）。kyber/bfq 则各自显式清/置此标志。

## 四、kyber：域令牌 + p99 自适应

### 4.1 思想

不做请求排序，改做**准入控制（pacing）**：把请求按类型分域，每域一个**设备级令牌池**（`sbitmap_queue domain_tokens[]`），派发前必须拿到令牌。深度不拍脑袋——用延迟直方图的 p99 对目标延迟的比例**自动缩放**。

```c
enum { KYBER_READ, KYBER_WRITE, KYBER_DISCARD, KYBER_OTHER, KYBER_NUM_DOMAINS };

static const unsigned int kyber_depth[] = {      /* 每域深度上限 */
    [KYBER_READ]=256, [KYBER_WRITE]=128, [KYBER_DISCARD]=64, [KYBER_OTHER]=16,
};
static const u64 kyber_latency_targets[] = {     /* 目标延迟(p99 对照物) */
    [KYBER_READ]=2ms, [KYBER_WRITE]=10ms, [KYBER_DISCARD]=5s,
};
static const unsigned int kyber_batch_size[] = {  /* 每域连发量 */
    16, 8, 1, 1,
};
```

每 hctx 侧：`struct kyber_hctx_data { rqs[4](域队列), cur_domain, batching, kcqs(per-ctx 域队列), kcq_map[4](sbitmap), domain_wait[4](等令牌的挂点) }`——kyber 尊重多 hctx（init 时 `blk_queue_flag_clear(QUEUE_FLAG_SQ_SCHED)`）。

### 4.2 自适应回路

```text
完成侧 kyber_completed_request(rq, now):
  双计时: TOTAL(now - start_time_ns) 与 IO(now - io_start_time_ns)
  按延迟/目标比例落入 8 桶直方图(每桶宽 1/4 目标; KYBER_LATENCY_SHIFT=2,
  前 4 桶=达标, 后 4 桶=超标)  per-cpu 无锁累加
  timer_reduce(kqd->timer, jiffies + HZ/10)        ← 100ms 节流定时器

kyber_timer_fn():                                  (每 100ms)
  汇总全部 CPU 直方图
  p90(IO 延迟) >= 达标桶?  → bad = true             ← 用 p90 抗离群值,
                                                       判"设备拥塞"
  对每域算 p99(总延迟):
    depth = orig_depth * (p99_bucket+1) >> 2        ← 线性映射:
                                                       p99 达标 → 缩容,
                                                       p99 超 2x → 翻倍
    kyber_resize_domain(): clamp(1..kyber_depth[域]) + sbitmap_queue_resize
```

派发侧：`kyber_dispatch_cur_domain` 从 `cur_domain` 取请求，令牌不足则 `kyber_get_domain_token` 挂 `domain_wait`（令牌释放时 `kyber_domain_wake → blk_mq_run_hw_queue`），域间轮转 + 批次（`kyber_batch_size`）。另外 `KYBER_ASYNC_PERCENT=75`：异步请求的 tag 浅水位留 25% 给同步——与 dd 的 async_depth 同一防饿思路。

## 五、bfq：比例公平的重量级选手

### 5.1 数据骨架

```c
struct bfq_entity {                     /* 通用调度实体(队列/组共用) */
    u64 start, finish;                  /* B-WF2Q+ 虚拟时间戳:
                                           finish = start + budget/weight */
    u64 min_start;                      /* 子树最小 start(O(logN) 查找) */
    int budget;                         /* 本轮服务预算(扇区或时间) */
    int weight, new_weight, orig_weight;/* 权重: ioprio 或 cgroup io.weight */
    ...
};
struct bfq_queue {                      /* 每个同步提交者一个 */
    unsigned short ioprio, ioprio_class;/* RT/BE/IDLE + level */
    struct rb_root sort_list;           /* 扇区树 */
    struct list_head fifo;
    struct bfq_entity entity;
    unsigned int inject_limit;          /* 注入: 服务 A 时混发 B 的请求
                                           (治"预算切换空转") */
    struct bfq_queue *new_bfqq;         /* stable merge: 合并同源队列 */
    ...
};
```

### 5.2 机制要点

* **WF2Q+（加权公平队列）**：所有实体按虚拟完成时间 `F_i = S_i + budget_i/weight_i` 竞争，权重来自 ioprio（`IOPRIO_BE` 的 level→weight 映射）或 **blkcg `io.bfq.weight`**（bfq 有完整的 per-cgroup 层级，bfq-cgroup.c）。预算按"扇区数或服务毫秒"两种成本模型配给（`bfq_params`）。
* **idling**：服务某队列到预算尽时**故意等待一小会**，赌它还会来（交互式负载的延迟保障）——这是 bfq 交互性好的根源，也是吞吐杀器（深队列设备空转）。
* **injection**：为了治 idling 空转，在 in-service 队列等待时**注入**其他队列的少量请求（`inject_limit` 动态调整）。
* **单队列串行**：同一时刻只有一个 in-service 队列 + SQ_SCHED 语义 —— 这就是"bfq 不适合多 hctx NVMe"的机制本质：多队列并行派发会破坏它的公平记账前提。

### 5.3 存在的理由与代价

| | 理由 | 代价 |
| :--- | :--- | :--- |
| 桌面/单盘 HDD | 交互任务（打开浏览器）不被 tar/dd 淹死，权重直接给延迟保证 | 吞吐显著低于 none/dd（单服务者+idling） |
| QoS 场景 | cgroup `io.weight` 的真公平（throttle 只能限速，不做比例） | CPU 开销大（每请求走 WF2Q+ 树） |
| 顺序吞吐盘 | 调度器内建 seek 优化（最后位置+扇区树） | 多队列设备自排序，优化失效 |

## 六、选型与 ioprio 传导

### 6.1 选型表

| 设备/场景 | 推荐 | 理由 |
| :--- | :--- | :--- |
| NVMe（多 hctx） | **none** | 硬件自排序；调度器锁反而伤延迟；默认即 none |
| SATA/SCSI SSD（单队列） | **mq-deadline** | 默认；读保护几乎免费 |
| HDD 服务器/混合负载 | **mq-deadline**（或 kyber） | 电梯排序 + 读优先 |
| 桌面 HDD | **bfq** | 交互公平性 |
| 高并发低延迟目标（p99 SLO） | **kyber** | 域令牌 + 目标延迟自适应 |
| 虚拟化共享盘/多租户 | bfq 或 kyber + blk-throttle | 比例/限速组合拳 |

### 6.1.1 四种实现风格速览

| 维度 | none | mq-deadline | kyber | bfq |
| :--- | :--- | :--- | :--- | :--- |
| 状态粒度 | per-ctx 链表 | **全队列共享**（`QUEUE_FLAG_SQ_SCHED`） | per-hctx + 设备级令牌 | 全队列共享 + per-task icq |
| 排序结构 | 无 | 红黑树（扇区序）× 3 prio × 2 方向 | 无排序（FIFO + 域） | 红黑树 + WF2Q+ 实体树 |
| 准入控制 | 无 | `async_depth` 浅水位 | **域令牌池**（深度自适应） | budget/weight 派生 |
| 自适应 | 无 | 无（参数静态） | **p99→深度** 每 100ms | 预算估计/注入动态 |
| 合并参与 | ctx 链 8 试 | `bio_merge/request_merge`（树查） | `bio_merge`（blk_mq_sched_try_merge） | 同左 + icq 提示 |
| per-request 开销 | 最低 | 低 | 低（无树维护） | **最高**（实体进出树） |
| ioprio 感知 | 否（仅 tag hint） | **RT/BE/IDLE 三份队列** | 否（域不看 prio） | **weight 直接来源** |
| 典型代价 | 弱读保护 | 多 hctx 锁竞争 | 无顺序优化 | 吞吐/并行度损失 |

这张表是"选型"的机制注脚：每一个"代价"栏都能在对应小节找到结构性原因。

### 6.2 切换与参数实例

```bash
echo mq-deadline > /sys/block/sda/queue/scheduler
cat /sys/block/sda/queue/iosched/{fifo_batch,read_expire,write_expire,
    writes_starved,prio_aging_expire}          # dd 参数(dd 支持 per-prio 微调)
cat /sys/block/nvme1n1/queue/iosched/{read_lat_nsec,write_lat_nsec}  # kyber 目标
```

### 6.3 ioprio：从任务到请求

```text
用户接口: ionice -c <class> -n <level> -p <pid>
          IOPRIO_CLASS_RT(1)/BE(2)/IDLE(3) + level 0..7
           (IOPRIO_CLASS_NONE(0) = "未指定")
内核侧 get_current_ioprio() → __get_task_ioprio:
    task 显式设过? 用之
    否则由 nice 换算: task_nice_ioprio() = (nice + 20) / 5
        class 由调度策略推: SCHED_IDLE→IDLE, RT task→RT, 其余 BE
bio_set_ioprio(bio)  [blk-mq.c, 每个新 bio 都过一遍]:
    class==NONE → bio->bi_ioprio = get_current_ioprio()
    blkcg_set_ioprio(bio): 若 cgroup 配了 io.prio_class (blk-ioprio.c),
        用 cgroup 覆盖 —— cgroup 级 hint 传导的入口
请求侧: blk_rq_bio_prep 把 bi_ioprio 存进 rq->ioprio
    dd: ioprio_class_to_prio[] → RT/BE/IDLE 三份队列
    bfq: 直接驱动 entity weight
    注意: 提交者可通过 bio 分配时的 blk_mq_alloc_data 把 prio 带进
    ctx 分配 → 高 prio 请求在 tag 竞争中享有 async_depth 保护
```

> ⚠️ ioprio 是**提示**而非硬保证：none 调度器下它只影响 `limit_depth` 类细节；真正硬隔离要上 blk-throttle（`io.max`）或 iocost（`io.cost`，rq_qos 框架，第 4 章的 `rq_qos_throttle` 钩子）。

### 6.4 调度器之外：rq_qos 家族

IO 策略不止调度器一维。6.6 的 `struct rq_qos`（q->rq_qos 链）在**提交/完成路径**上挂钩，与调度器正交：

| rq_qos 实现 | sysfs 接口 | 钩子时机 | 语义 |
| :--- | :--- | :--- | :--- |
| blk-throttle | `io.max`/`io.iops.max` | `blk_throtl_bio`（submit_bio_noacct 尾部） | 硬限速（挂起+延后重放） |
| iocost | `io.cost.*` | `rq_qos_throttle/track/done` | 按成本模型的加权带宽 |
| iolatency | `io.latency` | `rq_qos_done_bio` | p10~p90 目标延迟，超则压制 |
| wbt | `/sys/kernel/debug/.../wbt_*` | `rq_qos_throttle` | 写回节流保交互 |

它们全部独立于 scheduler 参数工作——"调度器管顺序与准入，rq_qos 管配额与延迟目标"是 6.6 策略面的正确心智模型。

## 七、观测与调试

* **状态窥视**：`/sys/kernel/debug/block/<disk>/scheduler/`（CONFIG_BLK_DEBUG_FS）——各调度器的内部状态在此一览：

```text
mq-deadline:  per_prio/{0,1,2}/dispatch|fifo_list|sort_list  与 per-prio 统计
              (inserted/merged/dispatched/completed 可核对合并率)
kyber:        0..3 号域的 {depth, tokens, rqs} 与 cur_domain/batching
共同:         /sys/block/<disk>/queue/iosched/* 运行时参数(dd 的 read_expire
              单位 ms; kyber 的 read_lat_nsec 单位 ns —— 别搞混!)
```

* **tracepoints**：`block_rq_insert/issue/complete` + kyber 专属 `kyber_latency/kyber_adjust`（`/sys/kernel/tracing/events/kyber/`）——后两者直接看到"直方图汇总"与"深度调整"事件，是验证自适应回路的最短路径。
* **延迟直方图**：`/sys/block/<disk>/stats` 之外，`blk-stat.c` 的 per-cpu 桶（bfq/kyber 用 `blk_stat_enable_accounting` 开启）可以经 debugfs 读；`iostat -x` 的 `await` 分组对比（`-p` 看分区）。
* **A/B 方法论**：fio 固定负载（`rw=randread,mixread=70`）× 三个调度器各跑一遍，看 p99 而非均值——dd/bfq 的差异主要在尾部。

## 八、思考题

1. mq-deadline 的 `fifo_batch=16` 意味着"即使读已到期，当前写批次也可能再发 15 个写"。把这个参数调到 1 会发生什么？调到 256 呢？分别以随机读延迟、顺序写吞吐为坐标描述。
2. kyber 用 **p90(IO 延迟)** 判拥塞、用 **p99(总延迟)** 调深度，为什么不用同一个分位数？
    *提示：IO 延迟只含设备段，判"设备本身拥塞"要抗离群（p90）；深度调整针对排队段，目标是尾部（p99 总延迟对齐 SLO）。kyber-iosched.c 注释原文："we don't want to be too sensitive to outliers"。*
3. bfq 的 `inject_limit` 与 kyber 的 domain token 解决的是同一个问题吗？分别是什么？
    *提示：bfq 治"in-service 队列空转"（服务切换成本）；kyber 治"域间比例失衡"（洪峰淹没）。*
4. 一个 NVMe 盘上强行加载 bfq（`echo bfq > .../scheduler` 会因多 hctx 失败吗？查 `elv_support_features` 与 `ELEVATOR_FLAG`），假设能加载，预言吞吐劣化的两个结构性原因。
5. `io.prio_class`（blk-ioprio）设置的 cgroup hint 会覆盖任务自身的 ionice 吗？跟踪 `blkcg_set_ioprio` 的调用时机回答：它在什么条件下生效？
    *提示：只在 bio 尚未指定 prio（class NONE）时由 bio_set_ioprio 走 blkcg 覆盖。*
6. 为什么 `dd_depth_updated` 把 async_depth 定为 sched_tags 深度的 3/4 而不是 1/2？结合 `sbitmap_queue_get_shallow` 的位图语义（按字浅取）解释这个数字的工程含义。
