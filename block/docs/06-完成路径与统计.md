# 完成路径与统计

> 阅读目标：一次 DMA 完成 → 中断 → request/bio 逐层 endio → 上层唤醒，这条链的每一跳都决定了 IOPS 上限与尾延迟。本章拆解 6.6 的完成分派（本 CPU 直调 / 远端 IPI / BLOCK_SOFTIRQ 批处理）、批量完成（`io_comp_batch`）、requeue 与 timeout 机制、`/sys/block/*/stat` 17 列的精确定义与 iostat 的算法来源，并对比 NVMe 与 virtio-blk 的完成路径，附 IO 抖动排查清单。核对自 `block/blk-mq.c`、`block/blk-core.c`、`block/blk-timeout.c`、`block/blk-pm.c`、`include/linux/part_stat.h`、`block/genhd.c`、`drivers/nvme/host/{core,pci}.c`、`drivers/block/virtio_blk.c`。

## 一、完成链全景

```text
NVMe 盘完成路径 (6.6 实测):

 硬件: CQ 阶段位翻转, MSI-X 中断
   │
   ▼
 nvme_irq(irq, nvmeq)                         [nvme-pci.c]
   DEFINE_IO_COMP_BATCH(iob);
   nvme_poll_cq(nvmeq, &iob):
     while (nvme_cqe_pending):                 /* phase 位轮询 + dma_rmb */
        nvme_handle_cqe(cqe):
           req = nvme_find_rq(tagset, cqe->command_id)  /* tag→request 直查! */
           nvme_try_complete_req(req, status, result)
             写 nvme_req(req)->status + WRITE_ONCE(rq->state, MQ_RQ_COMPLETE)
           └─ 优先 blk_mq_add_to_batch(req, iob, ...)   /* 攒批, §三 */
              否则 nvme_pci_complete_rq(req)
                 └─ blk_mq_complete_request(req)        /* 逐个走分派 */
   iob 非空 → nvme_pci_complete_batch(&iob) → blk_mq_end_request_batch
   nvme_ring_cq_doorbell(nvmeq)                /* 一次 doorbell 收整批! */
```

## 二、blk_mq_complete_request：把完成送回"正确的 CPU"

```text
blk_mq_complete_request(rq)                    [blk-mq.c]
 └─ blk_mq_complete_request_remote(rq):
      WRITE_ONCE(rq->state, MQ_RQ_COMPLETE)
      ├─ 本地直调 (返回 false → 调用者自己 q->mq_ops->complete(rq)):
      │    hctx->nr_ctx == 1 且 rq 的 ctx CPU == 本 CPU   /* 单 ctx 队列 */
      │    或 rq->cmd_flags & REQ_POLLED                  /* 轮询 IO */
      ├─ 远端 IPI (blk_mq_complete_need_ipi 判定):
      │    SMP && QUEUE_FLAG_SAME_COMP
      │    && !force_irqthreads()              /* 强制线程化中断时 IPI 反而贵 */
      │    && 目标 CPU 在线
      │    && 不同 CPU && (QUEUE_FLAG_SAME_FORCE || 不共享 LLC)
      │    → blk_mq_complete_send_ipi(rq):
      │        llist_add(&rq->ipi_list, &per_cpu(blk_cpu_done, cpu))
      │        首个节点时 smp_call_function_single_async(cpu,
      │                       &per_cpu(blk_cpu_csd, cpu))
      │        远端: __blk_mq_complete_request_remote → __raise_softirq_irqoff
      │              (BLOCK_SOFTIRQ)
      └─ 其余(多队列但同 LLC/同 CPU 且 nr_hw_queues>1):
           blk_mq_raise_softirq: 本 CPU llist + raise_softirq(BLOCK_SOFTIRQ)

 BLOCK_SOFTIRQ → blk_done_softirq(h)           /* blk_mq_init 里注册 */
   └─ blk_complete_reqs(this_cpu_ptr(&blk_cpu_done)):
        entry = llist_reverse_order(llist_del_all(list))  /* llist 无序,
                                                             逆序恢复时序 */
        逐 rq: rq->q->mq_ops->complete(rq)     /* 回到驱动: nvme_complete_rq
                                                   / virtblk_request_done */
```

设计要点：

* **request 的 `ipi_list` 与调度器 `hash` 共用 union**（第 3 章）——调度哈希在派发时已拆除，完成复用该内存，零额外空间。
* **为什么送回提交 CPU**：`rq->mq_ctx->cpu` 是请求的出生地，bio 的 endio（解锁 folio、唤醒等待者）大概率访问提交侧缓存行与锁——同 LLC/同 CPU 完成让"提交-完成"闭环。`cpus_share_cache` 检查避免对同 LLC 的 IPI 浪费。
* **CPU 热插拔**：`blk_softirq_cpu_dead` 在 CPU 下线时把残留 llist 收走处理。
* passthrough/驱动内同步完成可用 `blk_mq_complete_request_direct()` 跳过分派。

## 三、endio 三级结构与批量完成

```text
q->mq_ops->complete(rq)           ←驱动收尾(nvme_complete_rq: 错误裁决
                                     COMPLETE/RETRY/FAILOVER/AUTH)
 └─ nvme_end_req → blk_mq_end_request(rq, status)
     ├─ blk_update_request(rq, error, blk_rq_bytes(rq)):
     │    逐 bio: req_bio_endio
     │      ├─ error 传播: bio->bi_status = error
     │      ├─ ZONE_APPEND: 回写实际落点 rq->__sector(部分完成不允许!)
     │      ├─ bio_advance(bio, nbytes)
     │      └─ bi_size==0 且 !RQF_FLUSH_SEQ → bio_endio(bio)  ★
     │          (flush 序列的第一次"假完成"被 RQF_FLUSH_SEQ 挡下, 第 4 章)
     │    剩余部分: __sector 前移, nr_phys_segments 重算(部分完成支持)
     └─ __blk_mq_end_request:
          blk_mq_need_time_stamp? → blk_stat_add + blk_mq_sched_completed_
          request(dd/bfq 的完成记账, kyber 的直方图采样!) + blk_account_io_done
          blk_mq_finish_request (elevator finish_request: dd 摘树/kyber 还令牌)
          rq->end_io? (passthrough/flush 换装的回调) : blk_mq_free_request
            └─ __blk_mq_free_request: 还 tag(sched+driver)、
               __blk_mq_dec_active_requests、blk_mq_sched_restart(hctx)
               (SCHED_RESTART 在位则 run 队列 —— 完成驱动的再派发!)
               blk_queue_exit (freeze 计数--)
```

**批量完成**（`blk_mq_end_request_batch`，NVMe/virtio 都用）：驱动把无错误、无特殊 end_io 的完成攒进 `io_comp_batch`（`blk_mq_add_to_batch` 判定，`RQF_SCHED_TAGS` 除外——sched tag 的还法不同）；批尾统一处理：循环 `blk_complete_request`（bio 侧）+ 记账 + tag **按 32 个一批**（`TAG_COMP_BATCH`）`blk_mq_put_tags` + `percpu_ref_put_many` 一次放队列引用。中断里 4000 IOPS 的 per-request 开销被摊薄成 per-batch。poll 上下文则有第三种姿势：virtio-blk 的 `virtblk_poll` 直接调 `blk_mq_complete_request_remote()`，返回 false（轮询请求必本地）时就地调 `virtblk_request_done`（即 `->complete` 回调）——跳过整个软中断分派。

### 3.1 上层回调的三类消费者

`bio_endio` 最后跳进的 `bi_end_io`，按提交者分三类：

```text
① page cache / mm:  mpage_read_end_io: bio_for_each_folio_all 逐 folio
     mark_uptodate + unlock (读路径的缺页等待者被唤醒);
     mpage_write_end_io: folio_end_writeback 清写回标记 → folio 可回收
     —— 这正是第 2 章 bio_for_each_folio_all 迭代器的头号用户
② 文件系统/DIO:     iomap/dio 的 end_io 聚合"本 inode 在飞计数", 归零才
     唤醒 fsync 等待者 —— 这就是 fsync 延迟=最慢那笔 D2C 的原因
③ io_uring:         kiocb → io_req_task_work 兑付 CQE (可能走 task_work
     回到提交线程上下文, 与 blk 的 IPI/softirq 分派叠加成两级接力)
```

### 3.2 部分完成：为什么支持它

`blk_update_request` 的循环逐 bio 完成 `nr_bytes` 字节、把剩余部分留在 request 上（`__sector` 前移、`nr_phys_segments` 用 `blk_recalc_rq_segments` 重算）——驱动对深层设备常"收一段报一段"（如 SCSI 的 residual、nvme partial）。两个边界：ZONE_APPEND 禁止部分完成（写入位置无法回溯，`req_bio_endio` 里直接判错）；`RQF_SPECIAL_PAYLOAD`（discard 类）跳过段重算。

## 四、requeue 与 timeout

### 4.1 requeue：请求的"再来一次"

```text
blk_mq_requeue_request(rq, kick_requeue_list)
 ├─ __blk_mq_requeue_request: 还 driver tag、trace_block_rq_requeue、
 │   rq_qos_requeue; 已 STARTED 的置回 MQ_RQ_IDLE, 清 RQF_TIMED_OUT
 ├─ blk_mq_sched_requeue_request (调度器侧回滚)
 ├─ 挂 q->requeue_list (requeue_lock)
 └─ kick → kblockd 上的 q->requeue_work:
      blk_mq_requeue_work:
        RQF_DONTPREP (驱动已深度介入) → blk_mq_request_bypass_insert
                                        (直挂 hctx->dispatch, 免合并)
        其余 → blk_mq_insert_request(BLK_MQ_INSERT_AT_HEAD)  插队头保时序
        最后 blk_mq_run_hw_queues
```

典型来源：`BLK_STS_DEV_RESOURCE`（第 3 章 dispatch 循环）、dm 路径切换、NVMe AUTH/RETRY。`blk_mq_delay_kick_requeue_list(q, msecs)` 支持延时重放（重试退避）。

### 4.2 timeout：滚动定时器 + 两遍扫描

```text
q->timeout (timer_list) 到期
 └─ blk_rq_timed_out_timer → kblockd_schedule_work(&q->timeout_work)
     blk_mq_timeout_work:                       [blk-mq.c]
      percpu_ref_tryget(&q->q_usage_counter)     /* 直取而非 blk_queue_enter:
                                                    freeze 等待期也要能跑 */
      第一遍 blk_mq_queue_tag_busy_iter(check_expired):
        全 tagset 扫描在途 rq (MQ_RQ_IN_FLIGHT 且 deadline 已过 且
        !RQF_TIMED_OUT) → has_timedout_rq
      有过期? blk_mq_wait_quiesce_done(tag_set)  /* synchronize_rcu/srcu:
                                                    等"已经开始的提交"全落地,
                                                    防 use-after-free */
      第二遍 handle_expired:
        blk_mq_rq_timed_out(rq):
          rq->rq_flags |= RQF_TIMED_OUT
          ret = q->mq_ops->timeout(rq)           /* 驱动裁决 */
          BLK_EH_DONE       → 不再续命(驱动稍后自行完成或 abort)
          BLK_EH_RESET_TIMER→ blk_add_timer(rq) 续命
      无任何过期且队列为空 → 各 hctx blk_mq_tag_idle (共享 tagset 计数回落)
      mod_timer(q->timeout, expired.next)        /* 前滚到最近的 deadline */
```

timeout 是**逐请求** deadline（`rq->deadline = jiffies + q->rq_timeout`，`blk_mq_start_request` 时 `blk_add_timer` 起表），queue 定时器只是把"最近的到期"前滚。故注入工具 `CONFIG_FAIL_IO_TIMEOUT` + `/sys/block/*/device/timeout` 能精准伪造单请求超时。SCSI/NVMe 在 timeout 里触发 abort/LUN reset/controller reset 的层级恢复（联系 scsi 分册）。

## 五、blk-pm：runtime PM 交互

* 队列级开关：`q->rpm_status`（RPM_SUSPENDED/RESUMING/ACTIVE），`atomic_t q->pm_only`。
* **挂起时只放行 RQF_PM 请求**：`blk_try_enter_queue()`（blk.h）里 `blk_queue_pm_only(q) && (!pm || queue_rpm_status(q)==RPM_SUSPENDED)` 拒绝普通提交——普通 bio 在 `blk_queue_enter` 的 wait 点睡眠，直到 resume 放行（`wake_up_all(&q->mq_freeze_wq)`）。
* 驱动侧序列：runtime suspend 前 `blk_mq_stop_hw_queues`+quiesce；恢复由 PM core 的 `runtime_resume` 回调驱动；`blk_pm_resume_queue` 判定是否解禁。
* `blk_mq_complete_request` 的 freeze 语义在 PM 下同样适用：完成的 `blk_queue_exit` 减引用，引用归零才允许真正挂起（`blk_clear_pm_only` 唤醒等待者）。

## 六、统计：17 列逐列与 iostat 的算法

### 6.1 数据源：per-cpu disk_stats

```c
struct disk_stats {               /* include/linux/part_stat.h, bdev->bd_stats */
    u64 nsecs[NR_STAT_GROUPS];    /* 4 组(读/写/discard/flush)的累计耗时 ns */
    unsigned long sectors[4];
    unsigned long ios[4];
    unsigned long merges[4];
    unsigned long io_ticks;       /* 该设备"有 IO 在飞"的时间片累计(jiffies) */
    local_t in_flight[2];         /* 读/写在飞数(bio-based 设备用) */
};
/* 写入方: part_stat_add 对分区同时累加到整盘(bd_partno 检查) */
```

6.6 的耗时口径是 **nsecs**（`blk_account_io_done`：`part_stat_add(part, nsecs[sgrp], now - req->start_time_ns)`）——旧版的 jiffies ticks 已被 ns 精度取代，sysfs 展示时除以 `NSEC_PER_MSEC` 变毫秒。

### 6.2 `/sys/block/*/stat`（与 /proc/diskstats 主体一致）的 17 列

`part_stat_show()`（genhd.c）的**精确**顺序：

| # | 名称 | 来源字段 | 含义 |
| :--- | :--- | :--- | :--- |
| 1 | rd_ios | `ios[STAT_READ]` | 完成读数 |
| 2 | rd_merges | `merges[STAT_READ]` | 被合并掉的读 bio 数 |
| 3 | rd_sectors | `sectors[STAT_READ]` | 读扇区数 |
| 4 | rd_ticks | `nsecs[STAT_READ]/1e6` | 读累计耗时 ms |
| 5–8 | wr_* | `STAT_WRITE` 同构 | 写四件套 |
| 9 | inflight | `blk_mq_in_flight()` | 采样瞬间在飞数（**读+写**，遍历 tag 位图统计） |
| 10 | io_ticks | `io_ticks→ms` | 有 IO 在飞的时间累计 |
| 11 | time_in_queue | Σnsecs/1e6 | 四组总耗时 ms ≈ "加权队列长度积分" |
| 12–15 | dscd_* | `STAT_DISCARD` 同构 | discard 四件套 |
| 16 | flsh_ios | `ios[STAT_FLUSH]` | 完成 flush 次数（第 4 章状态机产出） |
| 17 | flsh_ticks | `nsecs[STAT_FLUSH]/1e6` | flush 累计耗时 |

`io_ticks` 的累积技巧（blk-core.c `update_io_ticks`）：用 `bd_stamp`（上次时间片）+ `try_cmpxchg` 保证"一个 IO 开始→最后一个 IO 完成"整段时间只记一次，分区写时**同步累加整盘**——这就是 `%util` 的分子。

`/proc/diskstats` 与 stat 同源（多出 major/minor/name 前缀三列）；注意它**包含所有分区行**，整盘行与分区行的差额 = 分区之外的碎片 IO（正常应为 0，非 0 说明有绕过分区的裸访问）。

**延迟直方图（blk-stat）**：`blk_stat.c` 提供 per-cpu 桶化直方图框架（`blk_stat_alloc_callback`：调用方给 bucket_fn 划桶，timer 定期聚合），kyber/bfq 借它完成采样；`iostat` 不读它，BCC `biolatency` 与 blktrace 才是用户态可见的直方图来源。

### 6.3 iostat 的推导

| iostat 指标 | 公式 | 备注 |
| :--- | :--- | :--- |
| `await`(r_await/w_await) | `nsecs/ios`（如 rd_ticks/rd_ios） | **块内总延迟**：含排队+调度+设备 |
| `aqu-sz` | `in_flight 均值`（time_in_queue/观察窗的近似） | Little's law |
| `%util` | `io_ticks / 采样窗口` | **多队列 SSD 会失真**：并行 IO 也按时间计满 → NVMe 上 util=100% 只代表"一直有 IO"，不代表饱和 |
| `svctm` | —— | **已废弃删除**：当年用 await−队列时间估算，数学上无依据（iostat 文档自 11.x 起移除），别再引用 |
| 延迟分解（q2c/d2c） | blktrace/btt | 见 §八 |

## 七、NVMe vs virtio-blk 完成路径对比

| | NVMe（nvme-pci.c） | virtio-blk（virtio_blk.c） |
| :--- | :--- | :--- |
| 完成信号 | CQ phase 位 + MSI-X 中断（`nvme_irq`） | virtqueue 回调 `virtblk_done`（vq 中断） |
| 收割循环 | `nvme_poll_cq`：phase 轮询 + `dma_rmb()` + doorbell | `virtqueue_disable_cb → get_buf 循环 → enable_cb`（NAPI 式开关窗） |
| tag→request | `nvme_find_rq`：`command_id` 即 tag | `blk_mq_rq_from_pdu(vbr)`：请求尾随 PDU 直查 |
| 批量 | `io_comp_batch` 攒批 + `nvme_complete_batch` | poll 路径 `virtblk_complete_batch`；中断路径逐个 `blk_mq_complete_request` |
| 完成分发 | `blk_mq_complete_request`（IPI/softirq 三选一） | 同左（`blk_mq_complete_request_remote` + add_to_batch） |
| 轮询队列 | `nvme_poll`（`cq_poll_lock` 保护，HIPRI 专用队列） | `virtblk_poll`（HCTX_TYPE_POLL） |
| 整批下发 | `queue_rqs` 未用（逐请求 doorbell + `commit_rqs`） | `virtio_queue_rqs`：plug 整链一次锁下发（第 3 章 §4.5） |
| 错误后处理 | `nvme_complete_rq` 四路裁决（RETRY/FAILOVER/多路径） | `virtblk_vbr_status` 直接换算 blk_status_t |

共性：两者完成最终都汇入 `blk_mq_end_request(_batch)` → `bio_endio` → 上层回调（folio `end_page_writeback`/解锁读页、文件系统 end_io、io_uring 的 `req->io_task_work` 兑付 CQE）。

## 八、观测与抖动排查

**blktrace / btt（联系 trace 分册）**：`blktrace -d sda -o - | blkparse -i -` 的关键事件 `Q`（block_bio_queue）、`G`（get request）、`I`（insert）、`D`（issued）、`C`（complete）。`btt` 汇总出延迟分解：

```text
Q2G: 等 request 可用(tag/调度器深度不足 → 加 nr_requests/queue_depth)
G2I: 进调度器的耗时(合并/排序)
I2D: 调度器滞留(调度延迟 → 换 scheduler/调参)
D2C: 设备服务时间(硬件/驱动段 → IRQ 亲和/中断合并/固件)
Q2C: 端到端
```

判定口诀：**Q2G 大**→ request 池/tag 不足（`nr_requests`、`queue_depth`）；**G2I+I2D 大**→ 调度器滞留（换 scheduler、调 fifo_batch/域深度，或干脆 none）；**D2C 大且毛刺**→ 驱动/硬件层（IRQ 亲和、中断合并、`nvme poll_queues`、固件 GC）；**requeue/timeout 事件密集**→ 资源型抖动（tag、SCSI can_queue、多路径切换）。尾延迟专项用 `biolatency -D`（BCC 直方图）对照 kyber 的 p99 目标；cgroup 干扰看 `io.stat`/`io.cost.*`（rq_qos 限流会连带冲刷 plug，第 4 章 §六）。

一级结论速查表：

| 症状 | 最可能的层 | 下一步 |
| :--- | :--- | :--- |
| await 高、util 低、aqu-sz 低 | 提交侧没喂饱（应用/锁） | 应用 profiling，非块层问题 |
| await 高、util 高、aqu-sz 高 | 真饱和或调度滞留 | btt 分解 I2D vs D2C |
| await 毛刺、均值正常 | requeue/超时/中断迁移 | block_rq_requeue、dmesg、IRQ 亲和 |
| 读延迟稳定、写尾长 | flush 叠加 | stat 第 16/17 列、write_cache 模式 |
| %iowait 高、盘不忙 | 同步等待路径（无队列深度） | io_uring/异步化，iowait≠块层问题 |

**排查清单**（iostat 高 util/高 await 时按序执行）：

```bash
# ① 定位: 哪块盘/哪个方向/什么请求类型爆了
iostat -x 1                      # r_await w_await aqu-sz %util 对比
cat /sys/block/sda/stat          # flush_ios 高? discard 高? —— iostat 看不见的列

# ② 在飞与中断: 堆积在请求侧还是完成侧
cat /sys/block/sda/inflight
grep -E 'nvme|sd[a-z]' /proc/interrupts | awk '{print $NF, $1}' | sort | uniq -c
mpstat -P ALL 1                  # %soft/%irq 单点集中?

# ③ 延迟分解: 四段各占多少
blktrace -d sda -w 10 -o sda     && btt -i sda.blktrace.0  # Q2G/G2I/I2D/D2C

# ④ 抖动源: requeue 风暴 / 超时 / 调度器滞留
echo 1 > /sys/kernel/tracing/events/block/block_rq_requeue/enable
dmesg | grep -iE 'timeout|reset|abort'          # 驱动层恢复动作
cat /sys/block/sda/queue/scheduler              # A/B 切换对照 I2D
```

## 九、思考题

1. `blk_mq_complete_need_ipi` 在 `force_irqthreads()` 时返回 false——强制线程化中断（PREEMPT_RT 常态）下，完成会走哪条路？为什么这条路反而更划算？
    *提示：线程化中断里 raise_softirq 只会唤醒 ksoftirqd——一次唤醒比"IPI→softirq 唤醒"便宜；不如就地 complete。*
2. NVMe 的 `command_id` 为什么能直接当 tag 用？若驱动 `queue_depth` 超过 `BLK_MQ_MAX_DEPTH=10240` 或 tag 与 cmdid 位宽不匹配，哪一层会先失败？
    *提示：`blk_mq_unique_tag`（hctx<<16|tag）用于跨队列命令（abort）；同队列内 cmdid=tag 是 NVMe 驱动与 blk-mq 的约定。*
3. `/sys/block/*/stat` 的 `inflight` 对 bio-based 设备（dm）与 mq 设备的统计来源不同（`part_in_flight` vs tag 遍历）。dm 之下这个数字含底层盘的排队吗？多路径 dm 会不会重复计数？
4. 一个 NVMe 盘 `io_ticks` 常年 100% 但吞吐远低于标称。给出三种机制层面的解释，并为每种给出下一个要看的文件/工具。
    *提示：并行度不足（fio iodepth）、D2C 抖动（blktrace）、上层限流（io.max/wbt `rq_qos_trace`）。*
5. `blk_mq_timeout_work` 为什么要先 `synchronize_rcu` 再第二遍扫描？若两遍之间有新请求完成，`RQF_TIMED_OUT` 与 `MQ_RQ_COMPLETE` 的状态竞态如何收场？
    *提示：第一遍标记 has_timedout_rq 后，"提交路径的 RCU 临界区"全部退出才保证 rq 生命周期稳定；完成的请求 state 已非 IN_FLIGHT，第二遍 `blk_mq_req_expired` 自然跳过。*
6. 批量完成里 `RQF_SCHED_TAGS` 的请求为何被 `blk_mq_add_to_batch` 排除？回想第 3 章 sched tag 与 driver tag 的归还路径差异。
