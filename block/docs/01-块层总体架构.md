# 块设备层总体架构（Linux 6.6）

> 阅读目标：建立块层（block layer）的全局地图——从文件系统调 `submit_bio()` 到驱动收件，看清 gendisk / block_device / request_queue 三大对象的分工、直接 IO 与缓冲 IO 的入队差异、块层与调度器/VM/cgroup 的耦合面，以及"为什么 4.x 之后世界上只剩 blk-mq 一种块设备驱动模型"。本章所有结构体与函数均核对自 Linux 6.6 源码（`block/blk-core.c`、`block/genhd.c`、`block/blk-mq.c`、`include/linux/blkdev.h`）。

## 一、分层全景：从 write() 到存储介质

```text
┌────────────────────────────────────────────────────────────────────┐
│ 用户态: write(fd, buf, n) / io_uring / fsync                       │
└──────────────────────────┬─────────────────────────────────────────┘
                           ▼
┌────────────────────────────────────────────────────────────────────┐
│ 文件系统 + page cache (mm)                                         │
│  buffered IO: 写 page → dirty → writeback(folio) → 构造 bio        │
│  direct IO:   不进 cache, 直接把用户页钉成 bio                      │
│  mpage/ext4/btrfs/XFS ... → submit_bio(bio)                        │
└──────────────────────────┬─────────────────────────────────────────┘
                           ▼
┌────────────────────────────────────────────────────────────────────┐
│ 块核心 block/blk-core.c                                            │
│  submit_bio()                                                      │
│   └→ submit_bio_noacct(): 边界/EOD/只读/分区重映射(flush 早期过滤)/  │
│       能力检查 (discard/zeroes/zone...) / blk-throttle             │
│   └→ __submit_bio():                                               │
│       bio-based 设备(dm/md/loop)? → disk->fops->submit_bio() 递归   │
│       普通设备?                → blk_mq_submit_bio()               │
└──────────────────────────┬─────────────────────────────────────────┘
                           ▼
┌────────────────────────────────────────────────────────────────────┐
│ blk-mq 提交侧 block/blk-mq.c                                       │
│  blk_mq_submit_bio():                                              │
│   ├→ 超限切分 __bio_split_to_limits()                              │
│   ├→ 合并尝试: plug 队列 → IO 调度器 (第 4 章)                      │
│   ├→ bio→request: blk_mq_bio_to_request() (分配 tag, 见第 3 章)    │
│   └→ 挂到 current->plug 或直接下发 blk_mq_try_issue_directly()     │
├────────────────────────────────────────────────────────────────────┤
│ blk-mq 派发侧                                                      │
│  per-CPU 软队列 blk_mq_ctx ──映射──▶ 硬件队列 blk_mq_hw_ctx        │
│  blk_mq_run_hw_queue() → blk_mq_sched_dispatch_requests()          │
│   → (elevator? dispatch_request : ctx 软队列) → blk_mq_dispatch_   │
│     rq_list() → q->mq_ops->queue_rq(hctx, bd)                      │
└──────────────────────────┬─────────────────────────────────────────┘
                           ▼
┌────────────────────────────────────────────────────────────────────┐
│ 驱动层: nvme/nvme-pci.c, virtio_blk.c, scsi(sd), md/dm ...        │
│  命令下发 → 硬件队列环(SQ/CQ, virtqueue, SCSI LLD)                  │
│  完成中断 → blk_mq_complete_request() (第 6 章)                    │
└────────────────────────────────────────────────────────────────────┘
```

分层的本质是**两套数据的转换**：

| 层 | 数据单位 | 关键转换 |
| :--- | :--- | :--- |
| 文件系统/mm | folio/page + 逻辑块号 | `mapping` → `submit_bio`：把 page 列表描述成 `bio_vec[]` |
| 块核心 | **bio** | 校验、重映射（分区偏移）、限流（blk-throttle）、分派 |
| blk-mq 提交 | bio → **request** | 合并（bio 挂上 request 的 `bio/biotail` 链） |
| blk-mq 派发 | request | ctx→hctx 排队、调度器决策、tag 分配、`queue_rq` |
| 驱动 | request → 硬件命令 | `nvme_setup_cmd()` / SCSI CDB / virtio 描述符 |

## 二、三大核心对象：gendisk / block_device / request_queue

### 2.1 关系图

```text
                 struct gendisk  (块设备"人格": 名字/容量/分区表/驱动回调)
                 block/genhd.c, include/linux/blkdev.h
 ┌───────────────────────────────────────────────────────┐
 │ disk_name[]="nvme0n1"   major/first_minor/minors       │
 │ part_tbl (xarray) ──┬── part0 (block_device, 整盘)      │
 │                     ├── part1 (block_device, 分区1)     │
 │                     └── part2 (block_device, 分区2)     │
 │ fops (block_device_operations: submit_bio/open/ioctl)  │
 │ queue ────────────▶ struct request_queue (I/O 引擎)     │
 │ bdi (writeback)                                        │
 └───────────────────────────────────────────────────────┘
            每个分区各自持有:
 struct block_device                struct request_queue
 ┌──────────────────────┐           ┌──────────────────────────┐
 │ bd_disk  ─▶ gendisk  │◀──────────│ disk                     │
 │ bd_queue ─▶ 同一 queue│──────────▶│ queue_ctx (per-CPU ctx)  │
 │ bd_start_sect(分区起点)│           │ hctx_table (xarray)      │
 │ bd_nr_sectors         │           │ elevator                 │
 │ bd_stats (percpu 统计)│           │ tag_set ─▶ blk_mq_tags   │
 │ bd_inode (bdev 文件)  │           │ limits (max_sectors...)  │
 └──────────────────────┘           └──────────────────────────┘
```

三句话总结：

1. **`gendisk` 是"设备"**：对应用户态的 `/dev/nvme0n1` 与 `/sys/block/nvme0n1`，携带分区表（`part_tbl` xarray，索引即 `bd_partno`）。
2. **`block_device` 是"可打开的节点"**：整盘是 `part0`，每个分区一个；它记录该节点的起始扇区（`bd_start_sect`）与 per-cpu 统计（`bd_stats`）。bio 里 `bi_bdev` 指向它。
3. **`request_queue` 是"I/O 引擎"**：一个 gendisk 只有一个 queue，整盘和所有分区**共享**同一个 queue——分区只是提交时的扇区平移（`blk_partition_remap()`：`bi_iter.bi_sector += p->bd_start_sect`，并置 `BIO_REMAPPED`）。

### 2.2 生命周期：现代驱动的三步曲

6.6 中一个 blk-mq 驱动（如 nvme）的装配过程：

```c
/* 1) 分配 tag_set: 描述硬件队列拓扑 */
struct blk_mq_tag_set set = {
    .ops        = &nvme_mq_ops,      /* queue_rq/complete/timeout... */
    .nr_hw_queues = nr_io_queues,    /* NVMe I/O 队列数 */
    .queue_depth  = q_depth,         /* 每队列 tag 数（= 请求数） */
    .nr_maps    = 3,                 /* DEFAULT/READ/POLL 三张 CPU→hctx 映射表 */
    .flags      = BLK_MQ_F_SHOULD_MERGE,
    ...
};
blk_mq_alloc_tag_set(&set);

/* 2) 分配 queue + gendisk（合二为一） */
disk = blk_mq_alloc_disk(&set, nvmeq);   /* __blk_mq_alloc_disk + __alloc_disk_node */

/* 3) 注册可见：sysfs + 分区扫描 */
device_add_disk(NULL, disk, NULL);       /* 或 add_disk() 宏 */
```

`device_add_disk()`（block/genhd.c，6.6 实测流程）是"设备上线"的总开关：

```text
device_add_disk(parent, disk, groups)
 ├─ elevator_init_mq(disk->queue)        /* 选默认 IO 调度器(第 5 章) */
 ├─ disk->part0->bd_has_submit_bio =     /* bio-based(dm/md/loop)标记 */
 │      (disk->fops->submit_bio != NULL)
 ├─ major 指定? 检查 minors ≤ DISK_MAX_PARTS
 │   否则动态分配: BLOCK_EXT_MAJOR + blk_alloc_ext_minor()
 ├─ dev_set_uevent_suppress(ddev, 1)     /* 先压住 uevent, 扫完分区再放 */
 ├─ device_add() + sysfs_create_link(block_depr)  /sys/block/ 链接
 ├─ holders/、slaves/ 目录
 ├─ blk_register_queue(disk)             /* /sys/block/*/queue/ 整棵树 */
 ├─ bdi_register(disk->bdi)              /* writeback 注册 (联系 mm 分册) */
 ├─ bdev_add(disk->part0, devt)          /* 整盘 block_device 入 part_tbl */
 ├─ disk_scan_partitions(disk, BLK_OPEN_READ)  /* 读分区表 */
 │    └─ bdev_disk_changed → blk_add_partitions → msdos/gpt/...
 └─ dev_set_uevent_suppress(0) + disk_uevent(KOBJ_ADD)
```

要点：

* **分区扫描发生在 add_disk 内部**：`GD_NEED_PART_SCAN` 置位后按 `BLK_OPEN_READ` 独占打开整盘，依次尝试 `block/partitions/` 下注册的探测函数（msdos/gpt/EFI/sgi/…）。`GENHD_FL_NO_PART` 可跳过。
* 6.6 起 `add_disk()` 返回值必须检查（`__must_check`），失败要自行回收资源。
* 卸载方向是 `del_gendisk()`：置 `GD_DEAD`、freeze 队列、清空 `part_tbl`、`blk_unregister_queue`。

### 2.3 bdev 文件接口：用户态如何摸到块层

`/dev/nvme0n1` 对应的 inode 类型是 `S_IFBLK`，其 file_operations 是 **`def_blk_fops`**（block/fops.c）：

```c
const struct file_operations def_blk_fops = {
    .open       = blkdev_open,      /* blkdev_get_by_dev: 独占/共享模式, 队列引用 */
    .release    = blkdev_release,
    .read_iter  = blkdev_read_iter, /* 裸设备读 */
    .write_iter = blkdev_write_iter,
    .fsync      = blkdev_fsync,     /* → blkdev_issue_flush */
    .unlocked_ioctl = blkdev_ioctl, /* BLKDISCARD/BLKZEROOUT/BLKFLSBUF... */
    ...
};
```

* `blkdev_open()` → `blkdev_get_by_dev()`：处理写独占（`bd_write_holder`）、`fmode` 到 `blk_mode_t` 的换算、`bd_openers` 计数。
* **裸设备 buffered 读写**走 `bd_inode->i_mapping`（bdev 自己的 address_space，页缓存属于块设备而非文件系统）；**O_DIRECT** 走 `blkdev_direct_IO()`，bio 直接钉用户页。
* `blkdev_fsync()` 的语义 = 先回写脏页，再 `blkdev_issue_flush()`（`REQ_OP_FLUSH`），把易失写缓存压到非易失介质（第 4 章的 flush 状态机）。
* ioctl 中的 `BLKDISCARD`→`REQ_OP_DISCARD`、`BLKZEROOUT`→`REQ_OP_WRITE_ZEROES`，是块层"类操作"（REQ_OP_*）的另一入口。

## 三、直接 IO 与缓冲 IO 的入队差异

```text
                    缓冲 IO (buffered)                  直接 IO (O_DIRECT)
────────────────────────────────────────────────────────────────────────
写路径   write() → 拷入 page cache           write() → bio_iov_iter_get_pages()
         (folio dirty)                        (直接钉用户页, REQ_SYNC)
         回收/writeback 触发:
           writeback worker
           write_cache_pages():
             blk_start_plug(&plug)   ◀── 提交侧 plug 批处理
             folio → bio_add_folio()
             submit_bio() … 直到 wbc 范围写完
             blk_finish_plug(&plug)
读路径   read() → 缺页/page cache 命中        read() → 直接构 bio
         未命中: mpage_read_folio           bio_alloc() + add_page
           → bio → submit_bio()
bio 属性  REQ_SYNC? 由 writeback 决定;        必带 REQ_SYNC;
         常为 async write, 可被深度合并        大块, 长度=用户请求
         单页/多页混合
合并机会  大(顺序脏页扫描, plug 窗口大)         小(提交即发, 但仍受益于 plug)
完成语义  bio 完成解锁 folio;                 bio 完成即 copy/done,
         end_page_writeback()                直接唤醒用户线程/io_uring cqe
```

两者最终都汇入同一个 `submit_bio()`——块核心不区分来源，差异只体现在：

| 维度 | 缓冲 IO | 直接 IO |
| :--- | :--- | :--- |
| 页来源 | page cache（`mapping`） | 用户页 pin（`bio_iov_iter_get_pages`） |
| 生命周期 | folio 写回保护（`writeback` 位） | DMA 期间页 pinned（`BIO_PAGE_PINNED`，6.6 用 pin 而非 get_page） |
| 延迟归属 | 用户看不到 writeback 延迟（fsync 才算总账） | 每次读写都吃全链路延迟 |
| 对 plug 依赖 | writeback 批量天然适合 plug | io_uring 自己 plug（`blk_start_plug_nr_ios`） |

> 📌 **fsync 的双重成本**：`blkdev_fsync`/文件系统 fsync 要先等 writeback（DATA）再等 flush（REQ_OP_FLUSH）。若设备无写缓存（`QUEUE_FLAG_WC=0`），`submit_bio_noacct` 会在最前面剥掉 `REQ_PREFLUSH|REQ_FUA`，纯数据请求零额外成本——这是第 4 章 flush 状态机的入口检查。

## 四、块层与其他子系统的接口

```text
              ┌───────────┐
   scheduler  │ io_schedule│  阻塞在 IO 上的任务: current->in_iowait=1,
   ◀──────────┤ nr_iowait  │  rq->nr_iowait++（/proc/loadavg 第二字段）,
              └───────────┘  负载均衡把它当"不存在"(non-runnable)
                     ▲
   vm (mm)   swap out/in: swap 分区的 bio (REQ_SWAP)
   ◀──────── writeback: per-bdi 回写线程 (bdi_writeback), laptop_mode,
              blk_start_plug 批量; OOM 回收在 plug flush 上有依赖
                     ▲
   cgroup    blkcg: bio_associate_blkg() 给 bio 记账 (bi_blkg)
   ◀──────── io.max (blk-throttle 限速) / io.cost (iocost) / io.latency
              io.weight → bfq 权重; blk-ioprio 按 cgroup 注 ioprio hint
                     ▲
   PM        runtime PM: 队列挂起时 RQF_PM 独占; blk_pm_resume_queue
   ◀──────── blk-pm.c; pm_only 计数挡住普通 IO
                     ▲
   sysfs/    /sys/block/*/queue/* 调优面 (scheduler/nr_requests/...)
   debugfs   /sys/kernel/debug/block/*/  (第 3/5/6 章观测)
```

值得展开的三条：

1. **调度器 ↔ iowait**：`io_schedule()` 里 `io_schedule_prepare()` 做 `current->in_iowait = 1; blk_flush_plug(current->plug, true)`——睡眠前**必须先放掉 plug 里的请求**（详见第 4 章），否则 OOM 回收可能永远等不到 plug 中那批脏页的写回完成，形成死锁。`rq->nr_iowait` 进 `/proc/loadavg` 的 `.../io` 字段，是"CPU 不忙但系统卡 IO"的典型指纹（对照 scheduler 分册 02 章）。
2. **VM ↔ writeback**：块层 `laptop_mode`（`blk_mq_free_request` 里 `laptop_io_completion`）、`/sys/class/bdi/*/` 的可调参数都服务于回写策略；swap IO 带 `REQ_SWAP`，在 tag 分配上享受保留通道避免自锁。
3. **cgroup ↔ blkcg**：`bio_associate_blkg()` 在 `bio_set_dev`/`bio_reset` 时把 bio 关联到 (blkcg, queue) 二元组 `bi_blkg`；限速（`io.max`）在 `submit_bio_noacct` 尾部的 `blk_throtl_bio()` 生效——被 throttle 的 bio 在这里被打断并延后重放，不进入后续路径。

## 五、从单队列到 blk-mq：演进史

```text
2.4 ─ 2.6早期        电梯(elevator) + 全局请求队列(request_fn 驱动模型)
  │                  一个 queue->queue_lock 锁住所有 CPU 的提交
  │                  CFQ(桌面公平)/deadline/AS(预测) 三选一
2.6.3x              I/O 调度器支持切换, CFQ 引入 per-process io_context
  │
2013-10, v3.13      ★ blk-mq 合入 (commit 320ae51feed5
  │                  "blk-mq: new multi-queue block IO queueing mechanism")
  │                  两级队列: per-CPU software queue + per-hw queue
  │                  sbitmap tag 分配, 无全局锁的快路径
v4.0                SCSI 引入 scsi-mq (opt-in: scsi_mod.use_blk_mq=1)
  │                  virtio-blk/nvme 全面上 mq
v4.11 ─ v4.12       mq-deadline(4.11)/kyber(4.12)/bfq(4.12) 入树
  │                  CFQ 退役——为多队列而生的三套新调度器就位
v5.9 (2020-07)      ★ bio 分派大清理 (c62b37d96b6e 系列):
  │                  generic_make_request() 更名 submit_bio_noacct(),
  │                  ->submit_bio 移入 block_device_operations,
  │                  make_request_fn 彻底删除 —— dm/md/loop 变成纯
  │                  bio-based 驱动 (bd_has_submit_bio), 单队列 request_fn
  │                  模型名存实亡
v6.x                单一队列模型: blk_sq 已死, 世界只剩 blk-mq +
  │                  bio-based 两类 (queue_is_mq())
v6.6                本分册基线: plug 单链表化+cached_rq 批量分配、
                     queue_rqs() 整批下发、REQ_POLLED/io_comp_batch
                     批量完成等持续微调
```

**为什么必须杀掉单队列？** 三个互相放大的问题：

* **全局锁热点**：单队列模型中 `queue_lock` 保护 request 的插入/合并/派发全流程。PCIe SSD（100 万 IOPS）下每秒数十万次锁竞争，锁本身成为吞吐上限——经典的 Amdahl 定律受害者。
* **中断与提交 CPU 的错配**：单队列意味着所有 CPU 的请求汇入一处，完成中断落在哪个 CPU 都无所谓；结果是 request 结构与完成处理跨 NUMA 弹跳。blk-mq 把 `ctx`（软件队列）做成 per-CPU、`hctx`（硬件队列）与 MSI-X 中断向量一一对应，"提交 CPU = 软队列 = 硬队列 = 完成 CPU"在同 LLC 内闭环。
* **不可扩展的公平性**：CFQ 的公平算法建立在"全局可见请求序列"上；多队列后每个 hctx 有独立时间线，全局排序语义无法维持，只能换成 per-queue 决策（mq-deadline/kyber）或显式分层记账（bfq）。

> ⚠️ **术语警报**：源码里已没有 `blk_sq` 这个词。判断设备类型的唯一标准是 `queue_is_mq(q)`（`q->mq_ops != NULL`）。mq 设备走 `blk_mq_submit_bio`，bio-based 设备（dm/md/loop）走 `disk->fops->submit_bio` 自行拆分后再对底层设备递归 `submit_bio_noacct`（见第 2 章）。

## 七、思考题

1. 一个分区的 `bd_start_sect` 平移发生在 `submit_bio_noacct()` 而不是更早的文件系统层。若文件系统已经持有"文件内偏移→分区 LBA"的映射，为什么还要在块核心再做一次平移？`BIO_REMAPPED` 标志防的是什么重复劳动？
    *提示：`blk_partition_remap()` 只对 `!bio_flagged(bio, BIO_REMAPPED)` 执行；栈式设备（dm）下发给底层盘时扇区空间会再次变化。*
2. 为什么整盘和所有分区共享同一个 `request_queue`？如果每个分区独立队列，调度器的"顺序性"和 flush 语义会遇到什么困难？
3. `device_add_disk()` 为什么要先 `dev_set_uevent_suppress(1)`、扫完分区再放行 uevent？若顺序反过来，udev/ systemd 可能观察到什么不一致状态？
4. 同样是 4KB 随机写，缓冲 IO 的 writeback 路径与 O_DIRECT 路径在"plug 命中率"上为什么差一个数量级？这对数据库 `writethrough` vs `writeback` 优化意味着什么？
    *提示：writeback 是按 inode/一段页范围批量扫描；O_DIRECT 常为同步单发，除非用 io_uring 批量提交。*
5. v5.9 把 `->submit_bio` 移入 `block_device_operations` 之后，dm 这类栈式设备的"递归提交"由谁保证不爆内核栈？
    *提示：`current->bio_list[2]` 两级列表 + `__submit_bio_noacct()` 的 lower/same 分流（第 2 章详解）。*
6. `rq->nr_iowait`（iowait 计数）和块层的 plug 机制有什么共同的设计动机？一个 "CPU 40% iowait、磁盘 util 100%" 的系统，瓶颈更可能在哪一层？
