# 时间子系统总体架构（Linux 6.6）

> 阅读目标：建立时间子系统的全局地图——从时钟硬件到 `clocksource` 抽象，到 timekeeper 的全局时间维护，到 tick 驱动，再到五套定时器框架（时间轮 / hrtimer / posix-timer / timerfd / alarmtimer）；理清 `start_kernel()` 中的初始化顺序，跟踪一次 `gettimeofday()` 和一次 `nanosleep()` 的完整路径，并掌握内核的几条时间轴。

时间子系统回答三个问题：**现在几点**（读时间）、**何时叫我**（定时到期）、**时间如何推进**（时钟维护与校正）。它是内核中最底层的基础设施之一——调度器、网络超时、RCU、printk、锁泄漏检测全部站在它上面。本章是分册地图，后续各章分别下钻每一层。

两个关键的不对称抽象，贯穿全分册：

| | `struct clocksource` | `struct clock_event_device` |
| :--- | :--- | :--- |
| 回答的问题 | 现在是"多少个周期" | 什么时刻产生下一次中断 |
| 硬件形态 | 自由运行计数器（只读） | 可编程比较器（可写） |
| 内核职责 | timekeeping 用它算时间 | tick/hrtimer 用它产生事件 |
| 典型实现 | x86 TSC / arm64 arch_sys_counter | x86 Local APIC / arm64 通用定时器 |

**为什么分成两个抽象**：x86 的 TSC 是纯计数器，不能编程产生中断；而 Local APIC timer 能编程却随频率变化（constant_tsc 之前不可靠）。二者能力正交，硬件演进中"计数"和"事件"也常常由不同 IP 提供。arm64 的通用定时器虽然计数器（System Counter）+ 比较器（per-CPU timer）成对出现，内核仍然保持两层抽象——统一所有架构。

## 🚀 二、start_kernel 中的初始化顺序

`init/main.c`（v6.6）中时间子系统的启动序列（行号为 6.6 参考）：

```c
// init/main.c :: start_kernel() (节选)
    tick_init();          // 973: tick_broadcast_init() + tick_nohz_init()
    init_timers();        // 975: 时间轮 per-CPU base + TIMER_SOFTIRQ 注册
    hrtimers_init();      // 977: hrtimer per-CPU base + HRTIMER_SOFTIRQ 注册
    timekeeping_init();   // 979: 安装默认 clocksource(jiffies), 初始化 tk_core
    time_init();          // 980: ★ 架构相关：探测并注册真正的时钟硬件
    ...
    if (late_time_init)   // 1030: x86: tsc_init() 在此替换 tsc-early→tsc
        late_time_init();
    sched_clock_init();   // 1032
```

逐行拆解（**顺序本身就是设计**）：

1. **`tick_init()`**：先建 broadcast 框架与 nohz_full 掩码基础设施，此时还没有任何 tick 设备。
2. **`init_timers()`**（kernel/time/timer.c）：

```c
void __init init_timers(void)
{
	init_timer_cpus();                     /* 每个 CPU、每个 base 初始化 timer_base */
	posix_cputimers_init_work();           /* CPU 定时器 task-work 机制 */
	open_softirq(TIMER_SOFTIRQ, run_timer_softirq);
}
```

3. **`hrtimers_init()`**（kernel/time/hrtimer.c）：

```c
void __init hrtimers_init(void)
{
	hrtimers_prepare_cpu(smp_processor_id());  /* 初始化本 CPU 的 8 个 clock_base */
	open_softirq(HRTIMER_SOFTIRQ, hrtimer_run_softirq);
}
```

4. **`timekeeping_init()`**（kernel/time/timekeeping.c）：`ntp_init()` → `clocksource_default_clock()`（即 jiffies，rating 1，kernel/time/jiffies.c）→ `tk_setup_internals()` → 用持久时钟（RTC/persistent clock）设置 `xtime_sec` 与 `wall_to_monotonic` → `timekeeping_update(TK_MIRROR | TK_CLOCK_WAS_SET)`。**此时系统时间精度只有 jiffies 级**——这是刻意的保守起步。
5. **`time_init()`**：架构钩子。x86 上注册 `tsc-early`（rating 299）、HPET、ACPI_PM 等 clocksource 与 clock_event_device；arm64 上注册 `arch_sys_counter`（rating 400）与通用定时器 clockevent。
6. **真正的切换发生在 `clocksource_done_booting()`**（clocksource.c，`fs_initcall`）：boot 完成 后先跑一遍 watchdog 清理不稳定 clocksource，再 `clocksource_select()` 选出 rating 最高者，`timekeeping_notify()` → `stop_machine(change_clocksource)` → `tk_setup_internals(tk, new)` 把 timekeeper 迁到新 clocksource，并打印著名的 `Switched to clocksource tsc`。

> 💡 这套"jiffies 兜底 → 硬件就位 → 运行时切换"的三段式，让时间子系统对硬件探测顺序完全不敏感：不管 TSC 多晚才被验证，系统时间从不中断——切换时 `timekeeping_forward_now()` 会先把旧钟上的时间累积进来。

## 📖 三、一次 gettimeofday 经过哪些层

### 3.1 vDSO 快路径（绝大多数调用走这里）

```
用户态 gettimeofday(CLOCK_REALTIME)
  → libc → vDSO __vdso_clock_gettime
      ① 读 vdso_data 页 (每 CPU 一份, kernel 维护):
          cs[CS_HRES_COARSE].{cycle_last, mask, mult, shift}
          basetime[CLOCK_REALTIME] = tk 的 sec/nsec 基准
          seq (seqcount, 由 update_vsyscall() 在写侧维护)
      ② 按 clockmode 读硬件计数器:
          VDSO_CLOCKMODE_TSC       → rdtsc_ordered()
          VDSO_CLOCKMODE_ARCHTIMER → 读 CNTVCT_EL0
          VDSO_CLOCKMODE_NONE      → 退回系统调用
      ③ cycles = (now - cycle_last) & mask
         nsec  = (cycles * mult) >> shift + basetime
      ④ seq 重读校验, 变了就重来
  → 返回, 全程无 syscall (数纳秒级)
```

写侧在 `kernel/time/vsyscall.c` 的 `update_vdso_data()`：每次 `timekeeping_update()` 都把 `tkr_mono/tkr_raw` 的 mult/shift/cycle_last 与各时钟的 basetime 搬进 vDSO 页（`CS_HRES_COARSE`/`CS_RAW` 两个集合）。

### 3.2 系统调用慢路径

```
clock_gettime(CLOCK_REALTIME) [syscall]
  → SYSCALL_DEFINE2(clock_gettime)            kernel/time/posix-timers.c
      → clockid_to_kclock()                   负数 id → CPU/FD 时钟;
                                             否则查 posix_clocks[] 分派表
      → kc->clock_get_timespec == posix_get_realtime_timespec
          → ktime_get_real_ts64()             kernel/time/timekeeping.c
              do {
                  seq = read_seqcount_begin(&tk_core.seq);
                  ts->tv_sec = tk->xtime_sec;
                  nsecs = timekeeping_get_ns(&tk->tkr_mono);
                        └─ tk_clock_read → cs->read(cs)     读 TSC/CNTVCT
                           clocksource_delta(now, cycle_last, mask) 回绕安全差值
                           timekeeping_delta_to_ns: (delta*mult + xtime_nsec) >> shift
              } while (read_seqcount_retry(&tk_core.seq, seq));
```

与 vDSO 路径**计算公式完全相同**——系统调用只是多了分派与 copy_to_user 的开销。慢路径存在的意义：vDSO 不可用（clockmode==NONE，如 TSC 不稳被降级、或 arm64 有 errata 修正）或架构尚未实现 vDSO。

> 细节：`CLOCK_REALTIME_COARSE` 走 `ktime_get_coarse_real_ts64()`——直接读 `tk_xtime(tk)`，**不读硬件计数器**，开销最低但精度只有一 tick；数据库 checkpoint、统计类代码应优先用它。

## 😴 四、一次 nanosleep 经过哪些层

`nanosleep(1ms)` 在高精度定时器使能的现代系统上的完整链条：

```
[用户态] nanosleep(rqtp={0,1000000}, NULL)
  → SYSCALL_DEFINE2(nanosleep)                     kernel/time/hrtimer.c
      → hrtimer_nanosleep(rqtp, HRTIMER_MODE_REL, CLOCK_MONOTONIC)
          slack = current->timer_slack_ns;          /* 普通任务默认 50us, rt_task→0 */
          hrtimer_init_sleeper_on_stack(&t, ...)    /* 栈上 hrtimer_sleeper,
                                                       function = hrtimer_wakeup,
                                                       task = current */
          hrtimer_set_expires_range_ns(&t.timer, rqtp, slack)   /* 允许内核
                                                       把到期批量化以省电 */
      → do_nanosleep()
          set_current_state(TASK_INTERRUPTIBLE | TASK_FREEZABLE)
          hrtimer_sleeper_start_expires(t, HRTIMER_MODE_ABS)
              └─ hrtimer_start_range_ns()
                  ├─ lock_hrtimer_base
                  ├─ __hrtimer_start_range_ns: remove→switch_base→enqueue_hrtimer
                  │    (插入 per-CPU 红黑树; CLOCK_MONOTONIC base)
                  └─ hrtimer_reprogram: 是最早的定时器?
                       → tick_program_event(expires)  ★ 编程 clockevent 硬件
                       → __hrtimer_reprogram → 本地 APIC / 通用定时器
          schedule()                                 /* 睡下去 */
                                   ⋮  (时间流逝 ~1ms)
[硬中断] clockevent 到期 → hrtimer_interrupt()        kernel/time/hrtimer.c
      → hrtimer_update_base (取 now + 更新 offsets)
      → __hrtimer_run_queues(HRTIMER_ACTIVE_HARD)
          → __run_hrtimer → base->running = timer
             → fn(timer) = hrtimer_wakeup()
                 → wake_up_process(t->task)           /* 唤醒睡眠者 */
      → hrtimer_update_next_event → tick_program_event (下一个事件)
[调度] 睡眠者上 CPU, do_nanosleep 返回 0, syscall 返回 0
```

低精度回退（`CONFIG_HIGH_RES_TIMERS=n` 或 clockevent 不支持 oneshot）时，第 [硬中断] 步换成周期 tick：`tick_periodic → update_process_times → run_local_timers → hrtimer_run_queues()` 在每个 jiffy 检查到期——hrtimer 框架**降级但可用**，精度退化为 tick。

## 🕐 五、时间轴：内核到底维护着几条时间

timekeeper（`kernel/time/timekeeping.c`）以 **CLOCK_MONOTONIC 为内部基准轴**，其他时钟都是"基准 + 偏移"：

```
             xtime_sec(REALTIME 秒)  +  tkr_mono.xtime_nsec(shifted)
REALTIME  = ─────────────────────────────────────────►
             ▲
             │ offs_real = -wall_to_monotonic (settimeofday 会改)
MONOTONIC = ─────► base_mono + delta(tkr_mono)      ← hrtimer 内部轴
             ▲
             │ offs_boot (suspend 注入的睡眠时间累加)
BOOTTIME  = ─────► (含系统挂起期间的"缺失"时间)
             ▲
             │ offs_tai = offs_real + tai_offset
TAI       = ─────► (国际原子时, 不受闰秒回拨, NTP 协商)

MONOTONIC_RAW = tkr_raw 单独累计 (mult 固定, 不吃 NTP 微调)  ← 测晶振频偏用
```

| 时钟 | 基准/偏移字段 | 会跳变吗 | 典型用途 |
| :--- | :--- | :--- | :--- |
| `CLOCK_REALTIME` | `xtime_sec` + `tkr_mono`，`offs_real` | settimeofday/闰秒会跳 | 墙上时间、文件时间戳 |
| `CLOCK_MONOTONIC` | `tkr_mono.base` + delta | **绝不后退**（NTP 只微调斜率） | 测量、超时、内核内部轴 |
| `CLOCK_MONOTONIC_RAW` | `tkr_raw` | 不受 NTP 调整 | 评估硬件时钟频偏（PTP） |
| `CLOCK_BOOTTIME` | MONOTONIC + `offs_boot` | 含 suspend 时间 | 开机以来总时长 |
| `CLOCK_TAI` | `offs_tai`（`tai_offset` 秒级） | 闰秒调整时**不**跳 | 电信/电力精确时间 |
| `CLOCK_*_COARSE` | 只读 `xtime_sec`/`ktime_sec` | tick 粒度 | 低开销读时间 |
| `*_ALARM`（REALTIME/BOOTTIME） | alarmtimer 基 | — | suspend 中用 RTC 唤醒 |

三个易混点：

1. **REALTIME 跳变时 MONOTONIC 不动**：`do_settimeofday64()` 修改的是 `offs_real`（同时反向修 `wall_to_monotonic`），基准轴纹丝不动——这保证基于 MONOTONIC 的定时器不受校时影响。
2. **BOOTTIME 与 MONOTONIC 的差**只在 suspend/resume 时增长：`__timekeeping_inject_sleeptime()` 累加 `offs_boot`。
3. **TAI 与 REALTIME 差**一个整数秒 `tai_offset`：闰秒插入时 REALTIME 回拨 1 秒（`second_overflow()` 返回 leap=-1），TAI 平滑继续——这是 6.6 处理闰秒的完整机制（`ntp.c` 的 `TIME_OK/INS/DEL/OOP/WAIT` 状态机）。

## 💭 八、思考题

1. `start_kernel()` 里 `timekeeping_init()` 在 `time_init()` **之前**执行。此时 timekeeper 用的是什么 clocksource？精度多差？切换到真硬件后，此前累积的时间误差如何被"无缝"接上？
   <details><summary>提示</summary>jiffies（rating 1，kernel/time/jiffies.c）。`change_clocksource()` 里先 `timekeeping_forward_now()` 把旧钟的最后一段 delta 累积进 `xtime_nsec`，再 `tk_setup_internals()` 重设 mult/shift 并转换 `xtime_nsec` 的 shift 单位。</details>
2. `gettimeofday` 的 vDSO 路径为什么必须把 `cycle_last` 也镜像到 `vdso_data`？只用 `basetime + now*mult` 不行吗？
   <details><summary>提示</summary>vDSO 计算的是 `(now - cycle_last) * mult >> shift + basetime`；`cycle_last` 是写侧最近一次锚点。没有它，`now * mult` 会轻易 64 位溢出（TSC 2.4GHz 运行数小时即超 2^63/mult）。对照 `clocksource_cyc2ns()` 注释"only intended to be used with relative cycles"。</details>
3. 时间子系统为什么需要 `clocksource` 与 `clock_event_device` 两个正交抽象，而不是一个"定时器硬件"结构？用 x86 的 TSC + Local APIC timer 组合说明。
   <details><summary>提示</summary>TSC 是自由计数器、不可编程中断但（constant_tsc 后）频率稳定；APIC timer 可编程但历史上随 P-state 变频且 deep-C 停机。能力正交 → 抽象正交。arm64 虽然计数/比较成对，抽象统一仍带来 broadcast、hrtimer 等通用机制。</details>
4. 一次 `clock_nanosleep(CLOCK_REALTIME, TIMER_ABSTIME, ...)` 睡眠期间管理员执行了 `settimeofday`（把墙钟前拨 10 分钟）。这个睡眠会怎样？换 `CLOCK_MONOTONIC` 呢？换成相对睡眠呢？
   <details><summary>提示</summary>绝对 REALTIME 定时器挂在 REALTIME base，`clock_was_set()` → `retrigger_next_event()` 更新 base 的 `offset` 并重编程；MONOTONIC 定时器完全无感；相对 CLOCK_REALTIME 睡眠在 `__hrtimer_init()` 已被换算成 MONOTONIC（POSIX 规定相对 REALTIME 不受校时影响）。</details>
5. `update_process_times()`（每次 tick 都跑）里依次调用 `run_local_timers()`、`scheduler_tick()`、`run_posix_cpu_timers()`。为什么 CPU 定时器要在调度器 tick **之后**？
   <details><summary>提示</summary>CPU 定时器（CPUCLOCK_PROF/VIRT/SCHED）的到期判定依赖 `utime/sum_exec_runtime` 记账；先跑 `account_process_tick`/`scheduler_tick` 才有新鲜的执行时间样本。对照 kernel/time/posix-cpu-timers.c 的采样逻辑。</details>
