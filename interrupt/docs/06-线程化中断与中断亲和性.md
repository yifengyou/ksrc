# 线程化中断与中断亲和性

硬中断 handler 的两大原罪——不可睡眠、霸占被打断任务的 CPU——在 Thomas Gleixner 的 threaded irq（2.6.31 起）与 PREEMPT_RT 中被系统性解决。本章解剖线程化协议（含 IRQF_ONESHOT 的精妙锁序）、PREEMPT_RT 的中断模型，以及多核时代的中断亲和性工程。

### 🧵 线程化机制：从 IRQ_WAKE_THREAD 到 irq/NN-name

`request_threaded_irq(irq, handler, thread_fn, ...)` 注册两条执行路径：`handler` 仍跑在硬中断里，`thread_fn` 跑在专属内核线程里。交接协议：

```c
// 硬中断侧: kernel/irq/handle.c (v6.6, 节选)
res = action->handler(irq, action->dev_id);
switch (res) {
case IRQ_WAKE_THREAD:                    /* handler 说: "我是我的, 剩下给线程" */
	if (unlikely(!action->thread_fn))
		warn_no_thread(irq, action);
	else
		__irq_wake_thread(desc, action);
	break;
}

// kernel/irq/handle.c (v6.6, __irq_wake_thread 核心)
desc->threads_oneshot |= action->thread_mask;   /* oneshot: 续闷 */
atomic_inc(&desc->threads_active);              /* synchronize_irq 等待用 */
wake_up_process(action->thread);
```

线程侧主体：

```c
// kernel/irq/manage.c (v6.6, 原文节选)
static int irq_thread(void *data)
{
	struct irqaction *action = data;
	struct irq_desc *desc = irq_to_desc(action->irq);
	irqreturn_t (*handler_fn)(struct irq_desc *, struct irqaction *);

	irq_thread_set_ready(desc, action);   /* 置 IRQTF_READY, 让 request 路径同步等待 */

	sched_set_fifo(current);              /* ★ SCHED_FIFO, prio = MAX_RT_PRIO/2 = 50 */

	if (force_irqthreads() && test_bit(IRQTF_FORCED_THREAD, &action->thread_flags))
		handler_fn = irq_forced_thread_fn;
	else
		handler_fn = irq_thread_fn;

	irq_thread_check_affinity(desc, action);

	while (!irq_wait_for_interrupt(action)) {   /* 睡眠等 IRQTF_RUNTHREAD */
		irq_thread_check_affinity(desc, action); /* 跟随亲和性迁移 */

		action_ret = handler_fn(desc, action);
		if (action_ret == IRQ_WAKE_THREAD)
			irq_wake_secondary(desc, action);  /* force-thread 的二级接力 */

		wake_threads_waitq(desc);   /* threads_active--, 归零唤醒 synchronize_irq 等待者 */
	}
	return 0;
}

static irqreturn_t irq_thread_fn(struct irq_desc *desc, struct irqaction *action)
{
	irqreturn_t ret;

	ret = action->thread_fn(action->irq, action->dev_id);  /* ★ 驱动线程体 */
	if (ret == IRQ_HANDLED)
		atomic_inc(&desc->threads_handled);   /* 供 spurious 延迟检测 */

	irq_finalize_oneshot(desc, action);
	return ret;
}
```

要点逐条：

- **线程命名**：`irq/%d-%s`（如 `irq/126-nvidia`），`ps -e | grep 'irq/'` 可见全机中断线程。
- **优先级**：`sched_set_fifo()` 设置 **SCHED_FIFO、优先级 50**（`MAX_RT_PRIO/2`）。注意这是 **6.6 的无条件行为**（5.13 起，commit 619e9860fb87 一族把 irq 线程从 SCHED_OTHER 提升为 FIFO 50）——旧资料里"默认 SCHED_OTHER、仅 RT 内核 FIFO 50"的说法已过时。50 的取值是折中：高于所有 CFS 任务（中断传递及时），低于典型业务实时任务（业务可抢占中断线程）。
- **交接位**：`IRQTF_RUNTHREAD`。`__irq_wake_thread` 置位 + wake，`irq_wait_for_interrupt()` 用 `test_and_clear_bit` **抢占式**取标记——若线程还没睡醒又来了第二次中断，标记再次置位，线程跑完当前 `thread_fn` 后循环回到 `irq_wait_for_interrupt` 会立刻取到而不睡眠（事件不丢，最多合并执行）。
- **`thread_fn` 返回值约定**：`IRQ_HANDLED`（我处理了，同时给 spurious 延迟检测记账）/ `IRQ_NONE`（不是我的——若 primary 已返回 WAKE_THREAD 却线程不认账，会累积 unhandled 触发 spurious 检测）/ `IRQ_WAKE_THREAD`（接力唤醒 secondary action，仅 force-thread 场景出现）。
- **primary 缺省时**：`request_threaded_irq(irq, NULL, thread_fn, ...)` 的 handler 被替换为 `irq_default_primary_handler()`——无条件 `return IRQ_WAKE_THREAD`，即"硬中断里什么都不做，直接甩给线程"。
- **同步**：`synchronize_irq()` 等待硬中断与**所有** irq 线程排空（`threads_active` 归零 + `wait_for_threads` 队列）；`free_irq()` 内部先 `synchronize_hardirq()` 再 `kthread_stop()` 线程。

### 🎯 primary handler 的职责清单

保留 primary（而不是传 NULL）的正当理由只有三类：

1. **ack/确认类硬件动作**：某些控制器要求 handler 侧读寄存器清 pending（虽然多数已由 flow handler/chip 完成）；
2. **共享中断判源**：多设备共线时快速读自己状态寄存器，不是自己的返回 `IRQ_NONE`（别人的 action 链会继续判），是自己的做最小处理再 `IRQ_WAKE_THREAD`；
3. **时间窗硬约束**：必须在微秒级完成的动作（如关掉一个会持续拉线的硬件事件源），在线程里做就来不及（风暴已起）。

典型模式：

```c
static irqreturn_t my_primary(int irq, void *dev)
{
	struct my_dev *d = dev;
	u32 st = readl(d->reg_status);

	if (!(st & MY_IRQ_MASK))
		return IRQ_NONE;            /* 共享线: 不是我 */
	writel(st & MY_IRQ_MASK, d->reg_clear);  /* 立刻掐断电平, 防风暴 */
	return IRQ_WAKE_THREAD;         /* 重活交给线程 */
}

static irqreturn_t my_thread(int irq, void *dev)
{
	struct my_dev *d = dev;
	/* 可睡眠: mutex, kmalloc(GFP_KERNEL), i2c 传输, 请求用户态固件... */
	return IRQ_HANDLED;
}

request_threaded_irq(irq, my_primary, my_thread,
		     IRQF_ONESHOT | IRQF_TRIGGER_LOW, "mydev", dev);
```

### 🛡️ IRQF_ONESHOT 深度解析

问题：电平触发的线程化中断，primary 返回后 flow handler 的 `cond_unmask_irq()` 若立刻 unmask，而设备的中断源要等 `thread_fn` 才清——线还拉着 → 立刻再触发 → 硬中断又进来甩给线程 → unmask → 再触发……**风暴**。反过来若一直不 unmask，线程万一被延迟调度（高负载），中断源被无限期闷着——**丢事件**（对边沿尤其致命）。

oneshot 的解法：**"线保持 masked，直到线程真正跑完"**，用 `desc->threads_oneshot` 位图协调：

```c
/* 硬中断侧 (flow handler 内): kernel/irq/chip.c */
cond_unmask_irq():
	if (!irqd_irq_disabled && irqd_irq_masked && !desc->threads_oneshot)
		unmask_irq(desc);
	/* threads_oneshot 非零 → 继续闷着, flow handler 先返回 */

/* 唤醒线程时: kernel/irq/handle.c */
__irq_wake_thread():
	desc->threads_oneshot |= action->thread_mask;   /* 占位: 我的线程没跑完 */

/* 线程侧收尾: kernel/irq/manage.c (v6.6, 节选) */
static void irq_finalize_oneshot(struct irq_desc *desc, struct irqaction *action)
{
	if (!(desc->istate & IRQS_ONESHOT) ||
	    action->handler == irq_forced_secondary_handler)
		return;
again:
	chip_bus_lock(desc);
	raw_spin_lock_irq(&desc->lock);
	/* 若硬中断还在别的 CPU 上执行(IRQD_IRQ_INPROGRESS), 等:
	 * 否则 unmask 后新中断进来 mask 又因 in-progress 退出, 线永远 masked */
	if (unlikely(irqd_irq_inprogress(&desc->irq_data))) {
		raw_spin_unlock_irq(&desc->lock);
		chip_bus_sync_unlock(desc);
		cpu_relax();
		goto again;
	}
	desc->threads_oneshot &= ~action->thread_mask;  /* 清位 */
	if (!desc->threads_oneshot && !irqd_irq_disabled &&
	    irqd_irq_masked)
		unmask_irq(desc);                       /* 最后一个线程跑完才 unmask */
	...
}
```

共享 oneshot 线上多个 action 时，每个线程清自己的 `thread_mask` 位，**全清才 unmask**——任意一个线程慢，线就继续闷着（正确性优先）。`irq_finalize_oneshot` 里对 `IRQD_IRQ_INPROGRESS` 的自旋等待解决"线程比硬中断还快跑完"的诡异竞态（注释原文称之为 implausible but necessary）。

**什么时候必须加 IRQF_ONESHOT**：电平触发的线程化中断（防风暴）；primary 为 NULL 时**强制要求**（`__setup_irq` 直接拒绝无 oneshot 的 NULL-primary 注册，因为无人挡风暴）；边沿+自 ack 硬件可不加（`IRQCHIP_ONESHOT_SAFE` 的芯片，如 MSI——消息中断无"线状态"，genirq 对这类芯片豁免 oneshot mask）。

### ⚡ PREEMPT_RT 的中断模型

RT 内核的哲学：**硬中断里只留不可线程化的最小集合，其余全部变成可调度的东西**。

收益与代价的量化视角：RT 的卖点是**可承诺的最坏延迟**（worst-case latency bound），验证手段就是 `cyclictest -m -Sp98` 类工具配合本章末尾的 irqsooff/preemptoff tracer；非 RT 的卖点是**平均吞吐**。两者不是"新旧行"，而是同一份 genirq 代码树上的两种构建配置（`CONFIG_PREEMPT_RT`），理解这条谱系比站队更重要。

**强制线程化**：boot 参数 `threadirqs`（`early_param("threadirqs", setup_forced_irqthreads)` → `force_irqthreads_key` 静态键）。`irq_setup_forced_threading()` 把普通注册改造成线程：

```c
// kernel/irq/manage.c (v6.6, 节选)
static int irq_setup_forced_threading(struct irqaction *new)
{
	if (!force_irqthreads())
		return 0;
	if (new->flags & (IRQF_NO_THREAD | IRQF_PERCPU | IRQF_ONESHOT))
		return 0;                          /* 这些旗标豁免强制 */
	if (new->handler == irq_default_primary_handler)
		return 0;                          /* 已是线程化注册 */
	new->flags |= IRQF_ONESHOT;            /* 强制补 oneshot 防风暴 */
	if (new->handler && new->thread_fn) {
		/* 双 handler 注册: 原handler塞进 secondary 的线程里跑 */
		new->secondary = kzalloc(sizeof(struct irqaction), GFP_KERNEL);
		new->secondary->handler = irq_forced_secondary_handler;
		new->secondary->thread_fn = new->handler;   /* 原primary降级为线程体 */
		...
	}
	set_bit(IRQTF_FORCED_THREAD, &new->thread_flags);
	new->thread_fn = new->handler;         /* 原primary移进线程 */
	new->handler = irq_default_primary_handler;
	return 0;
}
```

豁免旗标：`IRQF_NO_THREAD`（时钟中断等——tick 不能被调度延迟）、`IRQF_PERCPU`、`IRQF_ONESHOT`。PREEMPT_RT 内核自身默认等价于全员 threadirqs（RT 配置下多数驱动被构建为线程化）；真正的硬中断只剩 timer、IPI、以及被显式标记 IRQF_NO_THREAD 的关键路径。
- **软中断也线程化**：RT 上 `invoke_softirq()` 只唤醒 ksoftirqd（第 5 章），bh 禁用区可抢占（`softirq_ctrl` 本地锁）。
- **收益与代价**：收益是**延迟可承诺**——最长关中断区（irqsoff）与最长不可抢占区被压到极小，实时任务的最坏唤醒延迟有界；代价是每次中断多一次线程调度（µs 级），吞吐敏感路径（高频小包收发）延迟上升。
- NMI/perf 与某些 watchdog 走 `IRQS_NMI` 路径保持不可线程化（`request_nmi`），这是"最小硬中断集合"的例外名单。

**线程化的代价清单**（何时不该线程化）：

| 代价 | 量级 | 谁最疼 |
| :--- | :--- | :--- |
| 额外一次线程唤醒调度 | µs 级（唤醒→运行） | 每秒百万次中断的设备（高速网卡） |
| FIFO50 线程的抢占权 | 高于所有 CFS 任务 | CPU 饱和时的普通任务 |
| 缓存迁移 | handler 数据从硬中断栈搬到线程栈 | 本来可以一次性处理完的短工作 |
| 事件合并（IRQTF_RUNTHREAD 单 bit） | 语义合并而非丢失 | 需要逐事件精确计数的驱动（需自己攒批量） |

所以现实工程里的分工是：**高频高速路径**（万兆网卡、NVMe）用 hard handler + NAPI/软中断分片；**低频重活**（输入设备、I2C/SPI 传感器、USB 热插拔）用 threaded——一次线程调度开销在毫秒级工作面前可忽略。判断式很朴素：`中断间隔 >> 线程调度延迟` 时线程化几乎零成本；反之需要重新设计（合并、分片、轮询）。

### 🧲 中断亲和性

**设置链路**：

```
用户/驱动: echo 0c > /proc/irq/126/smp_affinity        (或 smp_affinity_list: "2,3")
  → irq_affinity_proc_write                          kernel/irq/proc.c
      → irq_set_affinity(irq, cpumask)               kernel/irq/manage.c
          → __irq_set_affinity → irq_set_affinity_locked
              → irq_do_set_affinity(data, mask, force)   manage.c
                    cpumask_copy(irqd_get_affinity_mask, mask)  /* 记录意图 */
                    → chip->irq_set_affinity(data, mask, force)
                          x86: assign_irq_vector + APIC 编程 (IO-APIC 重定向表
                               / MSI 地址里的 destination)
                          arm64: GIC 路由寄存器 (GICD_IROUTER<n>) 写目标核
                    返回 IRQ_SET_MASK_OK → core 更新 effective_affinity
```

- `/proc/irq/N/smp_affinity`（十六进制掩码）/ `smp_affinity_list`（CPU 列表）二选一，还有 `node`（NUMA 归属）与 `default_smp_affinity`（新 IRQ 的默认掩码，`irq_default_affinity`）。写失败的三种常见形态：掩码不含任何在线 CPU（`-EINVAL`）；`IRQD_AFFINITY_MANAGED` 管理的中断被写越界掩码（拒绝）；掩码全部落在 `IRQD_NO_BALANCING` 的禁区。写"成功"但 `effectiv` 变成另一个核则是 vector/路由约束的静默收窄——排障时永远以 `effectiv` 为准。
- **意图 vs 实效**：`affinity` 是请求掩码，`effective_affinity` 才是硬件真实生效的（`CONFIG_GENERIC_IRQ_EFFECTIVE_AFF_MASK`；x86 的 vector 分配受 CPU 在线/已占 vector 约束，arm64 的 GIC 单路由寄存器也常收窄成单核）。两者都在 `/sys/kernel/debug/irq/irqs/N/` 可见（`affinity:` / `effectiv:` 行）。
- 返回值协议 `IRQ_SET_MASK_OK` / `IRQ_SET_MASK_OK_NOCOPY`（chip 自己更新了 affinity）/ `IRQ_SET_MASK_OK_DONE`（层级 chip 用，跳过父层的重复设置）。
- 迁移时机：能进程上下文安全迁移的芯片（`IRQD_MOVE_PCNTXT`）立即写路由；不安全的（如 IO-APIC 级别）走 **pending move**——把目标掩码放 `desc->pending_mask`，置 `IRQD_SETAFFINITY_PENDING`，等该中断下一次在本 CPU 实际触发（此时本 CPU 上无其执行流）再 `__irq_move_irq()` 完成迁移（`kernel/irq/migration.c`），杜绝"路由已改、旧 CPU 上 handler 还在跑"的重入窗口。

**managed IRQ（IRQD_AFFINITY_MANAGED）**：多队列网卡（RSS）/blk-mq 在 `pci_alloc_irq_vectors(..., PCI_IRQ_AFFINITY)` 时由内核按队列分配**每队列一组专属 CPU**，驱动不能也不应手工改：

- 每个 queue→CPU 组一条 IRQ，`IRQD_AFFINITY_MANAGED` 置位后 `/proc/irq/N/smp_affinity` 写入被拒（`-EPERM` 或静默忽略，取决于掩码是否越出管理集）；
- 收益：IRQ 与处理它的软中断/进程在同一核，cache/TLB 全热——这是 NUMA 与大核数机器网络吞吐的基石；
- **CPU hotplug 与 managed IRQ**：`irq_migrate_all_off_this_cpu()` → `migrate_one_irq()`（`kernel/irq/cpuhotplug.c`）——目标 CPU 全部下线时，普通 IRQ 强制改投 `cpu_online_mask`（打 warn："no longer affine"）；**managed IRQ 则 `irqd_set_managed_shutdown()` + `irq_shutdown_and_deactivate()`**——宁可关掉这条队列（驱动队列也随 hotplug 下线），不破坏管理亲和性；CPU 重新上线时 `irq_affinity_online_cpu()` → `irq_restore_affinity_of_irq()` 恢复（`irq_startup(desc, IRQ_RESEND, ...)` 顺带补发下线期间的事件）。

### 🚀 多核性能工程实战

**IRQ 与进程亲和配对**：高频设备的标准姿势是"中断、软中断、用户进程"三合一在同核同 NUMA：

```bash
# 1) 看清现状: /proc/interrupts 列出各 RSS 队列 IRQ 与 per-CPU 计数
#    eth0-TxRx-0 → IRQ 126, eth0-TxRx-1 → IRQ 127 ...
# 2) 把应用线程钉在与队列对应的核
taskset -cp 2 <pid>     # 应用跑 CPU2
echo 4 > /proc/irq/126/smp_affinity      # IRQ126(=CPU2 mask) 同核
# 3) 开启 RPS 兜底(无硬件多队列时把 NET_RX 导流到别的核):
echo 00ff00 > /sys/class/net/eth0/queues/rx-0/rps_cpus
# 4) irqbalance 默认会周期性重排 —— 精心配对后应屏蔽之:
systemctl stop irqbalance
```

**irqbalance 的定位**：守护进程周期读 `/proc/interrupts` 与拓扑（`/sys/devices/system/cpu/*/cache|topology`），把 IRQ 分散到负载低/同 cache 域的核。适合"没精力手工调"的通用服务器；对延迟敏感或已手工配对的系统反而是干扰源（`IRQBALANCE_BANNED_CPUS`/affinity_hint 可约束——`irq_apply_affinity_hint()` 写的 hint 就是给 irqbalance 消费的）。

**/proc/interrupts 解读案例**（诊断三板斧）：

```
            CPU0       CPU1       CPU2       CPU3
 126:  184560123          0          0          0   PCI-MSIx  eth0-TxRx-0
 127:          0  129876544          0          0   PCI-MSIx  eth0-TxRx-1
 128:          0          0    9987123          0   PCI-MSIx  eth0-TxRx-2
 129:   87654321  81234567   79876543  80123456   PCI-MSIx  nvme0q1..4 → 正常分散
```

- `126` 行四个数只有 CPU0 非 0：单队列中断全压一个核（`CPU0 si%` 高、软中断延迟大）→ 加队列（`ethtool -L eth0 combined 4`）或 RPS；
- `LOC`/`RES`/`CAL`/`TLB` 行是架构向量（x86：本地时钟/重调度/函数调用/TLB shootdown），TLB 单核暴增常见于进程在多核间跳跃（亲和性没配好）；
- `ERR`/`MIS` 计数（IO-APIC 环境的 bus 冲突/坏路由）非零 = 硬件级异常。

**per-CPU 中断风暴案例**：典型症状 `mpstat -P ALL 1` 某 `%irq`+`%soft` 之和接近 100、`perf record -e irq_vectors:*` 看到 `local_timer_count` 或某设备 vector 独占。处置思路：① `/proc/interrupts` 定位元凶 IRQ；② 若为合法高频设备 → 分队列/调亲和/调合并参数（`ethtool -C` 把中断合并窗口调大以降频）；③ 若为无人认领（每行末尾无设备名或 spurious 计数飙升）→ 第 3 章 spurious 检测通常会自动禁它，配合 `irqpoll` 找真主；④ 若是 IPI 类（TLB/CAL）→ 检查任务迁移策略（`numactl`、调度域）。

### 🔬 观测与调试工具箱

**ftrace tracepoint**（零开销开关于 dynamic 探针）：

```bash
cd /sys/kernel/tracing
echo 'irq:*' > set_event           # 或精确: events/irq/irq_handler_entry/enable
echo 1 > tracing_on; sleep 5; echo 0 > tracing_on
# irq_handler_entry/exit 字段: irq, name, handler, ret
#   可测每次 handler 的 entry→exit 间隔 = 硬中断执行时长
#   可统计"哪个 handler 最常来"
```

**perf 量化中断延迟**（比肉眼读 trace 更适合出结论）：

```bash
# 1) 每个 IRQ 的到达频率排序
perf stat -e irq:irq_handler_entry -a sleep 10
perf record -e irq:irq_handler_entry -a -- sleep 10
perf report --sort=handler          # 哪个 handler 吃掉了 CPU

# 2) handler 执行时长分布 (entry→exit 配对直方图, BPF 亦可)
perf record -e irq:irq_handler_entry -e irq:irq_handler_exit -a sleep 10
bpftrace -e 'tracepoint:irq:irq_handler_entry { @ts[args->irq] = nsecs; }
            tracepoint:irq:irq_handler_exit  /@ts[args->irq]/
              { @dur_ns = hist(nsecs - @ts[args->irq]); delete(@ts[args->irq]); }'

# 3) 中断+软中断的总 CPU 占比
perf stat -a -e irq:irq_handler_entry,irq:softirq_entry sleep 10
mpstat -P ALL 1                     # %irq + %soft 两列
```

典型结论形态："irq/126-nvme0 均值 8µs、p99 25µs，集中在 CPU2"——三个数字分别回答"该不该线程化"、"抖动多大"、"亲和是否按预期生效"。

**irqsooff/preemptoff/preemptirqsooff tracer**（`CONFIG_IRQSOFF_TRACER` 等）：追踪**最长关中断区间**与**最长不可抢占区间**——PREEMPT_RT 验收（最长延迟承诺）的标准工具：

```bash
echo irqsoff > current_tracer
cat tracing_max_latency       # 历史最长关中断时长 (RT: 应在几十 µs 内)
cat trace                     # 定位: 是哪个函数路径关中断太久
```

**`/sys/kernel/debug/irq/`**（`CONFIG_GENERIC_IRQ_DEBUGFS`，`kernel/irq/debugfs.c`）：每 IRQ 一文件，dump handler 名、chip 名、`IRQD_*`/`IRQS_*` 全部置位状态、affinity/effective/pending 三掩码、action 链——比裸读 `/proc/interrupts` 丰富一个量级，是报 bug 时的标准附件：

```
# cat /sys/kernel/debug/irq/irqs/126
handler:  handle_fasteoi_irq
chip:     ITS
Status:   IRQD_IRQ_DISABLED | IRQD_AFFINITY_MANAGED | ...
affinity: 0-3
effectiv: 2
pending:  (empty)
```

**lockdep 与中断上下文**：`lockdep_hardirq_enter/exit()`（`irq_enter_rcu` 路径）让 lockdep 知道"现在处于硬中断上下文"，从而捕获两类经典 bug：① 在中断里拿 `spin_lock()` 却在进程里 `spin_lock_irqsave()` 不一致导致的潜在死锁；② 中断里误拿睡眠锁。`CONFIG_PROVE_LOCKING` 开启时，`/proc/lockdep_stats` 的 `hardirq-safe/unsafe` 计数即此机制的产出。**FTRACE_IRQFLAGS / CONFIG_TRACE_IRQFLAGS** 是这一切的前提：它让 `local_irq_save/restore/disable/enable` 带上 tracepoint（`trace_hardirqs_off/on`），irqsoff tracer 与 lockdep 的关中断状态追踪都挂在这些钩子上——没有它，"谁关了中断没开"这类 bug 无从查起。这也是为什么 `__handle_irq_event_percpu` 里那个 `WARN_ONCE(!irqs_disabled())` 能工作：handler 里偷开中断会被 flags 追踪立刻发现。

### 💭 思考题

1. 线程化中断的 primary 返回 `IRQ_WAKE_THREAD` 后、`thread_fn` 被调度前，同一设备又触发两次。最终 `thread_fn` 执行几次？丢事件吗？
   <details><summary>提示</summary>IRQTF_RUNTHREAD 是单 bit——合并为 1 次执行；事件语义上不丢（设备状态寄存器/oneshot masked 保证），但"两次事件的时序"被合并，handler 必须一次处理完所有积压状态。</details>
2. 为什么 `irq_finalize_oneshot()` 在清 `threads_oneshot` 位前要自旋等待 `IRQD_IRQ_INPROGRESS` 清零？构造它防御的具体交错序列。
   <details><summary>提示</summary>见源码注释：线程在 CPU0 跑完时，CPU1 上 flow handler 可能刚 mask 完还没走到 handle_irq_event 清 INPROGRESS——此刻 unmask，新中断进 CPU1、mask、因 INPROGRESS 退出，线永远 masked。</details>
3. managed IRQ 在目标 CPU 下线时被 shutdown 而不是改投其他 CPU。为什么不学普通 IRQ "broke affinity" 强制迁移？
   <details><summary>提示</summary>managed 的性能契约是"IRQ 与队列/进程同核"；迁移到任意核会破坏 cache 局部性与队列-CPU 对应关系，宁可暂停队列等 CPU 回来。</details>
4. `irqsoff` tracer 在 PREEMPT_RT 上测出的 max_latency 为何显著小于非 RT 内核？这与 threadirqs 有何因果关系？
   <details><summary>提示</summary>RT 把长关中断路径（驱动 handler 里的 local_irq_save 大段）变成线程化（中断里只剩 ack/唤醒），关中断区间缩短到核心 entry/exit 代码。</details>
5. 给定 `MAX_RT_PRIO/2 = 50`：若业务实时任务用 SCHED_FIFO 60 处理"被 irq 线程唤醒的请求"，会形成什么优先级反转形态？内核提供什么机制缓解？
   <details><summary>提示</summary>FIFO50 的 irq 线程持有设备锁、FIFO60 任务等锁 → 优先级反转（低 prio 的 irq 线程挡住高 prio 任务，且 FIFO 之间无抢占）。缓解：rt-mutex（RT 内核核心）与 `IRQF_NO_THREAD` 白名单化关键路径；用户态侧可把等待路径改 polling。</details>
6. `/proc/irq/N/smp_affinity` 写入成功，但 `/sys/kernel/debug/irq/irqs/N` 的 `effectiv:` 显示另一个核。举两个造成"意图与实效分离"的硬件/软件原因。
   <details><summary>提示</summary>x86：目标 CPU 的 vector 空间已满/离线，vector 分配被迫落到别的核；层级 domain 中父层（如 ITS collection）只支持部分目标；IRQD_SINGLE_TARGET 芯片被请求多核掩码时收窄。</details>
7. 观察你手头机器的 `/proc/interrupts` 与 `/proc/irq/N/smp_affinity`：找出一条 managed IRQ（多队列网卡）与一条普通 IRQ，尝试分别写入 `smp_affinity`，记录行为差异并与 `migrate_one_irq` 的代码对照。
   <details><summary>提示</summary>managed IRQ 的写入被拒或被收窄；用 `echo 0 > /sys/devices/system/cpu/cpuN/online` 下线目标核再观察该 IRQ 的去向（managed shutdown vs broke affinity 的 dmesg 差异）。</details>
