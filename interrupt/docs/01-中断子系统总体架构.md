# 中断子系统总体架构

Linux 6.6 的中断子系统（genirq，Generic IRQ framework）是内核中分层最清晰的子系统之一。它的核心设计哲学是：**把"架构相关"与"架构无关"彻底解耦**——架构只负责把 CPU 从硬件中断中"捞出来"并交出 irq 描述符，剩下的流控（mask/ack/eoi/unmask 的编排）、线程化、亲和性、嵌套 domain 翻译全部由通用层完成。本章给出全景图，后续各章逐层展开。

### 🎯 一张图看懂分层

```
┌──────────────────────────────────────────────────────────────────┐
│  设备驱动层                                                        │
│  request_threaded_irq() 注册的 handler / thread_fn                 │
│  (action->handler, action->thread_fn)                             │
├──────────────────────────────────────────────────────────────────┤
│  Generic IRQ Core (genirq, kernel/irq/)                           │
│                                                                   │
│  ┌─────────────────────────┐  ┌───────────────────────────────┐  │
│  │ highlevel flow handler  │  │ chip callbacks (struct        │  │
│  │ desc->handle_irq        │  │ irq_chip: ack/mask/eoi/...)   │  │
│  │ handle_level_irq        │  │ 由各中断控制器驱动实现          │  │
│  │ handle_edge_irq         │  │ x86: io_apic / msi_chip        │  │
│  │ handle_fasteoi_irq      │  │ arm64: gic_chip / its_chip     │  │
│  │ handle_simple_irq       │  └───────────────────────────────┘  │
│  │ handle_percpu_irq       │                                     │
│  └─────────────────────────┘  irq_desc / irq_data / irq_domain    │
│                                / irqaction                        │
├──────────────────────────────────────────────────────────────────┤
│  架构入口层 (asm entry)                                            │
│  x86:   IDT → DEFINE_IDTENTRY_IRQ(common_interrupt)               │
│         arch/x86/kernel/irq.c: vector_irq[vector] → desc          │
│  arm64: handle_arch_irq (函数指针, 由 set_handle_irq() 注册)       │
│         → gic_handle_irq (drivers/irqchip/irq-gic-v3.c)           │
│         → generic_handle_domain_irq(gic_data.domain, hwirq)       │
├──────────────────────────────────────────────────────────────────┤
│  硬件中断控制器                                                     │
│  x86:   Local APIC (每 CPU) + IO-APIC (南桥) + MSI/MSI-X 直写 APIC │
│  arm64: GICv3 (Distributor + Redistributor + ITS) / GICv4(vLPI)   │
└──────────────────────────────────────────────────────────────────┘
```

一条设备中断的旅程：**硬件线/消息信号 → 中断控制器选路 → CPU 异常/中断入口 → 架构入口函数 → `desc->handle_irq()`（flow handler 编排 chip 回调）→ `handle_irq_event()` 遍历 action 链调用驱动 handler**。可以看到 genirq 在中间"收口"：向上的驱动 API 与向下的芯片回调都是它定义的。

一条不为人注意的平行线：**不是所有"中断"都有 irq_desc**。x86 的 RESCHED/CALL_FUNCTION/TLB shootdown 等 IPI、local timer、NMI watchdog 走独立的 `DEFINE_IDTENTRY_SYSVEC`/`DEFINE_IDTENTRY_NMI` 入口，直接调用专用函数（`smp_send_reschedule` 的接收端），完全不进 genirq——它们没有共享、没有 flow handler、不需要 desc。`/proc/interrupts` 里它们表现为 LOC/RES/CAL/TLB 等"架构行"（计数来自 `irq_stats` percpu 而非 `kstat_irqs`）。只有**可注册、可共享、需要流控**的外设中断才值得 desc 的管理成本。这条边界线本身就是设计判断：**genirq 不是"中断的总入口"，而是"外设中断的通用管理框架"**。

### 🔩 硬件中断控制器速览

**x86（APIC 体系）**
- **Local APIC**：每 CPU 私有，接收 IO-APIC 转发来的中断、IPI（RESCHED/CALL_FUNCTION/TLB shootdown）、本地定时器（LOC）、性能计数器（PMI）、thermal 等。x2APIC 模式下用 MSR 访问，EOI 写 `MSR_IA32_EOI`（0x80b），避免物理广播写。
- **IO-APIC**：南桥里 24 个引脚（典型值），引脚可编程触发方式（edge/level），通过红表（redirection table）把引脚映射为"向量 + 目标 CPU"投递给 Local APIC。`irq_chip` 为 `ioapic_chip` / `ioapic_ir_chip`（中断重映射，Intel VT-d）。
- **MSI/MSI-X**：PCIe 设备执行 Memory Write 直接触发 Local APIC 的事件向量，完全绕过 IO-APIC 引脚（详见第 4 章 MSI domain）。

**arm64（GIC 体系）**
- **GICv3**：`Distributor`（SPI，共享外设中断，hwirq 32~1019）+ `Redistributor`（每 CPU，SGI 0~15 / PPI 16~31 / LPI）。CPU 接口读 `ICC_IAR1_EL1` 应答（ack），写 `ICC_EOIR1_EL1` 结束；若开启 FIQ 优先级屏蔽，pseudo-NMI 走 FIQ。
- **GICv3 ITS（Interrupt Translation Service）**：LPI 的翻译与路由表（Device Table / ITT / Collection Table）都在内存里由 ITS 硬件遍历，是层级 irq_domain 的典型样本。
- **GICv4/GICv4.1**：在 v3 基础上支持 vLPI **直接注入**（direct injection）vCPU，硬件完成 `irq_set_vcpu_affinity()`（IRQD_FORWARDED_TO_VCPU）对应的门铃语义，KVM 借此省掉一次 VM exit。

SGI/PPI/SPI/LPI 四类中断的编号空间：

| 类别 | hwirq 范围（GICv3） | 送达范围 | 典型用途 |
| :--- | :--- | :--- | :--- |
| SGI | 0–15 | 指定 CPU（软件触发） | IPI、CPU 间同步 |
| PPI | 16–31 | 每 CPU 独立实例 | arch timer（PPI 13/14/15）、VGIC 维护中断 |
| SPI | 32–1019 | 任意核（亲和性可配） | 传统外设引脚中断 |
| LPI | 8192+（ITS 管理） | 基于 ITS collection 路由 | PCIe MSI/MSI-X |

### 📜 演进史：从静态数组到 maple tree

理解 genirq 数据结构的演进，比记住结论更重要：

1. **2.6 早期（~2.6.22 前）**：全局静态数组 `struct irq_desc irq_desc[NR_IRQS]`，Linux IRQ number 就是数组下标。x86 上 `NR_IRQS` 由 `NR_VECTORS`、IO-APIC 数量等编译期常量拼出来，动辄预留 256~几百万项；每项 `irq_desc` 上百字节，嵌入式设备浪费严重。
2. **hwirq 与 Linux IRQ number 分离**：引入 irq_chip 抽象后，"控制器本地编号"（hwirq，如 IO-APIC 引脚号、GIC 的 INTID）与"内核逻辑编号"（virq）解耦。动机有三：
   - 多个控制器级联时（gpio → GIC），不同控制器的 hwirq 空间重叠，必须有一个全局唯一的逻辑号；
   - MSI/MSI-X 中断数量极大（每设备可达 2048 个 vector），不可能静态预留；
   - 嵌入式 SoC（如 device-tree 描述的中断树）只有一小段 hwirq 真正被使用。
3. **CONFIG_SPARSE_IRQ（2.6.28 引入 `irq_desc` 动态分配，2.6.39 Grant Likely 引入 irq_domain）**：`irq_desc` 按需 `kzalloc`，用基数树（radix tree）挂在全局 `irq_desc_tree` 上，`irq_to_desc(irq)` 查树；非 SPARSE 配置退回静态数组 `irq_desc[NR_IRQS]`（`include/linux/irqdesc.h`）。
4. **Linux 6.6（当前）**：全局查找结构从 radix tree 换成了 **maple tree**（`kernel/irq/irqdesc.c`）：

```c
// kernel/irq/irqdesc.c (v6.6)
static struct maple_tree sparse_irqs = MTREE_INIT_EXT(sparse_irqs, 0,
				mt_flags_lock_external, sparse_irq_lock);

struct irq_desc *irq_to_desc(unsigned int irq)
{
	return mtree_load(&sparse_irqs, irq);
}
```

maple tree 的 RCU 友好读路径与更紧凑的节点布局让 `irq_to_desc()` 的热路径更快；注意每个 irq_domain 内部的**反向映射**（hwirq→virq 的 revmap）在 6.6 中仍然是 radix tree（`domain->revmap_tree`），两者不要混淆。`irq_desc` 的释放走 `call_rcu()` 延迟回收（`free_desc()`），因为无锁读者（如 `/proc/interrupts` 的 `kstat_irqs_usr()`）可能正持有旧指针。

里程碑速查（精确定位用 `git log --grep` 验证）：

| 版本 | 事件 |
| :--- | :--- |
| 2.3 | softirq/tasklet 取代旧的 bottom half（BH）机制 |
| ~2.6.22 | genirq 通用层开始统一各架构 irq 核心 |
| 2.6.28 | `CONFIG_SPARSE_IRQ`：irq_desc 动态分配 + radix tree |
| 2.6.31 | threaded IRQ（Thomas Gleixner） |
| 2.6.39 | irq_domain 抽象（Grant Likely） |
| 3.12 | 层级 irq_domain（`CONFIG_IRQ_DOMAIN_HIERARCHY`，GICv3/MSI 铺路） |
| 5.13 | irq 线程提升为 SCHED_FIFO 50（见第 6 章） |
| 6.6 | 全局 desc 查找迁移到 maple tree（本文基准版本） |

### 🧩 genirq 的两个关键抽象

genirq 最重要的设计决策是**把"流控逻辑"与"芯片操作"拆成两个正交维度**：

#### 1) highlevel flow handlers —— `desc->handle_irq()`

flow handler 决定一次中断事件中 mask/ack/eoi/unmask 的**编排顺序**，对应硬件触发语义：

| flow handler | 适用触发 | 编排（简化） | 典型芯片 |
| :--- | :--- | :--- | :--- |
| `handle_level_irq` | 电平触发 | `mask_ack` → 执行 handler → `cond_unmask`（handler 清掉设备电平后才 unmask） | IO-APIC level、gpio 电平级联 |
| `handle_edge_irq` | 边沿触发 | `ack` → 循环执行 handler（`do{...}while(IRQS_PENDING)`）→ 需要时 `mask_ack` | IO-APIC edge、多数 SoC gpio |
| `handle_fasteoi_irq` | 控制器代管流控 | 仅在结尾 `eoi`（透明控制器，一次回调） | GICv3 SPI/PPI（gic_handle_irq 已经 ack 过 IAR） |
| `handle_simple_irq` | 无需硬件流控 | 什么都不做，直接调 handler | 软件模拟 irq（irq_sim）、级联 demux 后的子中断 |
| `handle_percpu_irq` | per-CPU 中断 | `ack` → handler → `eoi`，全程不拿 `desc->lock` | Local APIC timer、resched IPI、GIC 的 PPI percpu 模式 |

为什么必须区分？**电平中断**只要设备还拉着线，unmask 后会立刻再来一次（中断风暴），所以必须 mask 后等 handler 让设备 deassert 再 unmask；**边沿中断**的信号是瞬时脉冲，ack 后如果 handler 执行期间又来一个脉冲，只能记录 pending（IRQS_PENDING）回头补发，绝不能像电平那样依赖"线还拉着"。

#### 2) chip callbacks —— `struct irq_chip`

芯片回调是流控编排中每一步"动作"的硬件实现（完整定义见第 2 章）：

- `irq_ack`：边沿语义的"确认收到"，让控制器能记录下一个边沿；
- `irq_mask` / `irq_unmask`：屏蔽/放行该中断源；
- `irq_mask_ack`：合并操作，常见于 IO-APIC（一次寄存器写完成两件事，省一次锁开销）；
- `irq_eoi`：结束中断（GIC 写 EOIR、Local APIC 写 EOI/0x80b），通知控制器可以投递同优先级或更低优先级中断；
- `irq_set_affinity`：改变投递目标 CPU；
- `irq_set_type`：配置触发类型（edge/level、极性）；
- `irq_set_wake`：配置为系统唤醒源；
- `irq_retrigger`：软件重发一次中断（迁移场景防止丢失）。

genirq 在 chip.c 里提供了 `mask_ack_irq()`、`unmask_irq()`、`ack_bad_irq()` 等包装函数：先调 chip 回调，再同步更新 `irq_data` 里的 IRQD_IRQ_MASKED 等状态位，保证软件状态与硬件寄存器一致——驱动绝不应该绕过包装直接调 chip 回调。

两维正交的收益可以用一张矩阵直观化（行=触发语义，列=芯片实现）：

| | IO-APIC（x86） | GICv3（arm64） | gpio 控制器 |
| :--- | :--- | :--- | :--- |
| 电平 | `handle_level_irq` + ioapic_mask/ack | `handle_fasteoi_irq` + gic_eoi | `handle_level_irq` + gpio mask/unmask |
| 边沿 | `handle_edge_irq` + ioapic_ack | `handle_fasteoi_irq`（LPI 天然边沿） | `handle_edge_irq` + gpio ack |
| 组合数 | 2×N 份芯片代码复用 | 同左 | 同左 |

如果没有这个拆分，每种"触发语义 × 芯片"组合都要写一份流控代码——这正是 2.4 时代各架构 `do_IRQ` 各自为政的乱象来源。

#### 慢总线芯片的"线程化"特例

有一类中断控制器挂在 I2C/SPI 总线上（如 PCA9535 GPIO 扩展器），**读写它的寄存器可能睡眠**，根本不能在 hard IRQ 里 mask/ack。chip 回调里的 `irq_bus_lock`/`irq_bus_sync_unlock` 就为此设计：硬中断路径只调 `irq_bus_lock()`（拿一把普通自旋锁做标记）并记录"待处理变更"，真正的寄存器读写被推迟到 `irq_bus_sync_unlock()`——genirq 保证它运行在可睡眠上下文（通过 `chip_bus_sync_unlock` 的调用点约定）。这就是 `struct irq_chip` 注释里 "slow bus chips" 的含义：**线程化不只是 request_threaded_irq 一条路，芯片层自己也有**。

### ⚠️ 中断上下文的约束

hard IRQ handler 运行在**中断上下文**（atomic context），铁律：

1. **不能睡眠/阻塞**：此刻 `current` 是被打断的任意进程，调度器无法跟踪"中断睡在哪个任务上"。`might_sleep()` 类检查在 `in_atomic()` 时直接报 bug。`kmalloc(GFP_KERNEL)`、`mutex_lock()`、`copy_to_user()` 一律禁止。
2. **抢占被关闭**：入口处 `preempt_count_add(HARDIRQ_OFFSET)`（`__irq_enter_raw()`，`include/linux/hardirq.h`），`in_interrupt()`/`in_irq()`/`in_hardirq()` 即由此判断。这也是软中断检查 `if (!in_interrupt() && local_softirq_pending()) invoke_softirq()` 的依据。
3. **栈很小**：x86_64 独立 IRQ 栈 16KB（`irq_stack_ptr`）；arm64 同样切换到独立 IRQ 栈（`call_on_irq_stack`，`IRQ_STACK_SIZE` 通常 16KB）后才跑 C 代码。深递归、大局部数组都危险。
4. **保持入口的"关中断"状态**：handler 运行期间本地 CPU 关中断（NMI/pseudo-NMI 除外）。`__handle_irq_event_percpu()` 里有一道防御：

```c
// kernel/irq/handle.c (v6.6)
if (WARN_ONCE(!irqs_disabled(),
	      "irq %u handler %pS enabled interrupts\n", irq, action->handler))
	local_irq_disable();
```

驱动 handler 里偷跑 `local_irq_enable()` 会立刻被抓。凡是耗时、可能睡眠的工作，必须交给 thread_fn（第 6 章）、softirq/tasklet（第 5 章）或 workqueue。

### 🚩 IRQF_* 中断申请旗标概览

`request_irq` 家族共同的旗标（`include/linux/interrupt.h`），低 4 位与 IRQ_TYPE_* 触发类型共用编码：

| 旗标 | 值 | 含义 |
| :--- | :--- | :--- |
| `IRQF_SHARED` | 0x80 | 多设备共享一条中断线（必须提供非 NULL 的 `dev_id`） |
| `IRQF_PROBE_SHARED` | 0x100 | 探测共享时容忍"已被占用" |
| `__IRQF_TIMER` | 0x200 | 时钟中断专用（配合 NO_HZ） |
| `IRQF_PERCPU` | 0x400 | per-CPU 中断（IPI、local APIC） |
| `IRQF_NOBALANCING` | 0x800 | 禁止亲和性调整 |
| `IRQF_IRQPOLL` | 0x1000 | 侧漏轮询候选（配合 `irqpoll`） |
| `IRQF_ONESHOT` | 0x2000 | 线程化中断唤醒线程前保持 masked（第 6 章深挖） |
| `IRQF_NO_SUSPEND` | 0x4000 | 系统挂起时不屏蔽 |
| `IRQF_FORCE_RESUME` | 0x8000 | resume 时强制重新 enable |
| `IRQF_NO_THREAD` | 0x10000 | 禁止被 force-thread（如时钟中断） |
| `IRQF_EARLY_RESUME` | 0x20000 | 在 syscore 阶段之前 resume |
| `IRQF_COND_SUSPEND` | 0x40000 | 仅共享线上的 NO_SUSPEND 例外 |
| `IRQF_NO_AUTOEN` | 0x80000 | 注册后不自动 enable（6.1 新增，配合 runtime pm） |
| `IRQF_NO_DEBUG` | 0x100000 | 排除出 spurious 检测 |
| `IRQF_TIMER` | — | `__IRQF_TIMER\|IRQF_NO_SUSPEND\|IRQF_NO_THREAD` 三合一 |
| `IRQF_TRIGGER_*` | 1/2/4/8 | rising/falling/high/low 触发类型 |

注意区分两套：`IRQF_*` 是**申请时**驱动给 genirq 的要求；`IRQ_*`（`include/linux/irq.h` 里的 `IRQ_LEVEL`、`IRQ_NOPROBE`、`IRQ_NOAUTOEN`...）是**irq_desc 层**的描述状态，其中 bit8~ 与 IRQF 位对齐（`irq_modify_status` 可改）。另外还有芯片侧 `IRQCHIP_*` 与 per-irq_data 的 `IRQD_*`，共四层标志，第 2 章统一梳理。

### 🔌 request_irq 家族 API 概览与选型

```c
// include/linux/interrupt.h (v6.6, 节选签名)
request_threaded_irq(unsigned int irq, irq_handler_t handler,
                     irq_handler_t thread_fn,
                     unsigned long flags, const char *name, void *dev);
request_any_context_irq(unsigned int irq, irq_handler_t handler,
                        unsigned long flags, const char *name, void *dev_id);
request_percpu_irq(unsigned int irq, irq_handler_t handler,
                   const char *devname, void __percpu *percpu_dev_id);
request_nmi(unsigned int irq, irq_handler_t handler,
            unsigned long flags, const char *name, void *dev_id);
devm_request_threaded_irq(struct device *dev, unsigned int irq, ...);  // kernel/irq/devres.c
```

| API | 执行上下文 | 一句话定位 |
| :--- | :--- | :--- |
| `request_irq()` | hard IRQ | 静态内联，`request_threaded_irq(irq, handler, NULL, ...)` 的马甲；只适合极短、确定性的 handler |
| `request_threaded_irq()` | hard + 内核线程 | **现代驱动默认选择**：primary 只做 ack/判源，重活进 thread_fn |
| `request_any_context_irq()` | 视 chip 而定 | 尝试 hard，失败（chip 是 nested/线程化）退回 threaded；返回 `IRQC_IS_HARDIRQ`/`IRQC_IS_NESTED` |
| `request_percpu_irq()` | hard（per-CPU） | per-CPU 中断，`dev_id` 是 percpu 变量，handler 无锁跑在对应 CPU 上（如 local APIC timer） |
| `devm_request_threaded_irq()` | 同 threaded | devres 托管，probe 失败/驱动卸载自动 `free_irq`，消灭泄漏样板代码 |
| `request_nmi()` | NMI | 走 `IRQS_NMI` 路径（perf NMI watchdog、GHES）；handler 连自旋锁都不能拿 |
| `irq_set_chained_handler()` | hard（级联） | 中断控制器级联 demux 用（如 gpio→子中断），本质是挂 `chained_action` 而非驱动 action |

选型决策树：

```
需要睡眠/耗时 > 几十微秒?
├─ 是 → request_threaded_irq() (+ IRQF_ONESHOT 若电平/防风暴)
│        └─ 设备是 managed 资源? → devm_request_threaded_irq()
├─ 否, 但可能被强制线程化(PREEMPT_RT)?
│        → request_any_context_irq()
├─ per-CPU 硬件事件(timer/IPI)?
│        → request_percpu_irq() / __request_percpu_irq(IRQF_...)
└─ NMI 级可靠性(硬件错误,不能被屏蔽)?
         → request_nmi()
```

一个常见误用：把本来很短的 handler 也包成 threaded。线程化引入一次调度延迟（正常 µs 级，负载重时 ms 级），网络/存储高速路径至今保留真 hard handler（如 `e1000_intr` 只做 `__napi_schedule`，把收包交给 NAPI 软中断）。**"能线程化就线程化"是通用准则，"不能线程化的要给出理由"**。

常见陷阱对照（code review 检查单）：

| 陷阱 | 后果 | 纠正 |
| :--- | :--- | :--- |
| handler 里 `printk` 大段刷屏 | 控制台慢路径拖垮中断延迟 | `dev_info_ratelimited` / 线程里打印 |
| threaded 注册忘了 `IRQF_ONESHOT` | 电平设备风暴（第 6 章） | 加旗标或确认芯片 `IRQCHIP_ONESHOT_SAFE` |
| 共享中断 `dev_id` 传 NULL | request 直接 `-EINVAL`（6.6 校验） | 传设备结构体指针 |
| `request_irq` 后立刻 `enable_irq` | "unbalanced enable" WARN | 默认已 autoen；要延迟 enable 用 `IRQF_NO_AUTOEN` |
| 释放时只 `free_irq` 不 `irq_dispose_mapping` | domain 映射泄漏（动态映射场景） | probe/remove 成对处理 |
| handler 里 `spin_lock_irqsave` 后拿慢锁 | 关中断区间拉长（irqsoff 报警） | 换 threaded 或 workqueue |

### 🧪 走一遍真实例子：USB 网卡（x86）

用一条 x86_64 上 USB 网卡的收包中断把全章串起来：

1. **注册时**：`xhci` 驱动 `pci_alloc_irq_vectors()` 申请 MSI-X → msi domain 分配 vector（第 4 章）→ `devm_request_threaded_irq(...)` 注册 action；
2. **设备触发**：USB 控制器完成一次传输，写 MSI-X 消息（doorbell 地址+vector 数据）→ Root Complex 路由 → Local APIC 收到 vector，投递给路由目标 CPU；
3. **入口**：CPU 关中断、走 IDT → `DEFINE_IDTENTRY_IRQ(common_interrupt)` → `vector_irq[vector]` 查到 desc；
4. **genirq**：`desc->handle_irq` 是 `handle_fasteoi_irq`（MSI 走 fasteoi 语义）→ `handle_irq_event()` → action 链 → 驱动 handler → `IRQ_WAKE_THREAD` 或调度事件线程；
5. **退出**：`irq_exit_rcu()` → 若 NET_RX/TIMER 等 softirq pending → `__do_softirq()` 就地执行一轮（预算内）→ IRET 返回被打断的进程；
6. **观测**：`/proc/interrupts` 里该 IRQ 的目标 CPU 列 +1，`irq:irq_handler_entry` tracepoint 留下一条记录。

后文各章分别拆解其中的每一步。

### 🔭 观测入口速查

- `/proc/interrupts`：每 IRQ 的 per-CPU 计数（来源 `desc->kstat_irqs`，第 2 章）+ x86 特有的 LOC/RES/CAL/TLB 等架构行（`arch/x86/kernel/irq.c` 的 `arch_irq_stat` 系列）；
- `/proc/irq/N/`：`smp_affinity`、`smp_affinity_list`、`spurious` 计数、`node`；
- `/proc/softirqs`：软中断 per-CPU 计数（第 5 章）;
- `/sys/kernel/debug/irq/`（`CONFIG_GENERIC_IRQ_DEBUGFS`）：每 IRQ 的状态位/chip/affinity 明细（第 6 章）;
- tracepoint `irq:irq_handler_entry/exit`、`irq:softirq_entry/exit`；
- `/sys/kernel/irq/N/`（sysfs，`CONFIG_SPARSE_IRQ`）：desc 的 kobject 视角，与 debugfs 互补。

### 🧭 两个架构的入口对照表

| 维度 | x86 | arm64 |
| :--- | :--- | :--- |
| 硬件入口 | IDT 表（vector 0x20–0xEF） | 异常向量表 VBAR_EL1 |
| 通用外设入口 | `common_interrupt`（一套代码服务所有 vector） | `handle_arch_irq` 函数指针（GIC 驱动注册） |
| vector→desc 翻译 | per-CPU `vector_irq[]` 数组 | `irq_find_mapping(gic_domain, INTID)` |
| 无人认领时 | `apic_eoi()` + "No irq handler for vector" | WARN "Unexpected interrupt" + deactivate |
| 关中断方式 | CPU 自动清除 IF 标志 | 硬件置 DAIF.IF（入口后由 GIC PMR 管理） |
| 独立系统向量 | SYSVEC 族（RESCHED/CAL/TLB...） | SGI 直接处理（IPI 框架 `CONFIG_GENERIC_IRQ_IPI`） |
| NMI | `DEFINE_IDTENTRY_NMI`（真 NMI） | pseudo-NMI（FIQ + PMR 优先级屏蔽） |

这张表的深层含义：**架构差异被压缩在"从硬件信号到 `struct irq_desc *`"这一小段**，一旦拿到 desc，x86 与 arm64 的执行路径逐字相同（都进 `desc->handle_irq` → `handle_irq_event`）。这是 genirq 十几年演进的成果，也是写跨架构驱动时"handler 代码不用关心 CPU 类型"的根本保证。

### 💭 思考题

1. 同一个 GICv3 系统上，PCIe 设备的 MSI 中断为什么走 `handle_fasteoi_irq` 而 gpio 级联中断常走 `handle_level_irq`？从"LPI 没有物理电平"的角度解释。
   <details><summary>提示</summary>LPI 是基于内存表的消息中断，"线"的概念不存在，控制器硬件一次 EOI 即完成流控；gpio 级联背后是真实电平线，子中断未处理完前父线不会 deassert，需要 mask-处理-unmask 编排。</details>
2. `hwirq` 和 Linux IRQ number 为什么要分离？如果所有中断控制器都用"Linux IRQ = hwirq + 固定偏移"会出什么问题？
   <details><summary>提示</summary>多控制器级联 hwirq 空间重叠；MSI 数量爆炸；DT/ACPI 的中断号是控制器本地语义。</details>
3. `handle_percpu_irq` 为什么全程不拿 `desc->lock`？这种无锁性依赖什么前提？
   <details><summary>提示</summary>per-CPU 中断只会在本 CPU 触发，天然无并发；但 `desc->irq_data` 的 chip 状态在 hotplug/affinity 变更时仍需锁。</details>
4. `request_irq()` 与 `request_threaded_irq(irq, handler, NULL, ...)` 完全等价吗？那么 `request_threaded_irq(irq, NULL, thread_fn, ...)` 时 primary 是谁？
   <details><summary>提示</summary>等价（静态内联）；后者 primary 被替换为 `irq_default_primary_handler()`，它无条件返回 `IRQ_WAKE_THREAD`（kernel/irq/manage.c）。</details>
5. 6.6 用 maple tree 替换 radix tree 管理 `irq_desc`，但 per-domain 的 revmap 仍是 radix tree。猜猜为什么全局层先换、domain 层后换？
   <details><summary>提示</summary>全局 `irq_to_desc()` 是所有中断路径的第一跳（最热）；revmap 已有 RCU 快路径且与 `CONFIG_IRQ_DOMAIN_HIERARCHY` 耦合更深。</details>
6. 站在 2005 年（无 irq_domain 时代）设计者的角度：当时如何让 gpio 中断工作？这种旧方案在什么场景下必然崩溃？
   <details><summary>提示</summary>为每级级联预留互不重叠的 virq 段（如 gpio0 的 hwirq 映射到 virq base+offset）；崩溃点在于级联层数不可预知 + MSI 数量动态化 + DT 的中断号是控制器本地语义而非全局语义。</details>
