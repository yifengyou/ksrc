# 中断处理流程

本章沿一条真实中断的完整旅程走一遍端到端调用链：硬件信号 → 架构入口 → `irq_enter_rcu()` → flow handler → action 链 → 中断退出与软中断派发，最后解剖 spurious 检测与各阶段开销。所有代码均摘自 Linux 6.6 并标注文件路径。

### 🗺️ 端到端调用链总览

```
x86 (external IRQ, apic):
  硬件投递 vector → CPU 关中断、压栈 → IDT[idtentry]
  → DEFINE_IDTENTRY_IRQ(common_interrupt)          arch/x86/kernel/irq.c
      → irqentry_enter(regs)                       kernel/entry/common.c
          → irq_enter_rcu()                        kernel/softirq.c
              → __irq_enter_raw(): preempt_count_add(HARDIRQ_OFFSET)
      → run_irq_on_irqstack_cond(__common_interrupt)  (切换到 16KB IRQ 栈)
      → desc = __this_cpu_read(vector_irq[vector])
      → handle_irq(desc, regs) → generic_handle_irq_desc(desc)
          → desc->handle_irq(desc)                 ★ flow handler
      → irqentry_exit(regs, state)
          → irq_exit_rcu() → __irq_exit_rcu()
              → preempt_count_sub(HARDIRQ_OFFSET)
              → if (!in_interrupt() && local_softirq_pending())
                    invoke_softirq()

arm64 (GICv3, IRQ):
  GIC 投递 → CPU IRQ 异常 (DAIF.IF 置位) → vector EL1h
  → handle_arch_irq(regs)                         arch/arm64/kernel/irq.c (函数指针)
      → gic_handle_irq(regs)                       drivers/irqchip/irq-gic-v3.c
          → __gic_handle_irq_from_irqson(regs)
              → irqnr = gic_read_iar()             (读 ICC_IAR1_EL1, 硬件 ack)
              → __gic_handle_irq(irqnr, regs)
                  → gic_complete_ack(irqnr)         (写 ICC_EOIR1_EL1)
                  → generic_handle_domain_irq(gic_data.domain, irqnr)
                      → irq_find_mapping(domain, hwirq)  (revmap)
                      → generic_handle_irq_desc(desc)
                          → desc->handle_irq(desc)  ★ flow handler
      → 中断返回, gic_arch_enable_irqs() 恢复

flow handler (以 handle_fasteoi_irq 为例):         kernel/irq/chip.c
  desc->handle_irq(desc)
      → raw_spin_lock(&desc->lock)
      → handle_irq_event(desc)                     kernel/irq/handle.c
          → desc->istate &= ~IRQS_PENDING
          → irqd_set(IRQD_IRQ_INPROGRESS); raw_spin_unlock(&desc->lock)
          → handle_irq_event_percpu(desc)
              → __handle_irq_event_percpu(desc)
                  → for_each_action_of_desc: action->handler(irq, dev_id)
                  → IRQ_WAKE_THREAD → __irq_wake_thread(desc, action)
              → add_interrupt_randomness(irq)
              → note_interrupt(desc, retval)       kernel/irq/spurious.c
          → raw_spin_lock(&desc->lock); irqd_clear(IRQD_IRQ_INPROGRESS)
      → chip->irq_eoi(...) / cond_unmask_eoi_irq(desc, chip)
      → raw_spin_unlock(&desc->lock)
```

两条架构路径在 `generic_handle_irq_desc()` 处汇合——这就是 genirq 的"收口点"：**架构只负责把 hwirq 翻译成 `struct irq_desc *` 并保证中断上下文标记完成，之后一切交给通用层**。

### 🚪 架构入口细节

**x86：IDT 与 vector_irq**

x86 的外设中断以 vector（0x20–0xEF）投递。入口由 `DEFINE_IDTENTRY_IRQ` 宏生成，这个宏做了三件事（`arch/x86/include/asm/idtentry.h`）：`irqentry_enter()`（进入中断上下文）、`run_irq_on_irqstack_cond()`（切到独立 IRQ 栈执行 C 主体）、`irqentry_exit()`。主体：

```c
// arch/x86/kernel/irq.c (v6.6, 节选)
DEFINE_IDTENTRY_IRQ(common_interrupt)
{
	struct pt_regs *old_regs = set_irq_regs(regs);
	struct irq_desc *desc;

	RCU_LOCKDEP_WARN(!rcu_is_watching(), "IRQ failed to wake up RCU");

	desc = __this_cpu_read(vector_irq[vector]);   /* per-CPU vector→desc 表 */
	if (likely(!IS_ERR_OR_NULL(desc))) {
		handle_irq(desc, regs);               /* x86_64: generic_handle_irq_desc */
	} else {
		apic_eoi();                            /* 无人认领也要 EOI, 否则堵死 APIC */
		if (desc == VECTOR_UNUSED)
			pr_emerg_ratelimited("%s: %d.%u No irq handler for vector\n", ...);
		else
			__this_cpu_write(vector_irq[vector], VECTOR_UNUSED);
	}
	set_irq_regs(old_regs);
}
```

要点：
- `vector_irq` 是 per-CPU 数组——同一个 vector 在不同 CPU 可以绑不同的 desc（亲和性的底层载体）；
- 无人认领的 vector **必须 EOI**，否则 Local APIC 会持续屏蔽同级中断（这是"irq storm"里最常见的死法）；
- `handle_irq()` 在 x86_64 直接 `generic_handle_irq_desc(desc)`；32 位走 `__handle_irq`（带 regs 传参的旧接口）。
- `DEFINE_IDTENTRY_SYSVEC`（系统向量：RESCHED/CALL_FUNCTION/TLB 等）各有独立入口，不走 `vector_irq` 表，也不占用 irq_desc——它们是"无 desc 中断"。

**arm64：handle_arch_irq 函数指针**

arm64 没有查表式 IDT，而是全局函数指针 `handle_arch_irq`，GIC 驱动初始化时 `set_handle_irq(gic_handle_irq)` 注册（`arch/arm64/kernel/irq.c`）。GICv3 的处理在 `gic_handle_irq()`（`drivers/irqchip/irq-gic-v3.c`）：读 `ICC_IAR1_EL1` 取得 INTID（这一读本身就是 ack，硬件将中断置 active），`gic_complete_ack()` 写 `ICC_EOIR1_EL1`（EOI-deactive，GICv3 默认 EOI 模式即 drop priority + deactivate），然后 `generic_handle_domain_irq(gic_data.domain, irqnr)` 做 hwirq→virq 翻译并调 flow handler。若 `generic_handle_domain_irq()` 返回非 0（无映射），打 WARN 并 `gic_deactivate_unhandled()`。

**进入中断上下文：`irq_enter_rcu()`**

```c
// include/linux/hardirq.h (v6.6)
#define __irq_enter_raw()                     \
	do {                                      \
		preempt_count_add(HARDIRQ_OFFSET);    \
		lockdep_hardirq_enter();              \
	} while (0)

// kernel/softirq.c (v6.6)
void irq_enter_rcu(void)
{
	__irq_enter_raw();
	if (tick_nohz_full_cpu(smp_processor_id()) ||
	    (is_idle_task(current) && (irq_count() == HARDIRQ_OFFSET)))
		tick_irq_enter();          /* NO_HZ_FULL / idle: 补 jiffies、停/启 tick 交互 */
}
```

`preempt_count_add(HARDIRQ_OFFSET)`（值 `1<<16`）一举多得：`in_hardirq()` 为真、抢占关闭、`might_sleep()` 报警、RCU/lockdep 进入中断上下文记账。注意 x86 在 `irqentry_enter()` 内部已经处理 RCU watching 等项，所以走 `irq_enter_rcu` 而非 `irq_enter`（后者多一次 `ct_irq_enter()`）。

### ⚙️ 三个 flow handler 的对决

flow handler 的职责：在正确的时机调 chip 回调、处理"中断又来了"的竞态、调 `handle_irq_event()`。三个主角的差异本质是**硬件触发语义**。

#### `handle_level_irq` —— 电平：先闷住再说话

```c
// kernel/irq/chip.c (v6.6, 原文节选)
void handle_level_irq(struct irq_desc *desc)
{
	raw_spin_lock(&desc->lock);
	mask_ack_irq(desc);                       /* ① 立即 mask+ack, 掐断风暴 */

	if (!irq_may_run(desc))
		goto out_unlock;

	desc->istate &= ~(IRQS_REPLAY | IRQS_WAITING);

	if (unlikely(!desc->action || irqd_irq_disabled(&desc->irq_data))) {
		desc->istate |= IRQS_PENDING;     /* ② 没人处理: 记 pending 保持 masked */
		goto out_unlock;
	}

	kstat_incr_irqs_this_cpu(desc);
	handle_irq_event(desc);                   /* ③ 执行 handler (不持 desc->lock) */

	cond_unmask_irq(desc);                    /* ④ 条件 unmask */

out_unlock:
	raw_spin_unlock(&desc->lock);
}
```

电平语义：**线还拉着，unmask 必须等设备 deassert**。所以一进来就 `mask_ack_irq()`（优先 `chip->irq_mask_ack`，否则 `mask+ack` 两步）把源闷住；handler 执行中把设备的状态寄存器清掉，线落下后 `cond_unmask_irq()` 才放行。`cond_unmask_irq()` 的"条件"：

```c
// kernel/irq/chip.c (v6.6)
static void cond_unmask_irq(struct irq_desc *desc)
{
	if (!irqd_irq_disabled(&desc->irq_data) &&
	    irqd_irq_masked(&desc->irq_data) && !desc->threads_oneshot)
		unmask_irq(desc);
}
```

第三个条件是 oneshot：handler 若返回 `IRQ_WAKE_THREAD`，唤醒的线程还没跑完（设备可能还没真正清中断），`threads_oneshot` 非零则继续闷着，等线程 `irq_finalize_oneshot()` 清位后再 unmask（第 6 章）。

**电平中断的"丢失"问题不存在**：只要线拉着，unmask 后立刻再来一次，天然不丢。代价是 handler 若忘了清设备中断源，unmask 马上再进——风暴。

#### `handle_edge_irq` —— 边沿：ack 后边跑边收

```c
// kernel/irq/chip.c (v6.6, 原文节选)
void handle_edge_irq(struct irq_desc *desc)
{
	raw_spin_lock(&desc->lock);

	desc->istate &= ~(IRQS_REPLAY | IRQS_WAITING);

	if (!irq_may_run(desc)) {
		desc->istate |= IRQS_PENDING;
		mask_ack_irq(desc);               /* 被禁止运行(迁移中): 闷住记 pending */
		goto out_unlock;
	}

	if (irqd_irq_disabled(&desc->irq_data) || !desc->action) {
		desc->istate |= IRQS_PENDING;
		mask_ack_irq(desc);               /* 无 action 或被禁: 同上 */
		goto out_unlock;
	}

	kstat_incr_irqs_this_cpu(desc);

	desc->irq_data.chip->irq_ack(&desc->irq_data);   /* ① 只 ack, 不 mask */

	do {
		if (unlikely(!desc->action)) {
			mask_irq(desc);
			goto out_unlock;
		}
		/* ② 上轮循环中被 mask 过(因为又来中断而 action 处理慢?) → 放开 */
		if (unlikely(desc->istate & IRQS_PENDING)) {
			if (!irqd_irq_disabled(&desc->irq_data) &&
			    irqd_irq_masked(&desc->irq_data))
				unmask_irq(desc);
		}

		handle_irq_event(desc);           /* ③ 执行 handler */

	} while ((desc->istate & IRQS_PENDING) &&   /* ④ handler 期间又来边沿: 继续收 */
		 !irqd_irq_disabled(&desc->irq_data));

out_unlock:
	raw_spin_unlock(&desc->lock);
}
```

边沿语义：**脉冲是瞬时的，ack 之后下一个边沿还能被硬件记下**。所以 ack（不 mask），handler 跑期间再来的中断由谁记录？分三种情况：

1. 控制器有 pending 位：硬件记下，软件置 `IRQS_PENDING`（`irqd_set` 路径由 genirq 在 `check_irq_resend`/`note_interrupt` 相关路径维护——具体地，`handle_irq_event()` 清 pending 前若又触发，flow 侧重新置位）；
2. 被禁/无 action 时只能 `mask_ack` 把后续边沿挡在门外并置 `IRQS_PENDING`，等 enable/注册后由 `check_irq_resend()` **软件重发**（写 `irq_retrigger` 或 `IRQS_REPLAY` 标记）；
3. do-while 循环兜底：handler 返回后若 `IRQS_PENDING` 仍置位且未 disabled，直接再跑一轮，把积压的边沿一口气收完。

**边沿的丢失窗口**：如果硬件没有 per-source pending 位（老式 PIC），"ack 之后、handler 期间"再来一个边沿，控制器可能无法区分"同一个还没 ack 的脉冲"和"第二个脉冲"——这就丢了。genirq 的对策是尽量缩短窗口（ack 后立即跑 handler）、必要时 mask_ack+软件 resend。

#### `handle_fasteoi_irq` —— 透明控制器：一句话 EOI

```c
// kernel/irq/chip.c (v6.6, 原文节选)
void handle_fasteoi_irq(struct irq_desc *desc)
{
	struct irq_chip *chip = desc->irq_data.chip;

	raw_spin_lock(&desc->lock);

	if (!irq_may_run(desc)) {
		if (irqd_needs_resend_when_in_progress(&desc->irq_data))
			desc->istate |= IRQS_PENDING;
		goto out;
	}

	desc->istate &= ~(IRQS_REPLAY | IRQS_WAITING);

	if (unlikely(!desc->action || irqd_irq_disabled(&desc->irq_data))) {
		desc->istate |= IRQS_PENDING;
		mask_irq(desc);
		goto out;
	}

	kstat_incr_irqs_this_cpu(desc);
	if (desc->istate & IRQS_ONESHOT)
		mask_irq(desc);                   /* oneshot: 唤线程前先 mask */

	handle_irq_event(desc);

	cond_unmask_eoi_irq(desc, chip);        /* 正常路径只在最后 eoi 一次 */

	if (unlikely(desc->istate & IRQS_PENDING))
		check_irq_resend(desc, false);   /* 迁移竞态补发 */

out:
	raw_spin_unlock(&desc->lock);
}
```

GICv3 这类控制器在硬件里维护 per-interrupt 的 pending/active 状态机（读 IAR 即 ack，同源不会重复投递，直到 EOI），所以软件流控只需要在**结尾**调一次 `chip->irq_eoi`。注意结尾的 `check_irq_resend`：亲和性迁移竞态下（旧 CPU 还在处理，新 CPU 已经收到同一个中断），`IRQD_RESEND_WHEN_IN_PROGRESS` 的中断需要补发，这是 5.x 加的修复。

三个 handler 的对比总结：

| 维度 | handle_level_irq | handle_edge_irq | handle_fasteoi_irq |
| :--- | :--- | :--- | :--- |
| 入口动作 | mask_ack（先闷住） | ack（先放行记录） | 无（架构入口已 ack IAR） |
| handler 中断源再触发 | 硬件线仍有效，unmask 后再来 | IRQS_PENDING + do-while 收割 | 硬件 pending/active 状态机 |
| 出口动作 | cond_unmask_irq | （循环自然退出） | cond_unmask_eoi_irq（eoi） |
| 无 action/被禁时 | 置 pending，保持 masked | mask_ack + pending | mask + pending（不 eoi？—— eoi 由 cond 分支决定，此处直接 out 跳过 eoi，等待 resend） |
| 风暴防护 | mask 直到 handler 清设备 | 天然边沿不重发 | 硬件状态机 |
| oneshot 支持 | threads_oneshot 位图 | 同左 + 循环内 unmask 推迟 | IRQS_ONESHOT 显式 mask |

另外两个简化版：`handle_simple_irq()`（无任何 chip 流控编排，直接 `handle_irq_event`，用于 irq_sim/级联已 ack 的子中断）；`handle_percpu_irq()`（`ack → handle_irq_event_percpu → eoi`，全程不拿 `desc->lock`，因为 per-CPU 中断天然无跨核并发）。入口若 desc 没有 action 或 chip 没有对应回调，`handle_bad_irq()` 兜底（计数 + 打印 " nobody cared"）。

### 🎬 handle_irq_event：action 链的执行

```c
// kernel/irq/handle.c (v6.6, 原文节选)
irqreturn_t handle_irq_event(struct irq_desc *desc)
{
	irqreturn_t ret;

	desc->istate &= ~IRQS_PENDING;
	irqd_set(&desc->irq_data, IRQD_IRQ_INPROGRESS);
	raw_spin_unlock(&desc->lock);          /* handler 不持锁执行! */

	ret = handle_irq_event_percpu(desc);

	raw_spin_lock(&desc->lock);
	irqd_clear(&desc->irq_data, IRQD_IRQ_INPROGRESS);
	return ret;
}

irqreturn_t __handle_irq_event_percpu(struct irq_desc *desc)
{
	irqreturn_t retval = IRQ_NONE;
	unsigned int irq = desc->irq_data.irq;

	record_irq_time(desc);                 /* CONFIG_IRQ_TIMINGS: 记录时间戳 */

	for_each_action_of_desc(desc, action) {
		irqreturn_t res;

		trace_irq_handler_entry(irq, action);      /* tracepoint irq:irq_handler_entry */
		res = action->handler(irq, action->dev_id);
		trace_irq_handler_exit(irq, action, res);

		if (WARN_ONCE(!irqs_disabled(),
			      "irq %u handler %pS enabled interrupts\n", irq, action->handler))
			local_irq_disable();

		switch (res) {
		case IRQ_WAKE_THREAD:
			if (unlikely(!action->thread_fn)) {
				warn_no_thread(irq, action);  /* 返回 WAKE_THREAD 却没线程 */
				break;
			}
			__irq_wake_thread(desc, action);      /* 唤醒 irq/NN-name 线程 */
			break;
		default:
			break;
		}
		retval |= res;                       /* 共享中断: 任一 HANDLED 即整体 HANDLED */
	}
	return retval;
}

irqreturn_t handle_irq_event_percpu(struct irq_desc *desc)
{
	irqreturn_t retval = __handle_irq_event_percpu(desc);

	add_interrupt_randomness(desc->irq_data.irq);   /* 喂给熵池(可作为抖动源) */

	if (!irq_settings_no_debug(desc))
		note_interrupt(desc, retval);       /* spurious 检测入口 */
	return retval;
}
```

细节：
- **retval 的位或**：`IRQ_HANDLED=1`、`IRQ_WAKE_THREAD=2`。共享中断上所有 action 都跑一遍，只要有一个返回 HANDLED 就不算 spurious；全部返回 NONE 才计入 unhandled。
- **`__irq_wake_thread()`**（handle.c）：置 `IRQTF_RUNTHREAD`、`desc->threads_oneshot |= action->thread_mask`（oneshot 续闷）、`atomic_inc(&desc->threads_active)`、`wake_up_process(action->thread)`。唤醒发生在**持 desc->lock** 的 flow handler 里（handle_irq_event 外层），线程侧 `irq_wait_for_interrupt()` 用 `test_and_clear_bit(IRQTF_RUNTHREAD)` 抢标记，实现硬中断到线程的无缝交接（第 6 章展开完整协议）。
- `record_irq_time` 与 `add_interrupt_randomness` 都是可选编译项，热路径尽量无开销。

### 🏁 中断退出：irq_exit_rcu 与软中断派发

```c
// kernel/softirq.c (v6.6, 原文)
static inline void __irq_exit_rcu(void)
{
#ifndef __ARCH_IRQ_EXIT_IRQS_DISABLED
	local_irq_disable();
#else
	lockdep_assert_irqs_disabled();
#endif
	account_hardirq_exit(current);
	preempt_count_sub(HARDIRQ_OFFSET);          /* 离开 hardirq 上下文 */
	if (!in_interrupt() && local_softirq_pending())
		invoke_softirq();                       /* 关键分支 */

	tick_irq_exit();
}
```

`!in_interrupt()` 的含义：此刻 HARDIRQ_OFFSET 已减掉，若再无 softirq/bh 嵌套（`SOFTIRQ_OFFSET` 等也为 0），说明即将返回"干净"的进程或 idle 上下文，这时才允许就地跑软中断——**不能在硬中断嵌套软中断再嵌套硬中断的怪状态里跑**，也不能在 `local_bh_disable()` 临界区内跑（那是别人明确要求延后的区域）。

`invoke_softirq()` 在非 RT 内核的实现：

```c
// kernel/softirq.c (v6.6, 非 RT 分支)
static inline void invoke_softirq(void)
{
	if (!force_irqthreads() || !__this_cpu_read(ksoftirqd)) {
#ifdef CONFIG_HAVE_IRQ_EXIT_ON_IRQ_STACK
		__do_softirq();        /* IRQ 栈上就地执行(栈几乎已空) */
#else
		do_softirq_own_stack(); /* 否则切到独立 softirq 栈执行 */
#endif
	} else {
		wakeup_softirqd();     /* force_irqthreads(threadirqs): 全交 ksoftirqd */
	}
}
```

（x86_64 定义了 `HAVE_IRQ_EXIT_ON_IRQ_STACK`；arm64 无此配置，走 `do_softirq_own_stack()` → `call_on_irq_stack`。）

**PREEMPT_RT 的差异**（softirq.c 的 RT 分支）：`invoke_softirq()` 被简化为——

```c
// kernel/softirq.c (v6.6, PREEMPT_RT 分支)
static inline bool should_wake_ksoftirqd(void)
{
	return !this_cpu_read(softirq_ctrl.cnt);   /* bh 未被禁 */
}
static inline void invoke_softirq(void)
{
	if (should_wake_ksoftirqd())
		wakeup_softirqd();     /* RT: 永不就地执行, 只唤醒 ksoftirqd */
}
```

RT 内核里软中断一律由 per-CPU 的 ksoftirqd 线程执行（可调度、可被实时任务抢占），`__do_softirq()` 只在 ksoftirqd 线程内被调用。这消除了"中断退出路径里长尾软中断推迟最高优先级实时任务"的延迟源，是 RT "硬中断最小化"哲学的一部分（第 6 章）。`__do_softirq()` 的预算机制（2ms/10 轮）见第 5 章。

### 🕵️ spurious 中断检测：note_interrupt 全流程

设备线飘过来的杂散中断、驱动 handler 判断"不是我的"返回 `IRQ_NONE`、固件描述错误导致无主中断——这些都由 `note_interrupt()`（`kernel/irq/spurious.c`）记账：

```c
// kernel/irq/spurious.c (v6.6, 核心逻辑节选)
void note_interrupt(struct irq_desc *desc, irqreturn_t action_ret)
{
	/* (1) 线程化中断的延迟判定: 见下文 SPURIOUS_DEFERRED */
	if (action_ret & IRQ_WAKE_THREAD) { ... }

	if (unlikely(action_ret == IRQ_NONE)) {
		/* (2) 老化: 距上次 unhandled 超 1s 则重新计数,
		 *      避免偶发杂散累积成"末日时钟" */
		if (time_after(jiffies, desc->last_unhandled + HZ/10))
			desc->irqs_unhandled = 1;
		else
			desc->irqs_unhandled++;
		desc->last_unhandled = jiffies;
	}
	...
	/* (3) 每 100000 次触发检查一次 */
	desc->irq_count++;
	if (likely(desc->irq_count < 100000))
		return;

	desc->irq_count = 0;
	if (unlikely(desc->irqs_unhandled > 99900)) {   /* 99.9% 无人处理 */
		__report_bad_irq(desc, action_ret);          /* 打印 action 链与寄存器状态 */
		printk(KERN_EMERG "Disabling IRQ #%d\n", irq);
		desc->istate |= IRQS_SPURIOUS_DISABLED;
		desc->depth++;
		irq_disable(desc);                           /* 杀掉这条 IRQ */

		mod_timer(&poll_spurious_irq_timer,
			  jiffies + POLL_SPURIOUS_IRQ_INTERVAL); /* 启动轮询定时器 */
	}
	desc->irqs_unhandled = 0;
}
```

机制要点：
- **阈值 100000/99900**：10 万次触发里 99.9% 无人认领才判死。为什么这么保守？共享线上一个正常设备 + 一个哑设备，哑设备的每次触发都 IRQ_NONE，但正常设备的中断会把 `irqs_unhandled` 的累计节奏打乱；只有"几乎全是 NONE"才说明线真的没有合法主人。
- **老化窗口 HZ/10**：一次孤立的杂散（总线异步毛刺）后重置计数，不让健康系统攒出 doom 计数。
- **线程化的延迟判定（SPURIOUS_DEFERRED）**：handler 只返回 `IRQ_WAKE_THREAD` 时，到底有没有人处理要等 `thread_fn` 的返回值——`irq_thread_fn()` 里 `IRQ_HANDLED` 会 `atomic_inc(&desc->threads_handled)`。硬中断侧用 bit31 标记"延迟检测中"，下一次硬中断比较 `threads_handled` 是否变化，变了视同 HANDLED，没变视同 NONE。避免对每个正常线程化中断误报。
- **杀掉之后：轮询兜底**。`poll_spurious_irqs`（HZ/10 周期定时器）会对被禁中断调用 `try_one_irq()` 轮询所有 action——服务于著名的侧漏场景：**中断线被错误路由到别的 IRQ（misrouted）**，`try_one_irq` 遍历**所有** IRQ 的 action 去试探谁认领（`irqpoll` 内核启动参数开启主动模式），找到真主后可人工修复。boot 参数 `noirqdebug` 可整体关闭该机制（`noirqdebug_setup`），`irqfixup`/`irqpoll` 调整激进度。
- 观测：`/proc/irq/N/spurious` 显示 `count`（ irq_count 累计）与 `unhandled`；dmesg 的 "irq N: nobody cared (try booting with the 'irqpoll' option)" 即 `__report_bad_irq` 输出。

### 💸 各阶段开销分析

把一次"空转"外设中断（handler 什么都不做）在 x86_64 上的开销拆开（数量级，依硬件而异）：

| 阶段 | 主要开销 | 典型量级 |
| :--- | :--- | :--- |
| 硬件投递 + CPU 入口 | 保存寄存器、关中断、IDT 跳转、（x2APIC 无 EOI 广播写） | ~100–300 cycles |
| entry 宏 + 切 IRQ 栈 | `irqentry_enter`、`run_irq_on_irqstack_cond` | ~50–150 cycles |
| `irq_enter_rcu` | preempt_count/lockdep（关 CONFIG 时显著小） | ~20–100 cycles |
| vector_irq 查表 | per-CPU 数组读，**大概率 cache hit** | ~10 cycles |
| flow handler | desc->lock（**跨核中断同线才竞争**）+ chip 回调 | IO-APIC 远端寄存器写可达 **~1µs**（慢速 MMIO）；GIC 内存表同类 |
| `handle_irq_event` | 解锁/加锁、IRQD 状态翻转、tracepoint（关闭时近零） | ~50 cycles |
| 驱动 handler | 一次设备状态寄存器 MMIO 读（**可能上 µs**，PCIe 往返） | 差异主体 |
| 退出 + EOI | x2APIC：MSR 写（无广播）；legacy APIC：物理写可能**总线广播** | x2APIC ~100 cycles；legacy 可达 µs 级 |
| irq_exit → softirq 检查 | 读 `__softirq_pending`（per-CPU，常 0） | ~10 cycles |
| IRET/异常返回 | 恢复寄存器、可能重放被屏蔽事件 | ~100–300 cycles |

放大器效应：
1. **cache/TLB miss**：中断打断的进程现场被污染——handler 走的代码/数据（desc、chip_data、驱动结构）冷的话每 miss 上百 cycles；中断频繁时对被打断任务的间接代价常超中断本身（ 这是"中断亲和性配对"的动机，第 6 章）。
2. **IPI 的连带开销**：`smp_call_function` 类 IPI（CAL）会让**所有**目标 CPU 各进一次中断，TLB shootdown 在大核数机器上是著名的可扩展性瓶颈（与 genirq 无关但同走 IDT 入口）。
3. **中断风暴（thundering herd）**：电平线未清 + 无条件 unmask → 同一中断背靠背重入，CPU 100% sys；genirq 的 mask/oneshot 与 NAPI/irq_poll 等机制都是对此的防御。
4. **x2APIC 与 posted interrupt**：x2APIC 把 EOI 从广播写变 MSR 写；VT-d posted interrupt 把 IPI 投递合并进 APIC。硬件演进方向就是把上表中的每一行变便宜。

### 💭 思考题

1. `handle_level_irq` 里 handler 执行期间（已 mask），设备第二次拉线会发生什么？`handle_edge_irq` 同场景下呢？
   <details><summary>提示</summary>电平：线一直有效，状态在"拉着的线"上，unmask 后必然再触发，不丢；边沿：脉冲过去就没了，若控制器有 pending 位则记下，否则可能丢——所以 edge 依赖 IRQS_PENDING/REPLAY 补救。</details>
2. 为什么 `handle_irq_event()` 执行 action 前要先 `raw_spin_unlock(&desc->lock)`？持锁跑 handler 会破坏什么？
   <details><summary>提示</summary>handler 可能耗时；且线程唤醒路径（`__irq_wake_thread`）要求与 `irq_finalize_oneshot` 的锁协议（先持锁改 threads_oneshot）；持锁跑会把锁竞争放大到整个 action 执行期。</details>
3. `handle_fasteoi_irq` 中"无 action"分支为什么**不 EOI** 就直接退出？不 EOI 的话 GIC 不会堵住后续中断吗？
   <details><summary>提示</summary>置 IRQS_PENDING+mask 后等 action 注册/check_irq_resend；GIC 的同源重投递被 pending/active 状态机管着，而 mask 已挡住；EOI 时机由 cond_unmask_eoi_irq 分支决定，直接 eoi 反而可能让风暴进门。</details>
4. `irq_exit_rcu` 里 `preempt_count_sub(HARDIRQ_OFFSET)` 在 `invoke_softirq()` **之前**执行。若反过来（先跑 softirq 再减），`in_interrupt()` 判断会怎样出错？
   <details><summary>提示</summary>softirq 期待的是"半开上下文"：in_hardirq 已为假但 SOFTIRQ_OFFSET 尚未加（__do_softirq 自己再加）；顺序颠倒会让 in_interrupt() 恒真，软中断永远不被就地执行。</details>
5. 100000/99900 的 spurious 阈值为什么不用时间窗口（如"1 秒内 99% NONE"）？
   <details><summary>提示</summary>中断频率差异极大（1Hz 的按键 vs 100kHz 的网卡）；按次数计数天然归一化。HZ/10 的 last_unhandled 老化窗口已处理偶发毛刺。</details>
6. 一次 PCIe MSI 中断从设备 Memory Write 到 `action->handler()` 第一条指令，列出至少 5 个可能产生 µs 级延迟的环节。
   <details><summary>提示</summary>Root Complex 路由、IOMMU/ITS 硬件表遍历（LPI）、CPU 正在跑不可中断区（关中断窗口）、desc/chip 冷 cache、handler 第一次 MMIO 读的 PCIe 往返。</details>
