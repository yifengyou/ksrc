# 内核启动总览：从上电到 start_kernel

操作系统的启动本质上是一个"自举"（bootstrap）过程：MMU 关闭时如何执行需要地址翻译的代码？没有内存分配器时如何分配内存？没有调度器时如何"创建"第一个进程？Linux 6.6 的启动代码用一条精心编排的接力链回答了这些问题。本章以 Linux 6.6 为基准，画出从上电到 `start_kernel()` 的全景图，并沿 x86_64 与 arm64 两条路径逐段展开。

### 🎯 本章目标

* 建立"固件 → bootloader → 内核自解压 → 内核入口 → start_kernel → init"的全局时间线；
* 沿 x86_64 路径走通：实模式 setup → 保护模式 → 长模式 → 解压 → `.head.text` → `start_kernel`；
* 沿 arm64 路径走通：`primary_entry` → 临时恒等映射 → 开 MMU → KASLR → `__primary_switched` → `start_kernel`；
* 理解引导协议（boot_params / DTB）与 earlycon 的最早输出手段。

## 1. 全景图：启动的分层时序

```c
     电源/复位
        │
        ▼
┌───────────────────────────────────────────────────────────────┐
│ 固件层 (x86: BIOS/UEFI; arm64: ATF/UEFI 或板级 bootloader)      │
│  - 内存初始化、SPI/存储扫描、装载 bootloader                     │
└───────────────────────────┬───────────────────────────────────┘
                            ▼
┌───────────────────────────────────────────────────────────────┐
│ bootloader 层 (GRUB2 / U-Boot / systemd-boot ...)              │
│  - 读取内核镜像 + initrd，构造引导协议数据（boot_params / DTB）  │
│  - x86: 跳到 bzImage 的实模式 setup 代码                        │
│  - arm64: 跳到 Image 的 primary_entry，x0 = DTB 物理地址        │
└───────────────────────────┬───────────────────────────────────┘
                            ▼
┌───────────────────────────────────────────────────────────────┐
│ 内核自解压层 (仅压缩内核)                                        │
│  - x86_64: arch/x86/boot/compressed/                           │
│      startup_32 → startup_64 → extract_kernel → 解压/KASLR      │
│  - arm64: 通常无此层（Image 可不压缩，KASLR 由 head.S 完成）      │
└───────────────────────────┬───────────────────────────────────┘
                            ▼
┌───────────────────────────────────────────────────────────────┐
│ 内核入口层 (arch/*/kernel/head*.S)                              │
│  - 建立（或修正）早期页表、打开 MMU、进入内核虚拟地址             │
│  - 修正 RIP 相对/重定位、设置初始栈、early IDT                    │
└───────────────────────────┬───────────────────────────────────┘
                            ▼
┌───────────────────────────────────────────────────────────────┐
│ start_kernel() → rest_init()  ← init/main.c（第 2、3 章详解）   │
│  setup_arch → percpu → mm → sched → irq → time → console ...   │
│  → pid 0 (idle) + pid 1 (kernel_init) + pid 2 (kthreadd)       │
│  → initcall → 用户态 init/systemd                               │
└───────────────────────────────────────────────────────────────┘
```

从分层视角看，每一层只做"让下一层能跑起来"的最小工作：

| 层 | 执行模式 | 地址空间 | 内存分配手段 |
| :--- | :--- | :--- | :--- |
| 固件 | 固件自己的模式 | 物理地址 | 固件内部 |
| bootloader | 实模式 / 固件提供的环境 | 物理地址 | bootloader 自己的堆 |
| 自解压层 / 内核入口 | 实模式 → 长模式（MMU 逐步打开） | 物理地址 + 临时/早期页表 → 内核虚拟地址 | 内嵌 heap、`.brk`、`early_dynamic_pgts` |
| start_kernel | 虚拟地址、关中断、单 CPU | 内核页表 | memblock → buddy → slab |

## 2. x86_64 完整路径

### 2.1 bzImage 的双头结构：一个文件，两个入口

bzImage 实际上是两部分拼接而成：

```text
bzImage = [ setup（实模式代码，arch/x86/boot/） ]
        + [ 压缩的 vmlinux（arch/x86/boot/compressed/） ]
```

`arch/x86/boot/header.S` 的开头是一段刻意设计的双重身份头：

```asm
/* arch/x86/boot/header.S */
	.code16
	.section ".bstext", "ax"
#ifdef CONFIG_EFI_STUB
	# "MZ", MS-DOS header
	.word	MZ_MAGIC          /* 0x5A4D：UEFI 把 bzImage 当 PE 应用加载 */
	.org	0x38
	.long	LINUX_PE_MAGIC    /* "LR" */
	.long	pe_header         /* PE 头偏移 */
pe_header:
	.long	PE_MAGIC
    ...                         /* COFF/optional header + 节表 */
#endif
	.section ".header", "a"
hdr:
	.byte setup_sects - 1     /* setup 占用的扇区数 */
	.word 0xAA55              /* boot_flag：MBR 签名 */
	.ascii "HdrS"             /* Linux 引导协议魔数 */
	.word 0x020f              /* header 版本 */
...
_start:                          /* 偏移 0x200：实模式入口 */
	.byte 0xeb                /* 2 字节短跳转 */
	.byte start_of_setup-1f   /* 跳到 start_of_setup */
```

* 对 **legacy BIOS bootloader / GRUB**：这是一个"老式启动扇区"，从 `_start`（偏移 0x200）进入实模式代码；GRUB 读取 `HdrS` 与版本号，把 setup 加载到低内存、压缩内核加载到 `pref_address`（通常 0x1000000）后跳入；
* 对 **UEFI 固件**：这是一个 PE/COFF 可执行文件（`MZ` 头 + PE 头，入口为 `efi_pe_entry`），由 EFI stub 直接以 UEFI 应用身份运行。

`hdr` 中几个关键字段（完整定义见 `Documentation/arch/x86/boot.rst`）：

| 字段 | 含义 | 内核中的消费者 |
| :--- | :--- | :--- |
| `code32_start` | 保护模式入口（默认 0x100000） | `go_to_protected_mode()` |
| `cmd_line_ptr` | 命令行指针 | `copy_bootdata()` |
| `ramdisk_image/size` | initrd 位置 | `reserve_initrd()` |
| `payload_offset/length` | 压缩负载在 bzImage 内的偏移/长度 | `extract_kernel()` |
| `setup_data` | `struct setup_data` 链表头（EFI、PCIe ROM 等附加数据） | `parse_setup_data()` |
| `kernel_alignment` | KASLR/重定位对齐要求（`CONFIG_PHYSICAL_ALIGN`，2M） | `startup_32/64` |

### 2.2 实模式 setup：`arch/x86/boot/main.c`

从 `start_of_setup`（header.S 末尾：整理段寄存器、清 BSS、建堆栈）跳入 C 代码 `main()`：

```c
/* arch/x86/boot/main.c */
void main(void)
{
	init_default_io_ops();

	/* First, copy the boot header into the "zeropage" */
	copy_boot_params();       /* hdr → boot_params，兼容老式命令行协议 */

	console_init();           /* arch/x86/boot/early_serial_console.c 等 */
	init_heap();              /* CAN_USE_HEAP → heap_end_ptr */

	validate_cpu();           /* arch/x86/boot/cpu.c：CPU 是否满足要求 */
	set_bios_mode();          /* int 0x15 ax=0xec00：告知将进入长模式 */
	detect_memory();          /* arch/x86/boot/memory.c：INT 0x15 E820/E801/88
	                             → boot_params.e820_table */
	keyboard_init();          /* 其余 BIOS 查询：IST/APM/EDD、set_video() */
	query_ist();
	query_apm_bios();
	query_edd();
	set_video();

	go_to_protected_mode();   /* arch/x86/boot/pm.c */
}
```

这一阶段的两大产出：**`struct boot_params`（俗称 zero page）**——包括 E820 内存表、命令行、EFI 信息（若由 EFI stub 进入则由 stub 填好）；以及屏幕上的早期输出（`earlyprintk=serial,ttyS0` 一类的早期 console）。实模式的谢幕由 `go_to_protected_mode()`（`arch/x86/boot/pm.c`）完成：

```c
/* arch/x86/boot/pm.c */
void go_to_protected_mode(void)
{
	realmode_switch_hook();   /* 关中断，调用 realmode_swtch 钩子 */
	enable_a20();             /* 打开 A20 地址线 */
	reset_coprocessor();
	mask_all_interrupts();    /* 屏蔽 PIC 全部中断 */
	setup_idt();              /* 空 IDT */
	setup_gdt();
	protected_mode_jump(boot_params.hdr.code32_start,
			    (u32)&boot_params + (ds() << 4));
}
```

`protected_mode_jump`（`arch/x86/boot/pmjump.S`）置 `CR0.PE`，以 32 位保护模式跳到 `code32_start` —— 即压缩内核的 `startup_32`，并把 `boot_params` 物理地址放进了 `%esi`（这一寄存器约定贯穿整个 x86 早期启动：直到 `startup_64` 依然用 `%rsi` 传递它）。

### 2.3 解压器：`arch/x86/boot/compressed/head_64.S`

**`startup_32`（32 位入口，偏移 0）**——对 64 位内核，这是从实模式 setup 走过来的必经之路：

```asm
/* arch/x86/boot/compressed/head_64.S */
SYM_FUNC_START(startup_32)
	cld
	cli
	leal	(BP_scratch+4)(%esi), %esp
	call	1f
1:	popl	%ebp                  /* 经典技巧：call/pop 拿到运行时地址 */
	subl	$ rva(1b), %ebp       /* %ebp = 实际加载地址 - 链接地址（delta）*/
	...
	lgdt	(%eax)                /* 加载 32 位可用的 64 位段描述符 GDT */
	...
	call	verify_cpu             /* 确认 CPU 支持 long mode */
	/* 对齐到 kernel_alignment，得到解压目标 rbp */
	/* enable PAE：cr4.PAE = 1 */
	/* 建立早期 4G 引导页表（pgtable）：L4→L3→L2，2MB 大页 */
	movl	%eax, %cr3
	/* EFER.LME = 1 开启长模式 */
	...
	lret                            /* 跳入 64 位 startup_64 */
```

早期 4G 页表以 `pgtable`（`BOOT_INIT_PGT_SIZE` 区间）搭出：一个 L4 表、一个 L3 表（4 个表项）与 4 页连续的 L2 表共 2048 个 2MB 大页项（`0x183` = P|RW|A|PSE，4×512×2MB = 4G），同时兼容 SEV 内存加密掩码。

**`startup_64`（64 位入口，偏移 0x200，ABI 不可变）**——64 位 EFI/bootloader 可直接进入：

```asm
SYM_CODE_START(startup_64)
	cld
	cli
	/* %rbp = 解压目标（对齐 2M 的加载地址）；
	   %rbx = rbp + BP_init_size - _end（自搬迁目标） */
	leaq	rva(boot_stack_end)(%rbx), %rsp
	/* 4↔5 级分页切换：经低内存 trampoline_32bit_src 关再开 CR4.LA57 */
	...
	/* 将解压器自身搬到 %rbx 处，然后跳到 .Lrelocated */
	leaq	rva(.Lrelocated)(%rbx), %rax
	jmp	*%rax
```

**`.Lrelocated`** 是解压器的"主战场"：

```asm
SYM_FUNC_START_LOCAL_NOALIGN(.Lrelocated)
	/* 清 BSS */
	call	load_stage2_idt            /* SEV-ES #VC 处理 */
	movq	%r15, %rdi
	call	initialize_identity_maps    /* kaslr.c：解压器自己的动态页表 */
	movq	%r15, %rdi
	movq	%rbp, %rsi
	call	extract_kernel             /* 返回值 %rax = 解压后内核入口 */
	movq	%r15, %rsi                 /* %rsi = boot_params，再次交接 */
	jmp	*%rax
```

### 2.4 `extract_kernel()`：解压 + KASLR

```c
/* arch/x86/boot/compressed/misc.c */
asmlinkage __visible void *extract_kernel(void *rmode, unsigned char *output)
{
	boot_params = rmode;
	...
	console_init();                 /* "early console in extract_kernel" */
	boot_params->acpi_rsdp_addr = get_rsdp_addr();  /* 为内核提前找 RSDP */

	needed_size = max_t(unsigned long, output_len, kernel_total_size);

	choose_random_location((unsigned long)input_data, input_len,
			       (unsigned long *)&output, needed_size,
			       &virt_addr);  /* KASLR：物理与虚拟偏移 */

	...                              /* 对齐/范围检查 */
	entry_offset = decompress_kernel(output, virt_addr, error);
	/* decompress_kernel → __decompress：按 CONFIG_KERNEL_GZIP/LZ4/XZ/ZSTD...
	   解压到 output；随后 handle_relocations() 按 R_X86_64_RELATIVE
	   把静态链接的绝对地址改成"output + 偏移"（重定位内核镜像） */
	cleanup_exception_handling();
	return output + entry_offset;
}
```

两个深挖点：

* **KASLR（`kaslr.c: choose_random_location()`）**：物理地址随机化在可用 E820 区间里选一个 2M 对齐的位置（`process_e820_entries()` + `find_random_phys_addr()`）；虚拟地址随机化则在 `KERNEL_IMAGE_SIZE`（512M/1G）范围内平移 `__START_KERNEL_map` 段。成功随机化后置 `boot_params.hdr.loadflags` 的 `KASLR_FLAG`，内核侧的消费者是 `kernel_randomize_memory()`（物理内存分段随机化，`arch/x86/mm/kaslr.c`）与 panic 时的 `dump_kernel_offset()`。物理与虚拟偏移可以不同——这要求内核自身完全位置无关（PIE 链接 + RELATIVE 重定位）。
* **为什么解压后还要 `handle_relocations()`**：vmlinux 是按 `LOAD_PHYSICAL_ADDR` 静态链接的，解压到别处后，所有绝对地址引用（非 RIP 相对）都要按 `output - LOAD_PHYSICAL_ADDR` 修正。这就是 CONFIG_RELOCATABLE 的全部含义。

### 2.5 内核本体入口：`arch/x86/kernel/head_64.S` 的 `startup_64`

跳转到达时，CPU 处于"长模式 + 解压器的恒等映射页表"，`%rsi` = `boot_params` 物理地址，**仍在物理地址上执行**。

```asm
/* arch/x86/kernel/head_64.S */
SYM_CODE_START_NOALIGN(startup_64)
	mov	%rsi, %r15                       /* 保存 boot_params */
	leaq	(__end_init_task - PTREGS_SIZE)(%rip), %rsp  /* init_task 的栈顶！ */
	...
	call	startup_64_setup_env            /* 切 __KERNEL_CS + 启动 GDT/bringup IDT */
	...
	call	sme_enable                       /* AMD 内存加密 */
	call	verify_cpu
	leaq	_text(%rip), %rdi
	movq	%r15, %rsi
	call	__startup_64                     /* 关键：页表修正，返回 CR3 修饰符 */
	addq	$(early_top_pgt - __START_KERNEL_map), %rax
	/* 以下与 secondary_startup_64 共享：
	   cr4 |= PAE|PGE(+LA57) → cr3 = early_top_pgt → 翻转 PGE 刷 TLB
	   → jmp 到虚拟地址 1: → 设置栈/GSBASE/early_setup_idt
	   → .Ljump_to_C_code: lretq 到 initial_code（x86_64_start_kernel） */
```

`__startup_64()`（`arch/x86/kernel/head64.c`）是早期页表的总装车间：

```c
/* arch/x86/kernel/head64.c（节选） */
unsigned long __head __startup_64(unsigned long physaddr, struct boot_params *bp)
{
	la57 = check_la57_support(physaddr);        /* 5 级分页判定 */

	/* 加载偏移 = 实际物理地址 - 链接假定地址，必须 2M 对齐 */
	load_delta = physaddr - (unsigned long)(_text - __START_KERNEL_map);
	if (load_delta & ~PMD_MASK)
		for (;;);                              /* 不对齐：死循环 */

	/* 修正 early_top_pgt 链上的物理地址（全部 += load_delta）*/
	pgd = fixup_pointer(&early_top_pgt, physaddr);
	...
	pud = fixup_pointer(&level3_kernel_pgt, physaddr);
	pud[510] += load_delta;   /* 内核镜像映射 */
	pud[511] += load_delta;   /* fixmap */

	/* 用 early_dynamic_pgts 搭恒等映射：physaddr..physaddr+内核大小，
	   供切换 CR3 后继续在"物理地址"上执行 */
	...
	/* 修正 level2_kernel_pgt：镜像外清 PRESENT，镜像内 += load_delta */
	...
	*fixup_long(&phys_base, physaddr) += load_delta - sme_get_me_mask();
	return sme_postprocess_startup(bp, pmd);   /* SME: 加密内核镜像 */
}
```

`fixup_pointer(ptr, physaddr)` 是精髓：`__startup_64()` 本身可能被加载到任意物理地址执行，编译器生成的全局变量访问不是 RIP 相对的，所以**每一个**全局指针都要手动加 `load_delta`。这正对应标题里说的"RIP 相对寻址修正"——汇编层用 `%rip` 相对寻址自动免疫重定位，C 层则要手工修正。

### 2.6 `x86_64_start_kernel()`：跨入虚拟世界

`initial_code` 指向的 C 函数在 `arch/x86/kernel/head64.c`：

```c
/* arch/x86/kernel/head64.c（节选，顺序保持原样） */
asmlinkage __visible void __init __noreturn
x86_64_start_kernel(char *real_mode_data)
{
	cr4_init_shadow();
	reset_early_page_tables();   /* 写 cr3 = early_top_pgt，杀死恒等映射蹦床 */
	clear_bss();
	clear_page(init_top_pgt);    /* 最终页表先清 PGD（KASAN 依赖此页） */
	sme_early_init();            /* SME 加密掩码 → early_pmd_flags */
	kasan_early_init();
	__native_tlb_flush_global(this_cpu_read(cpu_tlbstate.cr4));
	idt_setup_early_handler();   /* bringup IDT：早期 #PF/#VC 处理 */
	tdx_early_init();
	copy_bootdata(__va(real_mode_data));  /* boot_params + 命令行 → boot_command_line */
	load_ucode_bsp();            /* BSP 早期微码装载 */
	init_top_pgt[511] = early_top_pgt[511];  /* 高端内核映射接到最终页表 */
	x86_64_start_reservations(real_mode_data);  /* → start_kernel() */
}
```

几个值得咀嚼的细节：

* `reset_early_page_tables()` 清空除第 511 项以外的 `early_top_pgt`，之后任何缺页都由 `do_early_exception() -> early_make_pgtable()` **按需**建立到 `__PAGE_OFFSET` 直接映射区——`early_dynamic_pgts[]` 就是为这些动态下级页表预留的（`EARLY_DYNAMIC_PAGE_TABLES` 个页面，用尽即整体重置）；`copy_bootdata()` 则把 `cmd_line_ptr` 指向的命令行拷入 `boot_command_line[]`（`sanitize_boot_params()` 清洗不合规的旧 bootloader 数据）。
* `load_ucode_bsp()`：微码在如此早的阶段装载（`arch/x86/kernel/cpu/microcode/core.c`），因为后续 `early_cpu_init()` 里的大量 `cpuid` 行为依赖微码版本。
* 从 `start_kernel()` 的视角看，此刻的状态是：**MMU 开启、运行于内核虚拟地址、IRQ/异常仅有最小处理、单一 CPU（BSP）、调度器未初始化、`current` 永远是 `init_task`（pid 0）**。

调用链总结（x86_64）：

```text
GRUB → start_of_setup → main() → go_to_protected_mode()
  → protected_mode_jump() → startup_32(compressed)
  → startup_64(compressed) → .Lrelocated → extract_kernel()
      ├─ choose_random_location()   [KASLR]
      ├─ __decompress()             [解压]
      └─ handle_relocations()       [重定位]
  → startup_64(kernel .head.text)
      ├─ __startup_64()             [早期页表修正]
      └─ x86_64_start_kernel()
           ├─ copy_bootdata() / load_ucode_bsp()
           └─ x86_64_start_reservations() → start_kernel()
```

## 3. arm64 完整路径

### 3.1 Image 头：64 字节的引导协议

arm64 内核镜像（`Image`）开头是一个 64 字节固定头（`arch/arm64/kernel/head.S`）：

```asm
/* arch/arm64/kernel/head.S */
	__HEAD
	efi_signature_nop        /* 特殊 NOP：让 Image 兼容 PE/COFF（EFI stub）*/
	b	primary_entry         /* 偏移 0x04：跳转到内核起点 */
	.quad	0                   /* text_offset：镜像相对 RAM 基址的偏移 */
	le64sym	_kernel_size_le     /* 镜像有效大小 */
	le64sym	_kernel_flags_le    /* 标志位（MTYPE_*，已基本废弃） */
	.quad	0                   /* reserved ×3 */
	.ascii	ARM64_IMAGE_MAGIC   /* "ARM\x64" 魔数 */
	.long	.Lpe_header_offset  /* PE 头偏移（EFI stub 用） */
```

bootloader 的契约（`Documentation/arch/arm64/booting.rst`）非常克制：

* **x0 = DTB（设备树 blob）的物理地址**，x1–x3 必须为 0；
* CPU 处于最高可达异常级（EL2 或 EL1）、MMU 关、D-cache 关、字节序与内核一致；
* 镜像可放在 `PAGE_OFFSET` 对齐的任意 2M（`MIN_KIMG_ALIGN`）对齐物理地址。

若固件走 UEFI 路径，则由 **EFI stub**（`drivers/firmware/efi/libstub/arm64-stub.c`）先以 EFI 应用身份运行：校验镜像、解析 EFI 内存图、装载 DTB/ACPI，最后把控制权交回 `primary_entry`，并保证 x0 指向 DTB。

### 3.2 `primary_entry`：在 MMU 关闭时铺路

```asm
/* arch/arm64/kernel/head.S */
SYM_CODE_START(primary_entry)
	bl	record_mmu_state      /* 记录进入时 MMU 状态（EFI stub 可能已开 MMU）*/
	bl	preserve_boot_args    /* x0..x3 → boot_args[]，x21 = FDT */
	bl	create_idmap          /* 建立覆盖内核镜像的恒等映射 */
	...
0:	mov	x0, x19
	bl	init_kernel_el        /* EL2/EL1 判定与初始化，w0=cpu_boot_mode */
	mov	x20, x0
	...
	bl	__cpu_setup           /* TCR 等系统寄存器，为开 MMU 做准备 */
	b	__primary_switch
```

三个子步骤各有深意：

* **`preserve_boot_args`**：bootloader 传入的 x0..x3 存入 `boot_args[]` 数组（供 `setup_arch()` 末尾校验"x1-x3 非零 = 违反协议"），x0（FDT）另存 x21 贯穿全程。
* **`create_idmap`**：在 `init_idmap_pg_dir` 上建立 **1:1 恒等映射**（VA == PA），覆盖 `_text` 到 `_end + MAX_FDT_SIZE + SWAPPER_BLOCK_SIZE`——不止内核，连 FDT 都一并映射。难点在：**PA 可能超过配置的 VA 位数**（如 39 位 VA 的系统把内核放在超过 512G 的物理地址），此时恒等映射需要临时增加一级翻译（`VA_BITS < 48` 分支，`EXTRA_SHIFT`），这是 arm64 早期页表最精巧的部分。所有映射用 `SWAPPER_RX_MMUFLAGS/RW`（2M block，非全局、可执行性受控），并把 FDT 区域重映射为 RW。
* **`init_kernel_el`**：ARM 上电可能在 EL2（hypervisor 模式）。内核策略：能用 EL2 就配置好 EL2（供 KVM VHE 使用）再降到 EL1，或直接留在 EL2；返回 `BOOT_CPU_MODE_EL1/EL2` 记入 `__boot_cpu_mode`。

### 3.3 `__primary_switch`：打开 MMU → KASLR → 正式内核映射

```asm
/* arch/arm64/kernel/head.S（节选） */
SYM_FUNC_START_LOCAL(__primary_switch)
	adrp	x1, reserved_pg_dir
	adrp	x2, init_idmap_pg_dir
	bl	__enable_mmu          /* TTBR0=恒等映射, TTBR1=空表, SCTLR.M=1 */
	/* CONFIG_RELOCATABLE：x23 = 加载地址 2M 内的错位部分 */
	and	x23, x23, MIN_KIMG_ALIGN - 1
	/* CONFIG_RANDOMIZE_BASE：经 idmap 调用 KASLR（临时栈在页表区之上）*/
	mov	x0, x22                       /* idmap 下的 FDT 地址 */
	mov	sp, init_pg_end
	bl	__pi_kaslr_early_init          /* KASLR：返回随机偏移 */
	and	x24, x0, #SZ_2M - 1           /* 线性映射随机种子 */
	orr	x23, x23, x0                  /* x23 = 内核最终偏移 */
	bl	clear_page_tables              /* 清 init_pg_dir..init_pg_end */
	bl	create_kernel_mapping          /* 建立正式高端内核映射(KIMAGE_VADDR+x23) */
	adrp	x1, init_pg_dir
	load_ttbr1	x1, x1, x2             /* 换 TTBR1 → 内核虚拟地址生效 */
	bl	__relocate_kernel              /* 应用 RELA/RELR 重定位 */
	ldr	x8, =__primary_switched
	adrp	x0, KERNEL_START              /* __pa(KERNEL_START) */
	br	x8                             /* 一去不回 */
```

注意顺序：**先开 MMU（用恒等映射），再做 KASLR**。`__pi_kaslr_early_init`（`arch/arm64/kernel/kaslr.c`，`__pi_` 前缀表示可在 MMU 开启前经恒等映射调用）从 DTB 的 `/chosen/kaslr-seed` 或 EFI RNG 获取熵，在 DRAM 范围内随机选择内核落点，返回 2M 对齐的偏移；随后才 `create_kernel_mapping` 按 `KIMAGE_VADDR + x23` 建立正式映射（`init_pg_dir`，仍是 2M block），`load_ttbr1` 切换后内核正式生活在 `0xffff8xxx...` 的高端地址，`__relocate_kernel` 把 `.rela`/`.relr` 段中的相对重定位应用到新地址。KASLR 的影响还延续到 `setup_arch()`：`arm64_use_ng_mappings = kaslr_requires_kpti()`——有 KASLR 种子的机器会从一开始就用非全局（NG）映射，为 KPTI 铺路。

### 3.4 `__primary_switched`：进入 C 世界的最后一跳

```asm
SYM_FUNC_START_LOCAL(__primary_switched)
	adr_l	x4, init_task
	init_cpu_task x4, x5, x6       /* sp_el0 = &init_task（current！），
	                                 当前栈 = init_task 的 THREAD_SIZE 栈 */
	adr_l	x8, vectors
	msr	vbar_el1, x8             /* 装入正式异常向量表 */
	str_l	x21, __fdt_pointer, x5  /* 保存 FDT 指针 */
	str_l	x4, kimage_voffset, x5  /* kimage_vaddr - __pa(_text)：
	                                 __pa/__va 换算从此可用 */
	mov	x0, x20
	bl	set_cpu_boot_mode_flag
	/* 清 BSS、记录 vabits_actual / memstart_offset_seed */
	...
	bl	early_fdt_map             /* 早期 fixmap 映射 FDT */
	bl	init_feature_override     /* 解析 cpu feature override */
	mov	x0, x20
	bl	finalise_el2              /* 若可能，切换到 VHE */
	bl	start_kernel              /* ！ */
	ASM_BUG()
```

`init_task`（`init/init_task.c`）是静态定义的 0 号进程（comm 为 "swapper"）——arm64 用 `sp_el0` 保存 `current`，`init_cpu_task` 一次完成了"当前任务指针 + 栈 + per-CPU 偏移"三件事。走到 `start_kernel()` 时，arm64 与 x86_64 的世界线合并了。

调用链总结（arm64）：

```text
U-Boot/EFI stub → primary_entry
  ├─ record_mmu_state() → preserve_boot_args() → create_idmap()
  ├─ init_kernel_el() → __cpu_setup()
  └─ __primary_switch()
       ├─ __enable_mmu()                [TTBR0 = 恒等映射]
       ├─ __pi_kaslr_early_init()       [KASLR，CONFIG_RANDOMIZE_BASE]
       ├─ clear_page_tables() → create_kernel_mapping()
       ├─ load_ttbr1(init_pg_dir) → __relocate_kernel()
       └─ __primary_switched()
            └─ start_kernel()
```

## 4. 引导协议与数据交接

### 4.1 x86：boot_params（zero page）

`struct boot_params`（`arch/x86/include/asm/bootparam.h`）是 bootloader 与内核之间唯一的"行李箱"，共 4096 字节：前半是 `hdr`（引导协议头本身），后半是 `screen_info`、`e820_table`、`efi_info`、`acpi_rsdp_addr` 等大块数据。它的旅程：

```text
bootloader 填写 hdr + 部分 → 实模式 main().copy_boot_params() 整理
→ compressed/head_64.S（%rsi/%r15 逐级传递）→ extract_kernel() 增补 RSDP
→ 内核 startup_64（%r15 → x86_64_start_kernel）→ copy_bootdata() 定居
→ setup_arch() 消费（E820/EFI/ACPI/initrd/命令行）
```

`struct setup_data` 链表则允许 bootloader 追加任意类型化数据（EFI 表、PCIe ROM、CET 状态等），`parse_setup_data()` 逐节点解析。

| 字段 | 含义 | 内核中的消费者 |

### 4.2 arm64：DTB 与 ACPI 双轨

arm64 硬件描述有两条腿：

* **DTB（Device Tree Blob）**：`/memory` 节点给出内存布局，`/cpus` 给出 CPU 拓扑与 enable 方法（`psci` / `spin-table`），`/chosen/bootargs` 是命令行、`/chosen/kaslr-seed` 是 KASLR 种子。`setup_arch() -> setup_machine_fdt()` 校验并 memblock_add 内存。
* **ACPI**：UEFI 服务器平台走 MADT/CFGSRAT 描述 CPU/NUMA，DTB 仅保留 EFI 传入的最小 stub。`acpi_boot_table_init()` 解析，`psci_acpi_init()` 取 PSCI 方法。两条腿最终都汇入 memblock 的 memory/reserved 两个列表（详见 mm/memblock 笔记）。

### 4.3 最早的串口输出：earlycon

在 printk 缓冲区与真正的 console 驱动就绪之前，唯一的输出手段是 **earlycon**（`drivers/tty/serial/earlycon.c`）：它以 `early_param("earlycon", param_setup_earlycon)` 注册，在 `parse_early_param()` 阶段（`setup_arch()` 内）被激活，按 `earlycon=uart8250,mmio,0xff1a0000` 或 DTB 的 `stdout-path` 匹配一个最小写函数（轮询、无中断、无缓冲）。x86 老式 `earlyprintk` 与之等价。由于处理的是 `early_param`，它比 `console_init()` 早了整整一个启动阶段——这是"内核没起来就黑屏"时唯一的救命稻草。

## 5. x86_64 vs arm64 启动对照表

| 维度 | x86_64 | arm64 |
| :--- | :--- | :--- |
| 引导协议载体 | `struct boot_params`（zero page）+ `HdrS` | 64 字节 Image 头 + x0=DTB / UEFI |
| 内核镜像 | bzImage（setup + 压缩 vmlinux） | Image（可选 gzip，EFI stub 情况下 PE 签名） |
| 内核解压 | 解压器自身（`compressed/head_64.S`） | 一般无独立解压层（U-Boot 可解压 gzip） |
| 入口物理地址 | 32 位:0x0 / 64 位:0x200（压缩镜像内，ABI 固定） | Image 头 `b primary_entry`（2M 对齐任意落点） |
| 早期页表建立者 | 解压器建 4G 恒等页表；内核 `__startup_64()` 修正 | `create_idmap()` 恒等映射 + `create_kernel_mapping()` |
| 开 MMU 的位置 | 解压器 `startup_32` 即开（4G 页表）；内核侧二次切换 | `__primary_switch() -> __enable_mmu()` |
| KASLR | 解压期 `choose_random_location()`（物理+虚拟独立） | `__primary_switch()` 内 `__pi_kaslr_early_init()` |
| 重定位机制 | `handle_relocations()`（RELATIVE 重定位） | `__relocate_kernel()`（RELA + 可选 RELR） |
| 固件接口 | BIOS INT 0x15 E820 / UEFI 表经 boot_params | DTB 为主，UEFI/ACPI 为辅 |
| 微码更新 | `load_ucode_bsp()`（进入 C 后立刻） | 无对应机制（固件负责） |
| secondary CPU 唤醒 | SIPI/SINIT → trampoline → `secondary_startup_64` | PSCI `cpu_on` / spin-table → `secondary_entry` |
| 恒等映射存续 | `reset_early_page_tables()` 尽早杀死 | idmap 表长期保留（用于关 MMU 的场合，如 kexec） |

> 一句话总结差异：**x86_64 的早期启动是"解压器搭台、内核修台"的两段接力；arm64 是 head.S 一段连续独舞——先用恒等映射自举，再在 MMU 开启后现场重铺正式页表。** x86 的复杂性来自实模式历史包袱与物理/虚拟双重随机化；arm64 的复杂性来自 VA 位数、EL2 与 52 位 PA 的组合。

## 6. 观测与调试

* **串口 earlycon**：`earlycon=uart8250,mmio32,0xff1a0000`（arm64 常配 `earlycon=pl011,mmio32,0x87xxxxx`）；DTB 平台用 `stdout-path` 更省事。
* **确认自己走到哪一层**：`early console in setup code` → 实模式 `main()` 活着；`Decompressing Linux...` → 解压器活着；`Linux version 6.6.x` banner → 已进 `start_kernel()`；`Kernel command line: ...` → 已过 `setup_command_line()`。
* **KASLR 排查**：panic 时 notifier 会打印 `Kernel Offset: 0x... from 0xffffffff81000000`（`arch/x86/kernel/setup.c: dump_kernel_offset()`）；`nokaslr` 可对比定位因重定位引发的问题。
* **dump 引导协议**：`dmesg | grep -i e820`、`/sys/firmware/dtb`、`/sys/firmware/efi` 回看固件交接的行李；QEMU 下 `-kernel bzImage` 不经 bootloader 直接进入解压入口，便于隔离实验。

## 7. 🧠 思考题

1. **为什么 x86_64 压缩内核的 32 位入口在偏移 0、64 位入口固定在 0x200，且被注释为 "ABI so immutable"？** 提示：谁在依赖这两个偏移？bootloader 与 EFI stub 没有"查找符号表"的能力。
2. **arm64 的 `create_idmap` 为什么必须在 `init_kernel_el`（可能关 MMU）之前执行？** 如果把顺序反过来会发生什么？提示：`init_kernel_el` 内部 `pre_disable_mmu_workaround` 会关闭再重开 MMU，其间 CPU 在物理地址上取指。
3. **x86_64 中 `__startup_64()` 为什么必须用 `fixup_pointer()` 修正常量指针，而同一文件的汇编代码却不需要？** 提示：对比 C 编译器对全局变量生成的寻址方式与 `leaq xxx(%rip)` 的语义差异。
4. **arm64 先开 MMU 再做 KASLR，x86_64 先做 KASLR 再跳内核——两者为什么都能保证正确性？** 提示：KASLR 随机化之后，谁在什么地址空间上执行计算？
5. **若 bootloader 违反 arm64 boot protocol（x1 ≠ 0），内核还能启动吗？在哪里被发现？** 提示：`__primary_switched` 只保存了 x0..x3，真正报错在 `setup_arch()` 末尾。
