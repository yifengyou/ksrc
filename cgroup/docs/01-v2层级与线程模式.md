# cgroup v2 层级与线程模式（Linux 6.6）

> 阅读目标：建立 cgroup v2 的完整世界观——统一层级为什么取代 v1 的多层级；吃透 cgroup_root / cgroup / cgroup_subsys_state / cgroup_subsys 四层结构与 kernfs 地基；掌握线程模式（cgroup.type 四态）与"内部进程约束"的因果；为第 2-4 章的 cpu/memory/io 控制器提供框架底座。

---

## 一、为什么是 v2：v1 的三宗罪

```
v1 的世界：每个控制器一棵独立树（cpu 树、memory 树、blkio 树……）
           + 可选的"命名层级"（name=xxx）
           + cpuset/blkio 等经常不在同一棵树上
```

| v1 问题 | 后果 | v2 对策 |
| :--- | :--- | :--- |
| 资源视图割裂 | 同一进程的 cpu 与 memory 限额分属两棵树，容器编排要挂两次、对齐两次 | **统一层级**：一棵树挂全部控制器（`cgroup.controllers` 列出可用者） |
| 语义不统一 | 各控制器各自的 enable 接口、任务迁移接口行为不一 | 统一文件族（`cgroup.subtree_control` 一处启用） |
| 无进程粒度区分 | 一切按 taskgroup 记账，进程组与线程组语义混淆 | **线程模式**显式声明粒度 |

v2 挂载点 `/sys/fs/cgroup`（systemd 默认已切 v2；`systemd.unified_cgroup_hierarchy=1`）。v1 兼容层保留（`cgroup-v1.c`），混合boot 下可用 `cgroup_no_v1=` 收缩。

## 二、四层结构（kernel/cgroup/cgroup-defs.h，已核对 6.6）

```c
struct cgroup_root {                    /* 一棵层级树的根（v2 只有一个统一根）*/
	struct kernfs_root *kf_root;    /* kernfs 根：cgroupfs 的目录树引擎 */
	unsigned int subsys_mask;       /* 本树挂载的控制器集合 */
	int hierarchy_id;
	struct cgroup cgrp;             /* 根 cgroup（内嵌，"上帝节点"）*/
	unsigned int flags;             /* CGRP_ROOT_* */
	...
};

struct cgroup {                         /* 树上每个目录节点 */
	struct cgroup_subsys_state self;/* ★"把自己当 css"——cgroup 本体也是
	                                   一个（无控制器的）css，靠它挂入父的 children */
	int level, nr_descendants, nr_dying_descendants;
	struct kernfs_node *kn;         /* ★目录即 kernfs 节点 */
	u16 subtree_control;            /* 本目录为子树启用的控制器位图 */
	u16 subtree_ss_mask;
	struct cgroup_subsys_state __rcu *subsys[CGROUP_SUBSYS_COUNT];
	                                 /* ★每个控制器一个 css 槽位（未启用的
	                                   指向根 css 或 NULL 语义）*/
	struct cgroup_root *root;
	struct cgroup *dom_cgrp;        /* 线程模式：本（threaded）组所属的
	                                   最近 domain 祖先 */
	int nr_populated_domain_children / threaded_children …
	...
};

struct cgroup_subsys_state (css) {      /* 控制器视角的"节点"抽象 */
	struct cgroup *cgroup;          /* 反向指针 */
	struct cgroup_subsys *ss;       /* 属于哪个控制器 */
	struct percpu_ref refcnt;       /* 引用计数（percpu，热路径零原子争用）*/
	struct list_head sibling, children;
	int id; unsigned int flags;     /* CSS_ONLINE 等状态位 */
	u64 serial_nr; atomic_t online_cnt;
	struct work_struct destroy_work; struct rcu_work destroy_rwork;
	                                 /* css 的释放是异步两段式（RCU）*/
};

struct cgroup_subsys {                  /* 控制器描述符（静态注册表）*/
	const char *name;
	struct cgroup_subsys_state *(*css_alloc)(struct cgroup *cgrp);
	int (*css_online)(struct cgroup_subsys_state *css);   /* 可见之前 */
	void (*css_offline)(...); void (*css_release)(...); void (*css_free)(...);
	int (*can_attach)(...); void (*attach)(...); void (*cancel_attach)(...);
	void (*fork)(...); void (*exit)(...);                 /* 6.6 仅少数
	                                                          控制器实现 */
	bool early_init; bool threadged?…
	struct cftype *dfl_cftypes, *legacy_cftypes;          /* v2/v1 两套
	                                                          接口文件表 */
	...
};
```

关系一图：

```
cgroup_root (统一根, kf_root)
   └── cgroup "/" (self=css0)
        ├── subsys[]: ── css(cpu)   ── css(memory) ── css(io) …
        │                 │              │
        │           cfs_rq/task_group  mem_cgroup   blkcg_gq   ← 各控制器
        │           （scheduler册）   （mm侧）      （block册）   的私有结构
        │                                                            都以 css
        ├── kn: "cgroup.procs" "cgroup.controllers" …               为宿主
        └── 子 cgroup …（children 链挂在 self.css 上）
```

**css 是控制器的"插槽"协议**：`task_group`、`mem_cgroup`、`blkcg_gq` 全部以 `css` 为第一个字段（container_of 回收），控制器代码与层级框架因此解耦——这是 cgroup 框架最优雅的一笔。

### 2.1 css 生命周期

```
启用控制器（subtree_control 写入）
  → css_alloc(cgrp)          驱动分配私有结构（可能睡眠）
  → css_online               挂入父 children、对用户态可见
（运行期：refcnt 保护——进程在组里、页在组里都计数）
摘除
  → css_offline              先对用户态隐藏（记账仍可短暂存在）
  → refcnt 归零 → css_release →（RCU）→ css_free
```

两段式（offline ≠ release）的存在原因：**记账对象的生命周期可能长于成员资格**——迁移走的进程还欠着旧组的内存页、还挂着旧组的 io 请求。

## 三、kernfs 地基

cgroupfs 的每个文件/目录都是 `kernfs_node`：cgroup 框架不自己造 VFS 树，而是把 `cftype`（文件描述表）注册成 kernfs 文件。收益：sysfs 同款引擎（顺序文件 seq_file、权限、命名空间隔离都是现成的）、cgroupns 的视图裁剪在 kernfs 层自然实现（不同 ns 挂载看到不同"根"）。

进程与 cgroup 的绑定经过 `css_set`（任务指向一组 css 的集合，相同组合的进程共享一个 cset——dedup 设计防止 task_struct 膨胀）：

```
task_struct → cgroups(指向) → css_set ──┬→ css(cpu@组A)
                                        ├→ css(memory@组B)   （跨树 v1 遗产；
                                        └→ …                v2 下通常同树）
```

## 四、线程模式：进程粒度 vs 线程粒度

**默认（domain）模式按进程记账**：`cgroup.procs` 迁移的是整个 thread group；组内所有线程共享记账。但现实需要"只把某几个线程限速"（如 JVM 的 GC 线程、异步 IO 线程池）——v2 的答案不是回到 v1 的 per-task 混乱，而是**子树级显式降粒度**：

```
/ (domain)
├── app/ (domain, cgroup.procs=进程粒度)
│   └── workers/ (cgroup.type=threaded)   ← 写 "threaded" 降级
│        ├── pool1/ (threaded)  cgroup.threads=线程粒度（tid）
│        └── pool2/ (threaded)
```

`cgroup.type` 四态（cgroup.c 已核对）：

| 值 | 含义 |
| :--- | :--- |
| `domain` | 默认：进程粒度，可有自己的资源域 |
| `threaded` | 线程粒度：本组的记账并入最近 domain 祖先（dom_cgrp 指针） |
| `domain threaded` | domain，但孩子里存在 threaded 子树（过渡态标记） |
| `domain invalid` | 结构失效（父变 threaded 时自动落下）——重导为 threaded 才可用 |

关键语义：**threaded 组的资源（cpu 带宽、内存限额）由 dom_cgrp 承担**——它只是"进程内线程的分拣器"，不是独立资源域。因此：

* 支持线程粒度的控制器天然受限（cpu 的权重/带宽可以，memory 页记账在 6.6 仍是进程粒度主导——具体以各控制器 `threaded` 支持位为准）
* `cgroup.threads` 用 **tid** 迁移单个线程；`cgroup.procs` 在 threaded 子树上不可用（write 返回 EACCES）

## 五、"内部进程约束"：subtree_control 的启用规则

v2 最常被问的问题："为什么在父目录里启用控制器会报错 `no internal process`？"

```
规则：一个 domain cgroup 若要为子树启用控制器（写 cgroup.subtree_control），
      自己不能直接持有进程（cgroup.procs 必须为空）。
```

为什么：

```
父组留了进程 + 又给子树启用 memory：
   父的进程 memory 记账算谁的？——父组自己的 memory.current；
   但子树的控制器已在父上创建（css 是"挂在父、作用于子"），
   语义出现二义：父的 limit 到底管不管自己这几个进程？
v1 正是栽在这——不同控制器不同答案。v2 一刀切：要管子树就别自己装进程。
```

配套布局（systemd 的标准做法）：

```
.slice（无进程，纯分组）
 ├── workload-a.slice（无进程）
 │    └── service（进程全在这里——叶子层）
```

例外：**根 cgroup** 天然允许进程与控制器并存；threaded 子树不受此约束（threaded 组无独立资源域）。

## 六、标准文件族速查（v2）

| 文件 | 读/写 | 含义 |
| :--- | :--- | :--- |
| `cgroup.controllers` | r | 本目录可用的控制器清单（由父的 subtree_control 决定） |
| `cgroup.subtree_control` | rw | 为**子树**启用的控制器（"+cpu +memory" 语法） |
| `cgroup.procs` | rw | 进程粒度成员（读=tgid，写=迁移整组） |
| `cgroup.threads` | rw | 线程粒度成员（仅 threaded 子树可写） |
| `cgroup.type` | rw | domain/threaded/…（第四节） |
| `cgroup.events` | r | populated（有进程吗）与 frozen 状态 |
| `cgroup.max.descendants` / `max.depth` | rw | 结构治理上限 |
| `cgroup.stat` | r | nr_descendants / nr_dying_descendants |
| `cgroup.freeze` | rw | 冻结全组（cgroup v2 freezer，进程组的 SIGSTOP 升级版） |
| `cgroup.kill` | w-only | 6.6 新：给全组发 SIGKILL（容器整组快速清理） |

## 九、进程迁移的机器（已核对 cgroup.c 源码）

写 `cgroup.procs` 最终走到 `cgroup_attach_task`（cgroup.c:2835）——这是理解"迁移原子性"的钥匙：

```
cgroup_attach_task(dst_cgrp, leader, threadgroup)
 ├─ ① 收集源：遍历线程组，cgroup_migrate_add_src(每个任务的 css_set, dst, &mgctx)
 │      —— mgctx 把"要动的一批 cset → 目标组"的迁移预先编排成
 │         preloaded_csets 链（持有 css_set_lock）
 ├─ ② cgroup_migrate_prepare_dst：为每个 (src_cset × dst) 组合
 │      查找/分配目标 cset（find_css_set——可能复用已有组合），
 │      并预先 link 好（防中途分配失败留半成品）
 ├─ ③ cgroup_migrate(leader, threadgroup, &mgctx)
 │      ├─ threadgroup_change_begin（停掉整个线程组的 exec/fork 竞争）
 │      ├─ 对每个任务：cgroup_task_migrate——task->cgroups 指针一次性换到新 cset
 │      │   （css_set_move_task 里同时处理引用计数与链表搬运）
 │      └─ 逐控制器回调：can_attach → attach（失败则 cancel_attach 回滚）
 └─ ④ cgroup_migrate_finish：释放预载链
```

三个设计点：

* **两阶段预编排**（②在③之前做完全部分配）：迁移中途不睡眠分配——`can_attach` 里做重活（如 cpuset 的内存迁移）时，结构层面已保证无回滚路径的半成品。
* **threadgroup_change_begin**：与 fork/exec 互斥——新生的任务不可能"逃逸"到旧组、exec 中的任务不会迁移到一半换 mm。
* **css_set 复用**：目标组合若已有别的进程在用（常见：把进程移回默认组），直接共享现成 cset，零分配。

### 9.1 fork/exit 钩子的现状

6.6 里 `cgroup_subsys` 的 fork/exit 钩子已**大幅收缩**（多数控制器不再实现——记账改走任务结构的 lazy 关联）：进程 fork 时 `cgroup_fork` 只把父的 css_set 引用过继给子（真正的控制器侧 fork 钩子仅少数如 cpuset 的早期初始化）；exit 时 `cgroup_exit` 把任务移回 root cset 的"坟场"语义。**资源记账的 fork/exit 通知改为惰性**：页第一次 charge 时才建立 objcg 关联（第 3 章），IO 请求提交时才挂 blkcg（block 分册）——省掉 fork 热路径上对 30+ 控制器的串行回调，这是 v2 相对 v1 的一次大减负。

### 9.2 rstat：cgroup.stat 的层级聚合

cgroup.stat 等层级统计走 **rstat（recursive stat）**：每 cgroup 一个 per-CPU `cgroup_rstat_cpu`（更新零原子开销），读全局值时 `cgroup_rstat_flush` 沿树把 per-CPU 增量逐级上卷（读时付费，写时免费——与 PELT 的哲学同源）。PSI 的组级聚合同样搭 rstat 快车。

## 九点五、v1 兼容层与混合模式

`cgroup-v1.c` 保留完整的多层级实现：每个控制器可独立挂一棵树（`-o` 选项带上控制器名），v1 树与 v2 统一树**可并存**（同一控制器只能归属一边）。6.6 常见的混合现实：

* systemd 混合模式（`legacy`/`hybrid`）：hybrid 下 v2 树挂 cpu/io/memory（无进程直接放树上），v1 树挂 net_cls/net_prio 等无 v2 对应者；
* 容器运行时的 `-cgroup-parent` 双语义：v2 是相对统一根的路径，v1 是逐控制器路径——排查"容器在哪个组"先确认 boot 模式（`stat -f /sys/fs/cgroup` 的类型）。

v1 侧独有的存量接口速记：`net_cls.classid`（用 cgroup 标记流量给 tc）、`hugetlb.*`、`freezer.state`（v2 的 cgroup.freeze 前身）。

## 十、思考题

1. `cgroup.self` 的存在让 cgroup 自己就是一个 css。框架哪三处代码依赖这个"自指"？（提示：children 链的统一遍历、根 css 兜底、destroy 路径。）
2. css 的 offline 与 release 分离。举一个 memory 控制器的具体场景说明"成员资格消失但记账仍在"的必要性（提示：迁移走的进程 + 它的已分配页）。
3. 为什么线程粒度用"子树降级"而不是 v1 那样全局 per-task？（对照：threaded 组的 memory 限额由 dom_cgrp 承担的设计收益。）
4. `css_set` 去重的动机是什么？一万进程同组时省的是什么？（结构数量 vs 遍历成本两个角度。）
5. systemd 为什么强制 `.slice → service` 的三层布局？对照第五节的内部进程约束给出结构解释。
