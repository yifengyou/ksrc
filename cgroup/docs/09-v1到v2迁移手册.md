# cgroup v1→v2 迁移手册（Linux 6.6）

> 定位：[01-v2层级](01-v2层级与线程模式.md)（模型）与 [08-v1淘汰史](08-v1淘汰史.md)（历史）之间的**实操桥**——控制器文件映射全表、五个语义陷阱、cgroup2 挂载选项、systemd 侧对照与迁移 playbook。前置：01/08 章。

## 一、迁移前置探测

```
cat /proc/1/cgroup          # 多行=v1 各树；单行 0::/...=v2
mount | grep cgroup         # cgroup2 单挂载 vs 多树
cat /sys/fs/cgroup/cgroup.controllers   # v2 根下可用的控制器
内核侧开关：cgroup_no_v1=（按子系统屏蔽 v1——迁移期软过渡）
systemd 侧：cgroup.unified_requests=1（内核参数）+ 单元里的
  cgroup 指令双栈兼容（systemd 自己处理映射）
```

## 二、控制器文件映射全表（两侧文件名均核对自 v6.6）

| 资源 | v1 文件 | v2 文件 | 备注 |
| :--- | :--- | :--- | :--- |
| CPU 带宽 | `cpu.cfs_quota_us` + `cpu.cfs_period_us` | `cpu.max`（"quota period" 合并格式） | 两文件并一 |
| CPU 权重 | `cpu.shares`（2..262144，默认 1024） | `cpu.weight`（1..10000，默认 100） | 量纲换算 ≈×100/1024 |
| CPU 统计 | `cpu.stat` | `cpu.stat`（[02 章]字段更全） | 名同义增 |
| 内存硬限 | `memory.limit_in_bytes` | `memory.max` | 直移 |
| ★内存软限 | `memory.soft_limit_in_bytes` | **`memory.low`（语义反转！）** | 见 §三陷阱① |
| 内存+swap | `memory.memsw.limit_in_bytes` | `memory.max` + `memory.swap.max` **组合** | 见陷阱② |
| swap 独立 | （v1 无独立 swap 限） | `memory.swap.max` | v2 新增 |
| io 限速 | `blkio.throttle.*_bps`/`_iops` | `io.max` | 前缀换族 |
| io 权重 | `blkio.weight` | `io.weight` | 机制换代（bfq→iocost/hweight） |
| cpuset | `cpuset.cpus`/`mems` | 同名 | 直移（+v2 的 partition 扩展） |
| 设备白名单 | `devices.allow/deny` | **无 v2 控制器**——BPF_CGROUP_DEVICE | [08 章] |

## 三、五个语义陷阱（迁移踩坑高发区）

```
① soft → low 方向反转：v1 soft_limit="压力大时优先回收我"（自弃）；
   v2 low="低于此值别动我"（自保）——语义相反！v1 的 soft 语义
   在 v2 没有直接对应（近似物是负向 low？不存在——用 memory.high
   的软节流替代思路）
② memsw 合计 → 拆分：v1 memsw.limit=内存+swap 总限；v2 只拆成
   两道独立闸（memory.max + memory.swap.max）——"总限"需自己
   保证 max+swap.max ≥ 旧 memsw 值的组合约束
③ use_hierarchy 隐含：v1 每层要写 1 才启用层级记账；v2 天生
   层级（子组受限在父组内）——迁移时删除该写入
④ 无内部进程约束：v2 启用控制器的组内不能有进程（进程须下沉
   到子组）——v1 迁来的"服务直接挂树上"布局必须重排
⑤ tasks → cgroup.threads：v1 可对任意线程单独写 tasks；v2 仅
   threaded 域可用 threads（[01 章]四态）——按线程分组要显式
   建 threaded 子树
```

## 四、cgroup2 挂载选项（cgroup.c:1905-1913 全表核对）

```
mount -t cgroup2 none /sys/fs/cgroup -o <opt>
  nsdelegate          委托以 cgroup namespace 为界（容器把整个
                      ns 视图交给容器内 root——安全委托的地基）
  favordynmods        动态控制器（进程首次触碰相关文件时自动
                      启用——省启动开销）
  memory_localevents  memory.events 记账本地化（不向层级冒泡）
  memory_recursiveprot（★实名注意：是 recursiveprot 不是
                      recursive_protect——min/low 保护递归生效）
```

## 五、systemd 侧对照（用户态事实，systemd 230+ 双栈）

```
CPUQuota=50%        → cpu.max "50000 100000"
CPUWeight=100       → cpu.weight（MemoryMax/IOWeight 同族直映）
Delegate=yes        + nsdelegate 挂载 = 容器内自治
slice/scope/service 三层布局即 v2 树的标准形态——单元即组
```

## 六、迁移 playbook（七步）

```
① 探测（§一）+ 盘点 v1 树上的非默认值
② 标注陷阱项（§三的 ①②④ 是必查）
③ systemd 系统：升 systemd + cgroup.unified_requests=1 重启
   （systemd 自动迁移大部分单元）
④ 非 systemd/裸机：手工建树——根启用 subtree_control →
   按服务建子组 → 进程迁入 → 写限额（先宽后紧）
⑤ 双栈并行期（cgroup_no_v1= 未设时两套并存）：以 v2 为准写、
   v1 只读观察，收敛后 cgroup_no_v1= 全屏蔽
⑥ 验证：压力下对照 memory.pressure/io.pressure 与旧 v1 表现
⑦ 回退预案：cgroup_no_v1 不设即可回挂 v1（数据两套独立）
```

## 七、思考题

1. soft→low 的语义反转为什么"合理"？（提示：soft 从未真正工作良好——回收倾向的实际效果差；low 的保护语义更可预期。）
2. v2 拆掉 memsw 合计闸的动机？（提示：swap 与内存的回收代价差异巨大——合并限让 swap 侵占无感知。）
3. nsdelegate 之前"按目录委托"漏了什么？（对照容器逃逸面：cgroup ns 内看到的 root 与真 root 的差。）
4. favordynmods 的代价是什么？（动态启用=首次触碰有延迟——对延迟敏感服务的启动路径。）
5. 无内部进程约束为什么反而帮了运维？（提示：强制"组=服务单元"的清晰拓扑。）
