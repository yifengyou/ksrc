# cgroup v1 淘汰史：从多挂载树到统一层级（Linux 6.6 视角）

> 定位：[01-v2层级与线程模式](01-v2层级与线程模式.md) 的历史纵深——v1 为什么长成那样、v2 砍掉了什么、**6.6 里 v1 还剩什么**（1308 行兼容层逐点盘点）。当前态全部对照 v6.6 核对；早期历史（2.6.24 引入、4.x 统一层级之争）为社区公认年表。前置：01 章。

---

## 一、v1 的世界：一个控制器一棵树（2008 起）

```
v1 模型：每控制器独立挂载树（/sys/fs/cgroup/{memory,cpu,...}
  各自一棵）——名字空间式分裂的根源：
  任务必须在每棵树上各自定位——"一个进程在 memory 树的 A 组
  而在 cpu 树的 B 组"合法且常见——治理视角的灾难
命名层级：name= 挂载参数允许"非控制器树"（仅 cpuset/空闲树）
  ——6.6 仍保留（cgroup_no_v1_named 于 cgroup-v1.c:33）
线程粒度：tasks 文件——任意线程可单独写（v2 的 cgroup.threads
  仅限 threaded 域——01 章的四态约束是回应）
noprefix：仅 cpuset 独挂时允许无前缀文件名（cgroup-v1.c:1056
  注释——"compatible with the old cpuset"的历史包袱）
```

## 二、v1 的标志性机制（6.6 兼容层盘点，已核对）

```
release_agent + notify_on_release：
  空组触发用户态 agent——容器逃逸名场面 CVE-2022-0492
  （root 容器写宿主 release_agent 执行任意命令）；
  6.6 现状：cgroup_release_agent_write 仍在（:544-565，
  release_agent_path 锁保护）——v2 已整体移除该机制
cgroup.clone_children（:605-635）：cpuset 的子组继承开关
  ——v2 无对应（创建时显式写）
pidlist 基础设施（:170 注释）：tasks/procs 的大列表分页
  ——纯 v1 产物
cgroup1_procs_write（:488-535）：写 tasks 的逐线程语义
cgroup_no_v1= boot 参数（:30-46 + __setup :1308）：
  按子系统屏蔽 v1 挂载（"cgroup_no_v1=memory,blkio"）——
  迁移期的软关闭阀
```

## 三、v2 砍掉了什么（对照表）

| v1 有 | v2 处置 | 6.6 现状 |
| :--- | :--- | :--- |
| 多挂载树 | 单一统一树（4.x 定，systemd 230+ 默认） | v1 层仍在（1308 行） |
| tasks 任意写 | cgroup.threads 限 threaded 域 | 已核（01 章） |
| release_agent | **删除**（安全） | 仅 v1 层残留 |
| devices 控制器 | 无 v2 版——由 **BPF_CGROUP_DEVICE** 接替 | security/device_cgroup.c 仅 v1 |
| net_cls / net_prio | 无 v2 版（设计上拒绝——流量标记属 BPF/TC 域） | ★两者 **6.6 仍在**（net/sched/cls_cgroup.c 与 net/core/netprio_cgroup.c——常被误传"已删"） |
| blkio | io.*（[04 章]） | 双轨 |
| cpu + cpuacct 分立 | 合并为 cpu.* | v1 挂载仍分离 |
| clone_children | 无（显式化哲学） | 仅 v1 |

## 四、未删之谜与淘汰节奏

```
官方立场：v1 无删除时间表（"soft deprecation"）——理由：
  大规模部署存量（嵌入式/老容器栈）+ 部分机制（多树）有真实
  用例（跨控制器的正交分组实验）
实际信号：新特性只进 v2（psr? uclamp/io.cost/psi 全部 v2-only）；
  文档导向 v2；v1 层只修不增
迁移：cgroup_no_v1= + systemd 的 UnifiedCgroupHierarchy
  （cgroup.unified_requests=1 全局）
```

## 五、观测与实战

```
cat /proc/<pid>/cgroup     # 每行一个层级——多行=v1；单行 v2 路径
mount | grep cgroup        # v1 各树 vs 单 cgroup2 挂载
系统鉴定：systemd status 的 CGroup 字段格式（v1 多前缀 vs
  v2 单路径）
排障：老工具（老 lxcfs/cgroup-bin）在 v2 下报"找不到控制器"——
  cgroup_no_v1 反向场景：确认系统没屏蔽 v1 再挂调试树
```

## 六、思考题

1. v1 多树的"正交分组"为何最终被否？（对照 css_set 的组合爆炸——[07- css_set 深挖](07-css_set深挖.md)：n 棵树各选一组=组合数增长。）
2. release_agent 的安全教训是什么类型？（对照 lockdown 分册：同样是"内核触发用户态执行"的信任面。）
3. devices 走 BPF 而非新控制器——设计动机？（提示：策略表达力（程序化规则）vs 声明式白名单。）
4. net_cls/net_prio 未删未迁——"冻结"状态的生态含义？（TC/BPF 已接管流量标记的用例。）
5. 若 v1 明日删除，最大阻力来自哪类用户？（嵌入式? 特定正交用例? 工具链?）
