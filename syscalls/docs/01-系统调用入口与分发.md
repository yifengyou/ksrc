# 系统调用入口与分发（Linux 6.6）

> 阅读目标：吃透用户态到内核态的完整交接协议——x86 的 `syscall`/`sysret` 快路径（MSR 装载、栈切换、寄存器布局）与 arm64 的 `SVC` 异常；通用入口层（kernel/entry/）的统一钩子序列（seccomp/audit/ptrace 在同一管线上）；系统调用表的组织与 x32/ia32 兼容表；vDSO 的布局与为什么 gettimeofday 不进内核。

---

## 一、x86-64：最快的一扇门

### 1.1 入口装配

```
boot 时 syscall_init()（arch/x86/kernel/cpu/common.c）装载：
  WRMSR(MSR_LSTAR, entry_SYSCALL_64)     —— 目标 RIP
  WRMSR(MSR_STAR, ...)                   —— 段选择子（user/kernel CS）
  WRMSR(MSR_SYSCALL_MASK, X86_EFLAGS_...)—— 自动清掉的标志位（IF/DF/TF…）

用户态执行 syscall 指令的硬件动作：
  RIP  → MSR_LSTAR（entry_SYSCALL_64）；RIP 旧值 → RCX；RFLAGS → R11
  CS/SS 切换到内核段；**RSP 不自动切换**——内核必须自己换栈！
```

### 1.2 entry_SYSCALL_64（arch/x86/entry/entry_64.S，已核对调用点 :120）

```
entry_SYSCALL_64:
    swapgs                          ← GS 基址切到内核 per-CPU
    movq %rsp, PER_CPU_VAR(cpu_current_top_of_stack)?? 反向：
                                      实为 mov PER_CPU_VAR(...), %rsp
                                      —— 把 RSP 换成本任务内核栈顶
                                    （syscall 与中断不同：不压 SS:RSP/中断号，
                                      只靠 RCX/R11 归还——省 3 次内存写）
    push 一组 pt_regs（用 PUSH_AND_CLEAR_REGS 宏：RDI..R15 逆序压栈）
    movq %rsp, %rdi                 ← 第一个参数 = pt_regs*
    movl %eax, %esi                 ← 第二个参数 = syscall nr
    call do_syscall_64              ← 返回时 IF 关闭（见 .S 注释）
    ...pop regs...
    swapgs; sysretq                 （若需 iret 的慢路径：swapgs_restore_regs_and_return_to_usermode）
```

### 1.3 do_syscall_64（arch/x86/entry/common.c，已核对）

```c
__visible noinstr void do_syscall_64(struct pt_regs *regs, int nr)
{
	add_random_kstack_offset();                    /* 栈基随机化（对抗侧信道）*/
	nr = syscall_enter_from_user_mode(regs, nr);   /* ★通用入口层（见第二节）*/
	instrumentation_begin();
	if (!do_syscall_x64(regs, nr) &&               /* sys_call_table[nr] */
	    !do_syscall_x32(regs, nr) &&               /* x32 ABI 的兼容表（位
	                                                  30 标记的 x32 调用号，
	                                                  已核对 x86_common.c:67）*/
	    nr != -1)
		regs->ax = __x64_sys_ni_syscall(regs);     /* 未实现 → -ENOSYS */
	instrumentation_end();
	syscall_exit_to_user_mode(regs);               /* ★通用出口层 */
}
```

表的组织（arch/x86/entry/syscall_64.c）：每个系统调用一个 `__x64_sys_*` 汇编桩（`SYSCALL_DEFINE` 宏的伴生物），把 pt_regs 里的参数按 ABI 拆给 C 实现——表项是**统一的五参数原型** `long (*)(const struct pt_regs *)`，参数个数差异被桩吸收。

> `sysret` 的著名裂缝：`sysret` 返回到**非规范地址**时 #GP 在**内核态**炸出历史漏洞（CVE-2012-0217）——现代入口在 sysret 前显式校验 RCX/R11 规范性，不合规走慢路径 iret。

## 二、通用入口层：kernel/entry/（6.x 的统一化成果）

架构汇编只做"换世界"，其余统一走通用层（`kernel/entry/common.c` + `include/linux/entry-common.h`，已核对钩子顺序）：

```
syscall_enter_from_user_mode(regs, nr)
 └─ __syscall_enter_from_user_work(regs, nr)
      ├─ ① __secure_computing(NULL)          seccomp 检查（下一章）
      ├─ ② ptrace 报告（PTRACE_EVENT_SECCOMP / syscall_enter）
      ├─ ③ audit_syscall_entry（CONFIG_AUDIT）
      └─ ④ trace_sys_enter（sys_enter tracepoint）
      返回可能被改写的 nr（seccomp 可劫持）

syscall_exit_to_user_mode(regs)
 └─ ① syscall_exit_work：audit exit / sys_exit tracepoint /
 │     单步标志（TIF_SINGLESTEP 的 SIGTRAP 注入点）
 ├─ ② exit_to_user_mode_prepare（process-mgmt 分册第 4 章已讲）：
 │     信号递送检查 / 需重调度检查 / task_work 执行
 └─ ③ exit_to_user_mode（真正回用户态前的最后一跳）
```

**信号、调度、task_work 都挂在"出口"**——系统调用慢半拍让出世界的机制（process-mgmt 分册的 get_signal 一节在此收口）。

### 2.1 系统调用重启（EINTR 的另一半）

慢系统调用被信号打断时：入口层在 `regs->ax` 打 `-ERESTARTSYS` 标记 → 出口递送信号前发现它 → **把用户 RIP 回拨 2 字节（syscall 指令长度）并把 nr 放回 orig_ax** → 信号 handler 返回后重新执行同一调用（`SA_RESTART` 时无感；否则改返 EINTR）。arm64 的 SVC 是 4 字节，回拨量不同，逻辑同构（`syscall_restart` 的架构实现差异点）。

## 三、arm64：SVC 异常向量

```
用户态 SVC #0 → 向量表 VBAR_EL1 的 el0_sync → el0_svc
（arch/arm64/kernel/entry-common.c）
 └─ el0_svc_handler
     ├─ syscall_enter_from_user_mode(regs, scno)   /* 同款通用层 */
     └─ invoke_syscall（arch/arm64/kernel/syscall.c，已核对源码）：
           syscall_fn = syscall_table[array_index_nospec(scno, sc_nr)];
                                           /* ★推注屏障：防分支预测训练的
                                             Spectre-v1 越界读调用表 */
           ret = __invoke_syscall(regs, syscall_fn);
           syscall_set_return_value(...);
           choose_random_kstack_offset(get_random_u16() & 0x1FF);
                                           /* 栈偏移随机化（x86 在入口侧做，
                                             arm64 在两侧都做）*/
```

arm64 的系统调用约定（AArch64 PCS）：x8=nr，x0..x5=参数，返回 x0；表是 `syscall_fn_t[]`（每项直接是统一原型，`CONFIG_COMPAT` 下另有 `compat_sys_call_table` 处理 AArch32 进程）。

## 四、vDSO：不进内核的"系统调用"

```
每个进程的地址空间（mm 分册 canonical_address_space 的布局）：
  [vsyscall]（旧，仅映射 1 页仿真，6.6 默认 emulate/xonly）
  [vvar]    内核数据页（只读映射：jiffies 序列、时钟数据、getcpu 缓存）
  [vdso]    可执行页：__vdso_clock_gettime / __vdso_getcpu / __vdso_time /
            __vdso_clock_getres / __vdso_sigtimedsuspend? 无此——即 clock 族
```

机制：`arch/x86/entry/vdso/vma.c` 在进程启动时映射两张页——**数据由内核在时钟 tick 时更新（timers 分册第 3 章的 tk_fast 序列保护），代码在用户态直接读**。`clock_gettime` 因此从"陷入+约 100ns 开销"变成"读缓存行 + 序列锁重试"，零上下文切换。

```
用户调用链：glibc 的 clock_gettime → PLT → vdso 中的 __vdso_clock_gettime
  → 读 vvar 的 gtod 数据（seqcount 保护：odd 重试）
  （若内核不支持/arch 不匹配 → 回落真系统调用）
```

**为什么 vdso 能安全地"读内核维护的数据"**：所有字段要么原子（时钟字），要么被 `vdso_data.clock_seq` 的 seqlock 保护（timers 分册已拆解该协议）。`getcpu` 则利用 per-CPU 段 + `lsl` 指令的用户态可读技巧。

## 六、思考题

1. `syscall` 指令不压入 SS:RSP 和中断号——pt_regs 里那些字段的值从哪来？（对照 `PUSH_AND_CLEAR_REGS` 前的 `mov %rsp` 系列与中断入口 `error_entry` 的差异。）
2. seccomp 检查为什么在 audit/ptrace 之前？如果顺序反过来，观测面会出现什么不一致？（提示：被 seccomp 拒掉的调用该不该出现在 audit 日志里。）
3. x32 ABI 的表为什么不能与 x64 共用（尽管都在 64 位长模式）？（提示：指针宽度差异如何影响 `SYSCALL_DEFINE` 的桩拆参。）
4. vDSO 的数据页映射进每个进程——一个 1000 进程的机器，内核更新 jiffies 时写的是几份内存？（对照 vvar 的全局唯一性。）
5. 设计：给一个新架构移植系统调用入口，通用层要求架构提供哪三个原语？（对照 entry-common.h 的契约：enter/exit 的最小集合。）
