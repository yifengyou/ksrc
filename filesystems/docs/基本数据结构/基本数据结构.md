`struct file_system_type`：文件系统的“身份证”

这是内核中用来描述一种**文件系统类型**（如 ext4, xfs, nfs, proc 等）的数据结构。它不针对具体的某个磁盘分区，而是针对“这一类”文件系统。

*   **基本情况**：
    *   它是一个全局的数据结构，通常在文件系统模块初始化时注册到内核中。
    *   内核维护一个链表（`next`指针），将所有已注册的文件系统类型串联起来。
*   **核心功能**：
    *   **定义属性**：通过 `name` 字段定义文件系统的名字，通过 `fs_flags`（如 `FS_REQUIRES_DEV`）定义它是否需要物理设备（例如 `proc` 文件系统就不需要）。
    *   **挂载入口**：最关键的是 `mount` 函数指针。当你执行 `mount -t ext4 /dev/sda1 /mnt` 时，内核会根据 "ext4" 找到对应的 `file_system_type`，然后调用它的 `mount` 函数来创建一个具体的 `super_block`。
    *   **上下文初始化**：`init_fs_context` 用于处理挂载时的上下文参数（如挂载选项 data=ordered 等）。
*   **使用场景**：
    *   **模块加载**：当 `modprobe ext4` 时，ext4 的驱动会填充这个结构体并调用 `register_filesystem()`。
    *   **挂载查找**：当你挂载一个设备时，内核在 `/proc/filesystems` 中展示的类型以及实际的挂载逻辑都依赖于此。

`struct super_block`：文件系统的“宏观控制中心”

如果说 `file_system_type` 是图纸，那么 `super_block` 就是根据图纸盖好的具体大楼。它代表一个**具体的、已安装的文件系统实例**（例如你的根分区 `/` 或者家目录 `/home`）。

*   **基本情况**：
    *   每个被挂载的分区或实例都有且仅有一个 `super_block`。
    *   它包含文件系统全局的元数据，如块大小 (`s_blocksize`)、最大文件大小 (`s_maxbytes`)、文件系统魔数 (`s_magic`) 以及 UUID (`s_uuid`)。
*   **核心功能**：
    *   **管理全局资源**：通过 `s_list` 和 `s_instances` 将属于同一个文件系统类型的实例串联起来。
    *   **操作函数集**：`s_op` 指向 `super_operations`，定义了如何读写 inode、如何写回脏数据等底层操作。
    *   **根目录定位**：`s_root` 指针指向该文件系统挂载点的根 `dentry`，这是访问该文件系统下所有文件的起点。
    *   **配额与安全**：包含磁盘配额 (`s_dquot`)、加密 (`s_cop`) 和安全模块 (如 SELinux 的 `s_security`) 的相关信息。
*   **使用场景**：
    *   **挂载过程**：挂载成功后，内核创建 `super_block` 并读取磁盘上的超级块信息填充它。
    *   **文件操作**：当你访问文件时，内核通过 `path` 找到 `super_block` 来获取文件系统的通用限制和操作方法。

`struct inode`：文件的“元数据档案”

在 Linux 中，“一切皆文件”。`inode` 代表一个文件的**元数据**（Metadata）和**数据指针**。它不包含文件名，只包含文件的属性和数据在磁盘上的位置。

*   **基本情况**：
    *   每个文件（或目录）在内核中都有一个对应的 `inode`。
    *   它是持久化的概念，即使没有进程打开它，只要文件存在，`inode` 就存在于磁盘或内存缓存中。
*   **核心功能**：
    *   **存储属性**：保存文件的权限 (`i_mode`)、所有者 (`i_uid`/`i_gid`)、大小 (`i_size`)、时间戳 (`i_atime` 等)。
    *   **数据定位**：`i_blocks` 记录占用的块数，配合地址空间映射 (`i_mapping` 和 `i_data`)，将文件的逻辑偏移量映射到物理磁盘块。
    *   **操作方法**：`i_op` 定义了针对该文件的操作（如创建文件、链接、重命名），`i_fop` 定义了打开文件后读写的操作。
    *   **特殊文件支持**：通过联合体 `i_pipe` (管道)、`i_cdev` (字符设备)、`i_link` (符号链接) 来支持不同类型的文件。
*   **使用场景**：
    *   **路径查找**：当你访问 `/home/user/file.txt` 时，内核通过 `dentry` 找到 `inode`，从而知道这个文件是普通文件还是目录，以及数据在哪里。
    *   **权限检查**：系统调用（如 `open`, `read`）都会检查 `inode` 中的权限位。

`struct dentry`：文件路径的“目录项缓存”

`dentry` 是 **Directory Entry** 的缩写。它是路径名（如 `/home`、`/home/user`）到 `inode` 的映射桥梁。它是纯内存的数据结构，用于加速路径查找。

*   **基本情况**：
    *   它构成了一个巨大的树状结构（Dentry Tree）。
    *   它是临时的，为了加速查找而存在，当内存紧张时可以被回收（通过 LRU 列表）。
*   **核心功能**：
    *   **路径解析**：它将人类可读的路径名（`d_name`）与内核内部的 `inode` 关联起来。例如，`dentry` "file.txt" 指向其对应的 `inode`。
    *   **缓存加速**：VFS 的缓存主要指的就是 `dentry` 缓存和 `inode` 缓存。通过哈希表 (`d_hash`) 快速查找。
    *   **父子关系**：通过 `d_parent`、`d_subdirs` 和 `d_child` 维护了目录的层级结构。
    *   **负向缓存**：`d_inode` 可以为 NULL，表示这是一个“负向 dentry”（Negative Dentry），即该路径对应的文件不存在。这能防止内核反复查询一个不存在的文件。
*   **使用场景**：
    *   **打开文件**：执行 `open("/etc/passwd")` 时，内核逐级查找 `/` -> `etc` -> `passwd`，每一步都会生成或查找一个 `dentry`。
    *   **减少磁盘访问**：如果没有 `dentry` 缓存，每次访问文件都需要去磁盘读取目录块来解析路径。

`struct file`：打开文件的“运行时状态”

当你调用 `open()` 系统调用打开一个文件时，内核就会创建一个 `struct file`。它代表一个**进程对文件的打开实例**。

*   **基本情况**：
    *   一个文件（`inode`）可以被多个进程同时打开，每个进程都会拥有独立的 `file` 结构体。
    *   它是进程私有的，生命周期从 `open` 开始，到 `close` 结束。
*   **核心功能**：
    *   **记录读写位置**：`f_pos` 是文件指针的当前位置。这是每个打开实例独立的，这就是为什么两个进程同时读同一个文件互不干扰。
    *   **访问模式**：`f_mode` 记录是只读、写还是读写。
    *   **文件操作**：`f_op` 指向具体的读写函数。例如，如果是普通文件，读操作会去读磁盘；如果是串口设备文件，读操作会去读串口数据。
    *   **关联关系**：`f_path` 关联到具体的 `dentry` 和挂载点，`f_mapping` 关联到地址空间以便进行页缓存管理。
*   **使用场景**：
    *   **系统调用**：`read()`, `write()`, `lseek()`, `ioctl()` 等系统调用直接操作 `file` 结构体。
    *   **文件描述符**：用户态的文件描述符（File Descriptor，一个整数）本质上是进程打开文件表（`files_struct`）指向这个内核 `file` 对象的索引。


## 关联

| 结构体 | 比喻 | 关键点 |
| :--- | :--- | :--- |
| **file_system_type** | 建筑规范（如“摩天大楼规范”） | 定义了这类系统能做什么，怎么挂载。 |
| **super_block** | 一栋具体的摩天大楼 | 对应一个磁盘分区，有唯一的地址（UUID）。 |
| **dentry** | 门牌号和电梯指引 | 只有名字和指向房间的路，没有实体数据。 |
| **inode** | 房间的档案 | 记录房间大小、装修风格、谁有钥匙（权限）。 |
| **file** | 一把具体的钥匙 | 记录了谁（进程）拿着这把钥匙，开到哪把锁（偏移量）。 |

**典型的数据流（打开文件）：**
1.  **挂载**：内核根据 `file_system_type` 挂载设备，生成 `super_block`，并找到根 `dentry`。
2.  **查找**：解析路径 `/a/b.txt`，内核在 `dentry` 树中查找，找到 `b.txt` 对应的 `dentry`，进而找到其 `inode`。
3.  **打开**：调用 `open`，内核基于 `inode` 创建一个新的 `file` 实例，并将其关联到进程的文件描述符表中。
4.  **读写**：进程通过文件描述符找到 `file`，通过 `file` 找到 `inode` 的操作方法，最终读取磁盘数据。
