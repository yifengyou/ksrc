# 内核代码生成惯用法：X-macro 与多重包含（Linux 6.6）

> 阅读目标：把散落全树的"一份清单、多种产物"惯用法收进一张地图——极简式（kernel_read_file_id 的一宏三表，[module/05](../../module/docs/05-kernel_read_file加载基础设施.md) 的主角）、隔空共定义式（LSM_HOOK 的 251 条清单喂 security/bpf_lsm 三家）、**多重包含式本家**（TRACE_EVENT 七阶段 + define_trace 的 `TRACE_HEADER_MULTI_READ`，[02 章](02-tracepoint机制.md) 的深层机制）、BPF 双例（uapi 的 helper ID 表、btf.c 三重包含教科书）、远亲 BTF_ID 族，以及**对照组**：syscall 表为何选择脚本生成而非 X-macro。全部对照 v6.6 逐一定位。前置：[02-tracepoint 机制](02-tracepoint机制.md)（七阶段的机制背景）。

---

## 一、问题：一份清单多种产物

```
清单（单一事实源）：  MODULE、FIRMWARE、KEXEC_IMAGE ...（7 个 ID）
需要的产品：         ① enum（编译期分派）
                    ② 字符串表（日志/审计）
                    ③ 映射数组（id→处理函数）
                    ④ 结构体字段（每项一个成员）
手写四份的下场：      加一项要改四处——漏一处 = 编译期或运行期的
                    静默漂移（这正是本仓库反复猎杀的"枚举值杜撰"事故源头）
```

X-macro 的契约：**清单只写一遍**（以 `FN(name, args...)` 的函数调用形态），使用者 `#define FN(...)` 成自己需要的形状再 `#include` 它。

## 二、极简式：一宏三表（include/linux/kernel_read_file.h）

[module/05](../../module/docs/05-kernel_read_file加载基础设施.md) 已解剖的样本，这里作为家族基线：

```c
#define __kernel_read_file_id(id) \
	id(UNKNOWN, unknown) ... id(MAX_ID, )      /* :9-16 唯一清单 */

#define __fid_enumify(ENUM, dummy)  READING_ ## ENUM,   /* 产品① */
#define __fid_stringify(dummy, str) #str,                /* 产品② */
enum kernel_read_file_id { __kernel_read_file_id(__fid_enumify) };
static const char * const kernel_read_file_str[] = { ... };
enum kernel_load_data_id {                                /* 产品③'隔空复用 */
	__kernel_read_file_id(__data_id_enumify) };          /* security.h:239-241 */
```

三张表从同一宏展开，**新增 ID 永不漂移**——家族里最紧凑的形态（清单与产品同文件）。

## 三、隔空共定义式：LSM_HOOK 的 251 条清单

清单单独成文件（include/linux/lsm_hook_defs.h），消费者各自定义宏后包含——文件自带用法注释（:21-25 原话）：

```c
/*	LSM_HOOK(<return_type>, <default_value>, <hook_name>, args...)
 *	...
 *   #define LSM_HOOK(RET, DEFAULT, NAME, ...) struct hlist_head NAME;
 *   #include <linux/lsm_hook_defs.h>
 */
LSM_HOOK(int, 0, binder_set_context_mgr, const struct cred *mgr)   /* :29 首条 */
...共 251 条（:29 起 grep -c 实证）
```

三个消费者（已核对 6.6）：

| 消费者 | 定义成 | 产物 |
| :--- | :--- | :--- |
| security/security.c:753 | static call 声明 + 分发数组 | LSM 钩子的 static_call 快路径 |
| include/linux/bpf_lsm.h:18 | BPF trampoline 原型 | `bpf_lsm_##name` 可被 eBPF 程序挂载 |
| security/bpf/hooks.c:12 | hlist 头 | BPF LSM 的注册位 |

## 四、多重包含式（本家）：TRACE_EVENT 的七阶段与"可重读头文件"

[02 章](02-tracepoint机制.md) 的七阶段表背后是家族里最重的机制——**同一头文件被连续包含七次**，每阶段重新定义 `__field`/`__array` 等字段宏（include/trace/trace_events.h + stages/stage1..7_*.h 七文件 + init.h）。

多重包含的合法性来自 define_trace.h 的**重读开关**（:92-95 原话）：

```c
/* Let the trace headers be reread */
#define TRACE_HEADER_MULTI_READ     /* :93 头文件内部的 #ifndef
                                       TRACE_HEADER_MULTI_READ guard
                                       因此可以再次 #include */
#include TRACE_INCLUDE(TRACE_INCLUDE_FILE)   /* :95 第二遍读事件头
                                                （第一遍定义 TRACE_EVENT，
                                                第二遍展开成 tracepoint）*/
```

对比普通头文件的 include guard（第二遍 #include 是空操作），多重包含式**故意让 guard 失效**、配合"每遍前 `#undef` 字段宏再重定义"完成流水线。这是 TRACING 在内核里演化出的最复杂代码生成机制（一次 TRACE_EVENT 定义产出 7 类产品）。

## 五、BPF 双例

### 5.1 uapi 侧：___BPF_FUNC_MAPPER（include/uapi/linux/bpf.h:5646-5865）

```c
#define ___BPF_FUNC_MAPPER(FN, ctx...)		\
	FN(unspec, 0, ##ctx)			\
	FN(map_lookup_elem, 1, ##ctx) ...	/* ~200 个 helper 的
	                                           (名字, ID) 清单 */
#define __BPF_FUNC_MAPPER_APPLY(name, value, FN) FN(name),   /* :5864 剥掉 ID */
#define __BPF_FUNC_MAPPER(FN) ___BPF_FUNC_MAPPER(__BPF_FUNC_MAPPER_APPLY, FN)
```

★两个看点：① 清单在 **uapi 头文件**里——`enum bpf_func_id` 是用户态 ABI（[10 章](10-eBPF验证器入门.md) 的 helper 调用即以 `BPF_CALL imm=ID` 索引）；② `__BPF_FUNC_MAPPER_APPLY` 的**中间层间接**——同一名单既能按 (name, id) 展开枚举、又能剥掉 id 只展开名字序列（宏参数位置重排的经典戏法）。

### 5.2 内核侧：BPF_PROG_TYPE 三重包含（kernel/bpf/btf.c:5580-5609）

include/linux/bpf_types.h（32 条 `BPF_PROG_TYPE(枚举, 名, prog_ctx_type, kern_ctx_type)`）在 btf.c 被连续包含**三次**（已核对）：

```c
/* ① :5584-5588 结构体：每 prog type 两个上下文字段 */
#define BPF_PROG_TYPE(_id, _name, prog_ctx_type, kern_ctx_type) \
	prog_ctx_type _id##_prog; kern_ctx_type _id##_kern;
#include <linux/bpf_types.h>                  /* bpf_ctx_convert 联合体 */

/* ② :5594-5600 枚举：__ctx_convert##id（紧凑序号） */

/* ③ :5601-5605 映射数组：[_id] = __ctx_convert##_id */
static u8 bpf_ctx_convert_map[] = { ... };    /* uapi 枚举→紧凑序号的翻译表 */
```

一份清单喂出"描述结构 + 紧凑枚举 + 翻译数组"三件套——verifier 判断 prog ctx 类型时查的就是这套（"internal file - do not include directly"，bpf_types.h:3 自我声明）。

## 六、远亲：BTF_ID 族（include/linux/btf_ids.h）

BTF_ID_LIST/BTF_SET 宏不生成"清单的多个产品"，而是**把清单本身作为产物**（往 `.BTF_ids` 段发射符号引用，:26 注释原话 *"Following macros help to define lists of BTF IDs placed"*、:35 `BTF_IDS_SECTION ".BTF_ids"`）。CO-RE 与 kfunc 的 `BTF_SET_START` 集合在链接期由 pahole 排序——家族里"以宏为发射器、链接期为消费者"的分支。

## 七、对照组：syscall 表为什么不用 X-macro

```
arch/x86/entry/syscalls/syscall_64.tbl（数据文件）
   └─ scripts/syscallhdr.sh / syscalltbl.sh（构建期 shell）
        ├─ uapi asm-generic/unistd 风格头 + arch 头（__NR_ 常量）
        └─ syscall 表汇编/C 数组（arch/x86/entry/generated/）
```

三个理由：① 清单是**跨语言契约**（asm/C/uapi/文档四方消费，tbl 的列语义由脚本统一解释）；② 要做 **ABI 号空洞/兼容别名**（x32、ia32 别名）这类表格级变换；③ uapi 号是**绝对 ABI**，禁止编译期重排——X-macro 的隐式顺序性反而是风险。结论：**清单在树内且顺序无 ABI 含义 → X-macro；清单是跨子系统的 ABI 契约 → 数据文件+脚本**。

## 八、对比表与选型

| 形态 | 样本 | 清单位置 | 产品数 | 适合 |
| :--- | :--- | :--- | :--- | :--- |
| 极简式 | kernel_read_file_id | 与产品同文件 | 2-3 | 十项以内、单子系统 |
| 隔空共定义 | LSM_HOOK、BPF_PROG_TYPE | 独立清单头 | 3+（多家消费） | 多消费者各自成型 |
| 多重包含 | TRACE_EVENT 七阶段 | 事件头自身 | 7 | 需要七种正交视图 |
| 中间层重排 | ___BPF_FUNC_MAPPER | uapi | 枚举+名序列 | 参数需要剥列/重排 |
| 链接期消费 | BTF_ID 族 | 宏发射 | 段内符号 | 需要排序/去重的集合 |
| （对照）脚本 | syscall_64.tbl | 数据文件 | uapi 头+表 | 跨语言 ABI 契约 |

## 九、实战：怎么找新的家族成员

```bash
# 签名一：'id(NAME,' / 'FN(name,' 形态的续行宏体
git grep -nE '^\s+(id|FN|EMIT)\([a-z_0-9]+,' -- 'include/*.h'

# 签名二：同一文件被 #include 两次以上（多重包含铁证）
git grep -n 'include <linux/bpf_types.h>' kernel/    # btf.c 三连
git grep -c 'include <linux/lsm_hook_defs.h>' security/security.c

# 签名三："Let the file be reread" 类注释与自定义 guard
git grep -rn 'MULTI_READ\|be reread' include/

# 反向验证：新发现疑似成员 → 检查其 guard 是否故意可重入
sed -n '1,10p' <candidate>   # #ifndef XXX → 常规 guard；
                             # 无 guard + "do not include directly" → 清单头
```

## 十、思考题

1. kernel_read_file_id 的 `id(MAX_ID, )`（名字为空串）为什么必须保留在清单里？（提示：字符串表的占位语义 vs 枚举的哨兵值——两产品对"终止项"的不同需求。）
2. `__BPF_FUNC_MAPPER_APPLY(name, value, FN) FN(name,)` 的中间层实现了什么参数变换？直接写 `___BPF_FUNC_MAPPER(FN)` 会怎样？（提示：枚举要 (name,value)、名序列只要 name——一份清单两种投影。）
3. define_trace.h 需要 `TRACE_HEADER_MULTI_READ` 而普通头文件不需要——多重包含下谁负责防止**无限递归包含**？（提示：trace 头里 TRACE_EVENT 定义在 `#ifdef TRACE_HEADER_MULTI_READ` 保护下的形状差异。）
4. btf.c 的第三重包含 `[_id] = __ctx_convert##_id` 为什么不直接用 `[_id] = _id`？（提示：uapi 枚举有洞/被禁用项，紧凑序号做密集数组——__ctx_convert_unused 哨兵的作用。）
5. LSM_HOOK 清单加一条钩子时，三家消费者中谁的产物**不需要**重新编译？（提示：static call 的声明/调用点在 security.c 与各 LSM 的 hooks 文件里——bpf_lsm.h 的 BPF trampoline 原型何时才实例化？）
6. 为 syscall 表选择"数据文件+脚本"而非 X-macro 的三个理由中，哪一条是 X-macro 的**根本不可达**？（提示：asm 与 C 同时消费同一份清单 vs 宏的编译单元隔离。）
