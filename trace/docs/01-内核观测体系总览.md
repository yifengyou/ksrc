# 内核观测体系总览（Linux 6.6）

> 阅读目标：建立"观测"的全景地图——从 printk 到 eBPF，八类观测技术各自解决什么问题、开销量级如何；ftrace 作为观测的"中枢系统"其 tracefs / trace_array / tracer / trace_event 的分层架构；一条事件从内核埋点写到用户态读出的全链路；以及本目录（trace/）下 .rst 镜像文档的导读。

---

## 一、为什么需要"观测体系"

内核是个没有 printf 调试器的黑盒：无法下断点（会拖垮实时性），无法打日志（热路径每秒调用千万次）。观测体系的设计哲学是**分级插桩**：

* **静态插桩**（编译期决定）：tracepoint、ftrace function tracer——代码里预埋调用点，运行时可零成本关闭；
* **动态插桩**（运行期决定）：kprobe/uprobe——不重编译、不打补丁，任意地址下钩子；
* **采样观测**（统计推断）：perf_events 硬件计数器——不拦截执行流，周期性"拍照"；
* **全量截获**（信息兜底）：printk/oops/kdump——出错时保住现场。

一个统一的矛盾贯穿始终：**信息量 vs 开销**。观测体系的所有设计（static_key 零开销分支、per-CPU 无锁 ring buffer、NMI 安全）都是在压低"观察者效应"。

### 1.1 观测技术族谱与开销量级

| 技术 | 插桩方式 | 典型用途 | 未启用开销 | 启用开销/次 | 可编程 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| printk | 静态（文本） | 通用调试、告警 | ~0（分支判断） | 数 μs（含格式化/锁） | 否 |
| tracepoint（TRACE_EVENT） | 静态（结构化） | 高频事件记录（sched/irq/block） | **~0**（static_key+jump label，一条 nop/跳转） | 数十~百 ns | 回调注册 |
| ftrace function tracer | 静态点+动态补丁 | 函数级跟踪、延迟归因 | ~0（nop 占位） | ~100-300 ns/函数（含 ring buffer 写） | ops 回调 |
| kprobe | 动态（int3 断点） | 任意内核地址、取参数/局部变量 | 0 | int3 陷阱 ~0.3-1 μs；optprobe jmp ~100-200 ns | C handler/BPF |
| uprobe | 动态（用户态 int3+XOL） | 用户态库函数、USDT | 0 | ~1-2 μs（跨上下文+XOL） | C handler/BPF |
| perf_events | 计数/采样 | CPU 占用剖析、PMU 微架构事件 | ~0 | 计数读 ~数十 ns；采样含 PMI ~数 μs | 工具生态 |
| eBPF | 挂载前四者之上 | 定制聚合、直方图、策略 | 0（附着时） | 宿主事件+程序执行，典型 < 1 μs | 是（验证器） |
| lockdep / DEBUG_* | 编译期检测器 | 死锁、竞态、内存错误 | 高（数倍减速） | —— | 否 |
| panic + oops + kdump | 崩溃路径 | 事后取证（vmcore） | 0 | 一次性 | 否 |

> 💡 开销是数量级估算，真实数字依赖架构与场景（详见第 4/6 章的对比实验方法）。核心结论：**未启用的 tracepoint 与 function tracer 是免费的**——这正是 ftrace 生态能被生产内核默认开启的原因。

### 1.2 技术间的依赖关系

这些技术不是并列的，而是层层叠加：

```
                eBPF（可编程层：程序+map 聚合）
                 │ 挂载于 ↓
   ┌─────────────┼───────────────────┐
   tracepoint   kprobe/uprobe      perf_events(PMU/软件事件)
   （静态点）    （动态点）            （采样计数）
   │             │                    │
   │  trace_kprobe 把 kprobe 包装成"合成 tracepoint"
   │  perf 可直接吃 tracepoint（perf_tracepoint pmu）
   ▼
  ftrace ring buffer（统一的事件落地格式 trace_entry）
   ▲
   tracer 家族（function/graph/irqsoff/wakeup/hwlat/osnoise）
   ——全都把输出写进同一个 buffer 体系
```

## 二、ftrace 整体架构

ftrace 之名容易误导——它不只是"function tracer"，而是**一整个观测框架**：tracefs 接口层、tracer 插件层、事件层、buffer 层四大件。

### 2.1 tracefs 挂载与目录

```
/sys/kernel/tracing（旧符号 /sys/kernel/debug/tracing）
├── trace                     # 读：快照式查看 buffer（读完不消费）
├── trace_pipe                # 读：流式消费（读走即删）
├── trace_marker              # 写：用户态注入标记（配合 blk inject）
├── tracing_on                # 全局开关（0/1，控制 ring buffer 是否接收事件）
├── current_tracer            # 切换 tracer：function/function_graph/irqsoff/...
├── available_tracers         # 内核编译进来的 tracer 清单
├── trace_options             # 行格式选项（print-parent/irq-info/latency-format...）
├── trace_clock               # 时钟源（见 2.5）
├── trace_buf size相关：buffer_size_kb / buffer_total_size_kb / per_cpu/
├── set_event / events/       # 事件子系统（见第四节）
├── set_ftrace_filter / set_ftrace_notrace     # function tracer 过滤
├── set_graph_function / set_graph_notrace     # function_graph 过滤

├── hwlat_detector/           # hwlat tracer 参数
├── osnoise/ timerlat/        # 6.6 的噪声分解 tracer
└── README                    # 内核自述文件清单
```

### 2.2 核心数据结构：trace_array

ftrace 的最顶层容器是 `struct trace_array`（kernel/trace/trace.h:319），每个 tracing 实例（包括全局实例）各有一个：

```c
// kernel/trace/trace.h (v6.6, 节选)
struct trace_array {
	struct list_head	list;              // 挂入 ftrace_trace_arrays 全局链
	char			*name;              // 实例名（全局实例为 NULL）
	struct array_buffer	array_buffer;   // 主 buffer（per-CPU ring buffer 的封装）
#ifdef CONFIG_TRACER_MAX_TRACE
	struct array_buffer	max_buffer;     // 快照 buffer：wakeup/irqsoff 存"最坏现场"
	bool			allocated_snapshot;
	unsigned long		max_latency;      // 历史最大延迟
#endif
	struct trace_pid_list	__rcu *filtered_pids;  // set_event_pid
	arch_spinlock_t		max_lock;          // 保护 buffer swap（轻量，避开 lockdep）
	int			stop_count;
	int			clock_id;              // trace_clock 索引
	struct tracer		*current_trace;   // ★当前 tracer（struct tracer 指针）
	unsigned int		trace_flags;      // trace_options 的位图
	struct dentry		*dir;               // tracefs 目录 dentry
	struct dentry		*event_dir;         // events/ 目录
	struct list_head	systems;             // trace_subsystem_dir 链表
	struct list_head	events;              // trace_event_file 链表
	cpumask_var_t		tracing_cpumask;    // 只在指定 CPU 上记录
	/* one per_cpu trace_pipe can be opened by only one user */
	cpumask_var_t		pipe_cpumask;       // per-cpu pipe 独占
#ifdef CONFIG_FUNCTION_TRACER
	struct ftrace_ops	*ops;             // 本实例的 function tracer ops
	int			function_enabled;
#endif
	...
};

// kernel/trace/trace.c (v6.6)
static struct trace_array global_trace = { ... };   // 顶层实例（line 489）
struct list_head ftrace_trace_arrays = LIST_HEAD_INIT(ftrace_trace_arrays);
```

要点：
* **`array_buffer` vs `max_buffer`**：延迟类 tracer（irqsoff/wakeup）持续往主 buffer 记录，一旦发现"新最大延迟"，就把主 buffer 与 max_buffer **整体交换**（swap），max_buffer 里冻结的就是那次最坏路径的完整现场——用户读 `per_cpu/cpuN/stats` 之外的 `trace` 时看到的即是 swap 后的快照；
* `trace_flags` 与 `trace_options` 文件一一对应（`TRACE_FLAGS` 宏展开，trace.c:1586），控制打印格式（irq-info、print-parent、latency-format 等 20+ 项）。

### 2.3 tracer 框架：struct tracer

每个 tracer 是一个插件，向框架注册回调（kernel/trace/trace.h:556）：

```c
// kernel/trace/trace.h (v6.6, 注释节选)
struct tracer {
	const char		*name;      // 出现在 available_tracers 的名字
	int			(*init)(struct trace_array *tr);  // echo X > current_tracer
	void			(*reset)(struct trace_array *tr);  // 切走时
	void			(*start)(struct trace_array *tr);  // echo 1 > tracing_on
	void			(*stop)(struct trace_array *tr);   // echo 0 > tracing_on
	void			(*open)(struct trace_iterator *iter);   // 打开 trace 文件
	void			(*pipe_open)(struct trace_iterator *iter); // trace_pipe
	ssize_t			(*read)(struct trace_iterator *iter, ...); // 覆盖默认 pipe 读
	void			(*print_header)(struct seq_file *m);  // 列头
	enum print_line_t	(*print_line)(struct trace_iterator *iter); // 每条格式
	int			(*set_flag)(struct trace_array *tr,
					    u32 old_flags, u32 bit, int set);
	struct tracer_flags	*flags;     // tracer 私有选项（tracer_opt 表）
	bool			print_max;  // 是否打印 max_buffer（延迟类）
	bool			allow_instances; // 是否允许在 instances 里使用
#ifdef CONFIG_TRACER_MAX_TRACE
	bool			use_max_tr;   // 是否需要快照 buffer
#endif
	...
};
```

框架的调度逻辑：`current_tracer` 写入 → 持 `trace_types_lock` → 调旧 tracer 的 `reset()` → 调新 tracer 的 `init()`（此时它注册自己的 ftrace_ops / tracepoint probe / 启动内核线程）→ 读取走 `print_line()`。**tracer 层之下只依赖两个原语：function tracer 的 ftrace_ops 回调、tracepoint 的 probe 注册**——第 2/5 章分别展开。

### 2.4 事件层：trace_event_call 与 trace_event_file

静态事件（TRACE_EVENT 宏定义）在内核里是三级结构：

```
struct trace_event_call（每个事件一个，静态生成，放 _ftrace_events 段）
  ├─ .class: struct trace_event_class（共享的 probe 回调/字段定义/reg 函数）
  ├─ .tp:    struct tracepoint（静态 key + funcs 数组，见第 2 章）
  ├─ .event: struct trace_event（print 回调表 trace/raw/hex/binary + 类型 id）
  └─ .print_fmt / .filter / .perf_refcount / .prog_array(BPF)
          │
          ▼ 每个 trace_array 实例 × 每个事件 = 一个
struct trace_event_file（实例侧的"开关+过滤+触发器"集合）
  ├─ .event_call: 反向指针
  ├─ .tr:        所属 trace_array
  ├─ .filter:    struct event_filter（谓词程序，见第 2 章）
  ├─ .triggers:  event_trigger_data 链表
  └─ .flags:     EVENT_FILE_FL_ENABLED / _FILTERED / _SOFT_DISABLED /
                 _TRIGGER_MODE / _PID_FILTER ...（原子位操作）
```

这个"call（全局静态）+ file（每实例动态）"的拆分是 3.x 引进 instances 之后的关键设计：**事件格式全局唯一（format 文件只有一份定义），但 enable/filter/trigger 每个实例独立**——于是一个生产实例可以只开 `sched_wakeup`+filter，另一个诊断实例同时开全套事件，互不干扰。

### 2.5 instances：多实例 buffer

```c
// kernel/trace/trace.c (v6.6, 节选)
static int instance_mkdir(const char *name)      // line 9584
{
	...
	tr = trace_array_create(name);           // 新 trace_array + 独立 buffer
	...
}
```

`mkdir /sys/kernel/tracing/instances/foo` 后，foo 下拥有与顶层同名的全套文件（trace/trace_pipe/events/...），buffer 大小独立（buffer_size_kb），tracer 独立（current_tracer）。删除目录即销毁（`trace_array_destroy`，要求引用计数归零）。内核代码侧也有 API：`trace_array_get_by_name()` / `trace_array_printk_buf()`——模块可以创建私有实例写事件而不污染全局 buffer（bpftrace 之外的很多工具这么用）。

### 2.6 时钟：trace_clock

跨 CPU 排序事件的正确性取决于时钟选择（trace.c:1591）：

| 时钟 | 实现 | 特点 |
| :--- | :--- | :--- |
| local（默认） | `trace_clock_local` → sched_clock | per-CPU 单调，读取代价最低；**跨 CPU 可能乱序** |
| global | `trace_clock_global` | 全局时钟，跨 CPU 严格；高争用（拿全局锁累加） |
| counter | 简单计数器 | 只保证顺序无物理意义 |
| uptime / mono / mono_raw / boot / tai | ktime_get_*_fast_ns 系列 | 单调钟，跨 CPU 可比；boot 含 suspend 时间 |
| perf | `trace_clock` | 与 perf 事件时间轴对齐 |

> 💡 排查"CPU 间事件顺序怪异"是新手最常见困惑——多 CPU 场景切 `global` 或 `mono` 即可（`echo global > trace_clock`），代价是写路径变慢。

## 三、一条 trace 事件的全链路

以 `sched_switch` 为例，从内核埋点到用户态读出的完整旅程：

```
━━━ 内核态：事件产生 ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
__schedule()
  └─ trace_sched_switch(preempt, prev, next)              include/trace/events/sched.h
       │ 内联展开为：
       ├─ if (static_key_false(&__tracepoint_sched_switch.key))   ← jump label，
       │    未启用时这里是一条 NOP（x86: 5 字节 jmp/nop 补丁）        零成本检查
       └─ __DO_TRACE(...)
            ├─ preempt_disable_notrace()                   防止回调中被调度
            ├─ __DO_TRACE_CALL → static_call(tp_func_sched_switch)  ← static_call
            │    （单消费者时直接跳到该回调；多消费者跳 iterator）
            │    落到 trace_event_raw_event_sched_switch()  ← TRACE_EVENT stage6 生成
            │        ├─ trace_trigger_soft_disabled(file)   trigger/soft-disable 检查
            │        ├─ trace_event_get_offsets_sched_switch()  动态字段偏移计算
            │        ├─ trace_event_buffer_reserve(&fbuffer, file, len)
            │        │     ├─ trace_event_get_buffer()     （filter 场景用 per-cpu 临时 buffer）
            │        │     └─ ring_buffer_lock_reserve()   ★per-CPU ring buffer 留位
            │        │          ├─ preempt_disable_notrace + trace_recursive_lock（重入保护）
            │        │          └─ __rb_reserve_next()     无锁留位（见第 3 章）
            │        ├─ TP_fast_assign() 展开体：逐字段填 __entry
            │        └─ trace_event_buffer_commit(&fbuffer)
            │              ├─ filter_check_discard()      filter 不匹配 → discard_commit
            │              ├─ event_triggers_call()       trigger 执行（traceon/stack/hist…）
            │              └─ ring_buffer_unlock_commit() 提交（推进 commit_page）
            └─ preempt_enable_notrace()
                                      │
━━━ 缓冲：per-CPU ring buffer（第 3 章详解）━━━━━━━━━━━━━━━━━━━━━━━
        head_page ⇄ [pages 循环链] ⇄ tail_page/commit_page
        事件 = 8 字节头(type_len:5|time_delta:27) + trace_entry + payload
                                      │
━━━ 用户态：读取 ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
cat trace（快照读，不消费）
  └─ tracing_open → trace_iterator 初始化（per-CPU ring_buffer_iter 游标）
  └─ seq_read → s_next → trace_find_next_entry_inc
       ├─ __find_next_entry: 跨所有 CPU 比时间戳，挑最早事件   ← 需可靠时钟
       └─ print_trace_line(iter)
            ├─ iter->trace->print_line()   tracer 定制格式（function_graph 等）
            └─ 默认: entry->type 查 event_hash → trace_event 的 .trace 回调
                 （trace_raw_output_sched_switch，TP_printk 格式化）

cat trace_pipe（流式消费）
  └─ tracing_open_pipe（每 CPU 最多一个读者，pipe_cpumask 独占）
  └─ tracing_read_pipe → find_next_entry → print_trace_line → trace_consume
       └─ ring_buffer_consume()  ★把已读页面交还（consumer 模式：读走即删）

per_cpu/cpu0/trace_pipe_raw + events/.../format
  └─ perf/BPF/trace-cmd 直接读二进制记录，按 format 文件自行解码
```

全链路的三级解耦值得注意：**埋点（tracepoint）不知道 buffer，buffer 不知道格式，格式（trace_event）不知道读取者**——同一份 `sched_switch` 事件可以被 ftrace 文本、trace-cmd 二进制、perf、eBPF 四种消费者复用。

## 四、事件子系统目录结构

```
/sys/kernel/tracing/events/
├── enable                        # 全系统事件总开关（写 1/0/2）
├── set_event_pid                 # （顶层另有）按 pid 过滤事件
├── sched/                        # ← 子系统（TRACE_SYSTEM）
│   ├── enable                    # 子系统级开关
│   ├── filter                    # 子系统级 filter（批量设置）
│   ├── sched_switch/             # ← 事件
│   │   ├── enable                # 事件开关（写 1 启用 / 0 停 / 'toggle'）
│   │   ├── filter                # 谓词，如 'prev_pid == 1234 && next_prio < 100'
│   │   ├── trigger               # 触发动作（见下）
│   │   ├── format                # ★二进制布局自描述（perf/BPF 靠它解码）
│   │   ├── id                    # 事件 id（perf_event_open attr.config 用）
│   │   ├── hist                  # 直方图（CONFIG_HIST_TRIGGERS）
│   │   └── inject                # 注入伪事件（CONFIG_TRACE_EVENT_INJECT，测试用）
│   ├── sched_wakeup/ ...
│   └── sched_process_exec/
├── irq/  block/  net/  kmem/  ...（每个 TRACE_SYSTEM 一个目录）
├── kprobes/                      # kprobe_events 动态生成的"合成事件"也在此
└── synthetic/                    # synth 事件（跨事件聚合出的新事件）
```

`format` 文件的内容即 `TP_STRUCT__entry` 的运行时反射（由 `event_define_fields()` 生成，trace_events.c）：

```
field:unsigned short common_type;  offset:0; size:2; signed:0;   ← trace_entry
field:unsigned char common_flags;  offset:2; size:1; signed:0;
field:unsigned char common_preempt_count; offset:3; size:1; ...
field:int common_pid;              offset:4; size:4; signed:1;
field:char prev_comm[16];          offset:8;  size:16; ...
field:pid_t prev_pid;              offset:24; size:4; signed:1;
...
print fmt: "task %s:%d [%d] ==> %s:%d [%d]", ...（TP_printk 原文）
```

trigger 文件支持的动词（`echo <trigger>[:count][if <filter>] > trigger`）：
* `traceon` / `traceoff`——条件启停全局记录；
* `stacktrace`——命中时抓内核栈；
* `enable_event/<sys>/<event>` / `disable_event/...`——事件联动（比如 sched_wakeup 命中时才打开 sched_switch）；
* `hist:keys=...`——直方图聚合（histogram.rst 有完整语法）；
* `snapshot`——抓 max_buffer 快照。

## 六、实战观测

```bash
# 1. 环境确认
mount -t tracefs none /sys/kernel/tracing      # 一般已由 systemd 挂好
cat available_tracers                           # nop function function_graph wakeup irqsoff ...

# 2. 最小闭环：事件 → buffer → 读出
echo 1 > events/sched/sched_wakeup/enable
echo 1 > events/sched/sched_switch/enable
echo 1 > tracing_on
sleep 2 && echo 0 > tracing_on
cat trace | head -20                             # 文本快照
head -c 4096 per_cpu/cpu0/trace_pipe_raw | xxd | head   # 原始二进制

# 3. 独立实例隔离（诊断不互相踩）
mkdir instances/diag
echo 1 > instances/diag/tracing_on
echo 'prev_pid < 10' > instances/diag/events/sched/sched_switch/filter
echo 1 > instances/diag/events/sched/sched_switch/enable
cat instances/diag/trace

# 4. 多 CPU 顺序错乱时换全局时钟
echo global > trace_clock

# 5. 查看每 CPU buffer 状态（含丢失数）
cat per_cpu/cpu0/stats
# entries, overrun, commit overrun, dropped events, ...
```

## 七、思考题

1. 为什么 `struct trace_event_call` 与 `struct trace_event_file` 必须拆成两级？如果合并（开关/过滤直接放 call 里），instances 机制会遇到什么问题？
2. `trace` 与 `trace_pipe` 的读取语义差异，如何影响它们各自适合的观测场景？"读到一半事件被覆盖"在哪个文件上不可能发生、为什么？
3. 默认时钟 `local` 下，跨 CPU 事件的时间戳可能乱序。结合第 3 章预告：ring buffer 是靠什么机制在读取侧（`__find_next_entry`）弥补这个乱序的？换 `global` 时钟后写路径多了什么代价？
4. 观察 `tracing_max_latency` 与 snapshot 机制：irqsoff tracer 发现新最大值时为什么必须**交换 buffer**而不是"复制一遍"？交换的原子性由哪个锁保护？
5. 对比表格里 kprobe 与 tracepoint 的开销量级差（约一个数量级）。从 int3 陷阱（异常陷入→IDT→do_int3→返回）与 static_call 直接跳转的路径长度，解释这个差距的来源。
6. 读取 `events/sched/enable` 可能返回 `0`/`1`/`X`/`?` 四种值（events.rst）。`X` 与 `?` 分别表示什么？再观察：给某事件装一个 trigger 但不 enable，`events/.../enable` 读数是多少？（提示：events.rst 第 7 节"soft mode"——trigger 安装时 tracepoint 已实际注册但事件处于 soft-disabled。）
