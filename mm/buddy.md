# buddy

Linux 6.6 内核中的伙伴系统（Buddy System）是物理内存管理的核心，它通过一种巧妙的“分”与“合”的策略，高效地分配和回收以页（Page）为单位的内存，并有效减少了外部碎片。

### 🎯 核心原理

伙伴系统的核心思想是将所有空闲的物理页框按照 **2的幂次方**（即 `2^order` 个连续页）进行分组管理。

*   **Order (阶)**：代表一个内存块的大小，其包含 `2^order` 个连续的物理页。例如，`order=0` 表示1个页（通常为4KB），`order=3` 表示8个页（32KB）。Linux内核通常支持从 `order=0` 到 `MAX_ORDER-1`（默认 `MAX_ORDER=11`）的块。
*   **Buddy (伙伴)**：两个物理地址相邻、大小相同（同order）、且源于同一个更大内存块的空闲块，互为“伙伴”。伙伴的地址可以通过一个简单的异或运算快速计算得出：
    `buddy_address = current_address ^ (1 << order)`
*   **设计目标**：通过按需拆分大块内存来满足小内存请求，并在释放时积极合并相邻的空闲伙伴，从而最大限度地减少**外部碎片**（即大量不连续的小空闲块无法满足大块内存申请的问题）。

### 🗂️ 核心数据结构

在 Linux 6.6 内核中，伙伴系统的核心数据结构定义在 `include/linux/mmzone.h` 等头文件中，主要涉及以下几个：

1.  **`struct page`**:
    这是描述系统中每一个物理页的核心结构体。对于伙伴系统，以下字段至关重要：
    *   `flags`: 包含 `PG_buddy` 标志位，用于标记该页是否为一个空闲的伙伴块的一部分。
    *   `private`: 当页面空闲时，此字段存储该块对应的 `order` 值。

2.  **`struct free_area`**:
    这个结构体用于管理特定 `order` 的所有空闲块。
    ```c
    struct free_area {
        struct list_head free_list; // 指向该阶所有空闲块的双向链表
        unsigned long nr_free;      // 该阶空闲块的总数
    };
    ```
    内核为每个 `order` (0 到 MAX_ORDER-1) 都维护一个 `free_area` 实例。

3.  **`struct zone`**:
    物理内存被划分为不同的区域（Zone），如 `ZONE_DMA`, `ZONE_NORMAL` 等，以满足不同硬件和内核的寻址需求。每个 `zone` 都拥有一套独立的伙伴系统，其核心就是 `free_area` 数组。
    ```c
    struct zone {
        // ... 其他字段 ...
        struct free_area free_area[MAX_ORDER]; // 管理本区域内所有阶的空闲块
        // ... 其他字段 ...
    };
    ```
    这意味着每个内存区域都独立地管理着自己的 `order=0` 到 `order=10` 的空闲页块链表。

### ⬇️ 基本分配算法

当一个进程或内核模块请求 `N` 个连续页时，分配流程遵循“先找最小可用，无则拆分大块”的原则：

1.  **计算 Order**: 将请求的页数 `N` 向上取整到最小的 `2^k`，确定所需的 `order = k`。
2.  **查找空闲块**: 从 `zone->free_area[order]` 的空闲链表中查找是否有可用的块。
3.  **直接分配**: 如果找到，直接从链表中移除该块，更新 `nr_free` 计数，并清除其 `PG_buddy` 标志，然后返回该内存块。
4.  **递归拆分 (Splitting)**: 如果当前 `order` 的链表为空，则向更高一阶 (`order+1`) 查找。找到一个更大的空闲块后，将其一分为二，形成两个新的“伙伴”。其中一个伙伴继续向下拆分，直到得到所需大小的块；另一个伙伴则被加入到对应低一阶的空闲链表中。这个过程会一直重复，直到满足最初的分配请求。

#### 📜 简化的分配伪代码

```c
struct page *alloc_pages(int order) {
    int curr_order = order;
    struct zone *zone = /* 根据分配策略选择合适的zone */;

    // 从请求的order开始，向上寻找第一个有空闲块的阶
    while (curr_order < MAX_ORDER) {
        if (!list_empty(&zone->free_area[curr_order].free_list)) {
            // 找到可用块
            struct page *page = list_first_entry(...);
            list_del(&page->lru); // 从链表中移除
            zone->free_area[curr_order].nr_free--;

            // 如果找到的是更大的块，则需要拆分
            while (curr_order > order) {
                curr_order--;
                // 计算伙伴块的地址
                struct page *buddy = page + (1 << curr_order);
                // 将伙伴块加入到低一阶的空闲链表
                list_add(&buddy->lru, &zone->free_area[curr_order].free_list);
                zone->free_area[curr_order].nr_free++;
                set_page_order(buddy, curr_order); // 设置伙伴块的order
                __SetPageBuddy(buddy);             // 标记为伙伴页
            }
            __ClearPageBuddy(page); // 清除分配出去的页面的伙伴标志
            return page;
        }
        curr_order++;
    }
    return NULL; // 分配失败
}
```

### ⬆️ 基本回收算法

当一块内存被释放时，回收流程遵循“释放先查伙伴，闲则合并”的原则，以对抗外部碎片：

1.  **确定 Order**: 根据被释放页面的 `private` 字段，获取其所属块的 `order`。
2.  **查找伙伴**: 利用异或公式计算出其伙伴块的物理地址。
3.  **检查并合并 (Coalescing)**:
    *   检查伙伴块是否也是空闲的（即 `PG_buddy` 标志被设置，且 `order` 相同）。
    *   如果伙伴块**不空闲**，则将当前块直接添加到 `zone->free_area[order]` 的空闲链表中。
    *   如果伙伴块**是空闲的**，则将其从所在链表中移除，并将当前块与伙伴块合并成一个更大的、`order+1` 的新块。
4.  **递归合并**: 将这个新合并成的更大块视为一个整体，重复步骤2和3，继续尝试与新的伙伴合并，直到无法再合并为止（通常是达到了 `MAX_ORDER-1` 或者其伙伴不空闲）。

#### 📜 简化的回收伪代码

```c
void free_pages(struct page *page, int order) {
    struct zone *zone = /* page所在的zone */;
    
    // 尽可能向上合并
    while (order < MAX_ORDER - 1) {
        // 计算伙伴的物理地址
        struct page *buddy = __page_find_buddy(page, page_to_pfn(page), order);

        // 检查伙伴是否空闲且有效
        if (!page_is_buddy(page, buddy, order))
            break; // 伙伴不空闲，停止合并

        // 伙伴空闲，将其从链表中移除
        list_del(&buddy->lru);
        zone->free_area[order].nr_free--;
        __ClearPageBuddy(buddy);

        // 合并成更大的块（地址取两者中较小的那个）
        if (buddy < page)
            page = buddy;
        
        order++; // 块的阶数加一
    }

    // 将最终合并后的块加入对应阶的空闲链表
    list_add(&page->lru, &zone->free_area[order].free_list);
    zone->free_area[order].nr_free++;
    set_page_order(page, order);
    __SetPageBuddy(page);
}
```

## 伙伴系统的碎片整理策略有哪些？

虽然伙伴系统（Buddy System）通过“分裂”和“合并”机制在一定程度上缓解了外部碎片，但在系统长期运行后，仍可能出现**总空闲内存充足，但无法满足大块连续内存分配请求**的情况。为了解决这个问题，Linux 内核在伙伴系统的基础上引入了多种策略来进一步整理和预防内存碎片。

### 🧬 核心策略：内存规整 (Memory Compaction)

这是 Linux 内核对抗外部碎片最主要、最直接的“主动出击”手段。当高阶（`order > 0`）内存分配失败时，内核会触发内存规整机制。

#### 工作原理
内存规整的核心思想是**移动页面**。它通过在内存区域内扫描，将分散的、正在使用的“可移动页”（如用户空间的应用程序数据页）迁移到内存的一端，从而在另一端腾出大块的、连续的物理空闲空间。这个过程就像整理书架，把零散的书推到一边，空出一大片区域来放一套新的大部头丛书。

#### 触发时机
*   **直接规整 (Direct Compaction)**: 当一个进程同步地申请大块内存失败后，会立即触发一次内存规整，试图为本次分配开辟空间。
*   **后台规整 (kcompactd)**: 内核有一个名为 `kcompactd` 的内核线程，它在后台异步运行，定期或在特定条件下对内存进行规整，以预防未来可能出现的碎片问题。

### 📦 预防策略：可移动区 (ZONE_MOVABLE)

这是一种从源头上减少碎片的“预防性”策略。内核将物理内存划分为不同的区域（Zone），其中一个特殊的区域就是 `ZONE_MOVABLE`。

#### 工作原理
*   **分类管理**: 内核将内存页分为“可移动的”和“不可移动的”。不可移动的页（如内核代码、某些硬件驱动分配的DMA缓冲区）被限制在 `ZONE_DMA` 或 `ZONE_NORMAL` 等区域。
*   **集中管理**: 所有可以被安全迁移的用户空间和部分内核数据页，都会被优先分配到 `ZONE_MOVABLE` 中。

通过这种隔离，`ZONE_MOVABLE` 内部的页面可以随时被内存规整机制自由地搬来搬去，而不用担心影响到那些固定不动的内核页，极大地提高了规整的效率和成功率。

### 💡 上层优化：SLUB 分配器

严格来说，SLUB 分配器本身并不是一个碎片整理策略，但它作为构建在伙伴系统之上的小内存分配器，对减少碎片有重要贡献。

#### 工作原理
*   **按需分配**: 对于内核中频繁使用的小对象（如几十到几百字节），如果每次都向伙伴系统申请一个最小为 4KB 的页，会产生大量的内部碎片。SLUB 分配器会为每种类型的小对象创建一个专门的缓存（Cache）。
*   **减少干扰**: SLUB 只在需要时才向伙伴系统申请较大块的内存（通常是多个页）来填充自己的缓存，然后将这些大块内存切割成许多小对象进行管理。这大大减少了对伙伴系统底层物理页的直接、零散请求，避免了因大量小块分配而快速产生外部碎片的问题。

### 💨 辅助策略：水位线与页回收 (Watermarks & Page Reclaim)

这个机制主要目的是保证系统有足够的空闲内存，间接地为伙伴系统的合并创造了条件。

#### 工作原理
每个内存区域都维护着一组水位线（`pages_min`, `pages_low`, `pages_high`）。当空闲页数低于某个阈值（如 `pages_low`）时，内核会唤醒 `kswapd` 后台线程。`kswapd` 会负责回收不再使用的页面（如换出不常用的匿名页、清理无用的页面缓存），将它们占用的物理页释放回伙伴系统。这些被释放的页就有可能与其相邻的空闲页合并成更大的块，从而增加了高阶内存分配的成功率。

## 伙伴系统如何为内核数据结构分配内存？

伙伴系统（Buddy System）并不直接为大多数内核数据结构分配内存，而是作为底层的物理页提供者，为上层的 **SLUB 分配器**（或其前身 SLUB）提供“原材料”。这是一种高效的分层内存管理设计。

简单来说，这个过程就像一个汽车制造厂：
*   **伙伴系统** 是负责采购和切割钢板的部门，它只提供标准尺寸（如 4KB, 8KB, 16KB...）的钢板（物理页）。
*   **SLUB 分配器** 是具体的生产线，它领取大块的钢板，然后根据需求将其精加工成各种特定形状的零件，比如方向盘、车门等（内核数据结构，如 `task_struct`, `inode` 等）。

下面是这个协作过程的详细步骤：

### 🔗 协作流程：从请求到分配

1.  **内核发起请求**
    当内核代码需要创建一个数据结构（例如，创建一个新的进程描述符 `task_struct`）时，它会调用相应的 API，如 `kmem_cache_alloc()`。这个请求最终会到达 SLUB 分配器。

2.  **SLUB 分配器接管**
    SLUB 分配器会为每种常用的内核对象维护一个或多个专用的缓存池（称为 `kmem_cache`）。它会首先在自己的缓存池中查找是否有空闲的对象可供使用。
    *   如果有，直接从缓存中取出一个返回，速度极快。
    *   如果没有，SLUB 就需要向底层申请新的内存来扩充自己的缓存池。

3.  **向伙伴系统申请“原材料”**
    SLUB 分配器通过调用伙伴系统的接口函数（主要是 `alloc_pages()`）来申请一块或多块连续的物理页。由于这些页将用于存放同一种类型的小对象，SLUB 通常会申请一个或多个完整的页（即 `order=0` 或更高阶的块）。

4.  **伙伴系统分配物理页**
    伙伴系统接收到 `alloc_pages(order)` 的请求后，会根据其核心算法（在对应的 `free_area[order]` 链表中查找，若无则拆分更大的块）分配出所需大小的连续物理页，并返回给 SLUB 分配器。

5.  **SLUB 初始化对象池**
    SLUB 拿到这些物理页后，会将它们视为一个“SLUB”，并按照该 SLUB 所管理的对象大小，将这片内存区域切割成许多个等大的槽位，每个槽位可以容纳一个对象。然后，它将这些空闲的槽位用链表串联起来，形成一个空闲对象列表。

6.  **返回最终对象**
    最后，SLUB 从这个新创建的空闲列表中取出第一个对象，返回给最初发起请求的内核代码。

### 🎯 为什么采用这种分层设计？

这种设计巧妙地结合了两种分配器的优点，解决了单一分配器无法兼顾的问题：

| 特性 | 伙伴系统 (Buddy System) | SLUB 分配器 |
| :--- | :--- | :--- |
| **分配粒度** | 较大，以页为单位（`2^order` 个页）。 | 很小，可以是几十字节到几KB不等的任意大小。 |
| **主要职责** | 管理物理内存，高效分配和回收页框，解决**外部碎片**问题。 | 管理内核对象，高效分配和回收小内存块，解决**内部碎片**问题。 |
| **优点** | 合并相邻空闲页的能力强，能有效产生大块连续内存。 | 针对特定对象优化，分配/释放速度快，缓存友好，复用率高。 |
| **缺点** | 对于小于1页的分配请求会造成严重的空间浪费（内部碎片）。 | 不适合直接管理大块物理内存，复杂度高。 |

综上所述，伙伴系统通过为上层的 SLUB 分配器提供稳定、高效的物理页支持，间接地为内核数据结构提供了内存。这种分工合作的方式，使得 Linux 内核能够同时满足对大块连续内存和小块对象内存的高效分配需求。

## 伙伴系统和SLUB如何协作分配大内存？

对于“大内存”的分配，伙伴系统（Buddy System）和 SLUB 分配器的协作方式与小对象分配截然不同。简单来说：**对于真正的大块内存请求，SLUB 会直接退居二线，完全由伙伴系统来负责分配。**

这里的“大内存”通常指大于 128KB（具体阈值可能因内核版本和配置而异）的连续内存。

### 🤝 协作流程：以 `kmalloc` 为例

当内核代码通过 `kmalloc(size, flags)` 请求一块大内存时，整个过程如下：

1.  **`kmalloc` 进行大小判断**
    `kmalloc` 是内核中最常用的内存分配接口。它首先会检查请求的 `size` 是否超过了预设的阈值（例如 128KB）。这个阈值是区分使用 SLUB 还是直接使用伙伴系统的分水岭。

2.  **分支一：小内存 (`size <= 128KB`)**
    *   这是 SLUB 的主场。`kmalloc` 会调用 SLUB 分配器（通过 `kmem_cache_alloc`），从相应的缓存（如 `kmalloc-64`, `kmalloc-4096`）中分配一个对象。
    *   如果 SLUB 的缓存不足，它会向伙伴系统申请页框来扩充自己的缓存池，正如我们之前讨论过的那样。

3.  **分支二：大内存 (`size > 128KB`)**
    *   **SLUB “退让”**：对于这个尺寸的请求，`kmalloc` 不会经过 SLUB 分配器。因为 SLUB 是为高效管理大量小对象而设计的，用它来分配大块内存不仅效率低，而且会造成不必要的内部碎片。
    *   **伙伴系统“接管”**：`kmalloc` 会直接调用伙伴系统的核心函数 `alloc_pages()`。
        *   它会根据请求的大小计算出所需的阶（order），即需要 `2^order` 个连续的物理页。
        *   然后调用 `alloc_pages(gfp_mask, order)`，从伙伴系统中直接获取一大块连续的物理内存。

### 💡 为什么这样设计？

这种设计是为了发挥各自的优势，实现整体性能的最优化：

| 特性 | 伙伴系统 (Buddy System) | SLUB 分配器 |
| :--- | :--- | :--- |
| **擅长领域** | 分配**大块、物理连续**的内存。 | 分配**海量、固定大小的小对象**。 |
| **分配粒度** | 粗粒度，以页（Page）为单位，大小为 `2^order`。 | 细粒度，可以是任意字节大小（在阈值内）。 |
| **主要问题** | 处理小对象会产生严重的**内部碎片**。 | 不适合直接管理大块物理内存，复杂度高。 |

*   **避免浪费**：如果用 SLUB 分配一个大内存，SLUB 本身也需要向伙伴系统申请页框作为基础。这中间多了一层管理，但并没有带来好处。
*   **提升效率**：对于大内存请求，直接使用伙伴系统是路径最短、效率最高的方式。伙伴系统的设计初衷就是高效地合并与拆分大块物理内存。

### 📌 总结

可以将它们的关系理解为：

*   **SLUB 分配器** 是一个高效的“零件分发中心”，专门处理各种标准小零件（小对象）的快速领取和归还。
*   **伙伴系统** 是一个强大的“原材料仓库”，既能给“零件分发中心”提供制造零件的原料（页框），也能直接处理那些对“大型设备”（大内存）的特殊订单。

因此，当需要分配大内存时，系统会选择最直接的路径，绕过“零件分发中心”（SLUB），直接向“原材料仓库”（伙伴系统）下订单。

## slab\slob\slub简单区分

Slab、SLUB 和 SLOB 是 Linux 内核中三种不同的内存分配器，它们都用于高效地管理内核中的小对象内存分配。

### 🔎 如何区分 Slab、SLUB 和 SLOB？

这三种分配器在设计目标、性能和适用场景上各有侧重。简单来说，**SLAB** 是功能完整的经典实现，**SLUB** 是为现代硬件优化的默认选择，而 **SLOB** 则是为资源极度受限的嵌入式系统设计的精简版本。

以下是它们的详细对比：

| 特性 | SLAB (传统实现) | SLUB (当前默认) | SLOB (极简实现) |
| :--- | :--- | :--- | :--- |
| **设计目标** | 功能完整、高性能，支持复杂特性 | 简化设计、降低内存开销，兼顾性能 | 极致精简、最小内存占用，适配嵌入式系统 |
| **核心特点** | 拥有独立的 `struct slab` 描述符，支持缓存着色等高级特性 | 复用 `struct page` 存储信息，无额外元数据开销，采用 per-CPU 缓存减少锁竞争 | 使用简单的链表管理空闲对象，代码量极少 |
| **内存开销** | 较高（需要额外的元数据结构） | 较低（几乎没有额外开销） | 极低（几乎无元数据开销） |
| **性能表现** | 高，但元数据开销可能影响性能 | 更高，分配/释放路径更短，多核扩展性好 | 低，适合低频小对象分配，不适合高并发 |
| **适用场景** | 旧版内核或对功能完整性要求极高的特定场景 | **当前主流内核（5.x/6.x）的默认选择**，适用于服务器、桌面及通用嵌入式设备 | 内存极度受限的嵌入式系统（如 IoT 设备） |

### 🖥️ 如何查看当前系统使用的分配器？

可以通过检查内核的编译配置文件来确定当前系统使用的是哪一种分配器。在终端执行以下命令：

```bash
cat /boot/config-$(uname -r) | grep CONFIG_SLAB
```

这条命令会查询与当前运行内核版本匹配的配置文件，并筛选出包含 "CONFIG_SLAB" 的行。输出结果中，值为 `y` 的选项即为当前启用的分配器。

#### 可能的输出结果：

*   如果显示 `CONFIG_SLUB=y`，则你的系统正在使用 **SLUB** 分配器（这是最常见的情况）。
*   如果显示 `CONFIG_SLAB=y`，则你的系统正在使用传统的 **SLAB** 分配器。
*   如果显示 `CONFIG_SLOB=y`，则你的系统正在使用 **SLOB** 分配器。
