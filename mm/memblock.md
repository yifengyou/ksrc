# memblock

Memblock 是 Linux 内核在启动早期，用于管理物理内存的分配器。它在伙伴系统（Buddy System）等更复杂的内存管理机制初始化之前，负责收集、管理和分配物理内存。

### 📦 核心数据结构

Memblock 的数据结构设计简洁高效，主要由三个结构体层层嵌套构成，通过两个列表来管理所有物理内存。

#### `struct memblock_region` (内存区域)
这是最基础的结构，代表一块连续的物理内存区域。
```c
struct memblock_region {
    phys_addr_t base;         // 物理起始地址
    phys_addr_t size;         // 区域大小
    enum memblock_flags flags; // 区域属性标志
#ifdef CONFIG_NUMA
    int nid;                  // NUMA 节点 ID
#endif
};
```
*   **`base`** 和 **`size`**：定义了内存块的物理地址范围。
*   **`flags`**：标记区域的特殊属性，例如 `MEMBLOCK_NOMAP` 表示该区域不加入内核的直接映射。

#### `struct memblock_type` (内存类型集合)

这是一个内存区域的集合，用于管理一组相同类型的 `memblock_region`。
```c
struct memblock_type {
    unsigned long cnt;          // 当前已使用的区域数量
    unsigned long max;          // regions 数组的最大容量
    phys_addr_t total_size;     // 所有区域的总大小
    struct memblock_region *regions; // 指向 memblock_region 数组
    char *name;                 // 类型名称，如 "memory" 或 "reserved"
};
```
Memblock 主要维护两种类型的集合：
1.  **`memory`**: 记录系统中所有可用的物理内存区域。
2.  **`reserved`**: 记录所有已被预留或占用的物理内存区域，这些内存不能被再次分配。

#### `struct memblock` (全局管理器)
这是顶层的管理结构，一个全局实例 `memblock` 负责协调整个早期内存管理。
```c
struct memblock {
    bool bottom_up;             // 分配方向：true为从低到高，false为从高到低
    phys_addr_t current_limit;  // 可分配内存的物理地址上限
    struct memblock_type memory;   // 可用内存集合
    struct memblock_type reserved; // 预留内存集合
};
```
*   **`bottom_up`**: 控制内存分配的查找方向。默认为 `false`，即从高地址向低地址分配，这有助于将内核镜像放在低地址处。
*   **`current_limit`**: 限制分配的最高物理地址。

这三个结构体的关系可以概括为：一个 `memblock` 实例包含两个 `memblock_type` (`memory` 和 `reserved`)，而每个 `memblock_type` 又管理着一个 `memblock_region` 数组。

### ⚙️ 核心原理与算法

Memblock 的核心思想是使用**区域描述法**来替代早期 bootmem 分配器的位图法。它不再用一个大数组的每一位来表示一页内存的状态，而是用一个个 `memblock_region` 来描述一段段连续的内存。这种方式对于稀疏内存布局的系统更加高效，并且天然支持内存热插拔。

其核心算法主要包括：
*   **合并算法**：当添加新的内存区域时，如果它与现有区域相邻且类型相同，Memblock 会自动将它们合并成一个更大的区域，以减少碎片和管理开销。
*   **First Match 算法**：在进行内存分配时，Memblock 会按照设定的方向（`bottom_up`）遍历 `memory` 列表，找到第一个能满足大小和对齐要求的空闲区域。

### 🔄 分配流程

Memblock 的分配是一个“申请-预留”的过程，主要步骤如下：

1.  **调用分配接口**：内核通过 `memblock_alloc(size, align)` 等接口请求一块指定大小和对齐方式的内存。
2.  **查找可用区域**：分配函数内部会调用 `memblock_find_in_range_node()`。该函数根据 `bottom_up` 的设置，在 `memblock.memory` 列表中查找，同时需要排除掉所有被 `memblock.reserved` 列表覆盖的区域。
3.  **标记为预留**：一旦找到合适的空闲区域，Memblock 会立即调用 `memblock_reserve()` 将该区域从 `memblock.memory` 中移除（或分割），并将其添加到 `memblock.reserved` 列表中，表示这块内存已被占用。
4.  **返回物理地址**：最后，将分配到的物理内存起始地址返回给调用者。

整个过程确保了分配的内存既是可用的，又是唯一的。

### ♻️ 回收流程

Memblock 的“回收”分为两个层面：内部的临时释放和最终向伙伴系统的移交。

#### 内部临时释放
在内核启动阶段，如果需要释放一块之前通过 `memblock_alloc` 分配的内存，可以调用 `memblock_free()`。这个操作非常简单，仅仅是将对应的内存区域从 `memblock.reserved` 列表中删除，使其重新变为可用状态，可以被后续的 `memblock_alloc` 再次分配。需要注意的是，这种释放在早期启动过程中并不常见，因为大多数分配都是永久性的。

#### 最终移交（向伙伴系统）
这是 Memblock 生命周期的终点。当内核启动流程进行到伙伴系统（Buddy System）初始化完成时，Memblock 会将其管理的所有**未被预留的空闲内存**一次性全部移交给伙伴系统。

1.  内核调用 `memblock_free_all()` 函数。
2.  该函数会遍历 `memblock.memory` 中的所有剩余区域。
3.  将这些大块的连续物理内存以页（Page）为单位，释放到伙伴系统的空闲链表中。
4.  从此以后，内核的内存分配将由更高效、更灵活的伙伴系统和 Slab 分配器等接管，Memblock 完成其历史使命并退出。

## memblock 为何能代替 bootmem

针对 `bootmem` 的缺陷，`memblock` 分配器通过一套全新的设计理念和技术手段进行了彻底的革新。它不再使用位图，而是采用了一种基于“区域（Region）”的列表管理方式，从而优雅地解决了前述所有问题。

### 🗺️ 核心机制：从“位图”到“区域列表”

`memblock` 的核心思想是放弃用比特位来追踪每一个物理页，转而将物理内存视为一组连续或不连续的“内存块”或“区域”。

*   **数据结构**：`memblock` 主要由两个 `memblock_type` 类型的列表构成：
    *   `memory`: 记录系统所有可用的物理内存区域。
    *   `reserved`: 记录已被保留、不可分配的内存区域（如内核镜像、设备树等）。
*   **区域描述**：每个列表都由一个 `memblock_region` 结构体数组组成，每个结构体精确地描述了一块内存的起始地址 (`base`)、大小 (`size`) 和所属的 NUMA 节点 (`nid`)。

这种设计使得 `memblock` 能够以极高的效率描述稀疏内存。无论内存之间有多大的空洞，`memblock` 只需要为实际存在的内存块创建条目，完全避免了 `bootmem` 在稀疏内存场景下的巨大空间浪费。

### 💡 针对性解决方案

`memblock` 的设计直接且精准地解决了 `bootmem` 的所有主要缺陷：

#### 1. 解决 32 位寻址瓶颈

*   **原生 64 位支持**：`memblock` 从一开始就使用 `phys_addr_t` 类型来表示物理地址。在 64 位架构或启用了 LPAE/PAE 的 32 位架构上，`phys_addr_t` 是一个 64 位的无符号整数。这使得 `memblock` 能够无缝地管理和分配超过 4GB 的物理内存，彻底打破了 `bootmem` 的 32 位地址限制。

#### 2. 优化稀疏内存与 NUMA 管理

*   **高效的稀疏内存描述**：如上所述，基于区域的列表天然适合描述稀疏内存。添加或删除一块内存，只需在列表中进行一次插入或删除操作，时间复杂度远低于扫描巨大的位图。
*   **原生的 NUMA 集成**：`memblock_region` 结构体中直接包含了 `nid` (NUMA 节点 ID) 字段。这意味着 `memblock` 在初始化时就可以方便地将内存区域与特定的 NUMA 节点关联起来。当伙伴系统在后续阶段初始化时，可以直接利用 `memblock` 提供的这些信息，快速构建出正确的 NUMA 拓扑，大大简化了流程并提高了效率。

#### 3. 更灵活的内存管理策略

*   **双向分配能力**：`memblock` 支持从高地址向低地址（top-down）或从低地址向高地址（bottom-up）两种分配方向。这对于满足特定硬件需求至关重要，例如某些 DMA 设备要求内存必须位于特定的低地址范围内。而 `bootmem` 的分配方向相对固定。
*   **简化的分配算法**：分配内存时，`memblock` 只需遍历 `memory` 和 `reserved` 这两个通常很短的列表，寻找合适的空闲区间即可。相比于 `bootmem` 需要逐位扫描庞大的位图，`memblock` 的分配速度更快，尤其是在内存容量巨大的系统上。

总而言之，`memblock` 通过引入“区域列表”这一更高级的抽象，不仅克服了 `bootmem` 在技术和性能上的所有短板，还为内核提供了一套更强大、更灵活、更易于维护的早期内存管理框架，完美适应了现代复杂多变的硬件环境。

## memblock内存分配流程

`memblock` 的内存分配流程是其作为内核引导期核心内存管理器的关键。它的工作方式与 `bootmem` 截然不同，主要依赖于对内存区域的列表管理，而非位图扫描。

整个流程的核心是**“首次适配”（First Match）**算法，即从可用的内存区域列表中，找到第一个能满足大小要求的空闲块进行分配。

### 🧭 分配方向：自上而下与自下而上

`memblock` 的一个显著特点是其灵活的分配方向，由 `struct memblock` 中的 `bottom_up` 标志位控制。

*   **默认模式：自上而下 (Top-Down)**
    *   这是 `memblock` 的默认行为 (`bottom_up = false`)。分配器会从可用内存区域的高地址端开始向低地址端查找。
    *   **优势**：这种策略有助于将早期内核分配的数据结构集中在内存的高端，而将大片的低端物理内存（通常对 DMA 等设备至关重要）保持空闲和连续，留待后续的伙伴系统使用。

*   **可选模式：自下而上 (Bottom-Up)**
    *   当 `bottom_up = true` 时，分配器会从低地址向高地址查找。
    *   **用途**：某些特定的硬件或场景可能要求分配的内存必须位于较低的物理地址，此时可以切换到该模式。

### ⚙️ 核心分配流程

当一个组件调用 `memblock_alloc(size, align)` 等接口申请内存时，会触发以下一系列操作：

1.  **调用核心查找函数**
    分配请求最终会委托给核心函数 `memblock_find_in_range_node`。这个函数负责在给定的地址范围和 NUMA 节点内寻找合适的空闲内存。

2.  **执行“首次适配”查找**
    根据 `bottom_up` 的设置，函数会分别调用 `__memblock_find_range_bottom_up` 或 `__memblock_find_range_top_down`。以默认的自上而下为例：
    *   它会遍历 `memblock.memory` 链表中的所有可用内存区域。
    *   对于每个区域，它会计算该区域内可分配的最高起始地址，确保分配的内存块不会超出区域边界，并满足对齐要求。
    *   一旦找到第一个能够满足 `size` 和 `align` 要求的区域，查找过程立即停止，并返回该内存块的物理地址。

3.  **标记为已保留**
    找到合适的物理地址后，`memblock` 并不会将其从 `memory` 链表中删除，而是立即调用 `memblock_reserve(addr, size)`。
    *   这个操作会将刚刚分配的 `[addr, addr + size]` 这段地址范围添加到 `memblock.reserved` 链表中。
    *   从此，这块内存就被明确标记为“已占用”，后续的分配请求在查找时会通过对比 `memory` 和 `reserved` 列表来自动避开它。

### 📝 流程总结

可以将 `memblock` 的分配过程想象成一个仓库管理员：

1.  **接收订单**：收到一个需要 `size` 大小空间的请求。
2.  **寻找货位**：根据预设的规则（从高到低或从低到高），在仓库的空闲货位清单（`memory` 列表）上找到第一个能放下的位置。
3.  **登记占用**：找到位置后，立刻在“已占用”清单（`reserved` 列表）上记下这个位置已被使用。

这个流程简单高效，避免了复杂的元数据管理和碎片整理，非常适合作为内核启动初期的临时内存分配器。当伙伴系统在后续阶段初始化完成后，所有未被 `reserved` 列表记录的内存都会被移交给伙伴系统进行统一管理。

## 当memblock初始化时候，mmu是否就绪

在 Linux 6.6（特别是 ARM64 架构）中，当 `memblock` 初始化并开始分配内存时，**MMU 实际上已经开启了**。

这与早期的 Linux 内核或 x86 架构有所不同。现代 ARM64 内核为了支持更复杂的地址空间布局（如 KASLR），在进入 C 语言主入口 `start_kernel()` 之前，就已经建立了临时的页表并开启了 MMU。

以下是基于 Linux 6.6 ARM64 启动流程的详细事实核查与纠正：

### 🕵️‍♂️ 1. 核心事实纠正：MMU 的状态

在 Linux 6.6 的 ARM64 启动流程中，时间线是这样的：

1.  **Head.S (汇编阶段)**：
    *   内核刚被引导加载程序（Bootloader）加载到内存时，MMU 确实是关闭的（物理地址直接访问）。
    *   **关键动作**：在执行 `start_kernel` 之前，汇编代码会调用 `__create_page_tables`。它会利用内核 BSS 段预留的空间，构建一套**临时的、最小化的页表**（通常使用 2MB 的大页映射）。
    *   **开启 MMU**：这套临时页表建立后，内核会立即开启 MMU。此时，内核代码和数据就被映射到了虚拟地址空间（例如从 `0xffff...` 开始的高位地址）。

2.  **Memblock 初始化阶段 (`setup_arch` -> `memblock_init`)**：
    *   当执行到 `start_kernel()` -> `setup_arch()` -> `memblock_init()` 时，CPU **已经在虚拟地址模式下运行了**。
    *   此时 MMU 是**开启**的。

### 🧠 2. Memblock 到底管理什么地址？

虽然此时 MMU 已开启，但 `memblock` 的设计哲学依然没有变：**它管理的依然是物理地址。**

*   **数据结构层面**：`memblock` 的结构体（`struct memblock_type`）中记录的 `base` 和 `size` 都是物理地址。它不知道也不关心虚拟地址是什么。
*   **分配接口层面**：
    *   `memblock_alloc(size, align)`：这个函数返回的是**物理地址**。
    *   但是，因为此时 MMU 已经开启且存在“内核直接映射”（Linear Mapping / Direct Map），内核代码可以安全地使用 `__va(phys_addr)` 宏将这个物理地址转换为虚拟地址来读写数据。

| 特性 | x86_64 (典型流程) | ARM64 (Linux 6.6 典型流程) |
| :--- | :--- | :--- |
| **进入 start_kernel 时** | MMU 通常未开启 (或仅开启极低限度映射) | **MMU 已开启** (建立了临时页表) |
| **Memblock 工作时** | 往往处于物理地址模式，依赖恒等映射 | **处于虚拟地址模式**，依赖早期页表 |
| **页表初始化时机** | 较晚，在 `paging_init()` 才正式大规模建立 | **很早**，在 `head.S` 就建立了临时页表 |

### 📌 4. 总结

在6.6 linux内核中，进入memblock初始化阶段，此时mmu还没有开启？此时直接管理物理地址？

**准确的答案是：**

1.  **MMU 状态**：**已开启**。在进入 `memblock` 初始化之前，ARM64/x86_64 内核已经通过汇编代码建立了临时的页表并开启了 MMU，以便能够使用高位虚拟地址运行内核。
2.  **管理对象**：**物理地址**。尽管 MMU 开了，`memblock` 依然只维护物理地址的区间（Region）。
3.  **访问方式**：虽然管理的是物理地址，但因为 MMU 已开，内核通过**直接映射（Direct Map）**机制，将物理内存线性映射到虚拟地址空间。所以 `memblock` 分配出物理地址后，内核可以通过简单的加减法偏移（`__va`/`__pa`）将其作为虚拟指针使用。

**一句话概括：**
在 Linux 6.6 ARM64/x86_64 上，`memblock` 是在**MMU 开启后的虚拟环境下**，继续坚持管理**物理内存块**，直到它把接力棒交给真正的虚拟内存管理系统（Buddy System）。

## memblock管理的是物理地址，如何解决虚拟地址映射

**在 Memblock 工作的阶段，通常还没有建立完整的虚拟内存映射（页表），因此 Memblock 管理的纯粹是物理地址。**

但是，为了让 C 语言编写的内核代码能够访问这些物理内存，系统依赖一种**临时的、静态的“恒等映射”**。只有当内核启动到后期，建立了真正的分页机制后，Memblock 分配的物理内存才会被纳入虚拟内存管理体系。

以下我为你详细拆解这个过程：

### 1. Memblock 阶段：物理地址与“恒等映射”

在内核启动的最早期（`start_kernel` 之前及初期），MMU（内存管理单元）通常尚未开启，或者仅开启了极其基础的映射。此时 CPU 发出的地址直接就是物理地址。在进入memblock初始化之前，已经开启了MMU。

为了让 C 代码能读写内存，架构代码（如 x86 或 ARM 的头文件）会预先定义一个**虚拟地址偏移量**。

*   **核心原理**：`虚拟地址 = 物理地址 + 偏移量`
*   **x86_64 示例**：内核通常会预留一段高位虚拟地址空间（例如从 `0xffff800000000000` 开始）作为**直接映射区**。在这个区域，虚拟地址和物理地址除了最高位的符号扩展不同外，低位是完全一一对应的。

**当你调用 `memblock_alloc()` 时发生了什么？**
1.  Memblock 返回一个**物理地址**（例如 `0x100000`）。
2.  内核代码不能直接用这个物理地址指针去读写（因为那是硬件总线地址），而是通过宏（如 `__va()`）将其转换为虚拟地址。
3.  **转换公式**：内核简单地加上那个预定义的偏移量。
    *   物理地址 `0x100000` -> 加上偏移 -> 虚拟地址 `0xffff8000100000`。
4.  此时，CPU 访问这个虚拟地址，实际上是通过这种简单的线性关系直接访问到了物理内存。

> **关键点**：这个阶段没有复杂的“页表查找”，也没有 TLB 缓存优化，仅仅是数学上的地址平移。

### 2. 过渡阶段：从物理分配到虚拟管理

随着内核启动继续，`paging_init()` 会被调用，这标志着真正的虚拟内存管理系统开始接管。

在这个阶段，Memblock 的角色发生了转变：它不再仅仅是一个分配器，而是变成了**页表构建者的数据源**。

#### 步骤 A：建立初始页表
内核利用 Memblock 提供的信息（哪些是可用内存，哪些是保留内存），开始初始化页全局目录（PGD）、页上级目录（PUD）等四级页表结构。
*   内核会将 Memblock 中记录的**可用物理内存**映射到内核的**直接映射区**。
*   此时，之前的“临时恒等映射”逐渐被标准的页表映射所取代。

#### B：Memblock 的终结与移交
当伙伴系统（Buddy System）和 Slab 分配器初始化完成后，Memblock 会执行 `memblock_free_all()`。
*   它将所有剩余的空闲物理内存移交给伙伴系统。
*   从此，这些物理内存页面成为了标准虚拟内存系统的一部分。

### 3. 最终形态：标准虚拟内存映射

一旦系统完全启动，Memblock 的历史使命结束。此时，由 Memblock 当初分配出去的物理内存（比如用于存放内核数据结构），是如何被进程或内核访问的呢？这就回到了标准的 MMU 映射流程：

| 步骤 | 描述 | 涉及组件 |
| :--- | :--- | :--- |
| **1. 虚拟地址生成** | 内核代码或进程发出一个虚拟地址（VA）。 | CPU |
| **2. 查表翻译** | MMU 利用 **页表** 将 VA 翻译成物理地址（PA）。 | MMU / 页表 |
| **3. 缓存加速** | 如果 Translation Lookaside Buffer (TLB) 中有缓存，直接获取 PA，跳过查表。 | TLB |
| **4. 物理访问** | 拿到 PA 后，访问真实的 DRAM。 | 内存总线 |

### 📌 总结

Memblock 本身**不负责**建立虚拟映射，它只负责**管理物理地盘**。

1.  **早期**：依靠**硬编码的偏移量**（恒等映射）让内核代码能访问 Memblock 分配的物理内存。
2.  **中期**：Memblock 的数据被用来**初始化页表**，正式建立物理内存到虚拟地址空间的映射。
3.  **晚期**：Memblock 退出，物理内存交由伙伴系统管理，并通过标准的 MMU 机制提供虚拟地址访问能力。

所以，Memblock 分配的内存之所以能被当作虚拟地址使用，是因为内核在启动早期就预设了一条规则：“这块物理内存，默认就对应那个固定的虚拟地址范围”。

## memblock之前内存地址映射如何实现的

在 Linux 6.6（特别是 ARM64 架构）中，**MMU 的开启和初始页表的建立并不是由 `start_kernel` 完成的，也不是由 `memblock` 完成的。**

这项工作是由 **汇编语言编写的早期启动代码（Head Code）** 在进入 C 语言主函数 `start_kernel` **之前** 完成的。

简单来说：**当 CPU 跳转到 `start_kernel` 的第一行代码时，MMU 已经是开启状态了。**

### 🕵️‍♂️ 1. 谁初始化了 MMU？

**执行者**：架构相关的汇编代码。
*   **文件位置**：`arch/arm64/kernel/head.S`
*   **关键函数**：`__primary_switch` -> `__enable_mmu`

在内核解压完成后，CPU 首先执行的是汇编代码。这段代码负责搭建最基础的运行环境。它的执行顺序如下：

1.  **解析设备树（FDT）**：获取内存大概布局（为了后续能访问内存）。
2.  **创建临时页表**：利用 BSS 段（未初始化的全局变量区域）的内存空间，手动构建一套极简的页表结构。
3.  **开启 MMU**：调用 `__enable_mmu`，将页表基地址写入系统寄存器，并置位控制寄存器的 MMU 使能位。
4.  **跳转**：一切就绪后，才通过 `bl` 指令跳转到 C 语言的 `start_kernel`。

### 🗺️ 2. 怎么建立内存地址映射？（核心机制）

在 `memblock` 还没开始工作前，内核需要一种机制来访问内存。此时建立的映射被称为 **“恒等映射”** 或 **“直接映射”**。

#### A. 映射策略：1:1 线性映射

为了让 C 代码能顺利运行，汇编代码建立的这套“临时页表”遵循一个简单粗暴的原则：
$$虚拟地址 = 物理地址 + 偏移量$$

*   **物理地址**：例如 `0x80000000` (DRAM 起始位置)。
*   **虚拟地址**：例如 `0xffff000080000000` (ARM64 内核空间的起始位置)。
*   **操作**：CPU 只是简单地把高位填上 `0xffff...`，低位保持不变。

这意味着，虽然 MMU 开了，但此时的虚拟地址和物理地址在物理内存中的位置是完全对应的。这保证了在 `memblock` 分配物理内存后，内核只要加上这个偏移量就能立刻访问到它。

#### B. 具体的建立步骤（基于 ARM64）

让我们看看 `arch/arm64/kernel/head.S` 中 `__enable_mmu` 到底干了什么：

1.  **准备页表基址**：
    汇编代码会计算出页表目录（Page Global Directory, PGD）的物理地址。这个页表通常存放在 `.pgtable` 节区中。
2.  **配置系统寄存器**：
    *   读取 ID 寄存器，检查 CPU 支持的页粒度（如 4KB, 16KB, 64KB）。
    *   将页表基地址写入 **TTBR0_EL1** (用户空间基址) 和 **TTBR1_EL1** (内核空间基址)。
3.  **刷新流水线 (ISB)**：
    确保前面的写寄存器操作完成。
4.  **开启开关**：
    读取系统控制寄存器 **SCTLR_EL1**，将 `M` 位（MMU enable bit）置为 1，然后写回。
5.  **生效**：
    从这一刻起，CPU 发出的所有指令地址和数据地址，都会经过 MMU 查表翻译。

### ⚠️ 3. 为什么是“临时”的？

你可能会问，既然这时候已经建好页表了，为什么还说它是临时的？

*   **范围有限**：这套由汇编代码建立的页表，通常只映射了**内核镜像本身**（代码段、数据段）以及**一小部分 DRAM**（用于栈和早期堆）。它并没有映射整个系统的物理内存。
*   **粒度粗糙**：为了快速启动，它通常使用 **2MB (Section)** 甚至 **1GB (Block)** 的大页映射，而不是标准的 4KB 页映射。这样页表项很少，初始化极快。

### 🔄 4. 完整的接力过程

结合你之前的提问，现在的完整图景是这样的：

| 阶段 | 执行者 | 动作 | MMU 状态 |
| :--- | :--- | :--- | :--- |
| **阶段 0** | Bootloader | 加载内核镜像到物理内存 | **关闭** (物理直连) |
| **阶段 1** | **Head.S (汇编)** | **建立临时页表，开启 MMU**。建立内核镜像的直接映射。 | **开启** (大页/块映射) |
| **阶段 2** | `start_kernel` | 进入 C 语言世界。此时 MMU 已开，可以使用虚拟地址。 | **开启** |
| **阶段 3** | `setup_arch` -> `memblock_init` | 初始化 memblock。Memblock 管理物理地址，但内核通过“直接映射”的虚拟地址来读写这些物理内存。 | **开启** |
| **阶段 4** | `paging_init` | **销毁临时页表，建立正式页表**。扫描所有物理内存，建立细粒度（4KB）的页表，完善直接映射区。 | **开启** (标准 4KB 页映射) |

### 📌 总结

在 Linux 6.6 中：
1.  **谁初始化的？** 是 **`arch/arm64/kernel/head.S`** 中的汇编代码。
2.  **什么时候？** 在 `start_kernel` 被调用**之前**。
3.  **怎么映射的？** 建立了**内核镜像和少量内存的直接映射（恒等映射）**，使得虚拟地址可以通过简单的偏移访问物理内存。

所以，当你看到 `memblock` 分配内存时，它虽然是在管理物理地址，但你是通过汇编代码预先铺设好的这条“虚拟高速公路”去访问它的。

## memblock如何转换成buddy的，为何要转换，不转行不行？

这是一个关于 Linux 内存管理“改朝换代”的关键问题。

简单来说，**Memblock 是“开国元老”，负责打江山（早期分配）；Buddy System 是“职业官僚”，负责治理国家（长期管理）。**

下面我为你详细拆解它们是如何交接的，以及为什么必须进行这次交接。

### 🔄 一、 Memblock 如何转换成 Buddy？（交接流程）

这个转换过程并不是把数据“搬运”一遍，而是**所有权的移交**。物理内存还是那块物理内存，只是管理它的数据结构变了。

这个交接仪式主要发生在内核启动的 `mm_init()` -> `mem_init()` 阶段，核心函数是 `free_all_bootmem()`（虽然名字叫 bootmem，但在现代内核中实际执行的是 memblock 的释放逻辑）。

#### 1. 准备阶段：建立档案 (`struct page`)
在交接之前，内核先做了一件大事：为系统中的每一个物理页框（Page Frame）都建立了一个身份证，也就是 **`struct page`** 对象。这些对象组成了全局数组 `mem_map`。
*   此时，Memblock 还在管理物理内存，但 `struct page` 已经准备好了，只是状态大多是“保留”或未初始化。

#### 2. 扫描与移交 (`free_low_memory_core_early`)
这是转换的核心步骤，内核会遍历 Memblock 的两个核心列表：

*   **处理“reserved”列表（扣留）**：
    内核遍历 `memblock.reserved`（存放内核镜像、设备树、DTB 等）。对于这些区域，内核会将对应的 `struct page` 标记为 **`PG_reserved`**。
    *   *含义*：这些内存是“皇产”，Buddy 系统以后不能随便分配给用户空间或普通内核模块使用。

*   **处理“memory”列表（放权）**：
    内核遍历 `memblock.memory` 中**未被保留**的空闲部分。
    *   **计算阶数 (Order)**：根据内存块的起始地址对齐情况，计算出它能切分成多大的块（比如 $2^0$ 页, $2^1$ 页...）。
    *   **加入链表**：调用 `__free_pages_core()`，将这些空闲页的 `struct page` 加入到 Buddy 系统的空闲链表（`zone->free_area[order].free_list`）中。
    *   **清除保留标记**：清除 `PG_reserved` 标志，将引用计数置为 0，表示“我是空闲的，谁都可以用”。

#### 3. 完成：Memblock 退休
当所有空闲内存都被挂载到 Buddy 系统的链表上后，Buddy 系统正式接管内存分配权。Memblock 的数据结构虽然还在内存里，但不再被用于常规分配，它的历史使命结束。

---

### ❓ 二、 为什么要转换？不转行不行？

**答案是：必须转，不转系统没法正常运行。**

Memblock 和 Buddy 的设计目标完全不同，Memblock 无法胜任系统运行时的内存管理任务。

#### 1. 算法效率不同（碎片问题）
*   **Memblock (线性/区间管理)**：
    *   它管理的是**大块的连续物理内存区间**。
    *   它的分配策略通常是简单的“首次适配”或“自上而下/自下而上”。
    *   **缺陷**：如果系统运行起来后，频繁地申请和释放各种大小不一的内存（比如几字节、几页），Memblock 会产生严重的**外部碎片**。它没有机制去合并零散的小块内存。
*   **Buddy (伙伴算法)**：
    *   它以**2的幂次方**（Order）来组织内存。
    *   **优势**：当释放内存时，Buddy 系统会检查“伙伴”是否也空闲。如果是，两者合并成更大的块。这种机制能最大程度地减少外部碎片，保证系统能随时拿出大块连续内存（这对 DMA 和高性能计算至关重要）。

#### 2. 管理粒度不同
*   **Memblock**：粗粒度。它只关心哪一段地址范围是可用的，不关心具体的“页”的状态。
*   **Buddy**：细粒度（页级）。它精确管理每一个 Page（通常 4KB）。Linux 的虚拟内存系统（MMU）是基于页表工作的，Buddy 天然契合这种以“页”为单位的管理需求。

#### 3. 功能特性支持
Buddy 系统不仅仅是分配内存，它还支撑了 Linux 的高级特性，而 Memblock 做不到：
*   **迁移类型 (Migrate Types)**：Buddy 将内存分为可移动、不可移动、CMA 等类型，防止某些长期占用的内存导致碎片化。Memblock 没有这个概念。
*   **NUMA 感知**：在多路 CPU 系统中，Buddy 知道哪个内存属于哪个节点，尽量让 CPU 访问本地内存。
*   **热插拔**：内存条拔掉或插上时，Buddy 可以动态调整。

### 📌 三、 总结

*   **Memblock** 就像是**盖房子时的临时工棚**。在房子（操作系统）还没盖好之前，工人们（内核代码）需要一个地方堆放工具（分配内存）。这个工棚结构简单，搭得快，拆得也快，适合临时用。
*   **Buddy System** 就像是**建成后的现代化仓库**。房子盖好后，东西越来越多，流转越来越快。这时候需要货架（链表）、分类标签（Zone/Order）、自动存取机制（合并/分裂）。

**如果不转换**：系统启动后，一旦开始运行应用程序，频繁的内存申请和释放会让 Memblock 迅速产生大量无法利用的内存碎片，最终导致系统明明还有内存，却无法分配出连续页面，进而崩溃（OOM）。

---

## 为何不能一步到位到buddy，完全不用memblock？

这是一个非常深刻且直击本质的问题。

简单来说，这就像**“鸡生蛋，蛋生鸡”**的问题：Buddy 系统本身是一个复杂的软件程序，它需要内存来存储自己的管理数据（比如 `struct page` 数组、各种链表）。但在系统刚启动时，内存还是一盘散沙，没有任何管理机制。

**Memblock 的存在，就是为了给 Buddy 系统的诞生提供“第一桶金”。**

如果不使用 Memblock（或早期的 Bootmem），直接一步到位初始化 Buddy 系统，会面临以下三个无法逾越的**死锁**难题：

### 🥚 1. “数据结构存放在哪”的死循环
Buddy 系统不是凭空存在的，它依赖大量的数据结构来管理内存。最核心的就是 **`mem_map` 数组**（包含系统中所有物理页对应的 `struct page` 对象）。

*   **困境**：
    *   要初始化 Buddy 系统，必须先创建并初始化 `mem_map` 数组。
    *   `mem_map` 数组非常大（例如 4GB 内存可能需要几十 MB 的空间来存元数据）。
    *   **问题来了：** 这个巨大的数组应该放在内存的哪个位置？
*   **Memblock 的作用**：
    *   在 Buddy 系统还没影的时候，Memblock 已经通过简单的线性扫描接管了物理内存。
    *   内核调用 `memblock_alloc()`，从物理内存中切出一块地盘，专门用来存放 `mem_map`。
    *   **没有 Memblock，Buddy 连自己的“户口本”（mem_map）都没地方建。**

### 🔍 2. 硬件探测与内存布局的收集需要时间
当 CPU 刚复位时，它并不知道内存条插在哪、有多大、中间有没有被硬件预留的空洞（MMIO 区域）。

*   **困境**：
    *   Buddy 系统是一个**全局管理者**，它需要知道整个系统的内存拓扑（哪些能用，哪些不能用）。
    *   获取这些信息需要运行驱动程序（如解析设备树 FDT、ACPI 表），而这些驱动程序的运行本身就需要分配内存（申请缓冲区、变量等）。
    *   如果此时强行初始化 Buddy，你甚至不知道要把哪些内存加进去，或者不小心把显卡的显存给覆盖了。
*   **Memblock 的作用**：
    *   Memblock 是一个**极简的“记录员”**。它不管理具体的页，只记录大块的区间（Region）。
    *   它允许内核在启动过程中，一边探测硬件，一边动态地 `add`（添加可用内存）或 `reserve`（保留被硬件占用的内存）。
    *   等到所有硬件信息都收集完毕，Memblock 手里就握着一份完整的、准确的“内存地图”，这时候再把它交给 Buddy 系统。

### ⚙️ 3. 复杂度的差异（造轮子 vs 用轮子）
Buddy 系统的初始化逻辑非常复杂，涉及 NUMA 节点划分、Zone 边界计算（DMA/Normal/HighMem）、页表映射建立等。

*   **困境**：
    *   如果在没有任何基础内存管理的情况下直接写代码去初始化 Buddy，代码将变得极其臃肿和脆弱。你需要手动硬编码指针去操作内存，稍有不慎就会覆盖正在运行的代码。
*   **Memblock 的作用**：
    *   Memblock 提供了类似于 `malloc` / `free` 的简单接口（虽然底层实现不同）。
    *   这让内核开发者可以用**正常的 C 语言风格**编写 Buddy 系统的初始化代码。
    *   比如：`zone = memblock_alloc(sizeof(struct zone), ...)`。有了 Memblock，初始化 Buddy 的代码看起来就像是普通的业务逻辑，而不是晦涩的汇编黑客技巧。

### 📌 总结：一个形象的比喻

想象你要建立一个**现代化的物流仓储中心**（Buddy System）：

1.  **现状**：你面前是一片荒地（物理内存），杂草丛生，不知道哪里是坑，哪里是路。
2.  **目标**：建立一个拥有自动分拣机、货架编号、计算机管理系统的超级仓库。
3.  **困难**：要建这个仓库，你需要先盖办公室、买电脑、印表格（Buddy 的数据结构）。但是，你还没开始建仓库，就没有地方放这些办公用品。
4.  **解决方案 (Memblock)**：
    *   你先派一支**工程队（Memblock）**进场。他们不需要复杂的系统，只需要简单的帐篷和记事本。
    *   工程队先把地平整好，画出哪里能建房，哪里是下水道（探测硬件、记录 Region）。
    *   工程队划出一块地，盖上临时板房，让管理人员入驻（分配 `mem_map` 和 `zone` 结构体）。
    *   等一切准备就绪，**正式仓库（Buddy）** 建成开业，工程队（Memblock）就可以撤场回家了。

**结论**：不能一步到位，是因为**构建复杂的管理系统本身就需要消耗资源**。Memblock 就是那个在资源匮乏时期，为复杂系统诞生提供资源的“ bootstrap （引导）机制”。

## memblock是如何获取可用内存的？是grub提供的还是bios提供的？

Memblock 获取可用内存的方式取决于你的硬件架构（是 x86 电脑还是 ARM 嵌入式设备）。

简单直接的回答是：**Memblock 本身不直接去“问”硬件，而是由 Bootloader（如 GRUB、U-Boot）或固件（BIOS/UEFI）先探测好，然后以特定的格式“告诉”内核。** Memblock 的工作就是**解析**这些信息。

具体是谁提供的，分两种情况：

### 💻 1. x86 架构（PC/服务器）：BIOS/UEFI 提供
在 x86 电脑上，Linux 启动时通常依赖 **BIOS** 或 **UEFI** 固件来探测内存。

*   **提供者**：主板上的 BIOS/UEFI 固件。
*   **传递方式**：
    *   Linux 内核启动早期（在 `start_kernel` 之前），会通过调用 BIOS 中断（经典的 **INT 0x15, EAX=0xE820**）或者通过 UEFI 的运行时服务来获取物理内存布局。
    *   这个调用通常是由 Bootloader（如 GRUB）协助完成的，或者内核自带的小型解压代码（`arch/x86/boot/compressed/`）直接调用的。
*   **Memblock 的动作**：
    *   内核将获取到的 E820 映射表（一个包含地址范围 and 类型的数组）保存下来。
    *   在 `setup_arch()` 阶段，内核遍历这张表，把标记为 **"Usable"**（可用）的区域调用 `memblock_add()` 添加到 Memblock 中；把标记为 **"Reserved"**（保留，如 ACPI 表、显存）的区域调用 `memblock_reserve()` 进行预留。

### 📱 2. ARM64 / RISC-V 架构（嵌入式/手机）：Bootloader 提供
在 ARM 等设备上，没有像 BIOS 那样标准的通用固件接口，通常依赖 **Bootloader（如 U-Boot）**。

*   **提供者**：Bootloader（最常见的是 **U-Boot**）。
*   **传递方式**：
    *   **设备树 (Device Tree / FDT)**：这是现代 ARM Linux 的标准方式。U-Boot 会在启动时根据硬件配置生成一个二进制文件叫 **设备树 Blob (DTB)**。
    *   DTB 里面有一个节点叫 `/memory`，里面明确写着 `reg = <0x0 0x80000000 0x0 0x40000000>;`（意为：从 0x80000000 开始，大小为 1GB）。
    *   U-Boot 把这个 DTB 文件的地址传给 Linux 内核（通常放在寄存器 `x0` 或通过 ATAGS）。
*   **Memblock 的动作**：
    *   内核启动后，早期的 C 代码会解析这个 DTB 文件。
    *   找到 `/memory` 节点，提取出起始地址和大小。
    *   调用 `memblock_add(base, size)` 将这些信息注册到 Memblock 管理器中。

### 🔄 3. 还有一种特殊情况：命令行参数

有时候为了调试或强制限制内存（比如模拟小内存环境），我们可以在 GRUB 或 U-Boot 的启动命令行里加参数：
`mem=512M@0x80000000`

在这种情况下，内核会优先解析这个字符串，并以此为准来初始化 Memblock，忽略硬件探测的结果。

### 📌 总结流程图

| 架构 | 谁探测硬件？ | 数据格式 | 谁传给内核？ | Memblock 怎么拿？ |
| :--- | :--- | :--- | :--- | :--- |
| **x86** | **BIOS / UEFI** | E820 Map / UEFI Memory Map | 固件 -> 内核实模式代码 | 解析 E820 表，循环调用 `memblock_add` |
| **ARM** | **Board Info / U-Boot** | **Device Tree (FDT)** | U-Boot -> 内核 (通过寄存器) | 解析 DTB 中的 `/memory` 节点 |

所以，Memblock 只是一个**接收者和管理者**，它依赖更底层的固件或引导程序先把“地图”画好递给它。
