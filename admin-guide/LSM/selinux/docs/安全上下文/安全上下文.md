# 安全上下文

在Linux运维的世界里，我们习惯了使用 `ls` 查看文件归属，用 `ps` 监控进程状态，用 `netstat` 洞察网络连接。然而，当系统启用了SELinux（Security-Enhanced Linux）后，传统的权限管理（rwx）之上又覆盖了一层严密的“安全标签”系统。

要理解并排查SELinux相关的问题，核心在于掌握如何查看这些“标签”。除了你可能已经熟悉的 `ls -Z`，还有一系列命令通过 `-Z` 参数，为我们打开了透视内核安全策略的窗口。本文将带你系统性地梳理这些命令，构建一套完整的SELinux上下文可视化方法论。

主体有标签、客体也有标签，客体有不同类别，但主体一般就是进程


## 一、核心概念：什么是安全上下文？

在使用命令之前，我们需要先读懂命令输出的内容。SELinux的安全上下文通常由四个字段组成，用冒号分隔：

`user_u:role_t:type:s0`

- **用户 (User):** 类似于Linux的标准用户，但专门用于SELinux（如 `system_u`, `unconfined_u`）。
- **角色 (Role):** 连接用户和类型的桥梁（如 `object_r` 通常用于文件，`system_r` 通常用于进程）。
- **类型 (Type):** **这是最关键的字段**。SELinux的策略规则主要基于“进程的类型”能否访问“文件的类型”来制定。
- **级别 (Level):** 用于多级安全策略（MLS/MCS），通常默认为 `s0`。

接下来的命令，本质上都是在不同的系统维度上展示这个字符串。

## 二、静态对象：文件与目录的标签

**命令：`ls -Z`**

这是最基础的用法。在传统的 `ls -l` 输出中，我们只能看到文件的属主和权限，而加上 `-Z` 后，SELinux的安全上下文会显示在最左侧。

**应用场景：**
当你部署Web服务（如Nginx/Apache）时，如果网页文件被移动到了非标准目录，或者被解压工具赋予了错误的上下文（例如 `default_t` 而不是 `httpd_sys_content_t`），Web服务就会报 403 错误。此时，`ls -Z` 是诊断问题的第一把手术刀。

**示例：**
```bash
ls -Z /var/www/html/index.html
# 输出: system_u:object_r:httpd_sys_content_t:s0 /var/www/html/index.html
```

## 三、动态主体：进程的身份标识

**命令：`ps -Z`**

进程是访问文件的主体。`ps -Z` 允许我们查看当前运行的进程被赋予了什么样的SELinux身份。通常我们会结合 `aux` 参数使用（即 `ps auxZ`），以便同时看到进程的所有者和上下文。

**应用场景：**
如果一个被黑客入侵的进程试图访问敏感文件，SELinux会进行拦截。通过 `ps -Z`，你可以确认该进程是否运行在受限的域（Domain）中，还是运行在无限制的 `unconfined_t` 域中。

**示例：**
```bash
ps auxZ | grep httpd
# 输出: system_u:system_r:httpd_t:s0 root 1234 ... /usr/sbin/httpd
# 这表明 httpd 进程运行在 httpd_t 的域中，只能访问允许 httpd_t 访问的文件。
```

## 四、当前操作者：用户的登录身份

**命令：`id -Z`**

`id` 命令通常用于查看用户的UID和GID，而 `id -Z` 则专门用于显示**当前登录用户**的SELinux上下文。

**应用场景：**
当你使用 `su` 或 `sudo` 切换用户，或者通过SSH登录系统时，你的操作权限受限于你的SELinux用户身份。如果你发现作为root用户却无法修改某些文件，使用 `id -Z` 可以检查你是否处于 `unconfined_u`（无限制）还是被限制在了某个特定的管理角色中。

```shell
[root@openeuler6 ~]# id -Z
unconfined_u:unconfined_r:unconfined_t:s0-s0:c0.c1023
[root@openeuler6 ~]# 
```

## 五、网络与登录：连接与会话的上下文

这两个命令往往容易被忽视，但它们在网络排查和审计中非常有用。

**1. `netstat -Z`**
该命令用于显示网络连接及其关联的SELinux上下文。
- **作用：** 它可以告诉你哪个SELinux域正在持有某个网络连接。

## 六、宏观视角：系统状态与策略查询

除了上述带 `-Z` 参数的命令外，要全面掌握SELinux信息，还需要两个不带 `-Z` 的核心命令作为补充：

- **`sestatus`**：这是查看SELinux整体健康状况的“仪表盘”。它告诉你SELinux是开启（Enforcing）、宽容（Permissive）还是关闭（Disabled），以及当前加载的策略名称。
- **`getsebool -a`**：SELinux的策略非常细致，通过布尔值（Boolean）来控制特定功能的开关（如允许HTTPD连接数据库）。这个命令列出了所有策略开关的状态。


## 七、如何获取文件的安全上下文

文件的安全上下文（Security Context）存储在文件系统的 **索引节点** 中。

*   **什么是索引节点？**
    在 Linux 文件系统中，索引节点是一个数据结构，用于存储文件的元数据（关于数据的数据）。除了 SELinux 上下文，文件的权限（rwx）、所有者、大小、创建时间等信息也都存放在这里。
*   **具体实现：扩展属性**
    SELinux 上下文是作为一种**扩展属性**存储在索引节点中的。
    *   在大多数现代 Linux 文件系统（如 ext4, xfs）中，这个特定的扩展属性键名通常是 `security.selinux`。
    *   这意味着，即使你把文件重命名，或者移动文件（在同一文件系统内），只要索引节点没变，它的安全上下文就会一直跟随它。


```shell
[root@openeuler6 ~]# getfattr -n security.selinux /etc/passwd
getfattr: Removing leading '/' from absolute path names
# file: etc/passwd
security.selinux="system_u:object_r:passwd_file_t:s0"

[root@openeuler6 ~]# stat /etc/passwd
  File: /etc/passwd
  Size: 1761            Blocks: 8          IO Block: 4096   regular file
Device: 8,3     Inode: 9458217     Links: 1
Access: (0644/-rw-r--r--)  Uid: (    0/    root)   Gid: (    0/    root)
Context: system_u:object_r:passwd_file_t:s0
Access: 2026-04-28 13:00:01.753992128 +0800
Modify: 2026-04-11 20:31:15.662987285 +0800
Change: 2026-04-11 20:31:15.670987559 +0800
 Birth: 2026-04-11 20:31:15.662987285 +0800
[root@openeuler6 ~]# 
```

理解“存储在索引节点中”对于运维有两个重要的实际意义：

1.  **移动与复制的区别：**
    *   **移动 (`mv`)：** 如果你在同一文件系统内移动文件，索引节点不变，**上下文会保留**。
    *   **复制 (`cp`)：** 复制文件会创建新的索引节点。默认情况下，新文件会继承**目标目录**的默认上下文，而不是保留原文件的上下文（除非使用 `cp --preserve=context`）。

2.  **备份与恢复：**
    *   普通的备份工具（如不带参数的 `tar`）可能不会保存扩展属性。如果你在备份还原后丢失了 SELinux 上下文，会导致服务无法启动。
    *   必须使用支持扩展属性的工具（如 `tar -X` 或 `star`）来备份和恢复这些存储在索引节点中的标签。


## 八、进程的安全上下文


文件的安全上下文是“持久化”在磁盘的索引节点（inode）中的。但进程是动态的、短暂的，它们存在于内存中。

简单来说，**进程的安全上下文存储在内存中，并随着进程的创建和继承规则动态生成。**

进程的安全上下文并不存储在硬盘上，而是存储在**内核内存**中。

*   **具体位置：** 在内核的 `task_struct` 结构体中。
    Linux 内核用 `task_struct` 来描述一个进程。SELinux 的相关信息被挂载在这个结构体的 `cred`（凭证）字段下。
*   **数据结构：** `task_security_struct`
    在 SELinux 的实现代码中，有一个专门的结构体用来存放进程的上下文 ID（SID）：
    ```c
    struct task_security_struct {
        u32 osid;       // 执行前的旧 SID
        u32 sid;        // 当前的 SID（这就是进程的安全上下文 ID）
        u32 exec_sid;   // 执行时的 SID
        u32 create_sid; // 创建文件时的 SID
        // ... 其他字段
    };
    ```
*   **如何查看：**
    虽然它在内存深处，但内核通过 `/proc` 文件系统将其暴露给用户空间。
    当你执行 `ps -Z` 时，系统实际上是在读取 `/proc/[PID]/attr/current` 文件。

```bash
[root@openeuler6 ~]# cat /proc/self/attr/current 
unconfined_u:unconfined_r:unconfined_t:s0-s0:c0.c1023
```


进程上下文是如何而来的？

文件是被动地被贴上标签，而进程的标签则是**“算”出来的**。当一个新进程诞生时，它的 SELinux 上下文主要通过以下三种方式确定：

A. 继承（最常见的情况）
**场景：** 当你在终端输入 `ls`，或者一个程序调用 `fork()` 创建子进程时。
**规则：** **子承父业**。
默认情况下，新进程会直接继承父进程的安全上下文。
*   **例子：** 你的 Shell（`bash`）通常是 `unconfined_t`。当你在 Shell 里运行 `ls` 时，`ls` 进程刚创建出来时也是 `unconfined_t`。

B. 域转换（最核心的安全机制）
**场景：** 当你运行一个特定的可执行程序（如启动 Apache 服务 `/usr/sbin/httpd`）时。
**规则：** **类型强制转换**。
这是 SELinux 最强大的地方。系统不仅看谁启动了它（父进程），还要看**启动的是什么文件**。
*   **机制：** 内核会检查 SELinux 策略库。如果策略规定：“当 `init_t` 域执行 `httpd_exec_t` 类型的文件时，必须转换为 `httpd_t` 域”。
*   **结果：** 即使父进程是 `unconfined_t`，只要它执行了带有 `httpd_exec_t` 标签的二进制文件，生成的进程就会立刻“变身”为 `httpd_t`。
*   **公式：** `父进程域` + `可执行文件类型` -> **`新进程域`**。

C. 显式指定（Android 或特殊场景）
**场景：** 在 Android 系统（SEAndroid）中，或者使用 `setcon` 命令。
**规则：** **查表指定**。
*   **Android 机制：** Android 的 `Zygote` 进程在孵化应用时，会根据应用的 UID 和名称，去查询 `/etc/selinux/seapp_contexts` 文件，强制给新进程赋予特定的上下文（如 `appdomain`）。
*   **手动修改：** 进程可以在运行中通过系统调用（`setcon`）尝试修改自己的上下文（通常只有特权进程或特定策略允许这样做）。

文件与进程上下文对比：


| 特性 | 文件安全上下文 | 进程安全上下文 |
| :--- | :--- | :--- |
| **存储介质** | **磁盘** (硬盘) | **内存** (RAM) |
| **具体位置** | 索引节点 (Inode) 的扩展属性 | 进程描述符 (`task_struct`) 的凭证 (`cred`) 结构 |
| **可见接口** | `ls -Z` | `ps -Z` 或 `/proc/[PID]/attr/current` |
| **生命周期** | 持久化，重启后依然存在 | 临时，进程结束即消失 |
| **生成方式** | 创建时继承目录标签，或由管理员设定 | **继承**父进程，或由**可执行文件**触发转换 |
| **核心逻辑** | 它是资源，是被动的标签 | 它是主体，是动态的身份 |

总结：文件的安全上下文是**“写在房产证上的名字”**（存在硬盘里，不容易变）；而进程的安全上下文是**“办事员胸前的工牌”**（存在内存里，由谁来带（继承）或者办什么事（域转换）决定）。




## 端口上下文 (Port Context)


网络端口也是一种资源，SELinux 通过端口上下文来控制哪些进程可以绑定或监听特定端口。

*   **存储位置：** **SELinux 策略库（内存/二进制文件）**。
    它不像文件上下文那样存储在端口本身（因为端口是逻辑概念），而是定义在策略配置中。
*   **如何查看：**
    *   `semanage port -l`：列出所有定义的端口上下文。
    *   `netstat -Z` 或 `ss -Z`：查看当前网络连接及其关联的进程上下文。



SELinux 的策略决策是基于“主体”（Subject，通常是进程）和“客体”（Object，如此处的网络端口）的安全上下文做出的。

为了在内核中高效地进行比较，这些人类可读的上下文（如 `httpd_t`）会被转换成唯一的数字标识符——**安全 ID（SID）**。

*   **主体 SID：** 发起操作的进程拥有一个 SID，它存储在进程的凭证（`struct cred`）中。这个结构体通过一个 `void *security` 指针（也称为 security blob）来存放 SELinux 特定的安全信息，其中就包括了进程的 SID。

*   **客体 SID：** 网络端口作为客体，也需要一个 SID。当内核为套接字（socket）分配资源时（例如在 `sk_alloc` 函数中），会调用 SELinux 的辅助函数（如 `selinux_netlbl_sk_alloc`）来为这个套接字分配一个 SID。这个 SID 会存储在套接字缓冲区（`struct sk_buff`）的 `secmark` 字段中，它是一个 32 位的整数，直接代表了该网络资源的安全标签。


在 Linux 6.6 内核中，网络端口（更准确地说是套接字 socket）的安全标签，即其对应的安全ID（SID），并不是存储在数据包缓冲区（`struct sk_buff`）中，而是直接存储在**套接字（socket）自身的安全结构体**里。

`struct sk_buff` 的 `secmark` 字段主要用于标记**网络数据包**，常用于网络流量控制或审计，而非标识套接字这个客体本身。

### 🔍 端口标签在内核中的存放位置

当一个进程创建一个套接字时（例如调用 `socket()` 系统调用），内核会为其分配一个 `struct socket` 和 `struct sock` 结构体。SELinux 会为这个新创建的套接字分配一个安全ID（SID），并将其保存在一个专门的安全结构体中。

这个结构体就是 **`struct sk_security_struct`**。

它的具体存放位置如下：

1.  **套接字对象：** 每个套接字在内核中都由一个 `struct socket` 结构体表示。
2.  **安全指针：** `struct socket` 结构体中包含一个 `void *security` 指针。这个指针是 Linux 安全模块（LSM）框架预留的，用于存储特定安全模块（如 SELinux）的私有数据。
3.  **安全结构体：** 对于 SELinux，这个 `security` 指针指向一个 `struct sk_security_struct` 类型的实例。
4.  **SID 字段：** `struct sk_security_struct` 结构体中有一个关键字段 `u32 sid;`，这个 `sid` 就是该套接字（端口）的安全ID，也就是其安全上下文的数字表示。


简单来说，内核通过以下路径找到端口的安全标签：

`struct socket` -> `security` 指针 -> `struct sk_security_struct` -> `sid` 字段

分配时机：

这个 `sid` 是在套接字创建时分配的。当进程调用 `socket()` 时，内核会：

1.  分配 `struct socket` 和 `struct sock`。
2.  调用 LSM 钩子函数 `security_socket_create`。
3.  SELinux 的实现函数 `selinux_socket_create` 会被触发。
4.  该函数会为新的套接字分配一个 `sk_security_struct` 结构体，并根据当前进程的安全上下文和 SELinux 策略，初始化其 `sid` 字段。
5.  最后，将这个 `sk_security_struct` 的地址赋值给 `struct socket` 的 `security` 指针。


| 概念 | 存放位置 (Linux 6.6) | 说明 |
| :--- | :--- | :--- |
| **端口安全标签 (SID)** | `struct sk_security_struct` 的 `sid` 字段 | 这是端口作为客体的核心安全标识。 |
| **结构体位置** | 由 `struct socket` 的 `security` 指针指向 | 通过 LSM 框架与套接字对象关联。 |
| **数据包标签** | `struct sk_buff` 的 `secmark` 字段 | 用于标记**数据包**，与套接字本身的标签是两个不同的概念。 |

因此，SELinux 对端口绑定的控制，就是通过检查**进程**的 SID（来自 `current_cred()->security`）是否被允许对**套接字**的 SID（来自 `sock->security->sid`）执行 `name_bind` 操作来完成的。
