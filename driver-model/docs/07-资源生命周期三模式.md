# 资源生命周期三模式：kref、挂靠与宽限期（Linux 6.6）

> 阅读目标：把内核"谁负责最后一次释放"的三种答案收进一张地图——**计数式**（kref：refcount_t 封装、release 回调、查找表与 `kref_get_unless_zero` 的 RCU 难题）、**挂靠式**（devres/devm_action：资源生命周期绑定到宿主）、**宽限期式**（kfree_rcu：读侧零开销的延迟释放与一页批量机制）。两个明星混合形态收束：kobject（kref 底座 + 随机延迟清理的测试武器）与 percpu_ref（percpu 计数 → kill 切原子的两阶段关闭）。全部对照 v6.6（include/linux/kref.h——★6.6 中 kref 全部内联于此，**不存在 lib/kref.c**；include/linux/percpu-refcount.h、lib/kobject.c、kernel/rcu/tree.c）。前置：[01-kobject 与 sysfs](01-kobject与sysfs.md)｜[05-devres](05-devres设备资源管理.md)。

---

## 一、问题：谁扣动最后一次释放的扳机

```
共享资源的困境：N 个持有者，谁触发 free()？
  答案一（计数）：每个持有者 +1/-1，归零者释放        → kref
  答案二（挂靠）：资源登记到宿主，宿主死则资源亡      → devres / devm_action
  答案三（宽限期）：等所有读者退出后再释放            → RCU / kfree_rcu
三者的成本模型完全不同：
  计数：每次 get/put 都是一次原子操作（热路径常驻成本）
  挂靠：挂靠时一次登记，此后零成本（但只对"有宿主"的资源成立）
  宽限期：读侧零开销（无原子、无屏障），代价是释放延迟与回收器复杂度
```

## 二、模式一：kref 计数（include/linux/kref.h，113 行全内联）

```c
struct kref {                     /* :19-21 —— refcount_t 的薄封装 */
	refcount_t refcount;          /* ★ hardened refcount：溢出/释放后
	                                 使用会 WARN 且拒绝继续 */
};
static inline void kref_init(struct kref *kref)   /* :29  refcount_set(1) */
static inline void kref_get(struct kref *kref)    /* :43  refcount_inc */
static inline int kref_put(struct kref *kref,
		void (*release)(struct kref *kref))  /* :62 */
{
	if (refcount_dec_and_test(&kref->refcount)) {
		release(kref);
		return 1;              /* 返回 1 = 你是最后的持有者 */
	}
	return 0;
}
```

两条 API 纪律与一个经典难题：

1. **release 不能直传 kfree**（:49-61 文档注释原话）：*"This pointer is required, and it is not acceptable to pass kfree in as this function."*——因为 kref 常嵌在更大结构里，release 必须做 `container_of` 后整体释放；这条规则是内核 review 的口头禅。
2. **锁转移变体**：`kref_put_mutex`（:71）/ `kref_put_lock`（:82）——`refcount_dec_and_mutex_lock/dec_and_lock` 把"归零判断"与"从查找结构摘除"所需的上锁**合并成一次原子序列**，消除 put 路径的锁窗口。
3. **查找表难题与 unless_zero**（:94-107 文档注释原话）：*"Operations on such objects require at least a read lock around lookup + kref_get, and a write lock around kref_put + remove from lookup structure. Furthermore, RCU implementations become extremely tricky. With a lookup followed by a kref_get_unless_zero **with return value check**...RCU lookups become trivial."*——RCU 查找与"并发归零"的竞态：找到时对象可能正被最后一个 put 释放；`kref_get_unless_zero`（:109，`refcount_inc_not_zero` + `__must_check`）让查找方在无锁下安全"捡起"对象——**失败就意味着对象已在死亡路上，当作没找到**。

## 三、模式二：挂靠式（[05 章](05-devres设备资源管理.md) 的两种形态）

```
devres 挂靠：资源入 dev->devres_head 链（FIFO 入队/LIFO 释放）
  契约："挂在谁身上，谁被解绑时释放"——宿主 device 是唯一锚点
  适用：probe 生命周期资源（IRQ/映射/时钟……宿主天然存在）
devm_action 挂靠：回调本身即资源（struct action_devres）
  适用：无结构体的任意清理逻辑（"我要在 detach 时跑这段代码"）
```

挂靠式与计数式的本质分野：**没有"最后一次"的判断成本**——释放时机由宿主的外部事件（unbind/probe 失败）触发，热路径零原子操作。代价是资源必须有自然宿主；一个被多方共享、无主从关系的对象挂靠不了。

## 四、模式三：宽限期式——kfree_rcu 的批量机制（kernel/rcu/tree.c）

```
调用：kfree_rcu(p, rcu) / kvfree_rcu → kvfree_call_rcu（:3346）
  └─ 批处理（:3341-3345 注释原话）："Each kvfree_call_rcu() request
     is added to a batch. The batch will be drained every
     KFREE_DRAIN_JIFFIES number of jiffies. All the objects in the
     batch will be free'd in workqueue context. This allows us to:
     batch requests together to reduce the number of grace periods
     during heavy kfree_rcu()/kvfree_rcu() load."

两个常量（自适应排空的两侧，:2772/:2795）：
  #define KFREE_DRAIN_JIFFIES (5 * HZ)               /* 常规 5 秒攒一批 */
  #define KVFREE_BULK_MAX_ENTR \                      /* 一页指针数组：
    ((PAGE_SIZE - sizeof(struct kvfree_rcu_bulk_data)) / sizeof(void *)) */
  /* 排空判据（:3095）：积压 ≥ 满页 → delay = 1（立刻排）；
     否则等满 5 秒——吞吐与延迟的自适应折中 */
  kfree_rcu_work（:3011）：workqueue 上下文逐批 kvfree
```

★宽限期式的独有语义：**读侧零开销**（读者不碰任何计数）、**释放顺序不确定**（批次内无序）、**延迟上界受 grace period 拖尾**——它买的是读路径性能，付的是"对象死后仍占内存一段时间"。

## 五、两个明星混合形态

### 5.1 kobject：kref 底座 + 随机延迟清理的测试武器（lib/kobject.c）

```c
static void kobject_release(struct kref *kref)     /* :705 */
{
	struct kobject *kobj = container_of(kref, struct kobject, kref);
#ifdef CONFIG_DEBUG_KOBJECT_RELEASE
	unsigned long delay = HZ + HZ * get_random_u32_below(4);   /* 1~4s 随机 */
	INIT_DELAYED_WORK(&kobj->release, kobject_delayed_cleanup);
	schedule_delayed_work(&kobj->release, delay);   /* :715 故意延迟清理 */
#else
	kobject_cleanup(kobj);                          /* :660 正常即时清理 */
#endif
}
void kobject_put(struct kobject *kobj) { ... kref_put(&kobj->kref, kobject_release); }  /* :733 */
```

★`CONFIG_DEBUG_KOBJECT_RELEASE` 的**随机 1~4 秒延迟**是给驱动作者上刑的：很多人在 release 路径里假设了"put 之后对象立即消失/立刻轮到我"的时序——随机延迟把这些竞态在测试机上放大成可复现 bug。生命周期框架反哺代码质量的一个漂亮设计。

### 5.2 percpu_ref：percpu 计数 → kill → 原子模式的两阶段（include/linux/percpu-refcount.h）

```c
struct percpu_ref {                 /* :105-122 */
	unsigned long percpu_count_ptr;  /* ★低位 = 模式标记（头注释原话：
	                                  "The low bit of the pointer indicates
	                                   whether the ref is in percpu mode"）*/
	struct percpu_ref_data *data;    /* 慢路径字段移出，缩 cache 足迹 */
};
```

设计注释的三连（:12-20 原话节选）：*"start shutting down you call **percpu_ref_kill() _before_ dropping the initial reference**"*；*"Before you call percpu_ref_kill(), percpu_ref_put() **does not check for the refcount hitting 0** - it can't, if it was in percpu mode"*——percpu 模式下计数散在各 CPU，**put 不可能查零**；kill 先把所有 percpu 计数收拢（加 `PERCPU_COUNT_BIAS`，:17）并切到原子模式，此后的 put 才恢复"归零判放"。

两阶段关闭的范式（头注释以 aio 的 `kill_ioctx` 为例，:28 起）：第一阶段 kill + 从查找表摘除（新读者再也找不到）；第二阶段存量引用陆续 put 归零 → release。**它把模式一的"查找表难题"和模式三的"读侧零开销"焊接在一起**：percpu 模式承担热路径（读写信号量/blk-mq 的 queue 引用），原子模式承担关闭窗口。

## 六、对照表与选型

| 维度 | kref | devres/devm_action | RCU/kfree_rcu | percpu_ref |
| :--- | :--- | :--- | :--- | :--- |
| get 成本 | 原子 inc | 零（挂靠时一次） | 零（读侧无操作） | percpu 模式下本地 inc（无跨核弹跳） |
| put 成本 | 原子 dec+test | 零（宿主事件触发） | 回调入队 | 本地 dec（percpu）/原子（kill 后） |
| 释放时机 | 精确（归零即放） | 宿主 unbind/失败 | 宽限期后（延迟不确定） | 两阶段（kill 后归零） |
| 查找表友好 | 需 unless_zero 技巧 | 不适用（无共享语义） | 天然（读侧免疫释放） | kill 摘除 + 存量过渡 |
| 典型用户 | kobject/task_struct/file | 驱动资源 | dentry-ish/热读结构 | percpu-rwsem/blk-mq |
| 失败模式 | use-after-free（少 put/多 put） | 泄漏或过早释放（宿主语义错） | 延迟回收内存 | kill 时序错（过早/过晚切模式） |

选型口诀：**有宿主就挂靠；共享对象计数；读多写少且能接受延迟用宽限期；计数热到跨核弹跳就用 percpu 再配两阶段关闭。**

## 七、思考题

1. `kref_put` 的 release 里做 `container_of` 整体释放——若两个子系统各自 kref_get 了同一个嵌入 kref，release 应该由谁定义？（提示：kref 属于"宿主结构"，释放语义唯一，与谁最后一次 put 无关。）
2. `kref_get_unless_zero` 失败返回 0 时对象"正在死"——调用方把它当"没找到"处理，但**刚被释放的内存能立刻被 slab 复用**给新对象吗？这会不会让查找表返回"另一个合法对象"？（提示：查找表自身的摘除时序；与 §5.2 的 kill 摘除对照。）
3. devres 的 LIFO 释放顺序为什么天然正确？（提示：后申请的资源常依赖先申请的——ioremap 依赖 request_region？倒过来释放谁先死？）
4. `KVFREE_BULK_MAX_ENTR` 按"一页能装多少指针"定批——为什么不是固定 128/256？（提示：批量数组本身用 kvfree 释放；页粒度分配与碎片。）
5. `CONFIG_DEBUG_KOBJECT_RELEASE` 的随机延迟若在**生产内核**打开，最坏会怎样？（提示：1~4s 延迟期间 sysfs 条目还挂着？引用者已全退出？内存驻留？）
6. percpu_ref 的 `PERCPU_COUNT_BIAS` 在收拢时加上——为什么不能直接把各 CPU 计数求和？（提示：收拢期间残留 put 还在减 percpu 计数；BIAS 给"已切原子"后的负向修正留余量。）
