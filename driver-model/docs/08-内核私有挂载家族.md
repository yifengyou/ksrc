# 内核私有挂载：kern_mount 家族（Linux 6.6）

> 阅读目标：盘点"不出现在任何 mount namespace"的挂载家族——`kern_mount()` 的机制（`SB_KERNMOUNT` 位 + `MNT_NS_INTERNAL` 归属）、六成员普查（pipefs/sockfs/aio/anon_inodes/mqueue/UMD tmpfs）、"伪 dname"技巧（`pipe:[%lu]` 的 d_path 输出），以及**为什么**要私有挂载（不被 umount、不被路径解析、namespace 免疫）。全部对照 v6.6（fs/namespace.c:4750、include/linux/fs.h:1124、fs/pipe.c、net/socket.c、fs/anon_inodes.c、fs/aio.c、ipc/mqueue.c、kernel/usermode_driver.c）。前置：[01-kobject 与 sysfs](01-kobject与sysfs.md)（kernfs——可见挂载的引擎对照）。

---

## 一、问题：内核对象为什么需要"文件"却不需要"路径"

```
pipe/socket/aio-ring/eventfd…… 这些内核对象在 VFS 眼里必须是 inode+file
（poll/epoll/fd 表全靠它们），但：
  × 不该出现在 /proc/mounts（用户不该 umount 它们）
  × 不该可被路径解析（没有 open("/pipe/123") 这种入口）
  × 不该受 mount namespace 生命周期牵连（容器退出≠pipe 消失）
答案：挂在"不属于任何 namespace"的私有 mount 上——
  superblock 打 SB_KERNMOUNT 位，mount 归属 MNT_NS_INTERNAL
```

## 二、机制：kern_mount 与两个标记（fs/namespace.c:4750-4762）

```c
struct vfsmount *kern_mount(struct file_system_type *type)
{
	struct vfsmount *mnt;
	mnt = vfs_kern_mount(type, SB_KERNMOUNT, type->name, NULL);
	if (!IS_ERR(mnt)) {
		/*
		 * it is a longterm mount, don't release mnt until
		 * we unmount before file sys is unregistered
		 */
		real_mount(mnt)->mnt_ns = MNT_NS_INTERNAL;
	}
	return mnt;
}
```

两个标记（已核对 6.6）：

| 标记 | 位置 | 作用 |
| :--- | :--- | :--- |
| `SB_KERNMOUNT = BIT(22)` | include/linux/fs.h:1124（注释原话 *"this is a kern_mount call"*） | super_block 的身份位：fs_context 走内核初始化路径（绕过用户态挂载选项解析）；后续同类型的用户挂载共享同一 fs_type 但各建 sb |
| `MNT_NS_INTERNAL` | real_mount(mnt)->mnt_ns 赋值 | ★mount 的归属设为"内部"——不属于任何用户 mount namespace：**umount2 够不着、namespace 退出不清点、/proc/mounts 不显示**（内部挂载列表另册管理） |

`vfs_kern_mount`（namespace.c:1121）本身是通用入口（用户挂载也走它，flags 无 SB_KERNMOUNT）——kern_mount 是它 + 两个标记的薄封装。

## 三、家族普查：六成员（全部已核对 6.6）

| 成员 | 挂载点 | 初始化 | sb 上的 inode 都是谁 | dname 输出 |
| :--- | :--- | :--- | :--- | :--- |
| **pipefs** | `pipe_mnt`（fs/pipe.c:857） | `init_pipe_fs` :1498，fs_initcall :1515 | 每个 pipe 一个 inode（`get_pipe_inode` :872 的 `new_inode_pseudo`） | `"pipe:[%lu]"`（:862-865） |
| **sockfs** | `sock_mnt`（net/socket.c:3260） | `sock_init` :3236，core_initcall :3285（注释 *"early initcall"*） | 每个 socket 一个 inode | `"socket:[%lu]"`（:360-364） |
| **anon_inodes** | `anon_inode_mnt`（fs/anon_inodes.c:259） | `anon_inode_init` :257，失败即 panic（:260-261） | ★一个共享 inode（`anon_inode_inode`）+ 大量 file（`__anon_inode_getfile` :78 的 `alloc_file_pseudo` :109）；另有 per-name 变体（头注释 :139 *"All the files created with anon_inode_getfile() will share a single inode"*） | `"anon_inode:%s"` 名字族 |
| **aio** | `aio_mnt`（fs/aio.c:298） | `aio_setup` :291（内联定义 `aio_fs` 文件系统类型，失败即 panic） | 每个 ioctx 的 ring file | `"aio:[%lu]"` 类 |
| **mqueue** | 特殊：不调 kern_mount，而是 `fs_context_for_mount(&mqueue_fs_type, SB_KERNMOUNT)`（ipc/mqueue.c:474） | 每用户 namespace 一个内部实例（mq_init_ns） | 每个消息队列一个 inode | 真实目录名（mqueue 也**同时**可被用户挂载可见——双面身份） |
| **UMD** | `blob_to_mnt` 返回的 tmpfs 挂载（kernel/usermode_driver.c:12/:24） | **运行时**（非 boot）：`umd_load_blob` :67 把内嵌 blob 写进私有 tmpfs（[module/08](../../module/docs/08-umh消费者全景.md) 已深挖） | 驱动程序本体（可 exec 的 .ko blob） | 内部路径 |

## 四、伪 dname：d_path 的输出改写

```c
/* fs/pipe.c:861-868 与 net/socket.c:358-367 同构 */
static char *pipefs_dname(struct dentry *dentry, char *buffer, int buflen)
{
	return dynamic_dname(buffer, buflen, "pipe:[%lu]",
				d_inode(dentry)->i_ino);
}
```

`ls -l /proc/<pid>/fd` 里形如 `pipe:[12345]` 的名字即此——**dentry 没有真实名字**（私有挂载无路径可走），`d_path` 落到 `d_dname` 回调动态合成"类型:[inode号]"。fd 表靠 inode 号找到同类对象（`/proc/<pid>/fd` 扫描正是按此关联）。

## 五、与 kernfs 的对照（可见挂载的引擎）

| 维度 | kern_mount 家族 | kernfs（[01 章](01-kobject与sysfs.md)） |
| :--- | :--- | :--- |
| 可见性 | 无路径、无 /proc/mounts 条目 | sysfs/cgroupfs：用户可挂载、可遍历 |
| 目的 | **给内核对象一个 VFS 载体** | **给内核对象一个用户接口** |
| inode 来源 | 各自 fs_type 的 pseudo inode | kernfs_node 1:1 映射 |
| 私有挂载？ | 是（MNT_NS_INTERNAL） | 否（但 sysfs 的**初始**挂载同样是 boot 时建立的常驻挂载——只是可见） |

★两个家族共享"内核数据结构 ↔ VFS inode"的桥接思想，分野在**要不要给用户路径**。

## 六、观测实战

```bash
# 1) 私有挂载确实不在 /proc/mounts
grep -c pipefs /proc/mounts        # 0（对照：sysfs 在）

# 2) 但 sb 与 inode 真实存在
cat /proc/filesystems | grep -E 'pipefs|sockfs'   # 注册表可见
ls -l /proc/self/fd | grep -oE '(pipe|socket|anon_inode):' | sort | uniq -c

# 3) mount namespace 的退出不清点它们
unshare -m sh -c 'mount -t tmpfs t /mnt; grep -c tmpfs /proc/mounts; exit'
#   tmpfs 随 namespace 消失；系统的 pipe（本 shell 的管道）不受影响

# 4) UMD 的私有 tmpfs（挂了 bpfilter 时）
grep -r bpfilter /sys/module/ 2>/dev/null          # 模块侧可见
#   但其文件本体在那个不可见挂载里
```

## 七、思考题

1. `MNT_NS_INTERNAL` 与"不设置 mnt_ns（NULL）"的差别是什么？（提示：NULL 意味着待接管的"无主"挂载；INTERNAL 是显式的"永不接管"——namespace 复制/传播逻辑对二者处理不同。）
2. anon_inodes 用**一个共享 inode** 对应成千上万的 file——哪些 file_operation 语义因此必须小心？（提示：inode 的 i_rwsem/i_mode 对所有实例共享；为什么 eventfd 不用共享 inode 而走 per-name？）
3. mqueue 双面身份（内核私有实例 + 用户可挂载）中 SB_KERNMOUNT 那份实例的作用是什么？（提示：mq_init_ns 时每个新 userns 需要一个"模板 sb"挂内部实例——为什么不全用用户挂载？）
4. 伪 dname 的 `[%lu]` 用 inode 号——`/proc/<pid>/fd` 的链接目标显示与 readlink 的成本在哪里？（提示：dynamic_dname 每次调用都 snprintf；与真实路径的 dentry+name 磁性链对照。）
5. UMD 选 tmpfs 而 pipefs 有自己的 fs_type——UMD 能不能也自造一个 fs_type？（提示：tmpfs 提供**可写**文件语义（写 blob 进去）+ exec；自造 fs_type 的成本与收益。）
6. 私有挂载保护了内核对象不被 umount——但 `kill_sb`（如 pipe_fs_type 的 `kill_anon_super`）在什么时候真正被调用？（提示：模块卸载/系统停机——pipefs 是内建永远不卸，对照 UMD 的 kern_unmount 动态用例。）
