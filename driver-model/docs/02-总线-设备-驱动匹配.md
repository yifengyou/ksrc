# 总线-设备-驱动匹配（Linux 6.6）

> 阅读目标：掌握 bus_type/device/device_driver 三层的职责与注册产物；吃透匹配-探测全链（`__driver_attach → really_probe` 已核对源码，含 -EPROBE_DEFER 的延迟机制与 async 路径）；理解 device link 的依赖治理与 probe 失败的排障法。

---

## 一、三层结构（include/linux/device.h）

```c
struct bus_type {
	const char		*name;
	int  (*match)(struct device *dev, struct device_driver *drv);  /* ★匹配仲裁 */
	int  (*probe)(struct device *dev);      /* 兼容老接口（新驱动用 drv->probe）*/
	int  (*remove)(struct device *dev);
	void (*shutdown)(...);  int (*dma_configure)(struct device *);
	int (*uevent)(struct device *dev, struct kobj_uevent_env *env);
	const struct dev_pm_ops *pm;            /* 电源分册的回调宿主 */
	struct subsys_private *p;               /* kset/klist/接口脚手架 */
	...
};
struct device { struct device_private *p; struct device_driver *driver;
	struct bus_type *bus; struct device *parent; struct kobject kobj;
	dev_t devt; void *driver_data; ... };   /* 宿主 kobject（上一章）*/
struct device_driver { const char *name; struct bus_type *bus;
	int (*probe)(struct device *dev); void (*remove)(...);
	const struct of_device_id *of_match_table;  /* DT 匹配（下一章）*/
	const struct acpi_device_id *acpi_match_table;
	const struct dev_pm_ops *pm; struct driver_private *p; ... };
```

`bus_register` 的产物（drivers/base/bus.c）：`/sys/bus/<name>/` + `devices/`、`drivers/` 两个 kset + 驱动模型的遍历底座（`bus_for_each_dev`/`bus_for_each_driver`——已核对调用点）。

## 二、匹配-探测全链（drivers/base/dd.c，已核对 6.6）

```
两个注册入口最终都汇聚到"把 device 和 driver 拉郎配"：
  driver_register → bus_add_driver → driver_attach
    └─ bus_for_each_dev(bus, NULL, drv, __driver_attach)
         __driver_attach(dev, drv):
           ① driver_match_device → bus->match(dev, drv)     /* 总线仲裁：
              失败直接跳过（不是错误）*/
           ② driver_probe_device → really_probe（dd.c:603，已核对）：
                if (defer_all_probes) → -EPROBE_DEFER        /* 全局延迟开关
                    （late initcall 阶段前）*/
                device_links_check_suppliers(dev)            /* 依赖未就绪
                    → EPROBE_DEFER */
                dev->driver = drv;                           /* 绑定成立 */
                pinctrl_bind_pins; bus->dma_configure        /* 引脚与 DMA 按总线族
                    配置 */
                driver_sysfs_add                             /* /sys 的
                    driver/<name>/<dev> 绑定符号链接 */
                dev->bus->probe 或 dev->driver->probe        /* ★驱动的真身 */
                probe 成功 → driver_bound（链入 klist）
                失败 → dev->driver = NULL 逐层回滚
  device_register → device_add → bus_probe_device → device_attach
    （对称：bus_for_each_driver 找 match）

async 路径：drv->probe_type == PROBE_PREFER_ASYNCHRONOUS 时
    async_schedule_dev(__driver_attach_async_helper)（多设备并行探测——
    大容量存储阵列的初始化提速，dd.c:1211 已核对）
```

## 三、-EPROBE_DEFER：延迟探测的机器

```
really_probe 返回 -EPROBE_DEFER → deferred_probe_insert：
  挂入 deferred_probe_pending_list；设备标记 dev->deferred_probe_reason
触发重试：
  ① 某驱动 probe 成功 → deferred_probe_trigger（把 pending 全部重排）
  ② late_initcall(deferred_probe_initcall)：开闸 driver_deferred_probe_enable
    （dd.c:349 已核对）+ 把满期未决的按依赖拓扑拍平重试
  ③ device_link 上下游注册/上线
满期兜底：deferred_probe_timeout（boot param，默认 30s? 单位/默认核对 boot
    文档）——超时后未决的以真实错误上报（防无限等待供应链）
排障：/sys/kernel/debug/devices_deferred（每个未决设备+原因）
```

**设计本质**：驱动加载顺序不可控的世界里，用"先欠条后重试"取代全局排序——supply-side ready 即重放。

## 四、device link：依赖的显式化

```
device_link_add(consumer, supplier, flags)
  DL_FLAG_AUTOREMOVE_CONSUMER/SUPPLIER / PM_RUNTIME? / SYNC_STATE_ONLY
效果：
  probe 顺序：supplier 先（really_probe 的 check_suppliers）
  电源（power 分册）：runtime PM 的链式唤醒/resume 顺序
  probe 拆链：DL_FLAG_AUTOREMOVE——consumer unbind 时自动清理
SYNC_STATE_ONLY：只管 suspend 晚下线（sync_state——声卡对 codec 的
  "最后使用者离开才关电"语义）
```

## 五、观测与实战

```
/sys/bus/pci/drivers/<drv>/            绑定的设备 symlink
/sys/devices/.../driver -> ...          反向链接
/drivers_probe、/drivers/<name>/bind   手工绑定/解绑（排障两件套：
   echo 0000:03:00.0 > /sys/bus/pci/drivers/nvme/bind）
cat /sys/kernel/debug/devices_deferred 延迟未决现场
dmesg | grep -E "probe.*failed|deferred"  失败第一现场
CONFIG_DEBUG_DRIVER? / probe timeout 排查路径
```

## 六、思考题

1. `bus->match` 与 `drv->probe` 的分工为什么不合并？（多驱动一次 match 全通过、probe 决定资源就绪性的两段式仲裁。）
2. `deferred_probe_initcall` 放在 late initcall 的理由？如果提前开闸，什么设备会遭殃？（IOMMU/时钟/电源域的注册时序。）
3. async probe 的乱序为什么安全？哪类驱动绝不能声明 PROBE_PREFER_ASYNCHRONOUS？（提示：boot 顺序语义。）
4. `device_link` 与 cgroup 分册的"内部进程约束"都在解决层级治理问题——两者的对象与强制力有什么对应？
5. 排障：设备 dmesg 只报 `-EPROBE_DEFER` 循环——用 devices_deferred + 依赖图给出系统性定位法。
