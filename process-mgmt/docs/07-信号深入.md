# 信号深入：RT 排队、signalfd 与 sigtimedwait（Linux 6.6）

> 定位：[04-信号子系统](04-信号子系统.md) 的纵深——RT 信号的真实排队语义（legacy 位图 vs RT 链表）、`sigqueue` 的分配与预分配、消费三通道（deliver/sigtimedwait/signalfd）的同源协议。前置：04 章、[06-namespace 全景](06-namespace全景.md)（pid 命名空间与 si_pid 的翻译）。

---

## 一、两个排队模型（已核对 6.6）

```
struct sigpending { struct list_head list; sigset_t signal; }
  ——信号状态 = 位图（signal）+ RT 队列链（list）双轨：
legacy（1..31，< SIGRTMIN=32 于 uapi/asm-generic/signal.h:50）：
  只看位图——已 pending 的同类信号再发 N 次仍是一个位
  （legacy_queue() 原句：(sig < SIGRTMIN) && sigismember(...)，
   signal.c:1079-1082——"同号不排队"即此一行）
RT（32..63，内核视角；glibc 暴露的 SIGRTMIN=34 是它保留 32/33
  给 NPTL——常被误记的口径差）：
  每次发送分配一个 sigqueue 挂 pending->list 尾——保序、不丢
两处 pending：task->pending（线程私有）与
  signal->shared_pending（线程组共享）——__send_signal_locked
  按 type != PIDTYPE_PID 选组队列（:1098）
```

## 二、发送链：__send_signal_locked（已核对 :1084-1170）

```
siglock 下：
  ① prepare_signal：忽略位/组停止等前置裁决
  ② 选队列（私有 vs 共享）
  ③ legacy 且已在位 → 直接返回（不重复排队）
  ④ __sigqueue_alloc（GFP_ATOMIC；rlimit_SIGPENDING 限额——
     但 SEND_SIG_NOINFO/内核态发送 override_rlimit 豁免
     :1120-1123 的三值逻辑）
  ⑤ 填 siginfo 三形态：SEND_SIG_NOINFO（SI_USER+发送者 pid/uid
     ——si_pid 经 pid ns 翻译 task_tgid_nr_ns）/ SEND_SIG_PRIV
     （SI_KERNEL，pid=0）/ 用户直发（拷贝完整 info，
     sig >= SIGRTMIN && si_code != SI_USER 时排队细节 :1160）
  ⑥ complete_signal：唤醒目标 + 组传播决策
预分配：SIGQUEUE_PREALLOC（POSIX 定时器/异步 IO 在事件源处
  __sigqueue_alloc(..., SIGQUEUE_PREALLOC) :1950——事件回调里
  不许 GFP_ATOMIC 失败，先备好）
```

## 三、消费三通道（同一份 pending 数据）

```
① 常规 deliver：get_signal 循环 dequeue_signal——先位图取号
  再从 RT 链摘对应 sigqueue（collect_signal）
② sigtimedwait/sigwaitinfo（do_sigtimedwait :3604）：
  ★"消费而不递送"——直接从 pending 摘出 siginfo 返回用户态，
  handler 不跑；阻塞在 siglock 等待队列，带超时
③ signalfd（fs/signalfd.c）：signalfd4() 创建 ctx（mask 存
  ctx 中，read 时以 ctx->sigmask 换 current 阻塞集）——
  poll 可读 ⇔ 有符合 mask 的 pending；read 走
  signalfd_copyinfo（:71）把 kernel_siginfo 拍平成
  signalfd_siginfo（定长结构体——语言中立）
三通道等价性：都是 dequeue 一个 sigqueue——事件循环模型
  （epoll+signalfd）与信号驱动模型可互换
```

## 四、si_pid 的命名空间翻译（跨 06 章联动）

```
发送侧即翻译：q->info.si_pid = task_tgid_nr_ns(current,
  task_active_pid_ns(t))——目标任务的 pid ns 视角（:1134-1135
原句）——容器里 kill 看到的发送者 pid 是"容器内编号"
```

## 五、观测与实战

```
cat /proc/<pid>/status | grep -E 'SigQ|SigPnd|ShdPnd'
  SigQ: <已排 RT 数>/<rlimit 上限>  SigPnd/ShdPnd: 十六进制位图
kill -l / kill -<sig> -<pgid>（组播：组内每任务各走一遍链）
pidfd_send_signal（send_signal 的 pidfd 变体——防 PID 复用竞态）
strace -e trace=rt_sigqueueinfo,signalfd4,rt_sigtimedwait
排障：RT 队列涨满（SigQ 到 rlimit）→ 发送方被 EAGAIN——
  典型于接收方死循环不消费（signalfd 未读）
```

## 六、思考题

1. legacy "同号不丢语义"为什么反而丢？（提示：SIGUSR1 连发 100 次与 SIGUSR1 一次在位图上等价——计数类应用必须用 RT。）
2. `override_rlimit` 为什么只豁免内核态发送？（对照 DoS 面：无限制用户排队 vs 内核信任边界。）
3. sigtimedwait"消费不递送"给库实现带来什么？（提示：条件变量/线程中断的经典替代实现。）
4. signalfd 的 mask 与线程阻塞 mask 的关系？（ctx->sigmask 换入换出——read 期间他人改了 tsk 阻塞集怎么办？）
5. SIGQUEUE_PREALLOC 预分配解决的那个"事件源上下文"具体是什么？（对照 timers 分册 POSIX 定时器的回调路径。）
