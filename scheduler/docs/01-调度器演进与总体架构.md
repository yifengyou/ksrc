# 调度器演进与总体架构

> 阅读目标：理解 Linux 6.6 调度器为什么长成今天这个样子——从 O(n)、O(1)、CFS 一路演进到 6.6 引入的 EEVDF；掌握调度类（sched_class）框架、策略（policy）与优先级（prio）三套体系如何协作；建立从系统调用、fork、唤醒、tick 到 `__schedule()` 的完整心智模型。

本章是调度器分册的总纲。数据结构细节见第 2 章，CFS/EEVDF 算法见第 3 章，调度时机与上下文切换见第 4 章，负载追踪与负载均衡见第 5、6 章，实时与 Deadline 调度见第 7 章。

## 一、调度器到底在解决什么问题

CPU 数量远少于可运行任务数量，调度器的本质工作是 **CPU 时间的复用器（multiplexer）**。它要在多个互相冲突的目标之间做权衡：

| 目标 | 含义 | 主要受益者 |
| :--- | :--- | :--- |
| **公平（Fairness）** | 每个 should-run 的任务获得与其权重成比例的 CPU 时间 | 批处理、多租户 |
| **延迟（Latency）** | 任务从唤醒到上 CPU 的时间尽量短 | 交互任务、在线服务 |
| **吞吐（Throughput）** | 单位时间完成的工作量尽量大 | 编译、训练等离线负载 |
| **能效（Energy）** | 尽量用"足够快"而不是"最快"的速度运行 | 手机、笔记本、边缘 |
| **隔离（Isolation）** | 一个任务的病态行为不能拖垮别人 | 容器、离在线混部 |

这些目标天然冲突：吞吐偏爱长切片、少切换（省掉 context switch 与 cache/TLB 污染），延迟偏爱短切片、快抢占。调度器的演进史，就是不断换一种数学模型来平衡这对矛盾的 历史。

除算法本身外，现代调度器还必须面对硬件现实：

* **cache / TLB 局部性**：任务在 CPU 间迁移代价很高，唤醒时倾向于留在唤醒者附近（cache-hot）。
* **NUMA**：跨 node 访存代价 2~3 倍起，催生了 NUMA balancing（第 6 章）。
* **异构算力**：大小核（arm64 big.LITTLE、Intel P/E-core）催生了 capacity-aware 调度与 EAS。
* **频率不变性（freq-invariant）**：CPU 频率变化时，负载统计必须按频率归一化，否则 cpufreq 会形成正反馈。

## 二、二十五年演进史：O(n) → O(1) → CFS → EEVDF

### 2.1 O(n) 调度器（2.4 时代，1998~2002）

* **数据结构**：全局单一 runqueue，双向链表挂所有可运行任务。
* **选任务**：每次调度遍历整个链表，用 `goodness()` 给每个任务打分，选最高分。复杂度 O(n)。
* **时间片**：启发式交互性评估——根据"睡眠时间/运行时间"的历史猜任务是不是交互式的，猜对了给更长的时间片和更高的唤醒优先级。

```
问题清单：
1. 锁全局 runqueue → SMP 扩展性灾难（所有 CPU 抢一把锁）
2. 每次调度 O(n) → 服务器上数千任务时调度开销不可接受
3. 交互性启发式是玄学，参数互相耦合，改一处崩三处
```

### 2.2 O(1) 调度器（2.6.8，2004，Ingo Molnar）

* **数据结构**：每个 CPU 一对 runqueue（active/expired），每个 runqueue 是 **140 个优先级链表 + 优先级位图**。
* **选任务**：位图找第一个非空优先级，O(1)。
* **交互性**：继续堆启发式：动态优先级（静态优先级 ± 奖惩）、交互式任务"时间片用完也留在 active 队列"的隐藏奖励、`sleep_avg`……

```
进步：SMP 扩展性、常数时间选取
新问题：启发式复杂到没人能推理；对"恶意睡眠"（sleep 立刻醒）的任务过度奖励；
        服务器（批处理）场景被桌面启发式系统性歧视
```

### 2.3 CFS 完全公平调度器（2.6.23，2007，Ingo Molnar）

CFS 的哲学转向：**不猜任务是什么，只记账任务拿了多少**。

* **核心量 `vruntime`（虚拟运行时间）**：`vruntime += delta_exec * NICE_0_LOAD / weight`。权重由 nice 值查表（nice 0 = 1024，每差一级约 1.25 倍）。
* **数据结构**：per-CPU 红黑树，按 vruntime 排序，永远调度最左节点（vruntime 最小者）。入队/出队 O(log n)。
* **公平定义**：任意时间窗口内，每个任务的运行时间与其权重成正比——vruntime 最多相差一个"调度延迟（sched_latency）"窗口。
* **交互性**：不再有交互性启发式。唤醒任务获得 vruntime 补偿（减去睡眠损失的一半），这本身就是"交互任务友好"的。

CFS 服务了内核 16 年（2.6.23 → 6.5），期间不断打补丁：sched_latency 与 min_granularity 两个参数纠缠不清、唤醒抢占的 wakeup_granularity、组调度的层级 vruntime 归一化……本质问题是：

```
CFS 的公平只定义了"比例"，没有定义"延迟"。
延迟由 sched_latency/min_granularity 两个人工参数控制：
  nr_running 超过 (sched_latency / min_granularity) 时调度周期被动拉长，
  延迟保证失效，且与任务权重、睡眠行为全部解耦。
```

### 2.4 EEVDF（6.6，2023，Peter Zijlstra，替代 CFS）

EEVDF = **Earliest Eligible Virtual Deadline First**，理论上是 1995 年就发表的算法（Stoica & Abdel-Wahab），6.6 把它实装到 fair 调度类。它在同一个虚拟时间（virtual time）体系里，把**公平与延迟统一成一个模型**：

* **公平 → eligibility（合格性）**：任务获得的服务没达到应得份额（lag ≥ 0）才是 eligible，eligible 的任务才允许被调度。
* **延迟 → virtual deadline（虚拟截止期）**：每个请求（request，即一次 slice）都有一个虚拟截止期 `vd_i = v_i + r_i / w_i`（到达虚拟时刻 + 请求时长/权重）。调度器在 eligible 集合中挑**最早虚拟截止期**者。

一句话对比：

| | CFS | EEVDF（6.6） |
| :--- | :--- | :--- |
| 挑谁 | vruntime 最小者 | eligible 集合中 virtual deadline 最早者 |
| 公平保证 | 比例公平（窗口式） | lag 守恒（\Sum lag_i = 0，随入队/出队传递） |
| 延迟保证 | sched_latency 参数，人数多时失效 | 由 slice/权重内生决定，短请求自然短延迟 |
| 核心数据 | 红黑树（vruntime 键） | 增广红黑树（vruntime + min_deadline 键） |
| 6.6 核心参数 | （已移除 latency/min_granularity） | `sysctl_sched_base_slice = 750000ns` |

第 3 章将逐行剖析 `avg_vruntime()`、`entity_eligible()`、`place_entity()`、`__pick_eevdf()` 的实现。

> 📌 顺带一提：EEVDF 落地后内核社区紧接着开发了 sched_ext（6.12 引入 BPF 调度器框架），两者是同一波"调度器可演进"思潮的产物。6.6 是最后一个纯 CFS 内核变体的"新起点"分界——学习 6.6 的 EEVDF 对理解后续所有版本至关重要。

## 三、6.6 调度器全貌：三套体系

### 3.1 调度类（sched_class）：策略的运行时多态

内核把"怎么调度一类任务"抽象成 `struct sched_class`（`kernel/sched/sched.h`），6.6 中共 5 个实例，**优先级从高到低**通过链接顺序固定：

```
stop_sched_class      (kernel/sched/stop_task.c)   CPU 停机任务（migration/*），最高优先级
   ↑
dl_sched_class        (kernel/sched/deadline.c)    SCHED_DEADLINE（EDF + CBS）
   ↑
rt_sched_class        (kernel/sched/rt.c)          SCHED_FIFO / SCHED_RR
   ↑
fair_sched_class      (kernel/sched/fair.c)        SCHED_NORMAL/BATCH/IDLE（EEVDF）
   ↑
idle_sched_class      (kernel/sched/idle.c)        idle 任务兜底
```

`pick_next_task()` 沿 `for_each_class` 从高到低问一遍"你有任务吗"（`class->pick_next_task(rq)`），第一个返回非 NULL 的类获胜。这就是"RT 永远抢占 CFS"的实现本质——不是什么魔法，只是问询顺序。

6.6 的 `struct sched_class` 关键操作（完整定义见第 2 章）：

```c
struct sched_class {
	int uclamp_enabled;

	void (*enqueue_task)(struct rq *rq, struct task_struct *p, int flags);
	void (*dequeue_task)(struct rq *rq, struct task_struct *p, int flags);
	void (*yield_task)(struct rq *rq);
	bool (*yield_to_task)(struct rq *rq, struct task_struct *p);
	void (*check_preempt_curr)(struct rq *rq, struct task_struct *p, int flags);
	struct task_struct *(*pick_next_task)(struct rq *rq);
	void (*put_prev_task)(struct rq *rq, struct task_struct *p);
	void (*set_next_task)(struct rq *rq, struct task_struct *p, bool first);
	int  (*balance)(struct rq *rq, struct task_struct *prev, struct rq_flags *rf);   /* 6.6 新签名 */
	int  (*select_task_rq)(struct task_struct *p, int task_cpu, int flags);
	struct task_struct *(*pick_task)(struct rq *rq);      /* 只挑不切换，供 sched_core/代理使用 */
	void (*migrate_task_rq)(struct task_struct *p, int new_cpu);
	void (*task_woken)(struct rq *this_rq, struct task_struct *task);
	void (*set_cpus_allowed)(struct task_struct *p, struct affinity_context *ctx);
	void (*rq_online)(struct rq *rq);
	void (*rq_offline)(struct rq *rq);
	struct rq *(*find_lock_rq)(struct task_struct *p, struct rq *rq);
	void (*task_tick)(struct rq *rq, struct task_struct *p, int queued);
	void (*task_fork)(struct task_struct *p);
	void (*task_dead)(struct task_struct *p);
	void (*switched_from)(struct rq *this_rq, struct task_struct *task);
	void (*switched_to)(struct rq *this_rq, struct task_struct *task);
	void (*prio_changed)(struct rq *this_rq, struct task_struct *task, int oldprio);
	unsigned int (*get_rr_interval)(struct rq *rq, struct task_struct *task);
	void (*update_curr)(struct rq *rq);
	void (*task_change_group)(struct task_struct *p);
	int (*task_is_throttled)(struct task_struct *p, int cpu);
	...
};
```

几个容易被忽视的语义细节：

* **`put_prev_task` / `set_next_task`**：`pick_next_task` 的语义是 `put_prev + set_next` 的组合。拆成两个回调是为了避免在"连续挑同一个类"时重复做类的内部记账。
* **`balance`**：这是 fair 类的 `newidle_balance` 钩子。当队列即将空闲时，`pick_next_task` 会先调用它尝试从别的 CPU 拉任务（第 6 章）。
* **`pick_task`**：轻量版 pick，不产生副作用（不修改任何状态），专供 **core scheduling**（`CONFIG_SCHED_CORE`，防 SMT 侧信道）做兄弟 CPU 的打包决策。

### 3.2 策略（policy）与优先级：用户态视角

用户通过 `sched_setscheduler(2)` / `nice(2)` 表达需求，内核内部统一成 **prio 数字（越小越优先）**：

```
prio 0 ~ 98   : RT（rt_priority 99~1；rt_priority 越大越优先，正好与 prio 反向）
                MAX_RT_PRIO = 100
prio 99       : 保留（rt_priority == 0 且 policy 变化过渡态）
prio 100~139  : CFS（static_prio = 120 + nice；nice -20~19 → prio 100~139）
```

| policy | 调度类 | 语义 | 典型用户 |
| :--- | :--- | :--- | :--- |
| `SCHED_DEADLINE` | dl | 保证（runtime, deadline, period）三元组 | 工业实时、音频 |
| `SCHED_FIFO` | rt | FIFO 同优先级不轮转，可无限占据 CPU | 内核线程、实时任务 |
| `SCHED_RR` | rt | 同优先级轮转（`sched_rr_timeslice`，默认 100ms） | 传统实时 |
| `SCHED_NORMAL` | fair | 普通任务 | 绝大多数进程 |
| `SCHED_BATCH` | fair | 同 fair，但禁止唤醒抢占（吞吐偏好） | 编译、批处理 |
| `SCHED_IDLE` | fair | 极低优先级（idle_nr_running 单独计数） | 后台清理 |

> 📌 nice 的效果：nice 每差 1 级权重比约 1.25（`sched_prio_to_weight[]` 表，`kernel/sched/core.c`），即 CPU 份额比 ~10:7.5:5.6:…；nice -20 vs +19 的权重比约 88.61:15，接近 5900:1。**注意**：这不是上限（cgroup cpu.max 才是上限），只是份额。

### 3.3 cgroup（cpu controller）：资源管制的第三层

v2 的 `cpu.weight`（= nice 语义的组级版）、`cpu.max`（CFS bandwidth：quota/period，6.6 里由 `sched_cfs_bandwidth_slice`（5000us，per-CPU 配额粒度）驱动 throttle/分发）与 `cpu.pressure`（PSI）构成了容器场景的 CPU QoS 三件套。组调度使 `task_group` 成为公平调度树里的中间节点（`sched_entity` 既可以代表任务也可以代表组），详见第 3 章。

## 四、调度器的工作入口：全景图

调度器没有单一入口，它由**五类事件**驱动。所有路径最终汇聚到 `__schedule()`（`kernel/sched/core.c`）：

```
                    ┌──────────────────────────────────────────────────┐
                    │                    __schedule()                    │
                    │  pick_next_task() ──► sched_class 链问询 ──► next  │
                    │  context_switch() ──► switch_mm() + switch_to()    │
                    └──────────────────────────────────────────────────┘
                        ▲              ▲               ▲            ▲
        1. 主动阻塞     │              │ 2. 被动抢占    │            │ 5. 中断/异常
   schedule()/io_wait/signal    wakeup 唤醒抢占          │       返回路径检查
                        │              │               │            │ need_resched
                        │              │               │            │
   ┌────────────────────┴───┐   ┌──────┴────────┐   ┌──┴─────────┐ ┌─┴──────────┐
   │ try_to_wake_up()       │   │ resched_curr() │   │ scheduler_ │ │ preempt_   │
   │  └► ttwu_queue()       │   │  设 TIF_NEED_  │   │ tick()     │ │ schedule() │
   │     └► check_preempt_  │   │  RESCHED，跨   │   │  task_tick │ │ (_irq)     │
   │        curr()          │   │  CPU 发 IPI    │   │  更新统计   │ └────────────┘
   └────────────────────────┘   └───────────────┘   └────────────┘
        3. fork 新任务                          4. yield / exit
   wake_up_new_task()                        sched_yield()/do_task_dead()
```

1. **主动让出**：任务调用 `schedule()`（阻塞在 futex/pipe/read 上、被信号打断……）。`schedule()` 内部直接调用 `__schedule(SM_NONE)`。
2. **唤醒抢占**：别的 CPU 唤醒了一个高优先级/更该跑的任务，通过 `check_preempt_curr()` → `resched_curr()` 给目标 CPU 设置 `TIF_NEED_RESCHED`；跨 CPU 时用 `smp_send_reschedule()` 发 **resched IPI**。
3. **时钟 tick**：`sched_tick_fallback`（低分辨率）或 `tick_nohz` 周期回调 `scheduler_tick(rq)`，更新当前任务统计并检查是否该让位。EEVDF 下 tick 的直接抢占决策权被削弱（详见第 3、4 章）。
4. **主动弃权/退出**：`sched_yield()`（`yield_task` 回调）、`do_exit()` → `do_task_dead()`。
5. **返回用户态/使能抢占**：内核态路径在 `preempt_enable()`、`local_bh_enable()`、中断返回（`preempt_schedule_irq`）、系统调用返回用户态（`exit_to_user_mode_loop`，x86；`ret_to_user`，arm64）等点检查 `TIF_NEED_RESCHED`，置位则调用 `__schedule(SM_PREEMPT)`。

### 4.1 抢占模型：四种配置与 PREEMPT_DYNAMIC

`preempt_count`（每个任务 `thread_info->preempt_count`）的低 8 位是抢占计数，往上依次是 SOFTIRQ/HARDIRQ/NMI 位。**只要低 8 位非 0（或 IRQ 位非 0），就不能发生任务级抢占**。

* `CONFIG_PREEMPT_NONE`：只在用户态边界抢占。服务器默认（吞吐、上下文切换最少）。
* `CONFIG_PREEMPT_VOLUNTARY`：`cond_resched()` 点让出。桌面旧默认。
* `CONFIG_PREEMPT`：内核态任意 `preempt_enable` 边界可抢占（除临界区）。低延迟。
* `CONFIG_PREEMPT_DYNAMIC`（6.6 默认，x86/arm64 等）：编译期含全部抢占点，用 **static_call**（`preempt_schedule` / `preempt_schedule_noirq`，见 `kernel/sched/core.c` 中 `DEFINE_STATIC_CALL(preempt_schedule, ...)`）在启动时通过 `preempt=` 参数选择 none/voluntary/full，运行时可再通过 `/sys/kernel/debug/sched/preempt` 切换。

`PREEMPT_RT` 在 6.6 仍是独立分支（spinlock→rt_mutex 化、大部分中断线程化、`preempt_schedule` 永远 full），其调度器部分的主线化工作（如 rtmutex 语义、`sched_mode` 里的 `SM_RTLOCK_WAIT`）已经逐步合入。

### 4.2 `resched_curr` 与跨核 IPI

```c
void resched_curr(struct rq *rq)
{
	struct task_struct *curr = rq->curr;
	int cpu;

	if (test_tsk_need_resched(curr))
		return;                       /* 已置位，无需重复 */

	cpu = cpu_of(rq);
	if (cpu == smp_processor_id()) {
		set_tsk_need_resched(curr);   /* 本 CPU：直接设 TIF_NEED_RESCHED */
		set_preempt_need_resched();   /* PREEMPT_DYNAMIC: 紧急标记 */
		return;
	}

	if (set_nr_and_not_polling(curr))
		smp_send_reschedule(cpu);     /* 远端：置位 + 发 resched IPI */
	...
}
```

resched IPI 是唤醒延迟的最后一环：**远端 CPU 正在内核态不可抢占区（如长列表遍历）时，抢占要等到下一个抢占点才发生**——这就是 CONFIG_PREEMPT 对尾延迟影响巨大的根本原因，也是 `runqlat` 观测的主要成分（第 4 章详述）。

## 五、调度器与相邻子系统的接口

```
             ┌────────────┐  util_avg/util_est/uclamp   ┌─────────────┐
             │  cpufreq    │◄───────────────────────────│  schedutil   │
             │  ( governors)│      (schedutil governor)   │  (fair)     │
             └────────────┘                              └─────────────┘
 cgroup v2 ──► task_group/cpu.max ──► CFS bandwidth ──► throttle ◄─── fair
             ┌────────────┐  sched tracepoints            ┌─────────────┐
             │ ftrace/perf │◄── sched_switch/sched_wakeup │  core.c     │
             │  psi/runqlat│◄── psi_sched_switch          │             │
             └────────────┘                               └─────────────┘
             ┌────────────┐  CPU capacity                 ┌─────────────┐
             │   topology  │──► sched_domain/capacity ───► │ topology.c  │
             │ (DT/ACPI)   │   (EAS, capacity_aware)       │  (第6章)    │
             └────────────┘                                └─────────────┘
```

* **cpufreq/schedutil**：PELT（第 5 章）输出 `util_avg`，schedutil 据此请求频率；`uclamp`（util clamp）给 util 设上下限，`uclamp` 的 cgroup 接口是 Android 的性能框架基石。
* **CPU idle（cpuidle）**：`select_task_rq` 与 idle 调度类的互动决定浅睡/深睡；`menu` governor 会参考任务预测。
* **热与能效**：thermal 的 `cpu_cooling`（power allocator）通过 capacity 缩放参与调度；EAS（`find_energy_efficient_cpu`）在能效模型可用时改变唤醒选核。
* **虚拟化**：KVM 的 vCPU 是普通 fair 任务，`yield_to` / `PLE`（paravirt scheduling）与其交互；本仓库 virt/kvm 分册。
* **BPF**：`scx_` 之前的 6.6 里 BPF 主要用于观测调度器（BPF tracepoint/iter）。

| 工具 | 来源 | 回答什么问题 |

| `/proc/sched_debug` | CONFIG_SCHED_DEBUG | 每 CPU/每任务的完整调度状态（vruntime、slice、负载） |

## 七、思考题

1. **为什么 `pick_next_task()` 是"从高到低问每个类"而不是全局一个优先级数字？** 提示：DL 的准入语义与 RT 的 prio 数字不可比；每个类内部有自己的记账（vruntime/EDF deadline）。
2. **CFS 移除了交互性启发式，为什么交互体验反而更好？** 提示：唤醒 vruntime 补偿 + `wakeup_preempt`；启发式最大的问题是被 workload 猜测绑架。
3. **`PREEMPT_DYNAMIC` 为什么用 static_call 而不是 static_key + 分支？** 提示：`preempt_schedule` 在返回路径的最热点上，static_call 直接改函数指针，零额外分支。
4. **EEVDF 下 `SCHED_BATCH` 和 `SCHED_IDLE` 还有什么存在意义？** 提示：`WAKEUP_PREEMPTION` 特性关闭路径；`idle_nr_running` 独立记账 + 强制 lag 惩罚。
5. **resched IPI 没有立刻生效（目标 CPU 在内核态长临界区），runqlat 会看到什么？哪三个手段能缓解？** 提示：PREEMPT 动态切换、拆临界区、affinity 绑核避开。
