# 观测扇出模式：一份采集，多本账（Linux 6.6）

> 阅读目标：提炼本分册 14/15 章与 trace/12 章反复碰撞出的结构规律——**热路径上只设一个采集点，多个观测账本从同一点扇出**（fan-out）。四个案例：`__update_stats_enqueue_sleeper` 的四账本（schedstat/delayacct/latencytop/SLEEP_PROFILING）、`__schedule` 切换点的**六连扇出**（nr_switches/sched_info/PSI/tracepoint/perf/kcov）、`update_rq_clock_task` 的 irq 双账本（delayacct_irq + psi irqtime）、`sched_info` 的双出口（/proc/<pid>/schedstat + taskstats）。理解**开关独立**设计（采集点常驻、每支扇出各自短路）与单一采集点的成本/一致性论证。全部对照 v6.6。前置：[14-schedstat](14-调度器统计纵深schedstat.md)｜[15-delayacct](15-任务延迟统计delayacct.md)。

---

## 一、模式定义

```
反模式（每账本自采）：
  N 个观测子系统各自在热路径插桩 → N 份侵入成本、N 套时间基、
  竞态窗口互不相同、维护者要读 N 处
扇出模式（单一采集点）：
  热路径 ──► 采集点（常驻，通常无门控）
              ├─► 账本 A（static key A 门控，未开=一条跳转）
              ├─► 账本 B（int/开关 B 门控）
              ├─► 账本 C（条件编译）
              └─► 事件出口（tracepoint——第三类消费者按需挂载）
```

三个性质：①**一致性**——同一 delta、同一时钟基、同一次锁临界区里记账；②**开关独立**——采集点不知道谁开着，各支扇出自己短路（static branch 的 nop 化）；③**新账本零侵入**——加账本只改扇出函数，热路径不动。

## 二、案例一：唤醒/睡眠点的四账本（kernel/sched/stats.c:47-107）

`__update_stats_enqueue_sleeper` 是本仓库追踪过多次的枢纽（[14 章 §四](14-调度器统计纵深schedstat.md)、[trace/12 §3.2](../../trace/docs/12-profile与latencytop.md)）——一个函数喂四本账：

```
任务入队唤醒（带 sleep/block 时间戳）
  └─ __update_stats_enqueue_sleeper(stats.c:47)
       ├─ schedstat 账：sleep/block 的 sum/max 计数族
       │    （stats->sum_sleep_runtime / block_max ...）
       ├─ tracepoint 出口：trace_sched_stat_sleep / _blocked（:69/:93）
       ├─ SLEEP_PROFILING 账：profile_hits(SLEEP_PROFILING,
       │    get_wchan(p), delta >> 20)（:100-105 —— ms 精度的 wchan 采样）
       ├─ latencytop 账：account_scheduler_latency(p, delta>>10, inter)
       │    （:68 inter=1 自愿睡 / :105 inter=0 阻塞——两分支两语义）
       └─ iowait 细分：p->in_iowait → iowait_sum/count +
            trace_sched_stat_iowait（:90——schedstat 账的子账本）
```

★**精度梯子**：同一个 delta 被三种单位消费——`delta` 原值（ns，schedstat）、`delta >> 10`（μs，latencytop）、`delta >> 20`（ms，profile，"shift by 20" 注释原话）。一份采集，三种粒度。

## 三、案例二：__schedule 切换点的六连扇出（core.c:6666-6691 + prepare_task_switch）

一次上下文切换是内核最大的观测事件，扇出横跨五层：

```
__schedule（prev != next 时，:6666）
  ├─ rq->nr_switches++                          /* :6667 rq 计数账 */
  ├─ RCU_INIT_POINTER(rq->curr, next)            /* :6672 状态账 */
  ├─ ...（pick 的后续、rq->last_seen_need_resched 清零 :6663 等）
  ├─ ++*switch_count                             /* :6689 n(v)ivcsw 账
  │                                               （task_struct 字段，
  │                                                taskstats/proc stat 消费）*/
  ├─ psi_sched_switch(prev, next, sleep)         /* :6690 ★PSI 账
  │                                               （stats.h:178 真身，
  │                                                static_branch_likely
  │                                                (&psi_disabled) 自门控）*/
  ├─ trace_sched_switch(...)                     /* :6691 事件出口
  │                                               （ftrace/perf/BPF 挂载）*/
  └─ context_switch(:5324)
       ├─ prepare_task_switch(:5178-5186)
       │    ├─ kcov_prepare_switch(prev)         /* :5182 覆盖率账 */
       │    ├─ sched_info_switch(rq, prev, next) /* :5183 SCHED_INFO
       │    │                                      时间戳账（14 章）*/
       │    ├─ perf_event_task_sched_out(prev, next) /* :5184 perf PMU
       │    │                                      上下文账 */
       │    ├─ rseq_preempt(prev)                /* :5185 用户态重启序列 */
       │    └─ fire_sched_out_preempt_notifiers  /* :5186 KVM 等订阅者 */
       └─（switch_mm / switch_to / finish_task_switch 镜像侧）
```

六个直接账本（nr_switches/switch_count/PSI/sched_info/perf/kcov）+ 一个事件出口（tracepoint）+ notifiers 订阅者——**热路径本身没有一行"if (观测开着)"**；每支扇出函数自带头部门控（psi_disabled static key、perf 的 ctxpin 检查、kcov 的 mode 检查）。

## 四、案例三：时钟点的 irq 双账本（core.c update_rq_clock_task）

[15 章 §五](15-任务延迟统计delayacct.md) 已见——`CONFIG_IRQ_TIME_ACCOUNTING` 算出的 `irq_delta` 一次算、两处吃：

```c
/* update_rq_clock_task（core.c:694 起，节选） */
irq_delta = irq_time_read(cpu_of(rq)) - rq->prev_irq_time;
rq->prev_irq_time += irq_delta;
delta -= irq_delta;                    /* ★同一 delta 还从 rq 时钟里扣除
                                          ——第三个消费者是 clock_task 本身 */
psi_account_irqtime(rq->curr, irq_delta);
delayacct_irq(rq->curr, irq_delta);    /* :726 delayacct 的 irq 族 */
```

**三消费者**：clock_task（扣账）、PSI（挤占账）、delayacct（任务账）——一份 irq_delta 服务三种语义的"中断时间到底算谁的"。

## 五、案例四：sched_info 的双出口（stats.h:198-289 + delayacct.c）

[14 章](14-调度器统计纵深schedstat.md) 的 SCHED_INFO 时间戳账（arrive/depart/switch 四函数）只有一个采集端，却有两个**消费出口**：

```
sched_info_arrive/depart/switch（stats.h:224/:251/:267）
  └─ tsk->sched_info（pcount/run_delay）
       ├─ 出口①：/proc/<pid>/schedstat 三元组（base.c:476-488）
       └─ 出口②：taskstats 的 cpu 族（delayacct.c:149-152：
                    cpu_count += pcount;
                    cpu_delay_total += run_delay;）
```

★与案例一的区别：这是**采集点与导出端分离**的形态——账本（sched_info）本身没有出口，两个出口各自读账（procfs 拉式 / netlink 推式）。

## 六、模式总结表

| 案例 | 采集点 | 账本数 | 门控形态 | 出口 |
| :--- | :--- | :--- | :--- | :--- |
| enqueue_sleeper | stats.c:43 | 4 | static key（schedstat）/int（latencytop·prof_on） | 计数+tracepoint |
| __schedule 切换 | core.c:6666 | 6+notifiers | 各支自门控（psi_disabled 等） | 计数+tracepoint+PMU |
| rq 时钟 | update_rq_clock_task | 3 | 条件编译+各支 | 时钟修正+两账本 |
| sched_info | stats.h 四函数 | 1（双出口） | 编译期 | procfs+netlink |

**设计收益的三条度量**：一致性（同 delta 同锁）、增量成本（每加账本热路径零修改）、失败隔离（一个账本的 bug 不传染采集点——除了 delta 算错这种共同根基）。

## 七、实战：发现新的扇出点

```bash
# 1) 找"一次采集多处消费"的函数——grep 同一 delta/计数被多个 *_account/统计函数吃
git grep -n 'account_.*delta\|_account_irqtime' kernel/sched/

# 2) 验证某支扇出的门控是否存在（没有门控=常驻成本，值得审查）
grep -B3 'psi_sched_switch\|delayacct_irq' kernel/sched/*.c

# 3) 交叉对账（三个出口同源，数值应可互相印证）
cat /proc/<pid>/schedstat            # 出口① run_delay（ns）
perf record -e sched:sched_stat_sleep -a sleep 3   # tracepoint 出口的同源事件
getdelays -p <pid>                   # taskstats 出口 cpu_delay_total

# 4) 找"账本没出口"的悬空采集（浪费：采了没人看——sched_info 在
#    !CONFIG_TASK_DELAY_ACCT 时若仅剩 schedstat 三元组一个出口，成本收益比）
```

## 八、思考题

1. 案例一的精度梯子（ns/μs/ms 三种右移）——为什么 latencytop 用 μs 而不用 ns？（提示：latencytop 的定容账本按回溯 key 聚合，数值宽度影响什么？`>> 10` 丢掉的精度对它的语义重要吗？）
2. `__schedule` 的六支扇出没有任何一支做"总开关检查"——如果全关，这段代码的净成本是多少？（提示：static key nop 化后的真实指令数；rq->nr_switches++ 这种无条件记账为什么不门控？）
3. 案例三的 clock_task 自己也是消费者（delta -= irq_delta）——这算"账本"还是"账本的修正项"？（提示：若 irq_delta 不扣，PELT 与 util 的语义会怎么漂？）
4. sched_info 的双出口形态下，两个出口读到**不一致**快照是可能还是必然？（对照 delayacct.c:146-149 的 "No locking available for sched_info...Mitigate by taking snapshot" 注释。）
5. 给扇出点加一个新账本（比如"per-cgroup 的切换计数"）应该改哪一层？若误改了热路径本体（在 __schedule 里直接加计数），违反模式的哪条性质？（提示：开关独立性。）
6. tracepoint 作为"第三类消费者"与 static key 门控账本的耦合方式不同（运行时 probe 注册 vs 编译期键）——tracepoint 的 funcs 数组机制（[trace/02](../../trace/docs/02-tracepoint机制.md)）如何做到"采集点常驻、消费者按需"？（提示：static_key_false + funcs 数组的组合。）
