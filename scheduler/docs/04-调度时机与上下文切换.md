# 调度时机与上下文切换（Linux 6.6）

> 阅读目标：吃透从"事件发生"到"寄存器换人"的完整链路——tick 驱动、唤醒路径（`try_to_wake_up` 的内存序与 wakelist 优化）、`__schedule()` 的逐行语义、`context_switch()` 的地址空间与栈切换、抢占检查的全部触发点。

---

## 一、调度时机的完整清单

回顾第 1 章的五类事件，本章逐条展开：

```
① 主动阻塞        prev 主动调 schedule()（__schedule(SM_NONE)）
② 唤醒抢占        ttwu → check_preempt_curr → resched_curr → (远端 IPI)
③ 周期 tick       scheduler_tick → task_tick → (EEVDF: update_deadline 已内联决策)
④ yield/exit      sched_yield / do_task_dead
⑤ 抢占检查点      preempt_enable / irq_exit / 返回用户态 → __schedule(SM_PREEMPT)
```

**核心分工**：①③④④ 只发生在"本 CPU"或"目标任务的宿主 CPU"；②⑤ 是跨 CPU 协作的两大主角。所有路径的公共终点是 `__schedule()`。

## 二、tick 路径：scheduler_tick

```
tick_nohz_handler / tick_sched_timer          (kernel/time/tick-sched.c)
  └─ tick_sched_handle() → …
update_process_times(user_tick, ticks)        (kernel/time/timer.c)
  └─ scheduler_tick()                         (kernel/sched/core.c)
       ├─ sched_clock_tick()                  修 rq->clock 漂移（TSC 不稳场景）
       ├─ rq_lock / update_rq_clock()
       ├─ curr->sched_class->task_tick(rq, curr, 0)   ★ 类回调
       ├─ hw_pressure / thermal 压力记账
       ├─ rq->idle_balance 触发判断、calc_global_load_tick()
       └─ trigger_load_balance(rq)            负载均衡（第 6 章）
```

fair 类的 `task_tick_fair()`（6.6 精简）：

```c
static void task_tick_fair(struct rq *rq, struct task_struct *curr, int queued)
{
	struct sched_entity *se = &curr->se;

	for_each_sched_entity(se) {            /* 组调度：逐层更新 */
		cfs_rq = cfs_rq_of(se);
		entity_tick(cfs_rq, se, queued);
	}
	if (static_branch_unlikely(&sched_numa_balancing))
		task_tick_numa(rq, curr);      /* NUMA 采样（第 6 章）*/
	update_misfit_status(curr, rq);
	update_overutilized_status(task_rq(curr));
	task_tick_core(rq, curr);             /* core scheduling */
}
```

而 `entity_tick()`（6.6）只剩三件事：`update_curr`（记账，内含 deadline 到期判断）、PELT 更新、hrtick 处理。**对比 6.5 少了 `check_preempt_tick`**——第 3 章已剖析：EEVDF 的抢占判定搬进了 `update_curr → update_deadline`，tick 从"决策者"降级为"记账触发器"。

> 💡 这个设计变化还有一个隐藏收益：**tickless（NOHZ_FULL）CPU 的公平性不再退化**。6.5 里无 tick 的 CPU 依赖 hrtick 或邻居 CPU 的周期来检查切片；6.6 里任何进入 `rq->lock` 的操作都会推进记账。

### 2.1 hrtick：微秒级切片的可选路径

`CONFIG_SCHED_HRTICK`（默认关）用 per-rq hrtimer 在"理论抢占时刻"精准到期，替代 tick 粒度。EEVDF 请求长度 0.75ms < 1/HZ(4ms@250HZ)，若追求严格 slice 语义可开（`SCHED_FEAT(HRTICK)`，debugfs 可调）。代价：hrtimer 编程开销与功耗。

## 三、唤醒路径：try_to_wake_up() 全解

唤醒是调度器最复杂、内存序最密集的路径（源码注释 200+ 行）。先看骨架（`kernel/sched/core.c`，6.6）：

```
wake_up_process(p) / wake_up_state / …
  └─ try_to_wake_up(p, state, wake_flags)
       0. guard(preempt)                       禁抢占作用域
       1. fast path: p == current 特判
       2. LOCK p->pi_lock
       3. smp_mb__after_spinlock + 读 p->__state（state & mask 不符 → 失败退出）
       4. 三种竞态短路：
          a) p->on_rq == QUEUED  → ttwu_runnable()   已在队列（比如 exit 时序），
                                                        仅需 check_preempt_curr
          b) p->on_cpu           → 自旋/走 wakelist 等 prev 完成 context_switch
                                   smp_cond_load_acquire(&p->on_cpu, !VAL)
       5. select_task_rq(p, cpu, wake_flags)   ★ 选目标 CPU（fair: select_task_rq_fair）
       6. set_task_cpu(p, new_cpu)             迁移记账（PELT detach/attach、rq lockseq）
       7. p->__state = TASK_WAKING → UNLOCK pi_lock
       8. ttwu_queue(p, new_cpu, wake_flags)
          ├─ TTWU_QUEUE 特性开 && 远端 → ttwu_queue_wakelist()
          │    挂到目标 CPU 的 wake_list + 发 sched IPI（resched_curr 走捷径）
          │    —— 目标 CPU 在下一次 __schedule 前的 enqueue 由自己完成
          └─ 否则直接 ttwu_do_activate() → enqueue + check_preempt_curr
       9. 成功统计 / psi 记账
```

### 3.1 竞态协议：on_rq / on_cpu / __state 三件套

`try_to_wake_up` 与远端 CPU 的 `__schedule`（把同一任务 p 换下）的对话完全依赖三个字段与显式屏障：

```
CPU0（唤醒者）                         CPU1（p 的宿主，正调度走 p）
-------                                -------
LOCK p->pi_lock
READ p->__state
若 state 匹配：
  WRITE p->__state = TASK_RUNNING
（关键控制依赖：先读 on_rq 再决定后续）
READ p->on_rq == 0                     __schedule():
  ↓ control-dependency                   prev_state = READ_ONCE(prev->__state)
  smp_acquire__after_ctrl_dep()          deactivate_task() → p->on_rq = 0
WRITE p->__state = TASK_WAKING           rq->curr = next; p->on_cpu = 1→0 …
                                         finish_task_switch: smp_store_release(on_cpu, 0)
若 p->on_cpu == 1:
  ttwu_queue_wakelist() 或
  smp_cond_load_acquire(&p->on_cpu, !VAL)   /* 等 CPU1 完成切换 */
```

要点：

* **为什么必须等 `on_cpu == 0`**：`switch_to()` 之后到 `finish_task_switch()` 之间，prev 的内核栈/寄存器仍被"上一个 CPU"引用。若此时把 p 入队被第三个 CPU 拿去跑，同一 task 会同时在两处执行——内核当场 OOPS。`smp_cond_load_acquire` 是最著名的"等待式"原语之一。
* **`TASK_WAKING` 状态**：把 pi_lock 与 rq->lock 的临界区解耦——state 置 WAKING 后即可放 pi_lock，真正的 enqueue 拿目标 rq 锁。
* **`ttwu_queue_wakelist`**（TTWU_QUEUE 特性，PREEMPT_RT 下关闭）：远端唤醒不再"拿别人 rq 锁"，而是投递到 `rq->ttwu_pending` 标记的 wakelist，由 sched IPI 在目标 CPU 本地处理。唤醒风暴下显著降低锁竞争。

### 3.2 选 CPU：select_task_rq_fair 的三段式

```
select_task_rq_fair(p, prev_cpu, wake_flags)
  ├─ want_affine?（prev_cpu 与 current 同 LLC 且 SD_WAKE_AFFINE）
  │    wake_affine_idler/weight 判断          "唤醒者旁边值不值得去"（cache 局部性 vs 队列长度）
  │    new_cpu = select_idle_sibling(p, prev_cpu, new_cpu)
  │        依次快查: target 空闲 → prev 空闲（同 LLC）→ per-CPU kthread 与
  │        唤醒者叠核 → recent_used_cpu；SMT 先试整个空闲 core
  │        然后扫 LLC：SIS_UTIL（6.6 默认）用 LLC 共享的 nr_idle_scan 作上限
  │        （按 LLC 聚合 util 动态收缩——util 越高越早放弃空扫，for_each_cpu_wrap
  │         自 target 起环形扫描）；大小核系统走 select_idle_capacity：
  │        不找"空闲核"，找"capacity 余量装得下任务 util"的核
  ├─ 不 affine → find_idlest_cpu()
  │    逐 sched_domain 下降，find_idlest_group + find_idlest_cpu
  │    （高负载下的"最空队列"策略，慢路径）
  └─ 兜底：allowed_mask 里选 prev_cpu / wake_cpu
```

SMP 唤醒策略本质是**两个代价的博弈**：迁移损失（cache/TLB/NUMA 冷启动）vs 等待损失（本地队列长）。6.6 用 PELT util 动态裁剪扫描（`SIS_UTIL` 替代了老的 `SIS_PROP`），是把"扫描本身也是开销"量化的版本。

### 3.3 唤醒之后：check_preempt_curr

入队完成（`ttwu_do_activate → enqueue_task`）即调用 `p->sched_class->check_preempt_curr(rq, p, wake_flags)`。fair 类在 6.6 的判定即第 3 章 `pick_eevdf(cfs_rq) == pse`（"该跑的是不是我刚唤醒的这个？"）。跨核场景 `resched_curr` 发 IPI（第 1 章）。

## 四、schedule() 与 __schedule()

用户路径 `schedule()` 是薄封装（`kernel/sched/core.c`）：

```c
asmlinkage __visible void __sched schedule(void)
{
	struct task_struct *tsk = current;

	sched_submit_task(tsk);            /* 离开运行态前的收尾：blk_flush_plug、
	                                      rcu_tasks_qs、SCHED_FLAG_BLOCK 报数 */
	do {
		preempt_disable();         /* __schedule 内部约定：禁止抢占调用 */
		__schedule(SM_NONE);
		sched_preempt_enable_no_resched();
	} while (need_resched());
	...
}
```

`__schedule()`（第 1 章已给出主体）的六个阶段，本节补齐关键语义：

### 4.1 sched_mode：SM_NONE / SM_PREEMPT / SM_IDLE / SM_RTLOCK_WAIT

```c
#define SM_NONE		0x00   /* 普通阻塞调度 */
#define SM_IDLE		0x01   /* idle 任务让位给刚唤醒者（pick 前不做 balance）*/
#define SM_RTLOCK_WAIT	0x02   /* rtmutex 等待路径（PREEMPT_RT 语义）*/
#define SM_MASK_PREEMPT	0x04   /* 抢占式调度的集合位 */
```

`SM_MASK_PREEMPT` 置位（preempt_schedule 路径）时，**不检查 prev->__state**（抢占不改状态，prev 仍在队列）；SM_NONE 时 prev 若非 RUNNING 则走 `deactivate_task(DEQUEUE_SLEEP)` 出队。

### 4.2 prev 出队与 D 状态记账

```c
	prev_state = READ_ONCE(prev->__state);
	if (!(sched_mode & SM_MASK_PREEMPT) && prev_state) {
		if (signal_pending_state(prev_state, prev))
			WRITE_ONCE(prev->__state, TASK_RUNNING);   /* 信号抢救 */
		else {
			prev->sched_contributes_to_load =
				(prev_state & TASK_UNINTERRUPTIBLE) &&
				!(prev_state & TASK_NOLOAD) &&
				!(prev_state & TASK_FROZEN);
			if (prev->sched_contributes_to_load)
				rq->nr_uninterruptible++;             /* loadavg 语义 */
			deactivate_task(rq, prev, DEQUEUE_SLEEP | DEQUEUE_NOCLOCK);
			if (prev->in_iowait) {
				atomic_inc(&rq->nr_iowait);            /* iostat 语义 */
				delayacct_blkio_start();
			}
		}
		switch_count = &prev->nvcsw;      /* 自愿切换计数 */
	}
```

> 📌 `TASK_KILLABLE`（D+可杀）不进 loadavg——`TASK_NOLOAD` 位决定它不计入 `nr_uninterruptible` 的 load 贡献，但计入 `nr_uninterruptible` 队列数。`/proc/loadavg` 前三列 = R 任务数 + 贡献 load 的 D 任务数的指数滑动平均（`calc_global_load`）。

### 4.3 pick_next_task：fast path 与 class 链

```c
static inline struct task_struct *
pick_next_task(struct rq *rq, struct task_struct *prev, struct rq_flags *rf)
{
	/* 快路径：prev 不高于 fair 且全队列都是 fair 任务 */
	if (likely(!sched_class_above(prev->sched_class, &fair_sched_class) &&
		   rq->nr_running == rq->cfs.h_nr_running)) {
		p = pick_next_task_fair(rq, prev, rf);
		if (unlikely(p == RETRY_TASK))
			goto restart;
		if (!p) {                       /* fair 空 → 直接 idle */
			put_prev_task(rq, prev);
			p = pick_next_task_idle(rq);
		}
		return p;
	}
restart:
	put_prev_task_balance(rq, prev, rf);   /* 先给 prev 类一次 balance 机会
	                                          （fair=newidle_balance）*/
	for_each_class(class) {                /* 从 stop 到 idle 依次问询 */
		p = class->pick_next_task(rq);
		if (p)
			return p;
	}
	BUG(); /* idle class 永远有兜底 */
}
```

**快路径的意义**：绝大多数机器的绝大多数时刻只跑 fair 任务（RT 任务存在时整条捷径失效）。`rq->nr_running == rq->cfs.h_nr_running` 一个比较就替代了 5 次类问询。`put_prev_task_balance` 是 6.6 的合并点：把 newidle balance 挂到 pick 路径，`fair_sched_class->balance = newidle_balance`。

### 4.4 prev == next 的快速出口

EEVDF 单任务独占核时 pick 结果就是 prev 自身：跳过 context_switch，直接 `rq->clock_update_flags` 收尾、解锁返回。这条静默路径是"为什么 perf 里没有 sched_switch 事件但 vruntime 在涨"的答案。

## 五、context_switch：地址空间、栈与寄存器

`__schedule` 的最后一步（`kernel/sched/core.c`，6.6）：

```c
static __always_inline struct rq *
context_switch(struct rq *rq, struct task_struct *prev,
	       struct task_struct *next, struct rq_flags *rf)
{
	prepare_task_switch(rq, prev, next);       /* fire_sched_in_preempt_notifiers 等 */
	arch_start_context_switch(prev);

	/* —— 地址空间四象限 ——
	 * kernel->kernel: lazy + transfer active
	 *   user->kernel: lazy + mmgrab_lazy_tlb() active
	 * kernel->  user: switch + mmdrop_lazy_tlb() active
	 *   user->  user: switch
	 */
	if (!next->mm) {                            /* 目标是内核线程 */
		enter_lazy_tlb(prev->active_mm, next);  /* ★lazy TLB：不改 CR3/TTBR0 */
		next->active_mm = prev->active_mm;      /* 借用 prev 的 mm 引用 */
		if (prev->mm)                           /* prev 是用户任务 */
			mmgrab_lazy_tlb(prev->active_mm);
		else
			prev->active_mm = NULL;
	} else {                                    /* 目标是用户任务 */
		membarrier_switch_mm(rq, prev->active_mm, next->mm);
		switch_mm_irqs_off(prev->active_mm, next->mm, next);  /* 真正换页表 */
		lru_gen_use_mm(next->mm);
		if (!prev->mm) {                        /* prev 是内核线程 */
			rq->prev_mm = prev->active_mm;      /* 延迟 mmdrop 到 finish */
			prev->active_mm = NULL;
		}
	}

	switch_mm_cid(rq, prev, next);              /* mm_cid：per-mm 的逻辑 CPU 号 */

	rq->clock_update_flags &= ~(RQCF_ACT_SKIP|RQCF_REQ_SKIP);
	prepare_lock_switch(rq, next, rf);

	/* —— 寄存器与栈的切换点（汇编，见下节）—— */
	switch_to(prev, next, prev);
	barrier();                                  /* 禁止编译器越过"我回来了" */

	return finish_task_switch(prev);            /* 运行在 next 的栈上！ */
}
```

### 5.1 lazy TLB：内核线程不换 CR3

内核线程 `mm == NULL`，只借用 `active_mm`。切换时不重载页表基址（x86 不写 CR3、arm64 不写 TTBR0），**省掉一次全量 TLB 冲刷**——这是上下文切换最贵的单项之一。借用是引用计数安全的：`mmgrab_lazy_tlb`（仅 mm_count，非 mm_users）+ `rq->prev_mm` 延迟释放。

`switch_mm_cid`：6.1 引入的 mm_cid 机制，给"同 mm 内并发执行"分配小整数逻辑 CPU 号，供 rseq/mCSN 用户态锁避免不必要的 cacheline 弹跳（per-cpu 数据的按 mm 视图）。

### 5.2 switch_to：架构相关的最后一跳

以 x86_64 `__switch_to_asm`（`arch/x86/entry/entry_64.S` + `arch/x86/kernel/process_64.c`）为例：

```
__switch_to_asm:                       （entry_64.S）
    push rbp/rbx/r12..r15              保存被调用者保存寄存器到 prev 内核栈
    movq %rsp, TASK_threadsp(%rdi)     prev->thread.sp = 当前栈顶
    movq TASK_threadsp(%rsi), %rsp     ★ 潮湿的一刻：rsp 指向 next 的栈
    pop rbp/rbx/r12..r15               恢复（next 上次被换出时压的）寄存器
    jmp __switch_to                    （C：DS/ES/fsbase/gsbase、FPU/XSAVE、
                                          MSR: sysenter/syscall、IO bitmap、TLS）
```

* **返回值幻觉**：`switch_to(prev, next, last)` 的宏魔术——调用者 A 换到 B，B 再换到 C，C 换回 A 时，A 的栈帧需要知道"谁把我换回来的"（`last`），否则 A 以为自己是 next。汇编层用三个参数的寄存器接力实现（经典的"i-cache 还是 d-cache 谁 dirty"面试题源）。
* **arm64 差异**：`cpu_switch_to`（`arch/arm64/kernel/entry.S`）同样保存 x19-x28/sp/pc/x0(作为 prev 返回)，页表在 `__switch_to_alternatives` 前已由 `switch_mm` 完成（TTBR0 + ASID：同 mm 复用 ASID 免刷 TLB）。
* **栈溢出探测**：`task_struct` 底部的 `STACK_END_MAGIC`（0x57AC6E9D）被踩即 `report_stack_overflow`；kernel thread 栈默认 16K（THREAD_SIZE），用户任务内核栈 16K（x86_64）/16K（arm64, 可配 2级）。

### 5.3 finish_task_switch：新任务的"开门七件事"

```c
static struct rq * finish_task_switch(struct task_struct *prev)
{
	...
	rq = finish_task_switch(prev) 主体：
	 - rq->clock 更新合法性检查、prev 的 sched_class->task_dead？(仅 exit 路径)
	 - __balance_callbacks(rq)        /* 延迟的负载均衡回调执行 */
	 - vtime_task_switch(prev)        /* 虚拟时间记账（NO_HZ_FULL）*/
	 - if (unlikely(prev_state == TASK_DEAD)) {
	       task_dead = prev; … p->thread.sp 越界检查；put_task_struct 延迟释放
	   }
	 - fire_sched_out_preempt_notifiers
	 - if (prev_mm) mmdrop_lazy_tlb()  /* 归还借用的 mm 引用 */
	 - finish_lock_switch: raw_spin_rq_unlock(rq)（rq 锁在这里才释放！）
	 - if (current->set_child_tid) …   /* CLONE_CHILD_SETTID 收尾 */
	 - calculate_sigpending()
}
```

两个关键点：**rq->lock 持有跨越了整个 context_switch**（换人完成前任何 CPU 都不能动这个队列）；**TASK_DEAD 的栈不能当场释放**（我们还站在它上面），延迟到 `put_task_struct → delayed_put_task_struct` RCU 回调。

## 六、抢占检查点地图（preempt_schedule 家族）

```
PREEMPT_DYNAMIC（static_call 可切换）:
  preempt_schedule()        用户态可抢占点：preempt_enable 后/softirq 完成后
  preempt_schedule_noirq()  硬中断退出点（irqexit 的 __irq_exit_rcu 路径）

固定路径：
  preempt_schedule_irq()    中断返回内核态（无条件编译于 PREEMPT）
  preempt_schedule_notrace  ftrace 自身的递归保护版
  irqentry_exit → exit_to_user_mode_loop（x86） / ret_to_user（arm64）
```

用户任务视角的完整抢占时间线（`TIF_NEED_RESCHED` 置位 → 真正换人）：

```
T0: resched_curr 置位 TIF_NEED_RESCHED（可能远端 IPI）
T1: 目标 CPU 到达下一个抢占检查点：
    a) 正在用户态 → 立即（IPI 返回路径即检查）
    b) 内核态 + CONFIG_PREEMPT → 下一个 preempt_enable / irq 返回
    c) 内核态 + !PREEMPT → 系统调用/中断返回用户态前
T2: __schedule(SM_PREEMPT) → pick → context_switch
```

`preempt_dynamic` 的运行时观察：

```
/sys/kernel/debug/sched/preempt   # none / voluntary / full（6.6 可读写）
dmesg | grep "Dynamic Preempt"    # 启动模式与编译默认
```

## 七、观测：从延迟毛刺到函数级归因

| 现象 | 工具 | 定位 |
| :--- | :--- | :--- |
| 唤醒后迟迟不上 CPU | `runqslower 100`（bcc） | 输出任务名/延迟，配合 `tracepoint:sched:sched_wakeup` |
| 毛刺到底是 IRQ、preempt-off 还是调度慢 | `perf record -e sched:sched_switch -e cycles` + `perf sched latency` | involuntary 切换密度 |
| 谁抢走了我 | `perf script` 里 sched_switch 事件的 prev/next 顺序 | 立刻跟随的 next 即抢占者 |
| 自愿 vs 强制切换 | `/proc/PID/status` 的 voluntary_ctxt_switches / nonvoluntary_ctxt_switches | involuntary 高 → 被抢占频繁 |
| schedule() 内部耗时 | `function_graph` tracer（`echo schedule > set_graph_function`） | 含 pick/balance/switch 的分段 |
| 抢占被延迟的长度 | `irqsoff`/`preemptoff`/`wakeup*` tracer | `preemptoff` 的最大值即最坏延迟上界 |

实用 tracepoint 组合（bpftrace 一行流）：

```
bpftrace -e 'tracepoint:sched:sched_wakeup /pid==TARGET/{@[pid]=nsecs}
tracepoint:sched:sched_switch /args->next_pid==TARGET/
{printf("lat %d us\n", (nsecs-@[args->next_pid])/1000); delete(@[args->next_pid])}'
```
