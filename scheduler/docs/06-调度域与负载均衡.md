# 调度域与负载均衡（Linux 6.6）

> 阅读目标：掌握 SMP 负载均衡的三层架构——拓扑层（sched_domain/sched_group 的构建与 flags）、决策层（`load_balance()` 的 group_type/migration_type 判定）、执行层（detach/attach 与 active migration）；理解 capacity 体系（频率/微架构不变性）、misfit、EAS 与 NUMA balancing 的协作。

---

## 一、为什么需要"域"：负载的层级世界观

盲目全局均衡是反模式：把任务从 L3 cache 的 LLC 内搬出去，省下的排队时间抵不上 cache 冷启动；跨 NUMA 搬运更贵。因此均衡被组织成**自底向上的域层级**，每个域内"搬运便宜"，域间"搬运贵但要更有理由"。

```
        ── NUMA level (multi-node)
        │   SD_NUMA: 均衡目标"有 spare 就行"（imbalance_pct 宽松）
        │   典型 flags: SD_BALANCE_EXEC|SD_WAKE_AFFINE|SD_OVERLAP…
        └── DIE level (socket / LLC 上界)
            │   flags: SD_BALANCE_NEWIDLE|SD_WAKE_AFFINE|SD_SHARE_PKG_RESOURCES…
            └── MC level (LLC，常含 SMT 兄弟)
                │   SD_SHARE_CPUCAPACITY（SMT）| SD_SHARE_PKG_RESOURCES
                └── CPU0 … CPUn   （rq 们，第 2 章）
```

域由启动时 `build_sched_domains()`（`kernel/sched/topology.c`）从**架构拓扑描述**构建：x86 用 CPUID/AMD 探测 + `CONFIG_SCHED_MC/SMT`；arm64 用 DT/ACPI 的 cache topology 与 cluster（`CONFIG_SCHED_CLUSTER`）；powerpc 有 `SD_ASYM_PACKING`（更强核优先编号语义）。每一层的 `sched_domain` 通过 parent/child 链接，同一层切成若干 `sched_group`（均衡的"搬运单位"）。

### 1.1 struct sched_domain 关键字段（include/linux/sched/topology.h，6.6）

```c
struct sched_domain {
	struct sched_domain __rcu *parent;   /* 上一层（顶层为 NULL）*/
	struct sched_domain __rcu *child;    /* 下一层 */
	struct sched_group *groups;          /* 本域的组环链（每组一批 CPU）*/
	unsigned long min_interval;          /* 均衡间隔下限（ms）*/
	unsigned long max_interval;          /* 均衡间隔上限（busy 时放大）*/
	unsigned int busy_factor;            /* 本域忙 → 降低均衡频率 */
	unsigned int imbalance_pct;          /* 不均衡水位线（%）*/
	unsigned int cache_nice_tries;       /* cache-hot 任务容忍次数 */
	unsigned int imb_numa_nr;            /* NUMA 容许的不均衡任务数 */

	int nohz_idle;
	int flags;                           /* SD_* 位集 */
	int level;

	unsigned long last_balance;          /* 上次均衡时刻（jiffies）*/
	unsigned int balance_interval;       /* 下次均衡距现在（ms，动态）*/
	unsigned int nr_balance_failed;      /* 连续失败 → 放弃该域一段时间 */

	u64 max_newidle_lb_cost;             /* newidle 均衡成本上限（动态衰减）*/
	u64 avg_scan_cost;                   /* select_idle_sibling 扫描成本 */

	unsigned int lb_count[CPU_MAX_IDLE_TYPES];   /* 以下为 schedstats 统计 */
	unsigned int lb_failed[CPU_MAX_IDLE_TYPES];
	...
};
```

### 1.2 常用 SD flags 速查

| flag | 含义 | 谁用 |
| :--- | :--- | :--- |
| `SD_BALANCE_NEWIDLE` | 本域做 newidle 均衡 | CPU 快空时拉任务 |
| `SD_BALANCE_EXEC/FORK` | exec/fork 后可跨本域放置 | wake_affine 决策 |
| `SD_WAKE_AFFINE` | 唤醒倾向留在唤醒者附近 | select_idle_sibling |
| `SD_SHARE_PKG_RESOURCES` | 组内共享 LLC/内存带宽 | 均衡按 pkg 利用率 |
| `SD_SHARE_CPUCAPACITY` | SMT 兄弟 | 6.6 的 `group_smt_balance`；misfit 记 capacity |
| `SD_ASYM_PACKING` | 低编号 CPU 优先（powerpc/部分 arm64） | `group_asym_packing` |
| `SD_PREFER_SIBLING` | 让下层域留空（把任务推向更"外"的核） | 大小核：小核域设此 flag，负载溢出到大核 |
| `SD_OVERLAP` | 域重叠（NUMA：一个 CPU 出现在多个同层域） | overlapping groups 构建 |
| `SD_NUMA` | NUMA 域 | 均衡门限放宽 + NUMA balancing |

## 二、capacity：均衡的第四个维度

裸 nr_running 均衡在异构机器上是错的：4 个满载任务放小核（cap 512）与放 LLC 兄弟大核（cap 1024）不同。capacity 体系（`arch_scale_cpu_capacity`，`topology.h`）：

* **capacity_orig**：微架构标称算力（DT `capacity-dmips-mhz` 或 ACPI，最大核归一到 1024）。
* **capacity_of(cpu)**：再乘**当前频率**（freq-invariant，`arch_scale_freq_capacity`：TSC/AMU/计数器折算）与**热压力**（`thermal_pressure`，6.6 用 hw_pressure）——即"此刻真实可用算力"。
* **util 与 capacity 同刻度**（都归一到 1024），直接可比：`cpu_overutilized := util > capacity*~90%`（`capacity_margin`，EAS 的开关阈值：一旦 overutilized，唤醒退回纯负载模式）。

**misfit 任务**：任务的 util > 所在 CPU capacity（例如 RT 线程太多把大核占了，fair 大任务挤在小核）。rq 记 `rq->misfit_task_load`，域判定出 `group_misfit_task`，均衡以 `migrate_misfit` 类型把任务推向更大的核。

## 三、均衡的三种触发与总入口

```
scheduler_tick(rq)                       (kernel/sched/core.c)
  └─ trigger_load_balance(rq)            (kernel/sched/fair.c, 6.6)
       ├─ 若 tick_stopped（NOHZ idle CPU？）→ nohz_idle_balance(this_rq, cpu)
       │    帮 idle 邻居们衰减负载/拉任务（_nohz_idle_balance 逐 CPU）
       └─ 若 jiffies > rq->next_balance:
            for_each_domain(cpu, sd):  /* 自底向上 */
               if (time_after_eq(jiffies, sd->last_balance + sd->balance_interval))
                    load_balance(cpu, rq, sd, CPU_NEWLY_IDLE?…)
                    break;             /* 一次 tick 只爬一层 */

CPU 即将空闲（第 4 章 pick 路径）
  └─ put_prev_task_balance → fair_sched_class->balance = newidle_balance()
       └─ load_balance(..., CPU_NEWLY_IDLE)   /* 最频繁也最廉价的均衡 */

唤醒放置不理想（select_task_rq_fair 无处可去）
  └─ 由后续均衡纠正（负载是慢变量，唤醒是快路径）
```

`balance_interval` 动态调整：均衡成功且失衡小 → 区间向 `max_interval`（受 `max_load_balance_interval = HZ/10` 封顶）靠；`nr_balance_failed` 累积 → 缩短重试甚至跳过该域（缓存弹跳自我保护）。

## 四、load_balance()：决策与执行（fair.c，6.6）

```
load_balance(this_cpu, this_rq, sd, idle, &continue_balancing)
 ├─ 1) 组扫描: update_sd_lb_stats()
 │      对 sd->groups 环链里每个 sched_group 调 update_sg_lb_stats()
 │      聚合每 CPU 的 nr_running/load_avg/util_avg/runnable_avg/capacity/misfit
 │      → local_group 与 busiest_group 的画像
 ├─ 2) 判定: find_busiest_group()
 │      compute_asym/imbalance → 若不值得动 → goto out_balanced
 │      产出: env->group_type（见 4.1）+ env->imbalance（要搬多少）+ env->migration_type
 ├─ 3) 找队列: find_busiest_queue()
 │      在 busiest_group 里按 migration_type 挑源 CPU：
 │        migrate_load → nr_running 最多 / load 最大
 │        migrate_util → util 与 spare 的差
 │        migrate_task → 直接指定（如 group_misfit/asym 的目标）
 ├─ 4) 搬运: detach_tasks() → __migrate_task 侧本地摘除（拿双 rq 锁）
 │      逐任务 can_migrate_task() 检查，直到搬够 imbalance 或循环上限
 │      （env->loop_max = min(sysctl_sched_nr_migrate, busiest->nr_running)）
 ├─ 5) attach_tasks() → 目标侧入队 + check_preempt_curr
 └─ 6) 统计/失败路径：连续失败 → active migration 挂起（见第五节）
```

### 4.1 group_type：7 种局势（6.6，`enum group_type`）

```
group_has_spare    (0)  本地组还有空闲算力——拉人填充（migrate_load/util）
group_fully_busy        刚好满——无事可做，除非别的类型
group_misfit_task       有任务装不下当前 CPU——migrate_misfit
group_smt_balance       ★6.6 新：SMT 组满载，把 SMT 兄弟忙的任务挪到空核
                          （SD_SHARE_CPUCAPACITY 下的细分策略）
group_asym_packing      SD_ASYM_PACKING：更优先的 CPU 空——migrate_task
group_imbalanced        亲和掩码/管理约束造成的"结构性失衡"（标记状态防反复尝试）
group_overloaded        超 1 任务/CPU 级别的过载——migrate_load
```

### 4.2 migration_type：四类搬运目的（6.6，`enum migration_type`）

```
migrate_load    搬 load_avg（经典均衡：让两边 load 对齐）
migrate_util    搬 util_avg（capacity-aware：把算力需求移到有 spare 的核）
migrate_task    搬任务本身（misfit/asym：不管负载多少，这个任务必须走）
migrate_misfit  同上（6.6 与 migrate_task 并存的细分）
```

> 6.6 的这套枚举是 5.13 重构的产物：以前的 `env->idle` 单变量混合表达了太多含义。现在的组合（group_type × migration_type）使 NUMA/大小核/SMT 的决策可组合、可测试。

### 4.3 can_migrate_task：六道关卡

```
1. cpumask 允许？              task_cpu_allowed(p, env->dst_cpu)
2. 正在运行且非 active 迁移？    跳过（任务在 src 上跑着，拿不下来）
3. cache hot？                 task_hot()：delta_exec > sysctl_sched_migration_cost
                                 (默认 500000ns=0.5ms) 且组内无 SD_SHARE_CPUCAPACITY；
                                 CACHE_HOT_BUDDY 特性下的 next 实体也视为热
4. per-CPU 内核线程？           kthread_is_per_cpu → 拒绝
5. 组亲和/隔离（cgroup cpuset）？ env->sd->flags 无 SD_WAKE_AFFINE 时的约束
6. 连续失败计数                 迁移失败时 sd->nr_balance_failed++ → 触发 active
```

**`sysctl_sched_migration_cost`（`/proc/sys/kernel/sched_migration_cost_ns`，默认 500000）**是均衡激进度最著名旋钮：调小 → 更愿意搬运（交互任务响应快，但 cache 命中率掉）；调 0 = 永不视为热；调 -1 = 永远视为热（事实上关闭均衡搬运）。**`sched_nr_migrate`（默认 32）**限制单次搬运上限——fork 风暴的自我保护。

## 五、active migration：唯一"硬抢"手段

常规均衡只能搬**在队列里等待**的任务；"最该搬走的那个任务正在 CPU 上跑"是常态（例如组 throttle 或 misfit 场景：小核上唯一的任务 util 超容量，它自己不睡，均衡永远搬不动它）。

```
load_balance 判定需要 active（env->migration_type 为 misfit 等）
  └─ stop_one_cpu_nowait(src_cpu, active_load_balance_cpu_stop, ...)
       └─ active_load_balance_cpu_stop()  /* 以 stop 任务身份执行（第 2 章第 8 节）*/
            ├─ 再确认 src/dst 状态
            ├─ detach + __migrate_task → dst 入队
            └─ resched_curr(dst_rq) / resched_curr(src_rq)
```

migration/N 内核线程的"最高调度类"在此兑现价值：它在 src CPU 上**必然**立刻运行，把正在跑的任务从 CPU 上请下来。代价是两次 IPI + stop 开销，所以仅在常规路径失败后作为兜底。

## 六、newidle balance：CPU 空闲前最后一捞

`newidle_balance()`（fair.c，6.6 摘要）在 pick 路径被调用（CPU 即将进 idle）：

```
newidle_balance(this_rq, rf)
 ├─ 若 this_cpu 有待处理 ttwu/在均衡中 → 快速放弃（避免干扰唤醒路径）
 ├─ cost 预算：sd->max_newidle_lb_cost（按历史成本指数衰减维护）
 │    若 this_rq->avg_idle < sysctl_sched_migration_cost → 放弃
 │    （预测 CPU 很快又有活，捞任务不划算——服务器高负载时省下大量锁操作）
 ├─ for_each_domain: load_balance(..., CPU_NEWLY_IDLE)
 │    newidle 语义：更激进（imbalance 水位降低），但受 cost 约束
 └─ 返回 moved；CPU 若仍空 → 进 idle（do_idle）
```

`rq->avg_idle` 是"该 CPU 平均每次空闲时长"的滑动估计——newidle 均衡的全部智慧就是**只在值得时才花钱**。`/proc/sys/kernel/sched_migration_cost` 同样闸这条路径。

## 七、NUMA balancing：把内存搬到任务旁边

远端访存代价由硬件决定，调度器唯一能做的是让任务的执行核与数据所在 node 逐渐对齐（`CONFIG_NUMA_BALANCING`）：

```
1) 采样：任务用户态执行期间周期触发 NUMA hinting page fault
     （PTE/PMD 置 _PAGE_PROTNONE，访问 → fault → handle_pte_fault
       → numa_migrate_prep 记录页的 node 访问统计）
   p->numa_faults[2*nr_nodes_id] : 私有/共享 × node 的 fault 计数矩阵
2) 统计：task_numa_placement()
     用 EMA 平滑（ faults_sum/16 的近似权重衰减）算出 task 的"理想 node"
     与 numa_group（进程组的聚合画像：并行线程数，同组不互拆）
3) 放置：select_task_rq_fair → find_idlest_cpu 的 numa aware 评分
     （task_numa_find_cpu：preferred node 有空位则去）
4) 惯性限流：numa_migrate_ratelimit（默认 8ms? 具体见 sysctl）防 fault 风暴
   imb_numa_nr（sd 字段）：允许 node 间"任务数不齐"的容差
     —— 重任务的理想 node 挤满时，不必强搬到差 node
```

管理接口：`/proc/sys/kernel/numa_balancing`（总开关，MIS 平台常用 0 关闭）、`numa_balancing_scan_period_*/…`。观测：`/proc/PID/numa_maps`（每 VMA 的 node 分布）、`numastat`、`/sys/kernel/debug/sched/debug` 的 `nr_numa_running/nr_preferred_running`。

> ⚠️ 判断该不该开：单 node 机器无意义；DB/JVM 类长驻大内存进程受益明显；**容器场景要小心**——cgroup cpuset 把任务钉在 node 子集时，hinting fault 仍按全 node 空间采样，可能反复"想搬搬不动"，浪费 fault 开销。

## 八、EAS：能效感知的任务放置

EAS（Energy Aware Scheduling，5.0+）改变**唤醒放置**而非周期均衡（均衡与能效天然冲突，EAS 系统上周期均衡基本让位）：

```
select_task_rq_fair
  └─ if (fair_server? no—) sched_energy_ready()      /* Energy Model 可用：
        EAS 只在 CPU 数 ≤ EAS_MAX_NUM_CPUS（默认 64，避免决策 O(大)）
        且 root_domain 未 overutilized 时启用 */
       find_energy_efficient_cpu(p, prev_cpu)
         ├─ compute_energy(target_cpu)   用 Energy Model（DT/ESI 供给的
         │     per-performance-state 功耗表）估算"把 p 放这儿"的系统总功耗
         │     （候选 = p 的 affinity ∩ 各 sched_domain 的 spare candidates）
         └─ 选功耗增量最小者；平手选 prev_cpu（cache）
     else 退回负载模式（wake affine + select_idle_sibling）
```

关键联动：**`overutilized` 是 EAS 的总开关**（第 5 章：单核 util 超 ~90% capacity 即全局翻转）。设计哲学：能效优化只在"有余量"时做，系统一忙就切换到纯性能导向，避免优化本身成为瓶颈。大小核手机是 EAS 的主场；服务器（同构 + 高压）上 EAS 通常不启用（无 EM 或 CPU 数超标）。

## 九、观测与调优

```
/sys/kernel/debug/sched/domains/cpuN/domain{0,1,..}/
    flags  groups  busy_factor  imbalance_pct  …
    /stats/{lb_count,lb_failed,lb_gained,…}[_newidle]   均衡成败账本
    /flags     运行时改 SD flags（实验用）
/proc/sys/kernel/
    sched_migration_cost_ns   （cache hot 阈值）
    sched_nr_migrate          （单次搬运上限）
    numa_balancing_scan_*     （NUMA 采样）
    sched_energy_aware        （6.6 顶层 EAS 开关！可运行时关）
tracepoint:
    sched:sched_load_balance / sched:sched_migrate_task  （搬运事件流）
    sched:sched_load_avg_cpu                           （util 变化，第 5 章）
perf sched record / bpftrace runqlat                   （均衡效果的最终指标）
```

均衡问题的标准排查顺序：

```
1. runqlat 直方图：跨节点/跨核的尾延迟是否分层？
2. sched_migrate_task 频率：搬运风暴 or 搬不动（lb_failed 高）？
3. lb_failed 高 → 看 imbalance_pct / 亲和掩码（group_imbalanced 的结构性原因）
4. 搬运风暴 → sched_migration_cost_ns 调大、检查 cpuset/topology 是否异常
5. NUMA → numastat 的远端比例 + numa_balancing 状态
```

## 十、思考题

1. 为什么周期均衡一次 tick 只爬一层 domain？如果一次爬到顶层（NUMA）会出什么事？提示：搬运成本与失衡频率的乘积。
2. `group_smt_balance`（6.6 新增）与 SMT 的 capacity 折半：两个线程挤一个物理核 vs 拆到两个物理核，调度器的收益模型是什么？为什么 `task_hot()` 对 `SD_SHARE_CPUCAPACITY` 域直接返回 0？
3. `rq->avg_idle` 低于 `sched_migration_cost` 时放弃 newidle 均衡。高负载服务器该值趋近 0，意味着 newidle 均衡基本关闭——这是 bug 还是 feature？谁在兜底（提示：唤醒放置 + periodic）？
4. EAS 的 `overutilized` 一旦翻转，系统行为会发生哪三处可观测变化？（提示：唤醒路径、均衡频率、schedutil 的 margin。）
5. 你的容器平台把离线任务用 cpuset 钉在 node1 的 8 个核上，但 `/sys/.../stats/lb_failed_node` 持续增长。给出至少两种结构性解释与验证方法。
