# 调度器核心数据结构（Linux 6.6）

> 阅读目标：掌握 6.6 调度器的六大核心结构 `task_struct`（调度相关字段）、`sched_entity`、`rq`、`cfs_rq`/`rt_rq`/`dl_rq`、`root_domain` 及其组织关系；理解每个字段"为什么存在"，以及 SMP/cache-line 级别的布局考量。

本章所有结构体均摘自 Linux 6.6 源码（`include/linux/sched.h`、`kernel/sched/sched.h`），可对照 <https://elixir.bootlin.com/linux/v6.6/source/kernel/sched/sched.h> 阅读。

## 一、数据结构全景图

```
                         struct root_domain (每 partition/machine 一个)
                        ┌──────────────────────────────────────────┐
                        │ span/online, overload, overutilized,     │
                        │ rto_mask(RT), dlo_mask(DL), cpupri,      │
                        │ cpudl, dl_bw(准入), max_cpu_capacity     │
                        └───────────────┬──────────────────────────┘
                                        │ 每个 CPU 的 rq 都指向所属 root_domain
  per-CPU: DEFINE_PER_CPU(struct rq, runqueues) ──► cpu_rq(cpu) / this_rq()
                        ┌───────────────┴──────────────────────────┐
                        │              struct rq                   │
                        │ ┌────────────┐ ┌────────────┐ ┌────────┐ │
                        │ │ cfs: cfs_rq│ │ rt: rt_rq  │ │dl:dl_rq│ │
                        │ │ (EEVDF树)  │ │ (位图+队列)│ │(EDF树) │ │
                        │ └────────────┘ └────────────┘ └────────┘ │
                        │ curr / idle / stop / nr_running / clock* │
                        │ nr_uninterruptible / next_balance        │
                        └───┬───────────────────────────────────────┘
                            │ sched_class 链: stop → dl → rt → fair → idle
        ┌───────────────────┼───────────────────────────────────────┐
        │                   │                                        │
 struct task_struct    struct sched_entity                      struct task_group
 ┌────────────────┐    ┌─────────────────────┐   FAIR_GROUP_SCHED ┌──────────────┐
 │ prio/static/   │    │ load / vruntime /   │◄──────────────────►│ cfs_rq[] 每CPU│
 │ normal_prio    │    │ deadline/vlag/slice │     组也是实体      │ sched_entities│
 │ rt_priority    │    │ run_node(rb_node)   │                    │ shares→weight│
 │ policy         │    │ avg(PELT)           │                    └──────────────┘
 │ se / rt / dl   │    └─────────────────────┘
 │ sched_class    │    sched_dl_entity: runtime/deadline/dl_timer/…
 │ on_rq / on_cpu │    sched_rt_entity:  run_list/time_slice/…
 │ cpus_mask...   │
 └────────────────┘
```

三句话总结：

1. **每个 CPU 一个 `struct rq`**，内嵌三个子队列（cfs/rt/dl），`rq->curr` 指向当前任务。
2. **每个任务三种身份**：`p->se`（fair 实体）、`p->rt`（rt 实体）、`p->dl`（deadline 实体），同一时刻只有 `p->sched_class` 指向的那份生效。
3. **组调度把 `cfs_rq` 变成一棵树**：task 的 se 挂在组的 cfs_rq 上，组的 se（sched_entities[i]）挂在 CPU 的 cfs_rq 上，逐层上传。

## 二、task_struct 的调度相关字段

摘自 `include/linux/sched.h`（6.6，节选）：

```c
struct task_struct {
	...
#ifdef CONFIG_SMP
	int				recent_used_cpu;  /* 唤醒时的候选 cache-hot CPU */
	int				wake_cpu;         /* fork 时父任务建议的初始 CPU */
#endif
	int				on_rq;            /* 0 / TASK_ON_RQ_QUEUED / TASK_ON_RQ_MIGRATING */

	int				prio;             /* 动态生效优先级（越小越优先）*/
	int				static_prio;      /* 静态优先级（CFS: 120+nice）*/
	int				normal_prio;      /* 无 PI 提权时的"常规"prio */
	unsigned int			rt_priority;     /* 用户态 RT 优先级 1~99（越大越优先）*/

	struct sched_entity		se;               /* fair 实体（见下节） */
	struct sched_rt_entity		rt;               /* RT 实体（FIFO/RR） */
	struct sched_dl_entity		dl;               /* DEADLINE 实体（EDF+CBS） */
	const struct sched_class	*sched_class;     /* 当前生效的调度类指针 */
	...
};
```

### 2.1 四个"优先级"字段的分工

这是初学者最容易混乱的地方，用一张生命周期表讲清楚：

| 字段 | 谁写 | 什么时候变 | 例子（SCHED_FIFO prio=10 任务被 PI 提权到 5） |
| :--- | :--- | :--- | :--- |
| `static_prio` | `sched_setscheduler`/`nice` | 用户改 | RT 任务为 `MAX_RT_PRIO-1-rt_priority`；CFS 为 `120+nice` |
| `normal_prio` | `__setscheduler_prio()` | policy/prio 变化、`switched_to` | = static_prio（RT/DL）或 120+nice |
| `rt_priority` | 用户态设置 | 仅 RT policy | 10（用户语义） |
| `prio` | `rt_mutex_setprio()` / `__setscheduler_prio()` | **PI 提权/恢复时** | 持有低优先级任务所需的锁时被临时提到 5（`prio < normal_prio` 即处于 PI boosted 状态） |

> 📌 **PI（Priority Inheritance）**：高优先级任务阻塞在低优先级任务持有的 `rt_mutex`/`futex` 上时，内核临时抬升持有者的 `prio`，防止优先级反转。DL 任务有专门的 `pi_se`（deadline 语义的继承，见 `struct sched_dl_entity`）。这是 `prio` 与 `normal_prio` 分离的唯一原因。

### 2.2 `on_rq` 的三态（SMP 唤醒路径的核心同步量）

```c
#define TASK_ON_RQ_QUEUED      1   /* 在某个 rq 上排队（TASK_RUNNING）*/
#define TASK_ON_RQ_MIGRATING   2   /* 正在 CPU 间迁移（短暂：锁保护下摘下再挂上）*/
```

`try_to_wake_up()` 与 `__schedule()` 之间用它做控制依赖级别的同步（见第 4 章）——`p->on_rq` 与 `p->__state` 的组合编码了任务的完整去向。

## 三、struct sched_entity：EEVDF 的载体（6.6 重点）

6.6 用 EEVDF 替换 CFS 后，`sched_entity` 的字段发生了结构性变化。6.6 真实定义：

```c
struct sched_entity {
	/* For load-balancing: */
	struct load_weight		load;          /* 权重（nice → 1024*1.25^Δnice）*/
	struct rb_node			run_node;      /* 红黑树节点 */
	u64				deadline;      /* ★EEVDF: 虚拟截止期 vd_i */
	u64				min_deadline;  /* ★EEVDF: 增广字段——子树最小 deadline */

	struct list_head		group_node;    /* 组调度：挂到 task_group 的链表 */
	unsigned int			on_rq;

	u64				exec_start;        /* 本轮 slice 开始执行的时刻 */
	u64				sum_exec_runtime;  /* 累计物理执行时间（ns，全程单调）*/
	u64				prev_sum_exec_runtime; /* 上次被 pick 时点的累计值 */
	u64				vruntime;          /* 虚拟运行时间（公平性的记账）*/
	s64				vlag;              /* ★EEVDF: 出队时保存的 lag */
	u64				slice;             /* ★EEVDF: 当前请求长度 r_i（ns）*/

	u64				nr_migrations;     /* 被负载均衡迁移的次数 */

#ifdef CONFIG_FAIR_GROUP_SCHED
	int				depth;          /* 在组层级中的深度 */
	struct sched_entity		*parent;
	struct cfs_rq			*cfs_rq;        /* 本实体所挂的（父）队列 */
	struct cfs_rq			*my_q;          /* 本实体拥有的（子）队列，task 为 NULL */
	unsigned long			runnable_weight; /* 缓存 my_q 的 h_nr_running 权重 */
#endif

#ifdef CONFIG_SMP
	struct sched_avg		avg ____cacheline_aligned;  /* PELT（第5章）*/
#endif
};
```

### 3.1 对比 6.5：EEVDF 改了什么

| 字段 | 6.5 (CFS) | 6.6 (EEVDF) | 说明 |
| :--- | :--- | :--- | :--- |
| `deadline` | ✗ | ✓ | 虚拟截止期，`vd_i = v_i + r_i/w_i`，取代了 leftmost-vruntime 选法 |
| `min_deadline` | ✗ | ✓ | 红黑树增广（augmented）字段：以该节点为根的子树内最小 deadline，使"最早截止期的 eligible 实体"查询 O(log n) |
| `vlag` | ✗ | ✓ | **双重复用**：出队（睡眠）时保存 lag 供唤醒补偿；被 pick 时暂存当时的 deadline（`set_next_entity` 的 HACK，供 `RUN_TO_PARITY` 判定"当前请求未耗尽"） |
| `slice` | ✗ | ✓ | 当前请求长度；6.6 统一为 `sysctl_sched_base_slice`（750000ns） |
| `vruntime` | ✓ | ✓ | 语义不变，但不再是唯一排序键 |
| `exec_start/sum_exec_runtime/prev_sum_exec_runtime` | ✓ | ✓ | 物理时间记账，供 schedstat/组配额使用 |

> ⚠️ 6.6 同时**删除**了 `sysctl_sched_latency`、`sched_min_granularity`、`wakeup_granularity` 等所有 CFS 调参——`/proc/sys/kernel/` 里它们不复存在。迁移老调优脚本时这是头号兼容性问题。

### 3.2 关键不变量（维护者视角）

* `se->vruntime` 单调不减；`cfs_rq->min_vruntime` 单调不减且 ≥ 所有 on_rq 实体的 vruntime（由 `update_min_vruntime()` 维护，同时钳制 avg_vruntime 不倒退）。
* `se->deadline = se->vruntime + calc_delta_fair(se->slice, se)`——deadline 是**虚拟时间**刻度，因此不同权重的任务可比较。
* `entity_key(cfs_rq, se) := (s64)(se->vruntime - cfs_rq->min_vruntime)`：红黑树排序与 avg_vruntime 计算共用此 key，防止 64 位回绕（用带符号差而非绝对值）。

## 四、struct rq：per-CPU 运行队列

`kernel/sched/sched.h`（6.6，节选并注释）：

```c
struct rq {
	raw_spinlock_t		__lock;            /* rq 锁：本队列的权威锁（rq_lock_irqsave 等包装）*/

	/* —— 远端 CPU 读得最多的两个量放同一 cache line —— */
	unsigned int		nr_running;        /* 所有类的 on_rq 任务总数（近似值）*/
#ifdef CONFIG_NUMA_BALANCING
	unsigned int		nr_numa_running;    /* 有 numa hint 的运行任务数 */
	unsigned int		nr_preferred_running;
	unsigned int		numa_migrate_on;
#endif
#ifdef CONFIG_NO_HZ_COMMON
	unsigned long		last_blocked_load_update_tick; /* NOHZ: 上次刷新阻塞负载的 tick */
	unsigned int		has_blocked_load;              /* 还有未衰减的阻塞负载？*/
	call_single_data_t	nohz_csd;                      /* NOHZ 负载同步 IPI 的 CSD */
	unsigned int		nohz_tick_stopped;
	atomic_t		nohz_flags;
#endif
	unsigned int		ttwu_pending;      /* 目标 CPU 上有待处理的 ttwu 队列 */
	u64			nr_switches;       /* 上下文切换计数 */

	struct cfs_rq		cfs;                /* ★ fair 队列（内嵌） */
	struct rt_rq		rt;                 /* ★ RT 队列 */
	struct dl_rq		dl;                 /* ★ DEADLINE 队列 */

	unsigned int		nr_uninterruptible; /* 本队列上 D 状态任务数（全局求和才有意义）*/

	struct task_struct __rcu *curr;        /* 当前任务 */
	struct task_struct	*idle;              /* 本 CPU 的 idle 任务 */
	struct task_struct	*stop;              /* 本 CPU 的 stop 任务（migration/N）*/

	unsigned long		next_balance;        /* 下次 periodic balance 的 jiffies */
	struct mm_struct	*prev_mm;            /* switch_mm 旧值（lazy TLB 用）*/

	u64			clock;               /* rq 时钟（update_rq_clock 维护）*/
	u64			clock_task ____cacheline_aligned; /* 扣除 IRQ 时间的任务时钟（PELT 用）*/
	u64			clock_pelt;          /* 频率不变 + 不含 idle 的"虚拟"时钟 */
	...
	atomic_t		nr_iowait;           /* 队列上 D 且 iowait 的任务数（/proc/loadavg 的第二字段）*/
	...
	struct root_domain	*rd;                 /* 所属 root_domain */
	struct sched_domain __rcu *sd;          /* 最底层的调度域（第6章）*/
	...
	struct balance_callback	*balance_callback;  /* 负载均衡延迟回调链 */
};
```

### 4.1 rq 时钟三兄弟：clock / clock_task / clock_pelt

| 时钟 | 内容 | 用途 |
| :--- | :--- | :--- |
| `rq->clock` | 单调递增的墙上时间（近似） | 日志、统计、`cpu_clock()` |
| `rq->clock_task` | 扣除本 CPU **硬中断时间** | `update_curr()` 的 delta_exec 基准：任务不该为 IRQ 买单 |
| `rq->clock_pelt` | 在 clock_task 基础上**再扣除 idle**，并按当前频率缩放 | PELT 的衰减基准：CPU 降频或空闲时，负载的"主观时间"变慢，避免 cpufreq 正反馈 |

三者都由 `update_rq_clock()` 推进（带 `RQCF_UPDATED` 防重复更新检查，`clock_update_flags` 的 `<<= 1` 提升机制是 PREEMPT_RT 的 REQ→ACT 协议）。**`rq->clock` 的推进点不连续**是内核时间审计（`sched_clock` 精度）与调度公平性的重要折衷——每进一次 `rq->lock` 临界区才更新一次。

### 4.2 `nr_running` 与 `h_nr_running` 的区别

* `rq->nr_running`：本 CPU 全部调度类队列的任务总数（近似——远程读不持锁）。
* `cfs_rq->h_nr_running`：**层级（hierarchical）计数**——子队列（组）每次入队/出队都会沿 `for_each_sched_entity(se)` 向父链传播。EEVDF/负载均衡大量依赖它判断"这棵子树里有几个任务"。
* `idle_h_nr_running`：单独统计 SCHED_IDLE 的层级计数，用于其特殊公平语义（强 lag 惩罚）。

### 4.3 rq 的锁序与远程访问

`rq->lock` 是调度器最热的锁。核心规则（`kernel/sched/sched.h`）：

```
两把 rq 锁：双 CPU 手拉手（double_rq_lock）必须按地址升序拿；
rq->lock → &p->pi_lock 的顺序：先拿 pi_lock 再拿 rq（try_to_wake_up 路径）；
任何"看别的 CPU 的 rq"的操作要么持双锁，要么接受数据是近似值。
```

`ttwu_queue`（`TTWU_QUEUE` 特性默认开启）把远端唤醒变成"投递到目标 CPU 的本地处理"（利用 `ttwu_pending` + `resched_curr` IPI），正是为了减少跨核 rq->lock 抖动。

## 五、struct cfs_rq：EEVDF 队列（6.6）

```c
struct cfs_rq {
	struct load_weight	load;             /* 队列总权重 */
	unsigned int		nr_running;       /* 直挂（含组实体）实体数 */
	unsigned int		h_nr_running;     /* 层级任务计数（向上传播）*/
	unsigned int		idle_nr_running;   /* SCHED_IDLE 实体计数 */
	unsigned int		idle_h_nr_running;

	s64			avg_vruntime;     /* ★EEVDF: \Sum (v_i - v0)*w_i 的有符号缓存 */
	u64			avg_load;         /* ★EEVDF: \Sum w_i 的缓存 */

	u64			exec_clock;
	u64			min_vruntime;     /* 单调虚拟时间基准（entity_key 的零点）*/

	struct rb_root_cached	tasks_timeline;  /* 增广红黑树：键=entity_key(vruntime)，
	                                              增广=min_deadline */

	struct sched_entity	*curr;            /* 正在运行的实体（不在树里）*/
	struct sched_entity	*next;            /* NEXT_BUDDY 特性的缓存候选（6.6 基本弃用）*/
	...
#ifdef CONFIG_SMP
	struct sched_avg	avg;              /* 队列级 PELT */
	struct {                                /* 迁移时先摘下的负载（removed）*/
		raw_spinlock_t	lock;
		int		nr;
		unsigned long	load_avg;
		unsigned long	util_avg;
		unsigned long	runnable_avg;
	} removed;
#endif
#ifdef CONFIG_FAIR_GROUP_SCHED
	struct rq		*rq;              /* 宿主 CPU 的 rq */
	int			on_list;
	struct list_head	leaf_cfs_rq_list;  /* 挂到 rq 的叶子链表（均衡遍历用）*/
	struct task_group	*tg;              /* 拥有者 */
	int			idle;               /* 组的 idle 状态缓存 */
#endif
#ifdef CONFIG_CFS_BANDWIDTH
	int			runtime_enabled;
	s64			runtime_remaining;  /* 本 period 剩余配额 */
	u64			throttled_clock;
	int			throttled;          /* 组被掐停（cfs_rq 整体出队）*/
	struct list_head	throttled_list;
	...
#endif
};
```

### 5.1 `avg_vruntime`/`avg_load`：EEVDF 的算术基石

6.6 的 `entity_eligible()` 需要加权和 `V = (\Sum w_i*v_i)/W`。若每次现算，n 个任务 O(n)。因此 cfs_rq 缓存**未除权的分子分母**：

```
avg_vruntime ≈ \Sum (v_i - v0) * w_i     （v0 = min_vruntime，做差防回绕）
avg_load     = \Sum w_i
入队: avg_vruntime_add() → 两者同步加
出队: avg_vruntime_sub() → 两者同步减
curr 不在树上 → entity_eligible() 里临时补上 curr 的贡献
```

这套增量维护是第 3 章 `entity_eligible()` 分析的前提。`removed` 结构的存在则是因为：任务迁移到新 CPU 时，旧 CPU 的 PELT 贡献不能瞬间消失（否则负载"凭空蒸发"），先挂入 `removed` 链表，在下一次 `update_load_avg()` 时记账性扣除。

### 5.2 组调度（FAIR_GROUP_SCHED）下的树

```
rq->cfs (CPU 级, tg=NULL)
 ├── se(tgA@CPU0) ──► tgA->cfs_rq[0] (组队列)
 │     ├── se(tgA1) ──► tgA1->cfs_rq[0]
 │     │      └── task x, y, z …
 │     └── task a, b …
 └── se(tgB) … / task t …
```

* 组的 `se->load.weight` 由 `tg->shares`（v2 `cpu.weight`）在 `update_cfs_group()` 里按子队列 h_nr_running 动态换算。
* 一次任务的 enqueue 最多改 O(层级) 个 `cfs_rq`，每个都要过 `enqueue_entity()`（update_curr、PELT、throttle 检查）——组层级越深，唤醒路径越贵（这是容器嵌套深时调度开销上升的直接原因）。

## 六、struct rt_rq 与 struct dl_rq

### 6.1 rt_rq：位图 + 优先级队列

```c
struct rt_prio_array {
	DECLARE_BITMAP(bitmap, MAX_RT_PRIO+1);  /* 101 位：100 优先级 + 1 分隔哨兵 */
	struct list_head queue[MAX_RT_PRIO];    /* 每优先级一个 FIFO 链表 */
};

struct rt_rq {
	struct rt_prio_array	active;            /* ★ 活跃集合 */
	unsigned int		rt_nr_running;
	unsigned int		rr_nr_running;       /* RR 任务数（区分 FIFO）*/
	struct {
		int		curr;   /* 本队列最高 RT 优先级（位图缓存，供 pull/push 决策）*/
		int		next;  /* 次高（含 pushable）*/
	} highest_prio;
#ifdef CONFIG_SMP
	unsigned int		rt_nr_migratory;     /* 允许迁移的 RT 任务数 */
	unsigned int		rt_nr_total;
	int			overloaded;          /* 挂入 root_domain 的 rto_mask */
	struct plist_head	pushable_tasks;      /* 本队列上"可被推走"的 RT 任务（按优先级）*/
#endif
	int			rt_queued;          /* 是否已挂入 rq 参与 pick */
	int			rt_throttled;       /* 配额耗尽被掐停 */
	u64			rt_time;             /* 本 period 已消耗 */
	u64			rt_runtime;          /* 本 period 配额（默认 950ms/1000ms）*/
	raw_spinlock_t		rt_runtime_lock;
	...
};
```

选任务 O(1)：`sched_find_first_bit(bitmap)` 找最高优先级位 → `queue[prio]` 链头出队。SMP 的 push/pull（`push_rt_tasks`/`pull_rt_task`）与 RT overload mask 是第 7 章主题，但**数据结构上要记住 `pushable_tasks` 是 plist**（优先级有序链表），使"找本 CPU 最该推走的任务"O(1)。

### 6.2 dl_rq：EDF 红黑树 + GRUB 带宽

```c
struct dl_rq {
	struct rb_root_cached	root;             /* ★ 按 deadline 排序的 EDF 树（最左=最早截止）*/
	unsigned int		dl_nr_running;
#ifdef CONFIG_SMP
	struct {
		u64		curr;          /* 本 CPU 正在跑的 dl 任务绝对截止期 */
		u64		next;          /* 队列里最早的截止期（迁移决策用）*/
	} earliest_dl;
	unsigned int		dl_nr_migratory;
	int			overloaded;       /* dlo_mask 位图 */
	struct rb_root_cached	pushable_dl_tasks_root;  /* 可推走任务（deadline 序）*/
#else
	struct dl_bw		dl_bw;
#endif
	u64			running_bw;       /* ★GRUB: 活跃带宽（醒着的任务带宽和）*/
	u64			this_bw;          /* ★GRUB: 本 CPU 认领的总带宽（含睡着的）*/
	u64			extra_bw;         /* 可被 reclaim 的空闲带宽 */
	u64			max_bw;
	u64			bw_ratio;
};
```

DL 的关键设计：**每任务自带两个 hrtimer**（`dl_timer` 补给配额、`inactive_timer` 在"0-lag 时刻"把带宽从 running_bw 挪回 inactive）——CBS（Constant Bandwidth Server）由此获得微秒级精度，代价是 DL 任务路径的 timer 依赖。`running_bw/this_bw` 的区分支撑了 GRUB（bandwidth reclaiming）：任务提前睡眠释放的带宽，允许 `SCHED_FLAG_RECLAIM` 的任务"借用"，而不是白白浪费。

## 七、struct root_domain：跨 CPU 的"总账本"

```c
struct root_domain {
	atomic_t		refcount;
	atomic_t		rto_count;          /* rto_mask 置位的 CPU 数 */
	struct rcu_head		rcu;                /* partition 变更时 RCU 释放 */
	cpumask_var_t		span;               /* 域内全部 CPU */
	cpumask_var_t		online;

	int			overload;           /* 有 CPU nr_running>1 或 misfit → 唤醒负载均衡加速 */
	int			overutilized;       /* 有 CPU util 超过 capacity（EAS 的开关阈值）*/

	cpumask_var_t		dlo_mask;           /* 有多个 dl 任务可跑的 CPU */
	atomic_t		dlo_count;
	struct dl_bw		dl_bw;              /* ★DEADLINE 准入控制的总带宽账本 */
	struct cpudl		cpudl;              /* 空闲 CPU 的截止期最小堆（DL push 用）*/
	...
#ifdef HAVE_RT_PUSH_IPI
	struct irq_work		rto_push_work;      /* ★RT_PUSH_IPI：用 IPI 让拥有者主动 push */
	raw_spinlock_t		rto_lock;
	int			rto_loop;
	int			rto_cpu;
#endif
	...
	unsigned long		max_cpu_capacity;  /* 域内最大 capacity（归一化基准）*/
};
```

`root_domain` 最初只为 RT 的 pull 提供共享的 overload 位图（否则每个 CPU 的 `pull_rt_task` 都要去远程扫队列——缓存弹跳灾难）。6.6 里它已演进为四类全局状态的聚合：RT push/pull、DL 准入与 push、fair 的 overload（newidle balance 的"值不值得去看一眼"）、EAS 的 overutilized。`cpuset` 的 exclusive partition 会创建新的 root_domain（`partition_sched_domains_locked`）——这是 cpuset root 上写 `cpuset.sched.partition` 的内核侧效果。

## 八、idle 任务与 stop 任务

每个 CPU 有两个"特殊任务"，都在 `sched_init()`（boot）与 `idle_thread_get()`（次级 CPU）就位：

* **`rq->idle`（idle_sched_class）**：每个 CPU 一个 `init_task` fork 出来的 `swapper/N`。它不是"没事干的任务"，而是**调度器问询链的最后兜底**；其 `pick_next_task` 永返回自身。进入它即执行 `do_idle()` 循环：`cpuidle` 选 C-state、`tick_nohz_idle`、`need_resched()` 检查（`TIF_NEED_RESCHED` 是唯一能叫醒它的信号）。
* **`rq->stop`（stop_sched_class）**：`migration/N` 内核线程（`sched_init_smp` 时由 `cpu_stop_init` 创建，`smpboot` per-CPU 线程家族之一）。它插队一切（包括 RT/DL/IRQ 线程默认行为之外的场景），专门执行 `cpu_stop` 工作：**active migration**（负载均衡把唯一的 running 任务推走）、ftrace 的 `stop_machine`（全 CPU 约定同时进入）、hotplug。`stop_one_cpu()` 的语义就是"在该 CPU 上以最高身份跑一个回调"。

> ⚠️ 调试陷阱：`stop` 任务长期运行（如 stop_machine 打包）期间，`/proc/scheduler_debug` 里 `migration/N` 的 runtime 暴涨是正常的；反过来说，业务延迟毛刺若与 `migration/N` 活动对齐，优先怀疑 active migration 或 hotplug。

## 九、cache-line 布局与"读多写少"分层

调度的数据结构布局是内存序敏感工程的教科书：

1. `nr_running` 与负载均衡读字段放 rq 头部同一行——远程 CPU 做均衡决策时一次读走。
2. `sched_entity.avg` 用 `____cacheline_aligned` 单独成行——PELT 每 ms 级更新，与"读多写少"的树节点隔离，避免伪共享把树遍历的 cache line 打脏。
3. `rq->clock_task ____cacheline_aligned`：同理，把高频时钟推进与统计字段隔开。
4. 红黑树缓存 `rb_root_cached.rb_leftmost`：CFS 时代最左节点就是答案；EEVDF 保留该缓存作 fallback（`__pick_first_entity`）与 debug。
5. `__randomize_layout`（sched_rt_entity 等）：配合 GCC 插件打散字段偏移，增加漏洞利用成本（randstruct）。

## 十、思考题

1. `entity_key()` 为什么返回 `(s64)(se->vruntime - cfs_rq->min_vruntime)` 而不是 `se->vruntime` 本身？提示：64 位回绕；树序比较用的是带符号差（`entity_before`）。
2. `avg_vruntime_add/sub` 保持增量不变式。若一次异常路径只调了 add 没调 sub，`entity_eligible()` 会向哪个方向系统性漂移？会导致什么行为（饿死谁）？如何用 `/sys/kernel/debug/sched/debug` 交叉验证？
3. 为什么 `pushable_tasks` 用 plist 而不是红黑树？（对比 `pushable_dl_tasks_root`。）提示：RT 优先级取值域仅 100 且查询模式单一（最小优先级），plist 节点更小、无增广维护成本。
4. `rq->clock_task` 扣除 IRQ 时间意味着：一个 CPU 若 50% 时间在跑网卡中断，其上任务的 vruntime 推进会慢一半吗？公平性会因此被破坏吗？提示：全局公平 vs 每队列公平；PELT 的 clock_pelt 又扣 idle——两者动机有何不同？
5. 组调度的 `h_nr_running` 传播沿 `for_each_sched_entity` 上行。深度为 d 的容器嵌套，一次任务唤醒的锁内工作量是多少？这如何转化为对"容器层数"的性能建议？
