# Introduction

腾讯的 `SCHED_BT` (Batch) 调度算法是其“如意”（RUE）离在线混部方案的核心组件，旨在解决服务器资源利用率低下的问题。它通过在内核层面实现**强隔离**和**绝对抢占**，确保低优先级的离线任务不会影响高优先级的在线业务。

下面将详细分析其工作原理、使用方法以及与其他调度策略的区别。

### 🤔 为什么需要 SCHED_BT？

在传统 Linux 系统中，即使是为后台任务设计的 `SCHED_BATCH` 或 `SCHED_IDLE` 策略，也与普通任务一样使用 CFS (完全公平调度器)。CFS 的设计哲学是“公平”，这意味着在 CPU 争抢时，即使是低优先级的后台任务，也可能对延迟敏感的在线服务（如 Web 请求、AI 推理）造成不可忽视的干扰。

为了实现真正的“离在线混部”——即在同一台服务器上同时运行在线业务和离线计算任务，并最大化利用 CPU 资源，腾讯开发了 `SCHED_BT`。它的核心目标是：
*   **保障在线业务 QoS**：确保在线任务的延迟和稳定性几乎不受任何影响。
*   **压榨离线资源**：在不影响在线业务的前提下，充分利用所有闲置的 CPU 算力来运行离线任务。

### ⚙️ 核心原理：绝对抢占与独立调度类

`SCHED_BT` 的关键创新在于它不是 CFS 的一个简单变种，而是一个独立的调度类，被插入到 Linux 内核调度器的优先级队列中，位于 `SCHED_NORMAL` (CFS) 和 `IDLE` 之间。

#### 调度层级

Linux 内核在选择下一个要运行的任务时，会按照以下优先级顺序检查各个调度类的运行队列：
1.  `SCHED_DEADLINE` (DL)
2.  `SCHED_FIFO` / `SCHED_RR` (RT)
3.  `SCHED_NORMAL` (CFS) -> **在线业务通常运行于此**
4.  **`SCHED_BT` (BT)** -> **离线业务运行于此**
5.  `SCHED_IDLE` (IDLE)

#### 工作机制

这个位置决定了 `SCHED_BT` 的行为：
*   **无条件让位**：只要 `SCHED_NORMAL` (CFS) 队列中有就绪的任务（即在线业务有需求），CPU 就一定会去执行它，而绝不会选择 `SCHED_BT` 队列中的任务。这实现了毫秒级的**绝对抢占**。
*   **拾荒者模式**：只有当 `SCHED_NORMAL` 队列为空时，调度器才会轮到 `SCHED_BT` 队列，从中挑选任务执行。一旦有新的在线任务唤醒，正在运行的 `SCHED_BT` 任务会被立即中断，CPU 控制权马上交还给在线任务。
*   **智能限额**：除了抢占，`SCHED_BT` 还具备动态限额控制能力。系统可以根据在线业务的负载水位线，动态调整离线任务可以使用的 CPU 上限，确保 CPU 既不过载也不闲置。

这套机制不仅作用于 CPU，还与网络、IO、内存等资源的 QoS 机制协同工作，形成一个完整的资源隔离体系，从根本上消除了混部风险。

### 💻 如何创建和使用 SCHED_BT

与普通进程不同，`SCHED_BT` 是一个非标准的调度策略，用户态程序无法直接通过 `sched_setscheduler()` 等标准系统调用将其设置为 `SCHED_BT`。它的使用方式体现了其“为离线业务设计”的定位。

#### 主要使用方式：通过 Cgroup v2
这是推荐且最常见的方式，特别适合容器化环境。系统管理员可以通过 Cgroup 接口，将一个或多个容器（或进程组）统一设置为 `SCHED_BT` 策略。

例如，在一个支持该特性的系统上，你可以通过 Cgroup 的接口文件进行配置，将某个容器的所有任务都标记为离线任务。这种方式便于批量管理和自动化部署。

#### 次要使用方式：内核内部设置
根据代码分析，在某些特定情况下，内核自身可能会将新创建的线程设置为 `SCHED_BT` 策略。但这通常是内核内部逻辑，并非供普通开发者直接调用的接口。

**重要提示**：不要尝试在普通应用程序中使用 `policy = SCHED_BT` (值为8) 来设置调度策略，这在标准内核中会失败，因为它不是一个面向用户的通用 API。

### 🔍 对比：SCHED_BT vs. SCHED_BATCH vs. SCHED_IDLE

为了更清晰地理解 `SCHED_BT` 的独特性，我们将其与内核原生的两种低优先级策略进行比较：

| 特性 | SCHED_BATCH | SCHED_IDLE | SCHED_BT (腾讯自研) |
| :--- | :--- | :--- | :--- |
| **调度器** | CFS | CFS | **独立的 BT 调度类** |
| **设计目标** | 非实时、吞吐量优先的批处理 | 极低优先级，仅在系统空闲时运行 | **离在线混部，保障在线业务零干扰** |
| **抢占行为** | 公平共享 CPU，**无法被强制剥夺** | 公平共享 CPU，**无法被强制剥夺** | **可被在线任务(CFS)毫秒级绝对抢占** |
| **适用场景** | 编译代码、视频编码等后台任务 | 日志收集、监控探针等背景任务 | **大规模离线计算、数据分析和 AI 训练** |

总而言之，腾讯的 `SCHED_BT` 是一种为实现极致资源利用率和严格服务等级协议（SLA）保障而生的内核级调度技术。它通过在调度器层面建立一道“防火墙”，使得高价值的在线业务和低价值的离线任务能够安全、高效地共享同一套硬件资源。

## 区分 SCHED_BATCH 和 SCHED_BT

这是一个非常专业且容易混淆的问题。虽然它们的名字里都有 "Batch"（批处理），缩写看起来也像，但 **`SCHED_BATCH`** 和 **`SCHED_BT`** 在 Linux 内核调度体系中完全是两个不同维度的概念。

简单来说：**`SCHED_BATCH` 是 Linux 主线内核的标准策略，旨在“优化吞吐量”；而 `SCHED_BT` 是腾讯 OpenCloudOS 等发行版引入的定制策略，旨在“保障在线业务隔离”。**

以下是详细的区别与联系分析：

### 🆚 核心区别对比表

| 维度 | SCHED_BATCH (标准) | SCHED_BT (腾讯/OpenCloudOS) |
| :--- | :--- | :--- |
| **全称** | Batch Scheduling | Batch Task / Offline Task Scheduling |
| **归属** | **Linux 主线内核** (Standard) | **特定发行版内核** (OpenCloudOS/TencentOS) |
| **调度类** | 属于 **CFS** (完全公平调度器) | 独立的 **BT 调度类** (位于 CFS 之下) |
| **设计目标** | **减少上下文切换**，提高 CPU 缓存命中率，适合计算密集型任务。 | **资源隔离**，确保离线任务绝对不抢占在线业务 CPU。 |
| **抢占行为** | **公平**。它仍然和其他普通进程公平竞争 CPU，只是不那么频繁地被唤醒抢占。 | **被压制**。只要有普通进程 (`SCHED_NORMAL`) 想运行，`SCHED_BT` 必须立即让出 CPU。 |
| **优先级** | 中等偏低 (受 nice 值影响，范围 -20 ~ 19)。 | 极低 (固定低优先级，通常不可调，低于所有 CFS 任务)。 |
| **适用场景** | 视频编码、科学计算、编译代码（希望一口气跑完，别老打断我）。 | 离线大数据分析、日志处理（只要不卡死在线业务，什么时候跑完无所谓）。 |

---

### 🔍 深度解析

#### 1. SCHED_BATCH：为了“效率”而生
*   **身份**：它是 Linux 原生支持的三种非实时策略之一（另外两个是 `SCHED_OTHER` 和 `SCHED_IDLE`）。
*   **原理**：
    *   在 CFS 调度器中，当一个进程被标记为 `SCHED_BATCH`，内核会假设它是一个 **CPU 密集型** 任务。
    *   **机制**：当你唤醒一个 `SCHED_BATCH` 进程时，调度器会给它施加一点微小的“惩罚”（增加虚拟运行时间 vruntime），让它不要立刻去抢占当前正在运行的进程。
    *   **目的**：这是为了让当前的进程多跑一会儿，减少进程切换带来的开销（比如 CPU 缓存失效）。它并不是要降低任务的优先级到“最低”，而是让它跑得“更连贯”。

#### 2. SCHED_BT：为了“混部”而生
*   **身份**：这是腾讯为了在云服务器上实现**离在线业务混部**而魔改内核加入的策略。
*   **原理**：
    *   它在调度层级上建立了一个全新的阶级。Linux 调度器检查顺序变成了：实时任务 -> 普通任务(CFS) -> **BT任务** -> 空闲任务。
    *   **机制**：这是一种“拾荒者”模式。只有当 `SCHED_NORMAL`（普通在线业务）队列为空时，`SCHED_BT` 才有资格获得 CPU。一旦有在线请求进来，`SCHED_BT` 会被毫秒级强制剥夺 CPU。
    *   **目的**：彻底消除离线任务对在线业务的干扰。

---

### 🔗 它们的联系

虽然两者截然不同，但在实际使用和演进上存在有趣的联系：

1.  **命名渊源**：
    `SCHED_BT` 中的 "BT" 显然也是指 "Batch"（批处理）。腾讯在设计这个调度类时，沿用了“批处理任务”这一传统概念，即后台运行的、非实时的任务。

2.  **功能替代与演进**：
    在腾讯的早期混部方案中，可能尝试过使用原生的 `SCHED_BATCH` 或 `SCHED_IDLE` 来运行离线任务。但发现即使设置了这些策略，在高负载下 CFS 的“公平性”依然会导致离线任务偶尔抢走在线业务的 CPU 时间片，造成延迟抖动。
    因此，腾讯开发了 `SCHED_BT`。**你可以把 `SCHED_BT` 看作是比 `SCHED_BATCH` 和 `SCHED_IDLE` 更激进、更彻底的“低优先级”版本**。

3.  **共存关系**：
    在 OpenCloudOS 内核中，这两个策略是共存的：
    *   如果你只是想优化一个本地视频转码任务，不希望它卡顿，可以用 `SCHED_BATCH`。
    *   如果你在运行一个大规模分布式计算集群，希望利用闲置算力但绝对不能影响 Web 服务，就用 `SCHED_BT`。

### 📌 总结

*   **SCHED_BATCH** = **“别老打断我”**（为了跑得快）。
*   **SCHED_BT** = **“大哥先请”**（为了不捣乱）。

在你提供的 OpenCloudOS 源码上下文中，`SCHED_BT` 是为了实现极致的云资源超卖和安全隔离而存在的特殊武器，而 `SCHED_BATCH` 则是 Linux 几十年前就有的标准配置。
