# 电源管理总体框架（Linux 6.6）

> 阅读目标：建立电源管理子系统的完整版图——CPU PM（cpufreq/cpuidle）、设备 PM（runtime PM/系统睡眠）、平台 PM（s2idle/suspend-to-RAM/hibernate）、PM QoS 与 wakeup source 五大板块的职责边界与协作关系；理解 `struct dev_pm_ops` 回调矩阵与 `kernel/power` 的核心数据流；为第 2、3 章（cpufreq/cpuidle）与后续 runtime PM、系统睡眠两章铺垫。

---

## 一、为什么要读电源管理

调度器优化的是"算得快"，电源管理优化的是"**在满足性能需求的前提下少耗电**"——两者在 `util_avg → 频率/C-state` 的决策链上直接耦合（PELT ↔ schedutil ↔ cpuidle，见调度器分册第 5 章）。同时电源管理是内核中**时序最苛刻**的子系统之一：suspend/resume 要求设备按依赖顺序下电/上电，任何一步失序都是睡不醒/醒来乱的死局。容器/笔记本/手机/边缘设备的一切续航与温控体验，都压在这套框架上。

## 三、核心抽象：struct dev_pm_ops

设备驱动通过一个回调结构体向 PM 核心声明"我在每种睡眠态下如何自处"（`include/linux/pm.h`，6.6 精选）：

```c
struct dev_pm_ops {
	/* —— 系统睡眠（传统 suspend）—— */
	int (*prepare)(struct device *dev);         /* 停止新工作、保存必要上下文 */
	void (*complete)(struct device *dev);

	int (*suspend)(struct device *dev);         /* MAIN 阶段：可睡眠、可分配 */
	int (*resume)(struct device *dev);
	int (*suspend_late)(struct device *dev);    /* noirq 前的最后可睡眠窗口 */
	int (*resume_early)(struct device *dev);
	int (*suspend_noirq)(struct device *dev);   /* IRQ 已关：只许做纯寄存器/直映射操作 */
	int (*resume_noirq)(struct device *dev);

	/* —— 系统睡眠（suspend-to-idle 用的冻结语义）—— */
	int (*freeze)(struct device *dev);          /* 快照状态而不下电 */
	int (*thaw)(struct device *dev);
	int (*poweroff)(struct device *dev);        /* 配合 hibernate 的下电路径 */
	int (*restore)(struct device *dev);
	（freeze/thaw/poweroff/restore 各有 _late/_noirq 变体，略）

	/* —— runtime PM（运行时按需上下电）—— */
	int (*runtime_suspend)(struct device *dev);
	int (*runtime_resume)(struct device *dev);
	int (*runtime_idle)(struct device *dev);    /* 通常 driver 不实现，交给 autosuspend */
};
```

### 3.1 回调矩阵：4 个睡眠族 × 3 个阶段

| 事件族 | MAIN（IRQ 开） | LATE（IRQ 开） | NOIRQ（IRQ 关） |
| :--- | :--- | :--- | :--- |
| suspend/resume（S3） | `suspend` | `suspend_late` | `suspend_noirq` |
| freeze/thaw（s2idle） | `freeze` | `freeze_late` | `freeze_noirq` |
| poweroff/restore（S4 前） | `poweroff` | `poweroff_late` | `poweroff_noirq` |
| runtime（随时） | `runtime_suspend/resume` | — | — |

**三阶段的存在理由**（也是 suspend 排障的第一分析框架）：

* **MAIN**：IRQ/调度器都正常，回调可以睡眠、分配内存、做 I/O——大部分设备在这里完成"软件侧关停"。
* **LATE**：仍在进程上下文，但设备依赖链的大头已停——适合"最后再看一眼硬件"的操作。
* **NOIRQ**：本 CPU 中断已关闭（`suspend_device_irqs` 之后），回调里**不许任何可能睡眠/等中断的操作**，只允许直寄存器写入（如向电源控制器发关断命令）。

> 💡 排障口诀："睡死在 resume 的 noirq 阶段"≈ 中断相关的驱动 bug；"resume 后设备行为怪异但活着"≈ MAIN 阶段恢复顺序问题（依赖倒置）。

### 3.2 SIMPLE_DEV_PM_OPS 与宏家族

```c
#define SIMPLE_DEV_PM_OPS(name, suspend_fn, resume_fn) \
	const struct dev_pm_ops name = { \
		SET_SYSTEM_SLEEP_PM_OPS(suspend_fn, resume_fn) \
	}
DEFINE_SIMPLE_DEV_PM_OPS(...)            /* 6.6 推荐：编译期检查 + runtime 同一套 */
```

驱动常把 suspend/resume 与 runtime_suspend/runtime_resume 指向同一实现（`UNIVERSAL_DEV_PM_OPS`）——正确性依赖 PM core 的"先 runtime suspend 再系统 suspend"去重逻辑（`dpm_suspend` 里 `dev->power.is_runtime_suspended` 的协调，详见系统睡眠章）。

## 四、系统睡眠总流程（s2idle/S3/S4 公共骨架）

用户态 `echo mem > /sys/power/state`（或 lid/电源键经 input → systemd loginctl suspend）之后的内核路径：

```
sys_write /sys/power/state
  └─ pm_suspend(state)                      kernel/power/suspend.c
       ├─ pm_prepare_console（console 冻结）
       ├─ pm_notifier_call_chain(PM_SUSPEND_PREPARE)   /* 驱动/模块注册的通知链 */
       ├─ suspend_freeze_processes()                  /* 冻结所有用户任务（含内核线程：
       │                                                 kthread 框架的 freezer，见
       │                                                 power/freezing-of-tasks.rst 镜像）*/
       ├─ suspend_devices_and_enter()
       │    ├─ platform_suspend_begin
       │    ├─ suspend_console()
       │    ├─ dpm_suspend_start(PMSG_SUSPEND)
       │    │    ├─ dpm_prepare（PREPARE 阶段，反向设备序）
       │    │    └─ dpm_suspend（MAIN：suspend 回调，反向设备序）
       │    ├─ dpm_suspend_late/resume_early 分段
       │    ├─ suspend_device_irqs()                  /* 关 IRQ → 之后是 noirq 世界 */
       │    ├─ dpm_suspend_noirq
       │    ├─ syscore_suspend()                      /* 时钟/tick/其他 syscore 静默 */
       │    ├─ suspend_disable_secondary_cpus()
       │    ├─ arch_suspend_disable_irqs
       │    ├─ platform_suspend_ops->enter()          /* ★ 真正下电：
       │    │     s2idle: s2idle_ops 循环（acpi 中断源收尾 + wfi）
       │    │     S3:     ACPI SLP_TYPa/b 写 PM1a/PM1b 控制寄存器 → CPU 失电 */
       │    └─（唤醒后严格逆序恢复，不再赘述）
       └─ suspend_finish：解冻任务、PM_POST_SUSPEND 通知、console 恢复
```

四条关键设计：

1. **设备顺序由 device model 决定**：suspend 反向（先子后父，消费者先于提供者），resume 正向——`dpm_list` 的拓扑排序在注册时维护（`device_pm_add`），与 kobject/驱动模型（后续设备模型分册）联动。
2. **任务冻结先于设备关停**：用户态不再产生新 I/O，驱动的 suspend 回调才可能不与并发访问竞争。内核线程则通过 `kthread_freezable_should_stop`/`try_to_freeze` 显式配合（不是所有 kthread 都可冻结——RCU/看门狗这类"基础设施"豁免，`PF_NOFREEZE`）。
3. **两级电源损失模型**：s2idle 只是"全设备冻结 + CPU 进最深的 C-state"（电还活着，恢复快）；S3 真断电（SDRAM 自刷新供电，恢复走固件 wakeup vector）；S4 把内存镜像写 swap 后全断（`kernel/power/hibernate.c`，恢复时由 bootloader 按 `signature` 识别并跳回 `restore_image`）。
4. **wakeup source** 贯穿始终：`/sys/kernel/debug/wakeup_sources` 与 `wakeup_count` 机制解决"冻结瞬间有事件抵达"的 lost wakeup 竞态（用户态 systemd 用 wakeup_count 做原子窗口）。

## 五、CPU PM 与调度器/时间子系统的耦合点

电源管理的三条"跨界高速路"：

```
① PELT(util_avg/util_est) ──► schedutil governor ──► cpufreq 频率请求
   （调度器分册第 5 章；本章第 2 章展开）        └► uclamp 修正

② do_idle → cpuidle_idle_call → menu governor
   ← tick_nohz_get_sleep_length（下一 timer 到期时长，timers 分册）
   ← nr_iowaiters（rq->nr_iowait，调度器分册）
   → C-state 选择（本章第 3 章展开）

③ thermal（温控）→ cpufreq_cooling：把 capacity 缩放注入 sched_domain
   → 调度器的 capacity_of() 变小 → 均衡/EAS 自动避开热核（调度器分册第 6 章）
```

一句话：**电源管理的决策输入几乎全部来自调度器（util/队列形态）与时间子系统（下一个事件何时来）**。这也是为什么本分册第 2、3 章需要引用前两个分册的机制。

## 六、PM QoS：把"延迟要求"做成分布式约束网络

`kernel/power/qos.c` + `include/linux/pm_qos.h`：各类消费者向约束类（`pm_qos_class`）提交"我要的界"，聚合出系统级最紧值，供给 PM 决策：

| 约束类 | 谁提交 | 谁消费 |
| :--- | :--- | :--- |
| `PM_QOS_CPU_DMA_LATENCY` | 应用（`/dev/cpu_dma_latency` 的 open+write；持有 fd 期间生效） | cpuidle governor 的 `latency_req`（第 3 章 menu） |
| `PM_QOS_NET_LATENCY/THROUGHPUT` | 网络应用 | （网络设备 PM 策略，使用渐少） |
| freq_qos（`freq_constraints`，挂在 cpufreq_policy 上） | thermal cooling、userspace `scaling_min/max_freq`、调度器 `uclamp`（间接） | cpufreq 的 `policy->min/max` |
| `PM_QOS_RESUME_LATENCY` | per-device（`power/pm_qos_resume_latency_us`） | 设备 suspend 决策（异步分组） |

经典应用：音频/实时应用打开 `/dev/cpu_dma_latency` 写入 `2`（µs）——cpuidle 从此只敢选 exit_latency ≤ 2µs 的浅 C-state；进程退出/关闭 fd 约束自动失效。这是"**用户态按压内核 PM 决策**"的标准接口。

## 八、思考题

1. 为什么 suspend 的设备顺序是"先子后父（消费者先于提供者）"，而 resume 反过来？给出一个"顺序错了导致睡死"的具体例子（提示： regulator/clk provider 悬空）。
2. `suspend_noirq` 阶段为什么必须存在？把一个"仅寄存器操作"的回调挪到 MAIN 阶段执行，什么情况下仍然正确？什么情况下是 bug？
3. 任务冻结（freezer）与 `PF_NOFREEZE` 内核线程的边界如何划分？如果 RCU 线程可冻结，会发生什么？（联系 RCU 分册的 grace period。）
4. s2idle 与 S3 在"设备回调走 freeze 族还是 suspend 族"上如何分派？`mem_sleep` 的 default 策略如何影响这个选择？
5. 设计：为一台"在线率 10%、消息延迟预算 50ms"的 IoT 网关设计电源策略（cpufreq governor、cpuidle 约束、wakeup 唤醒源清单），说明每一项的取舍。
