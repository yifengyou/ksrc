# 模块布局与加载器（Linux 6.6）

> 阅读目标：掌握 .ko 的 ELF 布局（专为模块设计的特殊段）；吃透 `finit_module` → `load_module` 的十四段流水线（已对照 v6.6 kernel/module/main.c）；理解签名校验、执行域分配（vmalloc/exec）、init 段的"一次性"生命周期与失败回滚。

---

## 一、.ko：一个特殊用途的 ELF

```
foo.ko（ET_REL 可重定位目标）的模块专用段：
  .gnu.linkonce.this_module   ★struct module 实例（唯一全局符号的锚：
                               MODULE_NAME_SIZE、init/exit 函数指针的宿主）
  .modinfo                    license/depends/vermagic/srcversion 等键值
  __versions                  CRC 版本对账表（struct modversion_info[]）
  __ksymtab / __ksymtab_gpl   本模块导出的符号（第二章）
  .init.text / .init.data     模块 init 的一次性段（加载后可释放）
  .text/.data/.bss/.rodata    常驻段
  .symtab/.strtab             完整符号表（strip 前的工具链产物）
```

与用户态 ELF 的本质差别：**模块不做链接期重定位**——内核在加载时按目标内核的符号地址现场 `apply_relocations`（这正是 ABI 脆弱性与 vermagic/CRC 对账存在的原因）。

## 二、加载流水线：load_module 十四段（已核对源码顺序）

```
finit_module(fd, uargs, flags)            SYSCALL_DEFINE3（main.c:3169）
 └─ may_init_module（并发限额/权限）→ fd 读入 load_info.hdr
 └─ load_module(info, uargs, flags)（main.c:2828）
     ① module_sig_check         签名验证（CONFIG_MODULE_SIG：附在 .ko 尾部的
                                 PKCS#7——强制策略 enforcer 由 flags/配置定）
     ② elf_validity_cache_copy  ELF 头与段表校验（布局缓存）
     ③ early_mod_check          名称冲突/vermagic/`_module` 段存在性
     ④ layout_and_allocate      ★按最终落位尺寸聚合各段，vmalloc 分配
                                 module_execmem（module_alloc 的 W^X 区），
                                 move_module 搬运（main.c:2222/2363）
     ⑤ add_unformed_module      挂入全局 modules 链（未成形态）
     ⑥ percpu_modalloc          per-CPU 段分配
     ⑦ module_unload_init       引用计数基建（use count 链）
     ⑧ find_module_sections     符号表/ksymtab/参数/异常表等定位
     ⑨ check_export_symbol_versions  __versions 逐项与内核 CRC 对账
     ⑩ simplify_symbols         符号归类（undefined → 待解析）
     ⑪ apply_relocations        ★重定位现场完成（R_X86_64_RELATIVE 等）
     ⑫ post_relocation          kallsyms 登记/符号可见性
     ⑬ complete_formation       签名终审+license 判定（taint）+ cfi/btf 收尾
     ⑭ do_init_module           mod->init() 执行；.init.* 段释放
                                 （module_free——"一次性代码"的物理回收）
```

**失败回滚**：任一步失败沿已执行步骤逆序释放（`free_module` 的分段清理与十四段一一对应）——加载器是内核里少见的、严格事务化的路径。

## 三、执行域与内存布局

```
module_alloc（x86: arch/x86/kernel/module.c）
  VMALLOC 空间 + 依据 CONFIG_ARCH_WANTS_MODULES_EXECMEM? 在 6.6：
  文本页 exec（W^X：数据段另区只写）；失败回退
  MODTEXT/INACTIVE/UNFORMED per-cpu slot（6.6 的 allocation state 机：
  slot 复用减少 vmalloc 碎片）
```

## 四、卸载与引用计数

`delete_module`：`try_stop_module`（GET 与 device removal 一致性）→ `mod->exit()` → `free_module`（符号注销/链摘除/段释放）。引用计数由 kallsyms 的 `__module_get`/`module_put` 维护（`/proc/modules` 的 Used by 列；`rmmod --wait` 与引用断链是排障常客）。

## 六、思考题

1. `.gnu.linkonce.this_module` 为什么必须叫这个名字？（提示：linkonce 的去重语义与"每模块恰好一份 struct module"的保证。）
2. vermagic 与 CRC 对账是两道独立的闸——分别防什么？（同一内核不同配置 vs 同一源码树不同版本。）
3. `module_alloc` 用 vmalloc 而非直接映射页的两个理由？（碎片/物理连续性 vs 执行域与 W^X。）
4. init 段释放后 `struct module` 里那些指针怎么办？（对照 ddebug/BTF 等对 init-only 数据的处理。）
5. 加载失败回滚为什么要逆序到第 ④ 步的 `layout_and_allocate` 为止停？
