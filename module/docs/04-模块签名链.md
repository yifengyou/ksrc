# 模块签名链：PKCS#7 与 lockdown（Linux 6.6）

> 阅读目标：掌握 KO 签名的完整闭环——威胁模型与四道开关（MODULE_SIG/FORCE/sig_enforce/lockdown）、.ko 尾部的签名布局、`mod_verify_sig → verify_pkcs7_signature` 验证链与密钥环体系、lockdown LSM 的三级别与 EFI Secure Boot 联动、构建侧签发。前置：[01-模块布局与加载器](01-模块布局与加载器.md)、[03-KO构建与BTF](03-KO构建与BTF.md)。

---

## 一、威胁模型与开关矩阵（已核对 6.6）

```
问题：root 可以 insmod 任意代码进内核——供应链/持久化攻击的主径
四道开关（层层收紧）：
  ① CONFIG_MODULE_SIG：验证能力编译在（不强制）
  ② CONFIG_MODULE_SIG_FORCE：强制（Kconfig "Require modules
     to be validly signed"）
  ③ sig_enforce（kernel/module/signing.c:22-23）：运行期参数
     module.sig_enforce=1——★bool_enable_only：只能开不能关
     （0644 也只许 0→1）
  ④ lockdown：LOCKDOWN_MODULE_SIGNATURE（include/linux/
     security.h:109）——签名强制是 lockdown 的一个子闸
双闸判定（signing.c:119-124 原文结构）：
  if (is_module_sig_enforced() ||
      security_locked_down(LOCKDOWN_MODULE_SIGNATURE))
      → 未签名模块拒绝加载
```

## 二、.ko 签名布局（已核对）

```
文件尾部（从后往前读）：
  "~Module signature appended~\n"  ← MODULE_SIG_STRING 标记串
  struct module_signature（12B 头）：algo/hash/id_type/
    signer_len/key_id_len/_pad[3]/sig_len(be32)
  PKCS#7 签名 blob（sig_len 字节）
加载侧 find_module_sections 之前：layout_and_allocate →
  检查尾部标记（:73-87 memcmp）→ 命中即走签名验证分支
```

## 三、验证链（mod_verify_sig，已核对全函数 :43-67）

```
mod_verify_sig(mod, info):
  ① 从模块尾部读 struct module_signature
  ② mod_check_sig（长度/结构合法）
  ③ sig_len = be32_to_cpu(ms.sig_len)；info->len -= sig_len+12
     ——签名剥离，模块"还原"为未签名体
  ④ verify_pkcs7_signature(mod, modlen, sig, sig_len,
       VERIFY_USE_SECONDARY_KEYRING,     ← 先查 secondary 再 builtin
       VERIFYING_MODULE_SIGNATURE, ...)  ← 用途限定（防签名挪用）
  ⑤ 内部：pkcs7_verify（摘要比对 + 证书链）→
     public_key_verify_signature（RSA/ECDSA 原语）
```

## 四、密钥环体系

```
builtin_trusted_keys：certs/x509_certificate_list——内核构建时
  编译进 vmlinux 的证书（龙芯/发行版/自签 CA）
secondary_trusted_keys：运行期追加（UEFI db、mok 等注册进）——
  VERIFY_USE_SECONDARY_KEYRING 的第一站
system_blacklist_keyring：UEFI dbx/吊销证书——命中即拒
观察：cat /proc/keys | grep -E 'builtin|secondary|blacklist'
```

## 五、lockdown：整树的"防篡改总闸"

```
三级别（security/lockdown/lockdown.c:19-21）：
  LOCKDOWN_NONE / INTEGRITY_MAX / CONFIDENTIALITY_MAX
开启途径：
  boot 参数 lockdown=integrity|confidentiality（:43-45，
    lock_kernel_down("command line", ...) 原句）
  EFI Secure Boot 开 → 自动 integrity（efi_link_seg6 的
    lockdown_lsm 钩子；CONFIG_SECURITY_LOCKDOWN_LSM_EARLY :160）
  内核配置 CONFIG_LOCK_DOWN_KERNEL_FORCE_*（:81-83）
同族限制（include/linux/security.h 的 LOCKDOWN_* 枚举族）：
  MODULE_SIGNATURE / MODULE_PARAMETERS / KEXEC（未签名镜像——
  [ras/kdump 分册] 的 KEXEC_SIG 联动）/ DEVMEM（/dev/mem 物理内存
  ——防内存读取绕过）/ PERF（某些计数器）/ IO_PORT...
观测与操作：
  cat /sys/kernel/security/lockdown   # [integrity] 方括号=当前级
  dmesg | grep -i lockdown            # "Lockdown: ..." 每次拦截审计
```

## 六、构建侧签发

```
CONFIG_MODULE_SIG_ALL（默认 y——make modules_install 自动签）
CONFIG_MODULE_SIG_HASH："sha256"/"sha512" 等五选（module/Kconfig
  :264-268 映射表）
手工：scripts/sign-file sha512 <privkey> <x509> module.ko
自建 CA：内核树 certs/ 的 genkey 脚本 + openssl
```

## 七、观测与排障

```
dmesg "module verification failed: signature and/or required key
  missing" —— 未签/密钥环无此证书
dmesg "Lockdown: modprobe: ... is restricted" —— lockdown 拦截
cat /proc/sys/kernel/tainted —— 未签名模块加载（未强制时）置
  TAINT_UNSIGNED_MODULE（'E'）
排障链：能否加载 → sig_enforce? lockdown 级? → 模块尾部有标记?
  → 证书在哪个环? → 是否被 blacklist?
```

## 八、思考题

1. `sig_enforce` 为什么用 bool_enable_only 而不是普通 bool？（提示：攻击面——加载恶意模块后回关验证。）
2. `VERIFYING_MODULE_SIGNATURE` 的用途限定防什么？（对照 kexec 签名：同一证书环，签名可否跨用途挪用？）
3. secondary 优先于 builtin 查询的语义是什么？（提示：发行版用 db 撤换内核内置 CA 的场景。）
4. lockdown 的 INTEGRITY 与 CONFIDENTIALITY 的分界线在哪？（DEVMEM 在哪侧？为什么？）
5. Secure Boot → lockdown → 模块签名三层传递中，哪一环被绕过会导致全链失效？（提示：dbx 与 rollback protection。）
